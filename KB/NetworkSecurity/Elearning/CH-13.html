Cloud Network Security & SDN/NFV Security — Shared Responsibility Model, Security Group, NACL, Cloud Firewall, SASE, ZTNA, SDN, NFV, Hybrid Cloud, Multi-Cloud Security, กรณีศึกษาการออกแบบเครือข่ายที่ปลอดภัยบน Cloud

2. Cloud Network Security Components

2.1 Security Group (AWS) / Network Security Group (Azure)

Security Group เป็น Stateful Firewall ที่ทำงานในระดับ Instance (VM Level):

AWS Security Group — Stateful:
───────────────────────────────
┌──────────────────────────────┐
│  Security Group: Web_SG       │
│  Inbound Rules:               │
│  ┌──────┬────┬────────┬─────┐ │
│  │ Type│Port│ Source  │ Desc│ │
│  ├──────┼────┼────────┼─────┤ │
│  │ HTTP │ 80 │ 0.0.0.0│ Web │ │
│  │HTTPS │443 │ 0.0.0.0│ Web │ │
│  │ SSH  │ 22 │10.0.0.0│ Mgt │ │
│  └──────┴────┴────────┴─────┘ │
│  Outbound Rules:              │
│  ┌──────┬────┬────────┬─────┐ │
│  │ ALL  │ ALL│ 0.0.0.0│     │ │
│  └──────┴────┴────────┴─────┘ │
└──────────────────────────────┘

ลักษณะสำคัญของ Security Group:

  • Stateful: Return Traffic ผ่านโดยอัตโนมัติ (ไม่ต้องเขียน Outbound Rule)
  • Allow Rules Only: ไม่มี Deny Rule — ถ้าไม่มี Allow = Deny
  • Instance Level: ใช้กับ EC2, RDS, ELB, Lambda
  • สามารถมีหลาย SG ต่อ Instance ได้

NACL เป็น Stateless Firewall ที่ทำงานในระดับ Subnet:

│  │ 100│ HTTP │  80  │0.0.0.0 │ │

│  ┌────┬──────┬──────┬─────────┐ │
│  │ #  │ Type │ Port │ Dest    │ │
│  ├────┼──────┼──────┼─────────┤ │
│  │ 100│ HTTP │  80  │0.0.0.0 │ │

3. SASE และ ZTNA

3.1 SASE (Secure Access Service Edge)

SASE (อ่านว่า "sassy") ถูกนิยามโดย Gartner ในปี 2019 — รวม Network และ Security Functions เป็น Cloud-based Service:

SASE Architecture:
───────────────────
[User] ──▶ [SASE POP] ──▶ [Internet / SaaS / Cloud / DC]
                 │
            SASE Functions:
            ├── SD-WAN
            ├── SWG (Secure Web Gateway)
            ├── CASB (Cloud Access Security Broker)
            ├── ZTNA (Zero Trust Network Access)
            ├── FWaaS (Firewall as a Service)
            └── DLP (Data Loss Prevention)

หลักการของ SASE:

  1. Identity-based Access: Policy ขึ้นอยู่กับ Identity ไม่ใช่ IP
  2. Cloud-native: Service ทำงานจาก Cloud POP ทั่วโลก
  3. Edge: ตรวจสอบ Traffic ใกล้ผู้ใช้ที่สุด
  4. Converged: รวม Network + Security Functions ในบริการเดียว
TraditionalSASE
MPLS + VPN + Firewall ใน Data CenterSD-WAN + SWG + FWaaS จาก Cloud
Branch → HQ → InternetBranch → SASE POP → Internet
Hardware Appliance ที่ BranchSoftware Agent หรือ uCPE
Security Backhaul (Branch→HQ→Internet)Local Breakout (ตรงถึง Cloud/Internet)

ผู้ให้บริการ SASE:

  • Zscaler (Cloud Security) + Cloudflare
  • Palo Alto Prisma Access
  • Cisco Umbrella + Meraki
  • Fortinet FortiSASE
  • Netskope (SASE + CASB)

3.2 ZTNA (Zero Trust Network Access)

ZTNA เป็นหัวใจของ SASE — เข้าใกล้ทรัพยากรโดยไม่ต้องต่อ VPN:

ZTNA vs VPN:
─────────────
Traditional VPN:
[User] ──▶ [VPN Gateway] ──▶ [Corporate Network] ──▶ [App]
                 │                        │
           Full Network Access      Once in = access ALL

ZTNA:
[User] ──▶ [ZTNA Broker] ──▶ [App]
                 │
           App-specific Access
           User → [เฉพาะ App A] เท่านั้น
           ไม่มี Network-level Access

หลักการ ZTNA:

  1. Never Trust, Always Verify — ไม่เชื่อถือผู้ใช้หรืออุปกรณ์โดยอัตโนมัติ
  2. Least Privilege — เข้าถึงเฉพาะ App ที่จำเป็น
  3. App-specific Connection — ไม่ใช่ Network Connection
  4. Continuous Verification — ตรวจสอบตลอดเวลา
Modelคำอธิบายตัวอย่าง
Endpoint-initiated (Client)ติดตั้ง Agent บนเครื่อง — เชื่อมต่อไปยัง ZTNA GatewayZscaler ZPA, Cloudflare Access
Service-initiated (Agentless)ZTNA Gateway เชื่อมต่อไปยัง Private App — ไม่ต้องติดตั้ง AgentTailscale, Twingate
Browser-basedใช้ Browser — Remote Browser IsolationCloudflare Browser Isolation

4. Software-Defined Networking (SDN)

4.1 โมเดล SDN

SDN แยก Control Plane (การตัดสินใจ) ออกจาก Data Plane (การส่งข้อมูล):

Traditional Network (Distributed Control):
─────────────────────────────────────────
[Switch 1]     [Switch 2]     [Switch 3]
Control+Data   Control+Data   Control+Data
(แต่ละ Switch ตัดสินใจเอง — OSPF, BGP, STP แยกกัน)

SDN (Centralized Control):
──────────────────────────
┌──────────────────────────────────────┐
│           SDN Controller              │
│  (OpenDaylight, ONOS, Ryu)           │
│  Control Plane — รู้ Topology ทั้งหมด  │
└──────┬──────────┬──────────┬─────────┘
       │          │          │
       ▼          ▼          ▼
   [OpenFlow Switch] [OpenFlow Switch] [OpenFlow Switch]
   Data Plane       Data Plane        Data Plane
   (Forwarding according to Controller)

4.2 SDN Architecture

SDN Architecture (ONF Model):

4.3 ความท้าทายด้านความปลอดภัยของ SDN

ความท้าทายคำอธิบายแนวทางป้องกัน
Single Point of FailureController ถูกโจมตี = ทั้ง Network พังController Cluster (High Availability)
Controller Hijackผู้โจมตีควบคุม ControllerAuthentication + TLS ระหว่าง Controller-Switch
Flow Table Floodingส่ง Flow ใหม่จำนวนมาก — ทำให้ Switch ทำงานหนักเกินไป (Overload)Rate Limiting, Flow Entry Timeout
Man-in-the-Middleโจมตี Northbound/Southbound APImTLS (Mutual TLS)
Application MaliciousApp ที่รันบน Controller เป็น MalwareApplication Sandbox, Code Review
Data Plane Spoofingปลอมแปลง Packet เพื่อหลบเลี่ยง ForwardingOpenFlow Flow Table Validation

4.4 แนวทางการรักษาความปลอดภัย SDN

SDN Security Best Practices:
─────────────────────────────
1. Controller Redundancy — Cluster อย่างน้อย 3 Nodes
2. mTLS — Southbound API (Controller ↔ Switch) ทั้งหมด
3. TLS — Northbound API (Controller ↔ App) ทั้งหมด
4. Authentication — ถ้า API ต้อง Authenticate ทุก Request
5. Flow Table Limits — จำกัดจำนวน Flow Entry ต่อ Switch
6. Logging — Log การเปลี่ยนแปลง Flow Table ทั้งหมด
7. Network Segmentation — แยก Management Network ของ SDN
8. SDN App Vetting — ตรวจสอบ App ก่อนติดตั้งบน Controller
9. Rate Limiting — จำกัด Packet-In Rate (ป้องกัน Controller DoS)
10. Update — อัปเดต SDN Controller Software สม่ำเสมอ

├── Inbound: 80, 443 from 0.0.0.0/0 (ผ่าน WAF)

└── Outbound: 8080 → App SG

App/API SG:
├── Inbound: 8080 from ALB SG
├── Inbound: 22 from Bastion SG (SSH)
├── Inbound: 8443 from Jenkins SG (CI/CD Webhook)
└── Outbound: 443 to Internet (API call ภายนอก)

DB SG:
├── Inbound: 5432 from App SG (PostgreSQL)
├── Inbound: 6379 from App SG (Redis)
└── Inbound: 22 from Bastion SG (SSH — Emergency)

S3 Bucket Policy:
├── Block Public Access: ✅ On
├── Server-Side Encryption: AES-256
├── Bucket Policy: อนุญาตเฉพาะ App Role เท่านั้น
└── Versioning: ✅ On (สำหรับ Ransomware Protection)

7.4 บทเรียนและข้อเสนอแนะ

  1. ใช้ Infrastructure as Code (IaC): Terraform หรือ AWS CDK — ทุก Resource ต้องสร้างผ่าน IaC
  2. Least Privilege IAM: ไม่ใช้ Root Account — ทุก Service ใช้ IAM Role
  3. Encryption ทุกชั้น: At Rest (KMS) + In Transit (TLS)
  4. Logging: CloudTrail + VPC Flow Logs + ALB Access Logs → ส่ง SIEM
  5. Backup: Automated Backup + Cross-Region Replication
  6. Monitoring: CloudWatch Alarm + GuardDuty + Security Hub
  7. Patch Management: Systems Manager — Patch ทุกเดือน
  8. Incident Response: CloudFormation Stack สำหรับ IR (Deploy Forensic Environment)

สรุปท้ายบท (Chapter Summary)

  1. Shared Responsibility Model — Cloud Provider รับผิดชอบ Security ของ Cloud, Customer รับผิดชอบ Security ใน Cloud
  2. Cloud Network Security ใช้ Security Group (Stateful, Instance Level) + NACL (Stateless, Subnet Level) + WAF + Cloud Firewall
  3. SASE รวม Network + Security Functions ใน Cloud Service เดียว — ใช้ SD-WAN + SWG + CASB + ZTNA
  4. ZTNA เข้าถึง App โดยตรง — ไม่ต้อง VPN — ใช้หลัก "Never Trust, Always Verify" + Least Privilege
  5. SDN แยก Control Plane และ Data Plane — มีความเสี่ยงเรื่อง Controller Hijack, Flow Table Flooding, API Security
  6. NFV ย้าย Network Functions จาก Hardware → VM/Container — ต้องระวัง Hypervisor Escape, VNF Isolation
  7. Hybrid/Multi-Cloud ต้องจัดการ Identity, Network, Policy, Visibility, และ Compliance — ใช้ CSPM Tools (Prisma, Wiz)
  8. กรณีศึกษา AWS แสดงแนวทาง Defense in Depth: WAF → Shield → ALB → SG → NACL → IAM → Encryption → Logging

คำถามทบทวน (Review Questions)

1

จงอธิบาย Shared Responsibility Model ในระบบคลาวด์ — เปรียบเทียบ IaaS, PaaS, SaaS ว่าคุณและ Provider รับผิดชอบอะไรบ้าง

ใน IaaS Customer รับผิดชอบ Data, App, OS, Network Config, Firewall Rules ส่วน Provider รับผิดชอบ Hypervisor, Physical Network, Physical Security ใน PaaS Customer รับผิดชอบ Data และ App Code ส่วน Provider รับผิดชอบ Runtime, OS, Network, Middleware, Database ใน SaaS Customer รับผิดชอบ Data Access และ User Permissions ส่วน Provider รับผิดชอบทุกอย่างด้านล่าง

2

ความแตกต่างระหว่าง Security Group และ Network ACL (NACL) ใน AWS คืออะไร? จงเปรียบเทียบ Stateful/Stateless, Rule Order, และ Use Case

Security Group เป็น Stateful, ทำงานระดับ Instance, Allow Rules Only, ไม่เรียงลำดับ Rule, Return Traffic ผ่านอัตโนมัติ เหมาะกับ Instance Protection NACL เป็น Stateless, ทำงานระดับ Subnet, มี Allow + Deny, เรียงลำดับ Rule, ต้องเขียน Rule สำหรับ Return Traffic เหมาะกับ Subnet Protection Layer

3

SASE คืออะไร? จงอธิบาย components หลักของ SASE (SD-WAN, SWG, CASB, ZTNA, FWaaS, DLP)

SASE คือแนวคิดที่รวม Network และ Security Functions เป็น Cloud-based Service ประกอบด้วย SD-WAN (เชื่อมต่อสาขา), SWG (กรองเว็บ), CASB (ควบคุมการเข้าถึง Cloud App), ZTNA (เข้าถึง App แบบ Zero Trust), FWaaS (Firewall จาก Cloud), และ DLP (ป้องกันการสูญหายของข้อมูล)

4

ZTNA แตกต่างจาก VPN อย่างไร? จงอธิบายหลักการ "Never Trust, Always Verify" และ "Least Privilege"

VPN ให้ Full Network Access เมื่อเชื่อมต่อแล้วสามารถเข้าถึงทรัพยากรในเครือข่ายได้เกือบทั้งหมด ZTNA ให้ App-specific Access เท่านั้น ไม่มี Network-level Access โดยใช้หลัก Never Trust, Always Verify คือตรวจสอบผู้ใช้และอุปกรณ์ตลอดเวลา และ Least Privilege คือเข้าถึงเฉพาะ App ที่จำเป็น

5

SDN มีกี่ Layer (Application, Control, Infrastructure)? จงอธิบายความท้าทายด้านความปลอดภัยของแต่ละ Layer

SDN มี 3 Layers: Application Layer (Security App, Network Policy, Load Balancer) มีความเสี่ยงจาก Malicious App Control Layer (SDN Controller) มีความเสี่ยง Controller Hijack, Single Point of Failure, DoS Infrastructure Layer (OpenFlow Switches) มีความเสี่ยง Flow Table Flooding, Data Plane Spoofing

6

NFV คืออะไร? จงอธิบายความแตกต่างระหว่าง Traditional Network Appliance และ NFV

NFV คือการย้าย Network Functions เช่น Router, Firewall, IDS, Load Balancer จาก Hardware Appliance ไปเป็น Virtual Machine หรือ Container บน Standard Server ข้อดีคือลดค่าใช้จ่าย Hardware ยืดหยุ่นในการ Deploy และ Scale แต่ต้องระวัง Hypervisor Escape, VNF Isolation, VNF Image Tampering

7

Hybrid Cloud และ Multi-Cloud แตกต่างกันอย่างไร? จงอธิบายความท้าทายด้านความปลอดภัยอย่างน้อย 4 ข้อ

Hybrid Cloud คือการเชื่อมต่อ On-premises กับ Cloud หนึ่ง Provider Multi-Cloud คือการใช้หลาย Cloud Provider พร้อมกัน ความท้าทายได้แก่ Identity Fragmentation, Network Connectivity, Security Policy Consistency, Visibility, Compliance, และ Cost Management

8

จงอธิบายหลักการออกแบบ Network Security สำหรับ Web Application บน Cloud — ครอบคลุม WAF, Shield, ALB, SG, NACL, IAM

ออกแบบแบบ Defense in Depth: WAF กรอง Layer 7 (SQLi, XSS) Shield ป้องกัน DDoS ALB กระจายภาระและทำ HTTPS Termination SG ควบคุม Traffic ระดับ Instance NACL ควบคุมระดับ Subnet IAM ให้สิทธิ์เฉพาะที่จำเป็น (Least Privilege) รวมถึง Encryption และ Logging ทุกชั้น

9

จากกรณีศึกษาในบทนี้ จงอธิบายว่าเหตุใด RDS ต้องอยู่ใน Private Subnet และ SG ต้อง Allow Traffic จาก App SG เท่านั้น

RDS อยู่ใน Private Subnet เพื่อไม่ให้มี Public IP และไม่สามารถเข้าถึงได้โดยตรงจากอินเทอร์เน็ต ลดพื้นที่ผิวที่ถูกโจมตี SG อนุญาต Traffic จาก App SG เท่านั้น เพื่อบังคับให้ทุกการเข้าถึง Database ต้องผ่าน Application Layer ตามหลัก Least Privilege และ Defense in Depth

10

จงเขียน Terraform snippet สำหรับ Security Group ที่อนุญาต HTTPS จาก ALB ไปยัง Web Server และ SSH จาก Bastion Host

resource "aws_security_group" "web_sg" {
  name        = "web_sg"
  description = "Allow HTTPS from ALB and SSH from Bastion"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.alb_sg.id]
    description     = "HTTPS from ALB"
  }

  ingress {
    from_port       = 22
    to_port         = 22
    protocol        = "tcp"
    security_groups = [aws_security_group.bastion_sg.id]
    description     = "SSH from Bastion"
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
