ส่วนที่ 2: Zero Trust Architecture (ZTA)

2.1 หลักการ Zero Trust

Zero Trust (NIST SP 800-207, 2020) — "Never Trust, Always Verify":

หลักการ 7 ข้อของ Zero Trust (ตาม CISA):

1. Continuous Verification — ตรวจสอบตลอดเวลา ไม่ใช่แค่ครั้งแรก
2. Limit Blast Radius — Micro-segmentation, Least Privilege
3. Automate Context Collection — Identity, Device, Location, Behavior
4. Assume Breach — ออกแบบระบบโดยคิดว่าถูกโจมตีแล้ว
5. Never Trust, Always Verify — ไม่เชื่อถือ Internal/Local โดยอัตโนมัติ
6. Least Privilege Access — ให้สิทธิ์เท่าที่จำเป็น
7. Data-Centric Security — ปกป้อง Data ไม่ใช่ Perimeter
ZT vs Traditional:
───────────────────
Traditional (Castle-and-Moat):
[Internet] ──▶ [Firewall ← Tight Security] ──▶ [Internal Network ← Loose]
                    │                                     │
                    │                                     │
               ถ้าเจาะ Firewall ได้ → เข้าถึงทุกอย่างได้ ❌

Zero Trust:
[Internet] ──▶ [ZTNA] ──▶ [App A]     (User → แค่ App A)
                           [App B]     (User → แค่ App B)
                           [Database]  (User → ไม่ได้เลย)
              │                               │
         ทุก Connection ต้อง Verify       Micro-segmentation
         + Authenticate                   + Least Privilege

2.2 BeyondCorp (Google)

Google BeyondCorp คือ Zero Trust Implementation ของ Google — เปลี่ยนจาก Network-Centric → User-Centric:

BeyondCorp Model:
──────────────────
Traditional Google (ก่อน 2010):
[Employee] ──▶ [VPN] ──▶ [Corporate Network] ──▶ [App]
                     │                          │
                เชื่อมต่อ VPN ก่อน         เข้าถึงทุก App

BeyondCorp (2011+):
[Employee] ──▶ [Internet] ──▶ [Access Proxy] ──▶ [App A]
                     │               │
                ไม่ต้อง VPN          ตรวจสอบ:
                                    ├── User Identity
                                    ├── Device Inventory
                                    ├── Device Certificate
                                    └── Context (Location, Time)

บทเรียนจาก BeyondCorp:

  1. ไม่ต้อง VPN — พนักงานเข้าถึง App ได้จากทุกที่โดยตรง
  2. Device Inventory ครบ — ทุกเครื่องต้องมี Certificate
  3. Access Proxy — ทุก Request ผ่าน Proxy (ตรวจสอบทุกครั้ง)
  4. App-level Access — พนักงานเข้าถึงเฉพาะ App ที่ได้รับอนุญาต
  5. No Network-level Access — ไม่มีใครเห็น Network ทั้งหมด

2.3 ZTNA (Zero Trust Network Access)

ZTNA (SASE Component) — เข้าใกล้ทรัพยากรโดยไม่ต้องต่อ VPN:

ZTNA vs VPN:
─────────────
VPN:
├── User ได้ IP ใน Corporate Network
├── User เห็น Network ทั้งหมด (Lateral Movement ได้)
├── Once Connected → Full Access
└── เปิด Port ไปยัง Internal Network

ZTNA:
├── User เชื่อมต่อไปยัง App โดยตรง (ไม่ใช่ Network)
├── User ไม่เห็น Network — ไม่มี Lateral Movement
├── ทุก Request ถูกตรวจสอบ
└── App ถูกซ่อนจาก Internet (ไม่ต้องเปิด Port)

ส่วนที่ 4: Post-Quantum Cryptography

4.1 Quantum Computing และผลกระทบ

เมื่อ Quantum Computer ที่มี Qubit เพียงพอ (หลายพัน Logical Qubit) มาถึง — การเข้ารหัสที่เป็นอยู่จะพัง:

Algorithmจุดประสงค์สถานะปัจจุบันผลกระทบจาก Quantum
RSA-2048Digital Signature, Key Exchangeใช้ทั่วไป❌ Shor's Algorithm — แก้ได้ในไม่กี่นาที
ECDSA / ECDHKey Exchange, Signatureใช้ทั่วไป❌ Shor's Algorithm — แก้ได้
AES-256Symmetric Encryptionใช้ทั่วไป✅ Grover's Algorithm — Reduction ครึ่งนึง (ยังปลอดภัยที่ 128-bit)
SHA-256Hashingใช้ทั่วไป✅ Grover's Algorithm — Reduction ครึ่งนึง (ยังปลอดภัย)

Timeline ที่คาดการณ์:

  • 2030: Quantum Computer ที่สามารถทำลาย RSA-2048 ได้? (ยังมีความไม่แน่นอนสูง)
  • NIST PQC Standardization: 2024 — มาตรฐาน Post-Quantum Algorithms
  • Migration: องค์กรควรเริ่มวางแผนตอนนี้ (Crypto Agility)

4.3 Crypto Agility

Crypto Agility = ความสามารถในการเปลี่ยน Algorithm ได้โดยไม่ต้องเปลี่ยนระบบทั้งหมด:

Crypto Agility Requirements:
─────────────────────────────
1. Protocol Negotiation — รองรับ Algorithm หลายแบบ
2. Algorithm Independence — ไม่ Hardcode Algorithm
3. Hybrid Mode — รองรับ Classic + PQC พร้อมกัน
4. Versioning — Version Algorithm ได้
5. Migration Plan — เปลี่ยน Algorithm ได้โดย Downtime น้อย

ส่วนที่ 5: 5G Security

5.1 สถาปัตยกรรมความปลอดภัยของ 5G

5G ปรับปรุงความปลอดภัยจาก 4G/LTE อย่างมีนัยสำคัญ:

คุณสมบัติ4G (LTE)5G
AuthenticationEPS-AKA5G-AKA + EAP-AKA'
SUCIIMSI (Plaintext)SUCI (Encrypted SUPI)
Network Slicing❌ ไม่มี✅
Edge Computing❌ จำกัด✅ MEC
User Plane Integrity❌ ไม่มี✅ (สำหรับ URLLC)
Roaming SecurityปานกลางSEAL (Security Edge Protection Proxy)
PrivacyIMSI ไม่เข้ารหัสSUCI encrypts IMSI

SUCI (Subscription Concealed Identifier):

  • 4G: IMSI (International Mobile Subscriber Identity) ส่งแบบ Plaintext — ใครก็ดักจับได้
  • 5G: SUCI = IMSI เข้ารหัสด้วย Public Key ของ Home Network — เฉพาะ Home Network เท่านั้นที่ถอดรหัสได้

Security Implications ของ Network Slicing:

  • แต่ละ Slice ต้อง Isolation แข็งแรง — บัคใน Slice หนึ่งไม่รั่วไปอีก Slice

  • Slice-Specific Security Policy — Security Profile ต่างกันตาม Slice
  • 5G Security Architecture กำหนดให้ Network Slicing ต้องมี Isolation ระดับ Network, Compute, Storage

5.3 Multi-access Edge Computing (MEC) Security

MEC นำ Compute มาไว้ใกล้ผู้ใช้ (Edge) — ลด Latency:

MEC Security:
─────────────
Traditional Cloud:
[Device] ────▶ [Cloud DC] — Latency 50-100ms
                      │
                 Security = ที่ Cloud

Edge (MEC):
[Device] ──▶ [Edge Node] — Latency 1-5ms
                 │            ─── ใกล้ Device
            Security = Edge + Cloud
                 │
            Edge Challenges:
            ├── Physical Security (Edge Node อยู่นอก Data Center)
            ├── Limited Resource (CPU/RAM ที่ Edge)
            ├── Update Management (Edge Node จำนวนมาก)
            └── Trust Model (Edge Node เชื่อถือได้?)

แนวทาง:
├── Trusted Execution Environment (TEE) — Intel SGX, ARM TrustZone
├── Attestation — ตรวจสอบ Integrity ของ Edge Node
├── Encryption — Data ทุกชั้น (Edge ↔ Cloud)
└── Zero Trust — Edge Node ต้อง Authentication ก่อนเชื่อมต่อ Cloud

6.2 Security Playbook ตัวอย่าง

Playbook: Phishing Response (Automated)
─────────────────────────────────────────
Trigger: 🚨 User รายงานอีเมลต้องสงสัย / SIEM Alert

Step 1 — Analyze Email:
├── 🔍 Extract URLs, Attachments, Headers
├── 🔍 Sandbox URL + Attachment
├── 🔍 Check Threat Intelligence (VirusTotal, OTX)
└── 🧠 ML Classification: Phishing (Confidence: 98%)

Step 2 — Contain:
├── 🛑 Block Sender Domain on Email Gateway
├── 🛑 Block URLs on SWG (Secure Web Gateway)
├── 🛑 Quarantine email from all recipients
└── 📧 Notify: "You received a phishing email" + instructions

Step 3 — Investigate:
├── 🔍 SIEM Query: อีเมลนี้ถูกเปิดโดยกี่คน?
├── 🔍 EDR Query: เครื่องที่คลิก Link มีพฤติกรรมผิดปกติหรือไม่?
└── 📋 Create Incident Ticket (Priority: High)

Step 4 — Remediate:
├── 🛑 If machine infected → EDR Isolate Host
├── 🛑 If credential phished → Force Password Reset + MFA Re-enroll
├── 📧 Send Organization-wide Phishing Alert
└── 📊 Update Phishing Metrics Dashboard

คำถามทบทวน (Review Questions)

1

จงอธิบายหลักการ Zero Trust ตาม NIST SP 800-207 — "Never Trust, Always Verify" — และเปรียบเทียบกับ Traditional Castle-and-Moat Model

Zero Trust (NIST SP 800-207, 2020) ยึดหลัก "Never Trust, Always Verify" — ไม่เชื่อถืออะไรโดยอัตโนมัติทั้ง Internal และ Local Network ทุก Connection ต้องถูกตรวจสอบ (Verify) และพิสูจน์ตัวตน (Authenticate) ทุกครั้ง หลักการ 7 ข้อตาม CISA: Continuous Verification, Limit Blast Radius, Automate Context Collection, Assume Breach, Never Trust Always Verify, Least Privilege Access และ Data-Centric Security เปรียบเทียบกับ Castle-and-Moat: Traditional Model เน้นป้องกันที่ Perimeter (Firewall แน่นหนา) แต่ภายใน Internal Network หลวม — ถ้าผู้โจมตีเจาะ Firewall ได้จะเข้าถึงทุกอย่างได้ (Lateral Movement อิสระ) ส่วน Zero Trust ใช้ Micro-segmentation + Least Privilege — ผู้ใช้ได้สิทธิ์เฉพาะ App ที่อนุญาตเท่านั้น ไม่มี Network-level Access

2

BeyondCorp ของ Google เปลี่ยนวิธีรักษาความปลอดภัยอย่างไร? จงอธิบายความแตกต่างระหว่าง BeyondCorp และ VPN

BeyondCorp คือ Zero Trust Implementation ของ Google — เปลี่ยนจาก Network-Centric → User-Centric พนักงานเข้าถึง App ได้จากทุกที่โดยไม่ต้องต่อ VPN ทุก Request ผ่าน Access Proxy ที่ตรวจสอบ User Identity, Device Inventory, Device Certificate และ Context (Location, Time) ก่อนให้เข้าถึงเฉพาะ App ที่ได้รับอนุญาต (App-level Access) ความแตกต่างจาก VPN: VPN ให้ผู้ใช้ได้ IP ใน Corporate Network และเห็น Network ทั้งหมด — Once Connected → Full Access (Lateral Movement ได้) และต้องเปิด Port เข้า Internal Network ส่วน BeyondCorp/ZTNA ผู้ใช้เชื่อมต่อไปยัง App โดยตรง ไม่เห็น Network — App ถูกซ่อนจาก Internet และทุก Request ถูกตรวจสอบทุกครั้ง

3

AI/ML ถูกนำมาใช้ใน Network Security อย่างไร? จงอธิบาย UEBA และยกตัวอย่างพฤติกรรมที่ UEBA สามารถตรวจจับได้

การประยุกต์ใช้ AI/ML: Network Anomaly Detection (Autoencoder, LSTM), Malware Detection (CNN, Random Forest — วิเคราะห์ PE Header, API Call Sequence), Phishing Detection (NLP, BERT), DNS Tunneling Detection (ML on DNS Metadata), DDoS Mitigation (Reinforcement Learning), Fraud Detection (Graph Neural Network) และ Automated Incident Response (AI Planning) UEBA (User and Entity Behavior Analytics) ใช้ ML (Isolation Forest, Bayesian) สร้าง Baseline พฤติกรรมปกติของผู้ใช้และ Entity แล้วแจ้งเตือนเมื่อพบ Deviation ตัวอย่างการตรวจจับ Insider Threat: ผู้ใช้ที่ปกติ Login 08:00-18:00 จาก Office แต่จู่ๆ Login เวลา 03:15 น. วันอาทิตย์ ผ่าน Tor Exit Node, เข้าถึง DB Server เป็นครั้งแรก, Download ไฟล์ 5 GB และ Forward อีเมล 500 ฉบับไป external@gmail.com → Risk Score 96/100 (CRITICAL) → ระบบ Disable account + Notify IR + Block IP อัตโนมัติ

4

Quantum Computing มีผลกระทบต่อการเข้ารหัสแบบปัจจุบันอย่างไร? RSA-2048 และ AES-256 ต่างกันตรงไหน?

เมื่อ Quantum Computer ที่มีหลายพัน Logical Qubit มาถึง การเข้ารหัสที่เป็นอยู่จะพัง RSA-2048 (และ ECDSA/ECDH) เป็นการเข้ารหัสแบบ Asymmetric ที่พึ่งพาปัญหาการแยกตัวประกอบ/Discrete Logarithm — Shor's Algorithm แก้ได้ในไม่กี่นาที ❌ ต้องย้ายไป Post-Quantum Algorithm AES-256 เป็นการเข้ารหัสแบบ Symmetric — ถูกกระทบเพียง Grover's Algorithm ซึ่งลดความแข็งแรงลงครึ่งนึง (256-bit → effective 128-bit) แต่ยังถือว่าปลอดภัย ✅ Timeline: NIST ประกาศมาตรฐาน PQC ปี 2024, คาดการณ์ว่า Quantum Computer ที่ทำลาย RSA-2048 ได้อาจมาประมาณปี 2030 (ยังไม่แน่นอนสูง) — องค์กรควรเริ่มวางแผน Migration ตอนนี้ (Crypto Agility) เพราะข้อมูลที่ถูกดักจับไปวันนี้ อาจถูกถอดรหัสในอนาคต (Harvest Now, Decrypt Later)

5

NIST PQC Standardization เลือก Algorithm ใดบ้าง? จงอธิบาย CRYSTALS-Kyber และ CRYSTALS-Dilithium

NIST Post-Quantum Cryptography Standardization (2016-2024) เลือก 4 Algorithms: 1) CRYSTALS-Kyber — KEM (Key Encapsulation Mechanism) ใช้สำหรับ Key Exchange มาตรฐาน FIPS 203 2) CRYSTALS-Dilithium — Digital Signature สำหรับ Signing มาตรฐาน FIPS 204 3) FALCON — Digital Signature ขนาดเล็กกว่า (smaller) 4) SPHINCS+ — Digital Signature แบบ Stateless มาตรฐาน FIPS 205 CRYSTALS-Kyber ทำหน้าที่แทน ECDHE ในการแลก Key ส่วน CRYSTALS-Dilithium ทำหน้าที่แทน RSA Signature ในการยืนยันตัวตนของ Certificate — ช่วง Migration ใช้ Hybrid Mode เช่น TLS 1.3: ECDHE(X25519) + Kyber-768 + AES-256-GCM + Dilithium3 Signature

6

5G Network Slicing คืออะไร? จงอธิบาย Security Implications ของ Network Slicing (Isolation, Authentication)

Network Slicing คือการสร้าง Virtual Network แยกตามการใช้งานบน 5G Core Network เดียวกัน — 3 Slice หลัก: eMBB (Enhanced Mobile Broadband — Speed 10 Gbps สำหรับ Video Streaming, Smartphone), URLLC (Ultra-reliable Low-latency — Latency 1 ms สำหรับรถยนต์อัตโนมัติ, อุตสาหกรรม, Remote Surgery) และ mMTC (Massive IoT — 1 ล้าน Device/km² สำหรับ Sensor, Smart Meter) Security Implications: 1) แต่ละ Slice ต้องมี Isolation แข็งแรง — ช่องโหว่ใน Slice หนึ่งต้องไม่รั่วไปอีก Slice 2) Slice Authentication — แต่ละ Slice ต้อง Authenticate แยกกัน 3) Slice-Specific Security Policy — Security Profile ต่างกันตาม Slice 4) 5G Security Architecture กำหนดให้ต้องมี Isolation ระดับ Network, Compute และ Storage

7

SUCI ใน 5G แตกต่างจาก IMSI ใน 4G อย่างไร? จงอธิบายว่าการเข้ารหัส IMSI ช่วยป้องกันการติดตามผู้ใช้อย่างไร

4G: อุปกรณ์ส่ง IMSI (International Mobile Subscriber Identity) แบบ Plaintext เมื่อลงทะเบียนเข้าเครือข่าย — ใครก็ดักจับได้ (เช่น IMSI Catcher / Fake Base Station) ทำให้ระบุตัวตนและติดตามตำแหน่งผู้ใช้ได้ 5G: ใช้ SUCI (Subscription Concealed Identifier) = IMSI/SUPI ที่เข้ารหัสด้วย Public Key ของ Home Network — เฉพาะ Home Network เท่านั้นที่ถอดรหัสได้ด้วย Private Key ของตนเอง การป้องกันการติดตาม: ผู้ดักฟังสัญญาณ (รวมถึงเครือข่าย_visited และอุปกรณ์ดักจับ) เห็นเพียง SUCI ที่เข้ารหัสและไม่ซ้ำรูปแบบ จึงไม่สามารถเชื่อมโยงการลงทะเบียนต่างๆ เข้ากับผู้ใช้คนเดิมหรือติดตามตำแหน่งได้ — Privacy ดีขึ้นอย่างมีนัยสำคัญ

8

SOAR มีองค์ประกอบอะไร? จงเขียน Security Playbook สำหรับ Incident Response (ตั้งแต่ Trigger → Report)

องค์ประกอบของ SOAR 4 ส่วน: 1) Orchestration — เชื่อมต่อ Tools (SIEM ↔ EDR ↔ Firewall ↔ Email ↔ IAM ↔ Ticketing) 2) Automation — ตอบสนองอัตโนมัติตาม Playbook 3) Response — ทำ Action บน Tools ผ่าน API (Firewall Block IP, EDR Isolate Host, Disable AD User, Create ServiceNow Ticket) 4) Case Management — ติดตาม Incident (Timeline, Evidence, Communication, Report) ตัวอย่าง Playbook — Phishing Response: Trigger: User รายงานอีเมลต้องสงสัย / SIEM Alert → Step 1 Analyze: Extract URLs/Attachments/Headers, Sandbox, Check Threat Intelligence (VirusTotal, OTX), ML Classification → Step 2 Contain: Block Sender Domain บน Email Gateway, Block URLs บน SWG, Quarantine อีเมลจากผู้รับทุกคน, แจ้งผู้ได้รับอีเมล → Step 3 Investigate: SIEM Query หาคนที่เปิดอีเมล, EDR Query หาพฤติกรรมผิดปกติ, สร้าง Incident Ticket (Priority: High) → Step 4 Remediate: ถ้าเครื่องติดเชื้อ → EDR Isolate Host, ถ้า Credential หลุด → Force Password Reset + MFA Re-enroll, แจ้งเตือนทั้งองค์กร, อัปเดต Dashboard → Step 5 Report: MITRE ATT&CK Mapping, Timeline + Impact, Lessons Learned

9

Crypto Agility คืออะไร และเหตุใดจึงสำคัญต่อการเปลี่ยนผ่านสู่ Post-Quantum Cryptography?

Crypto Agility = ความสามารถในการเปลี่ยน Cryptographic Algorithm ได้โดยไม่ต้องเปลี่ยนระบบทั้งหมด Requirements 5 ข้อ: 1) Protocol Negotiation — รองรับ Algorithm หลายแบบ 2) Algorithm Independence — ไม่ Hardcode Algorithm 3) Hybrid Mode — รองรับ Classic + PQC พร้อมกัน 4) Versioning — Version Algorithm ได้ 5) Migration Plan — เปลี่ยน Algorithm ได้โดย Downtime น้อย ความสำคัญต่อการเปลี่ยนผ่านสู่ PQC: การ Migration สู่ Post-Quantum ไม่ได้เกิดขึ้นชั่วข้ามคืน และมาตรฐานยังพัฒนาต่อเนื่อง (เช่น TLS 1.3 แบบ Hybrid: ECDHE(X25519) + Kyber-768 ก่อนจะเปลี่ยนเป็น Pure PQC: Kyber-1024 + Dilithium5) — องค์กรที่มี Crypto Agility จะสลับ Algorithm ได้เร็วเมื่อมาตรฐานนิ่งหรือเมื่อ Algorithm เดิมถูกโจมตี โดยไม่ต้องรื้อระบบทั้งหมด ซึ่งลดความเสี่ยงจากภัยคุกคาม Quantum Computing ที่จะมาถึง

10
