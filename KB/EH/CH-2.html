2.1 ทำไมผู้ทดสอบต้องเข้าใจลินุกซ์จากภายใน

สัปดาห์ที่แล้วปิดท้ายด้วยข้อความว่าผู้เรียนจะเริ่มสร้างทักษะชุดแรกคือการทำงานกับระบบปฏิบัติการลินุกซ์บน command line และทักษะนี้จะถูกใช้ในทุกสัปดาห์ที่เหลือ บทนี้จึงต้องตอบคำถามให้ชัดเจนเสียก่อนว่า "เข้าใจลินุกซ์" ในความหมายของรายวิชานี้หมายถึงอะไร เพราะคำว่าเข้าใจในที่นี้ลึกกว่าการเปิดเครื่องขึ้นมาแล้วใช้งานโปรแกรมสำเร็จรูปได้

สามระดับของความเข้าใจ

ความเข้าใจระบบปฏิบัติการลินุกซ์แบ่งได้เป็นสามระดับซึ่งให้ผลต่างกันโดยสิ้นเชิง

ระดับแรกคือ ระดับผู้ใช้ ผู้ใช้ทั่วไปรู้ว่าต้องเปิดโปรแกรมใดเพื่อแก้งานหนึ่ง และรู้ว่าไฟล์ของตนเก็บอยู่ที่ใดในโฟลเดอร์ส่วนตัว ความรู้นี้เพียงพอต่อการใช้งานประจำวัน แต่แทบไม่ให้ข้อมูลใดแก่ผู้ตรวจสอบระบบ เพราะผู้ใช้มองเห็นเฉพาะส่วนที่ระบบจัดสรรให้เห็น

ระดับที่สองคือ ระดับผู้ดูแลระบบ ผู้ดูแลระบบรู้ว่าบริการแต่ละตัวอ่านค่าตั้งต้นจากไฟล์ใด รู้ว่าบัญชีผู้ใช้ถูกเก็บไว้ที่ไหน และรู้ว่าบันทึกเหตุการณ์ของระบบอยู่ที่ใด ความรู้ระดับนี้ทำให้เข้าใจว่าระบบประกอบกันอย่างไร และเป็นระดับที่ผู้ทดสอบเจาะระบบจำเป็นต้องมีเป็นอย่างน้อย

ระดับที่สามคือ ระดับผู้ตรวจสอบ ผู้ตรวจสอบระบบมองทุกองค์ประกอบในสองด้านพร้อมกัน ด้านหนึ่งคือด้านการทำงานว่าสิ่งนั้นมีไว้ทำอะไร แต่อีกด้านหนึ่งคือด้านความเสี่ยงว่าสิ่งนั้นเปิดช่องให้ผู้ไม่หวังดีทำอะไรได้บ้าง บทนี้จะพาผู้เรียนขึ้นไปถึงระดับที่สามทีละชั้น โดยเริ่มจากคำถามที่ตรงที่สุดว่า ผู้ทดสอบเจาะระบบเห็นอะไรในระบบปฏิบัติการที่ผู้ใช้ทั่วไปและผู้ดูแลระบบมักมองข้าม

ทุกการกระทำทิ้งร่องรอย

ระบบลินุกซ์สร้างขึ้นบนปรัชญาที่ต่างจากระบบปฏิบัติการแบบหน้าจอเป็นหลักอย่างชัดเจน ปรัชญาหนึ่งที่สำคัญที่สุดกล่าวว่า "ทุกอย่างคือไฟล์" (Everything is a file) ไม่ว่าจะเป็นเอกสารรายงาน ไฟล์ปรับแต่งระบบ อุปกรณ์ต่อพ่วง ไปจนถึงสถานะของกระบวนการที่กำลังทำงานอยู่ ระบบล้วนเปิดให้เข้าถึงผ่านส่วนติดต่อแบบเดียวกันคือไฟล์

ผลที่ตามมาข้อแรกคือความสามารถในการตรวจสอบ ระบบลินุกซ์บันทึกเวลาเข้าถึง เวลาแก้ไข และเวลาเปลี่ยนแปลงเมทาดาทาของไฟล์ไว้แทบทุกครั้งที่มีการกระทำ ผู้ที่เข้าใจโครงสร้างนี้ย่อมรู้ว่าต้องไปถามหลักฐานที่ใดเมื่อต้องการตอบคำถามว่าใครทำอะไรกับไฟล์ใดเมื่อไร

ผลที่ตามมาข้อที่สองคือความสามารถในการเชื่อมโยง ระบบลินุกซ์ทำงานด้วยโปรแกรมเล็กๆ จำนวนมากที่รับข้อมูลจากโปรแกรมหนึ่งส่งต่อให้อีกโปรแกรมหนึ่งผ่านช่องทางมาตรฐาน ผู้ที่เข้าใจการเชื่อมต่อนี้จะประกอบเครื่องมือขนาดเล็กเหล่านี้เข้าด้วยกันเป็นงานที่ซับซ้อนได้ โดยไม่ต้องรอโปรแกรมสำเร็จรูปที่ทำทุกอย่างให้เสร็จ

เหตุใดเครื่องมือมาตรฐานจึงสำคัญกว่าที่คิด

ในการทดสอบเจาะระบบ ผู้ทดสอบมักต้องทำงานบนเครื่องเป้าหมายที่ตนไม่ได้เป็นผู้ติดตั้ง และบ่อยครั้งไม่มีสิทธิ์ติดตั้งโปรแกรมเพิ่มเติม ไม่ว่าจะด้วยเหตุผลด้านสิทธิ์หรือด้วยเหตุผลว่าไม่ควรทิ้งร่องรอยที่ผิดปกติไว้บนเครื่องของผู้อื่น เครื่องมือที่ใช้ได้จึงมักจำกัดอยู่ที่โปรแกรมมาตรฐานซึ่งมีติดมากับระบบอยู่แล้ว วิธีคิดแบบนี้เรียกกันว่า การอยู่กับเครื่องมือที่มีอยู่ (Living off the Land) หมายถึงการใช้เครื่องมือที่ถูกต้องตามกฎหมายและมีอยู่แล้วในระบบทำหน้าที่ซึ่งผู้บุกรุกต้องการ

แนวคิดนี้ให้บทเรียนสองด้านแก่ผู้เรียน ด้านหนึ่งคือผู้ทดสอบต้องรู้จักเครื่องมือมาตรฐานอย่างลึกพอที่จะประกอบมันเข้าด้วยกันได้ อีกด้านหนึ่งคือผู้ป้องกันต้องตระหนักว่าเครื่องมือมาตรฐานเหล่านี้จะไม่ถูกจับตามองว่าเป็นภัย เพราะมันคือส่วนหนึ่งของระบบ การตรวจจับจึงต้องดูที่รูปแบบการใช้มากกว่าตัวโปรแกรม

เครื่องมือทั้งชุดที่ผู้เรียนจะได้ในบทนี้ ได้แก่ find, grep, awk, sed, cut, ss, ps, systemctl และ crontab ทั้งหมดเป็นโปรแกรมที่ติดตั้งมาพร้อมระบบลินุกซ์แทบทุกสายพันธุ์ ไม่ต้องดาวน์โหลดเพิ่ม และทำงานได้แม้ในสภาพแวดล้อมที่จำกัดสิทธิ์อย่างมาก

ลำดับของบท

บทนี้เรียงหัวข้อตามลำดับที่ผู้ตรวจสอบระบบอ่านเครื่องหนึ่งเครื่องจริงๆ เริ่มจากโครงสร้างระบบไฟล์เพื่อรู้ว่าโลกทั้งใบตั้งอยู่บนฐานใด ต่อด้วยระบบสิทธิ์ซึ่งเป็นกติกาว่าใครแตะอะไรได้ ตามด้วยบัญชีผู้ใช้และกลไกยกระดับสิทธิ์ซึ่งเป็นกุญแจหลักของงานนี้ จากนั้นจึงไล่ขึ้นไปถึงสิ่งที่กำลังทำงานอยู่บนเครื่องทั้งในขณะนี้และตามกำหนดเวลา ปิดท้ายด้วยบันทึกเหตุการณ์ซึ่งเป็นหลักฐานสำหรับตอบคำถามย้อนหลัง และเครื่องมือบรรทัดคำสั่งซึ่งใช้เก็บทุกอย่างที่เห็นให้อยู่ในรูปที่นำไปใช้ต่อได้

2.2 โครงสร้างระบบไฟล์และตำแหน่งสำคัญ

ต้นไม้เดียวจากรากเดียว

ระบบไฟล์ของลินุกซ์ต่างจากระบบปฏิบัติการที่ผู้ใช้ทั่วไปคุ้นเคยในจุดพื้นฐานที่สุดจุดหนึ่ง ระบบปฏิบัติการตระกูลวินโดวส์แบ่งพื้นที่จัดเก็บออกเป็นไดรฟ์แยกกัน เช่น C: และ D: ซึ่งแต่ละไดรฟ์มีลำดับชั้นของตนเองเป็นอิสระต่อกัน ส่วนลินุกซ์มีลำดับชั้นเดียวที่เริ่มจากจุดเดียวคือเครื่องหมายทับ (/) เรียกว่า ราก (Root) และทุกอย่างในระบบอยู่ภายใต้จุดนั้น ไม่ว่าจะเป็นฮาร์ดดิสก์ลูกที่สอง อุปกรณ์เก็บข้อมูลแบบถอดได้ หรือแม้แต่ระบบไฟล์ที่อยู่บนเครื่องอื่นซึ่งเชื่อมต่อผ่านเครือข่าย ทั้งหมดถูกต่อเข้าที่รากเดียวกันในตำแหน่งที่เรียกว่า จุดเชื่อมต่อ (Mount Point)

ผลของโครงสร้างนี้คือที่อยู่ของไฟล์ใดๆ ในระบบเขียนได้ด้วยเส้นทางเดียวเสมอ การเข้าใจว่าไฟล์หนึ่งอยู่ที่ใดจึงเท่ากับเข้าใจว่าไฟล์นั้นทำหน้าที่อะไร เพราะตำแหน่งในระบบลินุกซ์ไม่ได้เรียงตามความสะดวกของผู้ใช้ แต่เรียงตามหน้าที่และอายุการเก็บรักษาของข้อมูล

มาตรฐานที่กำหนดว่าไดเรกทอรีใดควรบรรจุสิ่งใดชื่อ มาตรฐานลำดับชั้นระบบไฟล์ (Filesystem Hierarchy Standard หรือ FHS) มาตรฐานฉบับปัจจุบันคือ FHS 3.0 ซึ่งเผยแพร่โดย Linux Foundation แม้ผู้พัฒนาลินุกซ์แต่ละสายพันธุ์จะมีการปรับรายละเอียดต่างกันบ้าง แต่โครงหลักยังตรงกันจนผู้เรียนสามารถย้ายความรู้จากระบบหนึ่งไปใช้อีกระบบหนึ่งได้

/usrโปรแกรมและข้อมูลที่ติดตั้งจากแพ็กเกจ/usr/local ใช้สำหรับสิ่งที่ติดตั้งเอง
/optซอฟต์แวร์เสริมจากผู้จำหน่ายรายอื่นมักเป็นที่วางเครื่องมือของบุคคลที่สาม

/sysระบบไฟล์เสมือนแสดงสถานะอุปกรณ์ฮาร์ดแวร์ใช้ปรับค่าอุปกรณ์ผ่านเส้นทางไฟล์
/devไฟล์อุปกรณ์ เช่น ดิสก์และเทอร์มินัลสิทธิ์ผิดพลาดที่นี่มีผลร้ายแรงมาก
/bootเคอร์เนลและไฟล์เริ่มต้นระบบมักถูกแยกเป็นพาร์ทิชันของตนเอง
/runข้อมูลชั่วคราวของผู้ใช้และบริการที่กำลังทำงานสูญหายเมื่อรีบูต ใช้เก็บไฟล์ PID
/srvข้อมูลสำหรับบริการที่เครื่องให้บริการเช่น เนื้อหาเว็บหรือไฟล์แชร์

ข้อที่ควรทำความเข้าใจตั้งแต่ต้นคือ /proc และ /sys ไม่ใช่พื้นที่จัดเก็บบนดิสก์ แต่เป็นหน้าต่างที่เคอร์เนลเปิดให้ผู้ใช้มองเข้าไปในสถานะภายในของระบบ การอ่านไฟล์ใน /proc จึงเท่ากับการถามเคอร์เนลว่าขณะนี้ระบบกำลังทำอะไรอยู่ ซึ่งจะเป็นประโยชน์อย่างมากในหัวข้อ 2.5

สี่ตำแหน่งที่ผู้ตรวจสอบต้องรู้จักก่อนใคร

แม้ระบบไฟล์จะมีไดเรกทอรีนับร้อย แต่มีสี่ตำแหน่งที่ให้ข้อมูลมากที่สุดและถูกอ้างถึงบ่อยที่สุดในงานตรวจสอบระบบ ได้แก่ /etc/passwd, /etc/shadow, /etc/sudoers และ /var/log/ ทั้งสี่ตำแหน่งมีลักษณะร่วมกันคือเป็นที่เก็บความจริงเกี่ยวกับอำนาจและร่องรอยของผู้ใช้

ตาราง 2.3 สี่ตำแหน่งสำคัญและสิ่งที่บอกได้
ตำแหน่งบรรจุอะไรตอบคำถามอะไรได้สิทธิ์โดยทั่วไป
/etc/passwdบัญชีผู้ใช้ทุกบัญชีในระบบมีใครบ้างในระบบ แต่ละคนมีรหัสประจำตัวเท่าไร ใช้เชลล์ใด644 (ทุกคนอ่านได้)
/etc/shadowรหัสผ่านที่เข้ารหัสและข้อมูลอายุรหัสผ่านบัญชีใดมีรหัสผ่าน บัญชีใดถูกล็อก รหัสผ่านหมดอายุเมื่อไร640 หรือเข้มกว่า
/etc/sudoersนโยบายว่าใครสั่งงานด้วยสิทธิ์สูงได้ใครยกระดับสิทธิ์ได้ และได้เฉพาะคำสั่งใด440 (อ่านได้เฉพาะผู้ดูแลระบบ)
/var/log/บันทึกเหตุการณ์ของระบบและบริการใครเข้าสู่ระบบเมื่อไร เกิดข้อผิดพลาดอะไร และเมื่อใดแตกต่างกันตามไฟล์

การที่ /etc/passwd อ่านได้โดยทุกคนแต่ /etc/shadow อ่านได้เฉพาะกลุ่มที่กำหนด คือตัวอย่างแรกของหลักการแยกข้อมูลที่ไม่เป็นความลับออกจากข้อมูลที่เป็นความลับ ซึ่งระบบยูนิกซ์ใช้มาแต่ทศวรรษ 1970 ในอดีตระบบเก็บรหัสผ่านไว้ใน /etc/passwd โดยตรง แต่เมื่อคอมพิวเตอร์เร็วขึ้นจนเดารหัสผ่านได้เร็วขึ้น ระบบจึงย้ายส่วนที่ละเอียดอ่อนออกไปไว้ในไฟล์ที่จำกัดสิทธิ์แทน

บัญชีที่ UID เป็นศูนย์คือผู้ดูแลระบบสูงสุด หรือที่เรียกว่า root ระบบหนึ่งระบบอาจมีบัญชีที่ UID เป็นศูนย์มากกว่าหนึ่งบัญชีก็ได้ และนี่คือสิ่งที่ผู้ตรวจสอบต้องค้นหาเสมอ เพราะบัญชีที่ดูเหมือนผู้ใช้ธรรมดาแต่มี UID เป็นศูนย์คือประตูหลังที่ซ่อนไว้อย่างแนบเนียนที่สุด

กลุ่มและไฟล์ที่เกี่ยวข้อง

ไฟล์ /etc/group เก็บรายชื่อกลุ่มทั้งหมด แต่ละบรรทัดมีสี่ฟิลด์คือ ชื่อกลุ่ม ฟิลด์รหัสผ่านที่ไม่ได้ใช้แล้ว รหัสกลุ่ม หรือ GID และรายชื่อสมาชิกที่คั่นด้วยเครื่องหมายจุลภาค กลุ่มในลินุกซ์มีสองบทบาท บทบาทแรกคือเป็นกลุ่มหลักซึ่งกำหนดไว้ใน /etc/passwd และระบบใช้เมื่อสร้างไฟล์ใหม่ บทบาทที่สองคือเป็นกลุ่มเสริมที่ผู้ใช้คนหนึ่งเป็นสมาชิกได้หลายกลุ่มพร้อมกัน และสิทธิ์จากทุกกลุ่มจะถูกรวมเข้าด้วยกัน

ในระบบรุ่นใหม่ กลุ่มหนึ่งกลุ่มอาจมีชื่อเดียวกับชื่อผู้ใช้และมี GID ตรงกับ UID ของผู้นั้น เป็นวิธีที่ระบบใช้แยกพื้นที่ส่วนตัวของผู้ใช้แต่ละคนออกจากกันโดยอัตโนมัติ

นอกจากกลุ่มแล้ว ยังมีไฟล์อีกสองไฟล์ที่ทำหน้าที่เสริม คือ /etc/gshadow ซึ่งเก็บข้อมูลกลุ่มที่ละเอียดอ่อน และ /etc/subuid กับ /etc/subgid ซึ่งใช้ในระบบคอนเทนเนอร์เพื่อกำหนดช่วงรหัสที่ผู้ใช้หนึ่งคนสามารถใช้ได้ภายในเนมสเปซของตน

ไฟล์ปรับแต่งที่ผู้ตรวจสอบมักเปิดอ่าน

ไดเรกทอรี /etc มีไฟล์นับพัน แต่มีไฟล์จำนวนหนึ่งที่ให้ข้อมูลมากเป็นพิเศษและถูกเปิดอ่านบ่อยในงานตรวจสอบระบบ

ตาราง 2.7 ไฟล์ปรับแต่งใน /etc ที่ควรรู้จัก
ไฟล์ข้อมูลที่ได้เหตุใดจึงสำคัญ
/etc/os-releaseชื่อและรุ่นของลินุกซ์บอกว่าควรค้นหาช่องโหว่ในทิศทางใด
/etc/hostnameชื่อเครื่องใช้ยืนยันว่ากำลังทำงานกับเครื่องที่ถูกต้อง
/etc/hostsการแปลงชื่อเครื่องเป็นที่อยู่ในเครื่องนี้เผยชื่อเครื่องอื่นและการตั้งค่าที่ผิดปกติ
/etc/resolv.confเซิร์ฟเวอร์แปลงชื่อโดเมนเผยโครงสร้างเครือข่ายภายใน
/etc/fstabอุปกรณ์ที่ถูกต่อเข้าในระบบตอนเริ่มเครื่องเผยพาร์ทิชันและตัวเลือกการต่อ
/etc/ssh/sshd_configนโยบายของบริการเชื่อมต่อระยะไกลบอกว่าอนุญาตรหัสผ่านหรือกุญแจใด
/etc/crontabตารางงานตามกำหนดเวลาของทั้งระบบเป็นตำแหน่งที่ใช้ฝังการทำงานอัตโนมัติ
/etc/ld.so.preloadไลบรารีที่ถูกโหลดเข้าทุกโปรแกรมจุดซ่อนกลไกดักจับที่มีอำนาจสูงมาก
/etc/environmentตัวแปรสภาพแวดล้อมของทั้งระบบมีผลต่อทุกโปรแกรมที่ทำงาน
/etc/profileสคริปต์ที่ทำงานเมื่อเข้าสู่ระบบจุดที่ใช้แก้พฤติกรรมของทุกผู้ใช้
/etc/issueข้อความที่แสดงก่อนเข้าสู่ระบบเผยรุ่นระบบให้ผู้บุกรุกเห็นโดยไม่ต้องเข้าไป

ไฟล์สองไฟล์สุดท้ายในตารางคือ /etc/ld.so.preload และ /etc/profile ซึ่งควรอธิบายเพิ่มเติมเพราะเป็นตัวอย่างที่ดีของหลักการที่ว่าไฟล์ปรับแต่งที่ถูกต้องตามปกติก็กลายเป็นเครื่องมือของผู้ไม่หวังดีได้ ถ้าผู้ไม่หวังดีเขียนไฟล์เหล่านี้ได้ ระบบจะโหลดสิ่งที่เขาวางไว้ให้ทุกโปรแกรมและทุกผู้ใช้โดยอัตโนมัติ โดยไม่ต้องแก้ไขโปรแกรมใดเลย นี่คือเหตุผลที่สิทธิ์การเขียนบนไฟล์ปรับแต่งของระบบจึงต้องถูกจำกัดอย่างเข้มงวด และเป็นเหตุผลที่ผู้ตรวจสอบต้องตรวจสอบไฟล์เหล่านี้เสมอเมื่อสงสัยว่ามีการฝังกลไกไว้ในระบบ

/var/log และบันทึกเหตุการณ์

ไดเรกทอรี /var/log เป็นที่เก็บบันทึกเหตุการณ์ของระบบและบริการ แม้จะเป็นเพียงโฟลเดอร์เดียว แต่โครงสร้างภายในแตกต่างกันมากตามลินุกซ์แต่ละสายพันธุ์ ตระกูลเดเบียนและอูบุนตูมักใช้ /var/log/syslog และ /var/log/auth.log ขณะที่ตระกูลเรดแฮตและเฟดอราใช้ /var/log/messages และ /var/log/secure สำหรับการบันทึกที่เข้มข้นขึ้น ระบบรุ่นใหม่ใช้บริการกลางชื่อ systemd-journald ซึ่งเก็บบันทึกในรูปแบบไบนารีและอ่านผ่านคำสั่ง journalctl รายละเอียดของหัวข้อนี้จะกล่าวถึงในหัวข้อ 2.6 โดยเฉพาะ

ข้อที่ควรเข้าใจในที่นี้คือบันทึกเหตุการณ์ไม่ใช่ไฟล์เดียวแต่เป็นกลุ่มไฟล์ที่แยกตามแหล่งที่มาและอายุการเก็บรักษา ระบบจะหมุนไฟล์บันทึกเมื่อไฟล์ใหญ่เกินกำหนด และลบไฟล์เก่าตามนโยบายที่ตั้งไว้ ซึ่งหมายความว่าข้อมูลเก่าอาจหายไปก่อนที่ผู้ตรวจสอบจะได้เห็น การเก็บหลักฐานจึงต้องทำก่อนที่ระบบจะหมุนไฟล์รอบถัดไป

โลกเสมือนใน /proc และ /sys

แม้ /proc และ /sys จะปรากฏเป็นไดเรกทอรี แต่ไม่ได้เก็บข้อมูลบนดิสก์เลย เมื่อมีโปรแกรมอ่านไฟล์ในสองตำแหน่งนี้ เคอร์เนลจะสร้างข้อมูลขึ้นมาขณะนั้นตามสถานะจริงของระบบ

ภายใน /proc มีไดเรกทอรีที่ตั้งชื่อตามหมายเลขกระบวนการ (PID) ของทุกโปรแกรมที่กำลังทำงานอยู่ และภายในไดเรกทอรีนั้นมีไฟล์ที่บอกรายละเอียดของกระบวนการนั้น เช่น cmdline บอกรายละเอียดคำสั่งที่ใช้เปิดโปรแกรม environ บอกตัวแปรสภาพแวดล้อม cwd เป็นลิงก์ไปยังโฟลเดอร์ที่โปรแกรมกำลังทำงานอยู่ exe เป็นลิงก์ไปยังไฟล์โปรแกรมจริง และ fd เป็นไดเรกทอรีที่แสดงไฟล์ทุกไฟล์ซึ่งโปรแกรมนั้นเปิดอยู่

ไฟล์ /proc/net/tcp และ /proc/net/udp แสดงการเชื่อมต่อเครือข่ายในรูปแบบตัวเลขฐานสิบหก ซึ่งเป็นข้อมูลชุดเดียวกับที่คำสั่ง ss นำมาแสดงในรูปแบบที่อ่านง่าย นี่คือตัวอย่างของหลักการที่ว่าเครื่องมือบรรทัดคำสั่งจำนวนมากไม่ได้มีข้อมูลของตัวเอง แต่เพียงอ่านข้อมูลจากที่ที่เคอร์เนลเตรียมไว้แล้วจัดรูปแบบให้น่าอ่าน

ไฟล์ environ มีข้อจำกัดด้านสิทธิ์ที่ควรรู้ ผู้ใช้ทั่วไปอ่านได้เฉพาะไฟล์ของกระบวนการที่ตนเป็นเจ้าของ ส่วนกระบวนการของผู้ใช้อื่นอ่านได้เฉพาะผู้ดูแลระบบหรือผู้ที่ได้รับสิทธิ์พิเศษ มิฉะนั้นระบบจะเปิดเผยความลับ เช่น ค่ารหัสผ่านที่ส่งผ่านตัวแปรสภาพแวดล้อม ให้แก่ผู้ใช้ทุกคน

ตำแหน่งที่เขียนได้และความเสี่ยงที่ตามมา

ในงานตรวจสอบระบบ หนึ่งในคำถามแรกๆ คือ "ที่ใดในระบบที่ผู้ใช้ธรรมดาเขียนไฟล์ได้บ้าง" เพราะทุกตำแหน่งที่เขียนได้คือพื้นที่ที่ผู้บุกรุกสามารถวางไฟล์ของตนไว้ได้โดยไม่ต้องยกระดับสิทธิ์

โดยปกติมีสามตำแหน่งที่ทุกคนเขียนได้คือ /tmp, /var/tmp และ /dev/shm ทั้งสามตั้งค่าในลักษณะเดียวกันคือให้สิทธิ์เต็มแก่ทุกคน แต่ป้องกันการลบไฟล์ของผู้อื่นด้วยบิตพิเศษที่จะอธิบายในหัวข้อ 2.3 ความแตกต่างระหว่างสามตำแหน่งนี้อยู่ที่อายุการเก็บและที่ตั้งทางกายภาพ /tmp มักถูกล้างเมื่อรีบูตหรือตามรอบของระบบ /var/tmp เก็บไว้นานกว่า และ /dev/shm อยู่ในหน่วยความจำจึงเร็วกว่าและไม่ถูกเขียนลงดิสก์

ความเสี่ยงที่พบบ่อยที่สุดของตำแหน่งเหล่านี้คือ การโจมตีผ่านลิงก์สัญลักษณ์ (Symlink Attack) เนื่องจากชื่อไฟล์ในพื้นที่ร่วมกันคาดเดาได้ง่าย ผู้ไม่หวังดีอาจสร้างลิงก์สัญลักษณ์ชี้ไปยังไฟล์สำคัญของระบบ แล้วรอให้โปรแกรมที่ทำงานด้วยสิทธิ์สูงเขียนทับไฟล์นั้นผ่านชื่อที่คาดเดาได้นี้ มาตรการป้องกันที่ใช้กันมานานคือการตั้งค่าพื้นที่เหล่านี้ให้ไม่ยอมให้เรียกโปรแกรมจากภายใน (ตัวเลือก noexec) และการเขียนโปรแกรมอย่างระมัดระวังให้สร้างไฟล์ชั่วคราวด้วยชื่อสุ่มที่ปลอดภัย

การอ่านเมทาดาทาของไฟล์

ก่อนจะเข้าสู่ระบบสิทธิ์ ควรรู้จักเครื่องมือสองตัวที่ใช้ดูเมทาดาทาของไฟล์ ซึ่งจะเป็นพื้นฐานของการอ่านผลลัพธ์ในหัวข้อถัดๆ ไป

คำสั่ง ls -l แสดงข้อมูลเก้าคอลัมน์ แต่ละคอลัมน์ตอบคำถามต่างกัน คอลัมน์แรกคือชนิดและสิทธิ์ของไฟล์ คอลัมน์ที่สองคือจำนวนลิงก์ที่ชี้มาที่ไอโหนดเดียวกัน คอลัมน์ที่สามและสี่คือเจ้าของและกลุ่ม คอลัมน์ที่ห้าคือขนาด คอลัมน์ที่หกถึงแปดคือเวลาแก้ไขล่าสุด และคอลัมน์สุดท้ายคือชื่อ

คำสั่ง stat ให้ข้อมูลละเอียดกว่านั้น โดยแสดงหมายเลขไอโหนด ขนาด จำนวนบล็อกที่ใช้จริง และเวลาสามชนิดที่แยกจากกัน คือ เวลาที่เข้าถึงล่าสุด (atime) เวลาที่แก้ไขเนื้อหา (mtime) และ เวลาที่เปลี่ยนเมทาดาทา (ctime) ความแตกต่างระหว่างสามเวลานี้สำคัญมากในงานสืบสวน เพราะการเปลี่ยนสิทธิ์หรือเจ้าของไฟล์จะเปลี่ยน ctime แต่ไม่เปลี่ยน mtime ขณะที่การแก้ไขเนื้อหาจะเปลี่ยนทั้งสองอย่าง ผู้ที่พยายามปิดร่องรอยด้วยการปรับเวลาแก้ไขไฟล์ (Timestomping) จึงมักทิ้งร่องรอยไว้ที่ ctime ซึ่งแก้ไขได้ยากกว่ามากในระบบไฟล์สมัยใหม่

ส่วนชนิดของไฟล์ในคอลัมน์แรกมีอักขระบอกหกแบบหลัก ได้แก่ - คือไฟล์ปกติ d คือไดเรกทอรี l คือลิงก์สัญลักษณ์ c คืออุปกรณ์อักขระ b คืออุปกรณ์บล็อก และ s คือซ็อกเก็ต การรู้ชนิดของไฟล์ช่วยในการคาดเดาว่าตำแหน่งนั้นทำหน้าที่อะไร

ลิงก์ในลินุกซ์มีสองชนิดที่ต้องแยกให้ออก ลิงก์แข็ง (Hard Link) คือชื่อเพิ่มเติมของไฟล์เดียวกันจริงๆ ทั้งสองชื่อชี้ไปที่ไอโหนดเดียวกัน การลบชื่อหนึ่งไม่ทำให้ข้อมูลหายจนกว่าจะลบครบทุกชื่อ และไม่สามารถข้ามระบบไฟล์ได้ ส่วน ลิงก์สัญลักษณ์ (Symbolic Link) คือไฟล์ชนิดพิเศษที่เก็บเส้นทางไปยังไฟล์ปลายทาง เป็นเพียงทางลัด การลบไฟล์ปลายทางทำให้ลิงก์เสีย และลิงก์สัญลักษณ์สามารถชี้ข้ามระบบไฟล์ได้

2.3 สิทธิ์การเข้าถึง: rwx เจ้าของ และบิตพิเศษ

สามคำถามของระบบสิทธิ์

ระบบสิทธิ์ของลินุกซ์ตอบคำถามสามข้อพร้อมกันสำหรับทุกการกระทำ คือ ใคร เป็นผู้กระทำ อะไร คือสิ่งที่ถูกกระทำ และ อนุญาตให้ทำอะไร กับสิ่งนั้น คำตอบของคำถามสองข้อแรกอยู่ในรูปตัวเลข คือ UID และ GID ของผู้กระทำ กับ UID และ GID ของเจ้าของไฟล์ ส่วนคำตอบของคำถามที่สามอยู่ในรูปบิตเก้าบิตที่ติดอยู่กับไฟล์ทุกไฟล์

บิตเก้าบิตแบ่งออกเป็นสามชุด ชุดละสามบิต แต่ละชุดตรงกับกลุ่มผู้กระทำหนึ่งกลุ่ม ชุดแรกสำหรับเจ้าของไฟล์ ชุดที่สองสำหรับกลุ่มเจ้าของไฟล์ ชุดที่สามสำหรับผู้ใช้อื่นทั้งหมดที่เหลือ ภายในแต่ละชุด บิตทั้งสามมีความหมายต่างกันเมื่อใช้กับไฟล์และเมื่อใช้กับไดเรกทอรี

ตาราง 2.8 ความหมายของ rwx เมื่อใช้กับไฟล์และไดเรกทอรี
บิตต่อไฟล์ปกติต่อไดเรกทอรี
r (อ่าน)เปิดอ่านเนื้อหาได้ดูรายชื่อไฟล์ภายในได้
w (เขียน)แก้ไขหรือตัดทอนเนื้อหาได้สร้าง ลบ หรือเปลี่ยนชื่อไฟล์ภายในได้
x (เรียกใช้)สั่งให้โปรแกรมทำงานได้เข้าไปข้างในหรือผ่านไดเรกทอรีนั้นได้

ความแตกต่างที่ผู้เรียนมักเข้าใจผิดมากที่สุดคือความหมายของ w บนไดเรกทอรี การลบไฟล์หนึ่งไฟล์ไม่ได้ขึ้นอยู่กับสิทธิ์เขียนบนไฟล์นั้นเลย แต่ขึ้นอยู่กับสิทธิ์เขียนบนไดเรกทอรีที่บรรจุไฟล์นั้น กล่าวคือ ผู้ใช้ที่ไม่มีสิทธิ์เขียนบนไฟล์อาจลบไฟล์นั้นได้หากมีสิทธิ์เขียนบนไดเรกทอรี ขณะที่ผู้ใช้ที่มีสิทธิ์เขียนบนไฟล์แต่ไม่มีสิทธิ์เขียนบนไดเรกทอรีกลับลบไฟล์นั้นไม่ได้ นี่คือเหตุผลที่โฟลเดอร์ส่วนตัวของผู้ใช้ต้องถูกจำกัดสิทธิ์ ไม่ใช่เพียงเพราะไฟล์ข้างใน

ในทางกลับกัน บิต x บนไดเรกทอรีคือสิทธิ์ที่ขาดไม่ได้สำหรับการเข้าถึงไฟล์ข้างใน ผู้ใช้ที่มีสิทธิ์อ่านรายชื่อไฟล์แต่ไม่มีสิทธิ์ x จะเห็นชื่อไฟล์ได้แต่เปิดไฟล์เหล่านั้นไม่ได้ เปรียบเหมือนการยืนดูป้ายชื่อที่ติดอยู่หน้าประตูแต่ไม่มีกุญแจเข้าห้อง

การอ่านสิทธิ์จากผลลัพธ์ของ ls

คำสั่ง ls -l แสดงสิทธิ์เป็นอักขระสิบตำแหน่งติดกัน ตำแหน่งแรกบอกชนิดของไฟล์ ส่วนเก้าตำแหน่งที่เหลือคือบิตสิทธิ์สามชุดตามลำดับ เจ้าของ กลุ่ม และผู้อื่น ตัวอย่างเช่น

-rwsr-xr-x  1 root root  68208 Jan 10 09:14 /usr/bin/passwd

อักขระตำแหน่งแรกเป็น - แปลว่าเป็นไฟล์ปกติ สามตำแหน่งถัดมาคือ rws ซึ่งเป็นสิทธิ์ของเจ้าของ สังเกตว่าตำแหน่งที่ควรเป็น x กลับเป็น s ตัวพิมพ์เล็ก ซึ่งหมายถึงบิต SUID ถูกตั้งไว้และไฟล์นี้ยังคงเรียกใช้ได้ สามตำแหน่งถัดมาคือ r-x ซึ่งเป็นสิทธิ์ของกลุ่ม และสามตำแหน่งสุดท้ายคือ r-x ซึ่งเป็นสิทธิ์ของผู้อื่น หากบิตพิเศษถูกตั้งไว้แต่ไม่ได้ให้สิทธิ์เรียกใช้ควบคู่ไปด้วย ตัวอักษรจะเปลี่ยนเป็นพิมพ์ใหญ่ เช่น S หรือ T ซึ่งเป็นสัญญาณว่าการตั้งค่าอาจผิดพลาด เพราะบิตพิเศษที่ไม่มีการเรียกใช้ไม่เกิดประโยชน์ใดๆ

การคำนวณสิทธิ์แบบเลขฐานแปด

การเขียนสิทธิ์แบบตัวอักษรนั้นอ่านง่ายแต่นิยมใช้ในเอกสารมากกว่าในคำสั่งจริง เพราะการตั้งสิทธิ์ผ่านคำสั่ง chmod มักทำในรูปแบบตัวเลข

ตาราง 2.9 ค่าของบิตสิทธิ์ในรูปแบบเลขฐานแปด
บิตค่าความหมายเมื่อรวมกัน
r4อ่าน
w2เขียน
x1เรียกใช้
ไม่มีสิทธิ์0ห้ามทุกอย่าง

การคำนวณทำโดยบวกค่าของบิตที่เปิดใช้ในแต่ละชุด แล้วเขียนตัวเลขสามหลักเรียงตามลำดับ เจ้าของ กลุ่ม ผู้อื่น เช่น rwxr-xr-x คือ 4+2+1 = 7 สำหรับเจ้าของ 4+0+1 = 5 สำหรับกลุ่ม และ 5 สำหรับผู้อื่น จึงเขียนเป็น 755 ส่วน rw-r----- คือ 6, 4, 0 จึงเขียนเป็น 640

บิตพิเศษสามบิตที่อธิบายในหัวข้อถัดไปมีค่าเพิ่มอีกรอบละหนึ่งหลัก คือ SUID เท่ากับ 4, SGID เท่ากับ 2 และ Sticky Bit เท่ากับ 1 ตามลำดับ และเขียนไว้หน้าตัวเลขสามหลักปกติ เช่น สิทธิ์ของ /usr/bin/passwd คือ 4755 และสิทธิ์ของ /tmp คือ 1777

คำสั่ง chmod รับได้ทั้งสองรูปแบบ รูปแบบตัวเลขใช้เมื่อต้องการกำหนดค่าทั้งหมดพร้อมกัน เช่น chmod 640 report.txt ส่วนรูปแบบสัญลักษณ์ใช้เมื่อต้องการปรับเพียงบางส่วนโดยไม่แตะส่วนที่เหลือ เช่น chmod u+x script.sh หรือ chmod g-w,o=r document.txt ข้อดีของรูปแบบสัญลักษณ์คือสามารถใช้ตัวอักษร X พิมพ์ใหญ่ซึ่งหมายถึง "ให้สิทธิ์เรียกใช้เฉพาะเมื่อเป็นไดเรกทอรีหรือไฟล์ที่มีสิทธิ์เรียกใช้อยู่แล้ว" ซึ่งมีประโยชน์มากเมื่อสั่งงานแบบเรียกซ้ำทั้งโฟลเดอร์ เพราะจะไม่เผลอทำให้ไฟล์ข้อมูลธรรมดากลายเป็นไฟล์ที่เรียกใช้ได้

ค่าเริ่มต้นของสิทธิ์และ umask

เมื่อโปรแกรมสร้างไฟล์ใหม่ ระบบจะไม่ให้สิทธิ์เต็มแต่จะเริ่มจากค่าฐานแล้วตัดสิทธิ์บางส่วนออกตามค่าที่เรียกว่า อูมาสก์ (umask) ค่าฐานของไฟล์ปกติคือ 666 และของไดเรกทอรีคือ 777 เพราะไฟล์ใหม่ไม่ควรมีสิทธิ์เรียกใช้โดยอัตโนมัติ ส่วนอูมาสก์คือค่าที่บอกว่าบิตใดจะถูก ตัดออก

อูมาสก์ที่พบบ่อยที่สุดคือ 022 ซึ่งตัดสิทธิ์เขียนของกลุ่มและผู้อื่นออก ผลคือไฟล์ใหม่มีสิทธิ์ 644 และไดเรกทอรีใหม่มีสิทธิ์ 755 หากต้องการให้ไฟล์ใหม่เห็นได้เฉพาะเจ้าของ ใช้ umask 077 ซึ่งให้ผลเป็น 600 สำหรับไฟล์และ 700 สำหรับไดเรกทอรี การตั้งอูมาสก์ที่เข้มขึ้นจึงเป็นมาตรการป้องกันพื้นฐานที่ควรทำบนเครื่องที่เก็บข้อมูลอ่อนไหว

เจ้าของ กลุ่ม และคำสั่งที่เกี่ยวข้อง

การเปลี่ยนเจ้าของไฟล์ทำได้ด้วยคำสั่ง chown และการเปลี่ยนกลุ่มด้วยคำสั่ง chgrp ทั้งสองคำสั่งรองรับรูปแบบ เจ้าของ:กลุ่ม ในคราวเดียว เช่น chown alice:developers notes.txt

ข้อจำกัดที่สำคัญคือผู้ใช้ทั่วไปไม่สามารถเปลี่ยนเจ้าของไฟล์ให้เป็นคนอื่นได้ แม้จะเป็นเจ้าของไฟล์นั้นเอง เพราะการอนุญาตเช่นนั้นจะเปิดช่องให้ผู้ใช้ยกไฟล์ของตนให้บัญชีที่มีสิทธิ์สูงกว่าแล้วใช้ประโยชน์จากสิทธิ์นั้นได้ มีเพียงผู้ดูแลระบบเท่านั้นที่เปลี่ยนเจ้าของได้

นอกจากนี้ เมื่อมีการเปลี่ยนเจ้าของหรือกลุ่มของไฟล์ที่เคยถูกตั้งบิต SUID หรือ SGID ไว้ ระบบจะล้างบิตเหล่านั้นออกโดยอัตโนมัติ เพื่อป้องกันไม่ให้ผู้ไม่หวังดีอาศัยการเปลี่ยนเจ้าของเพื่อรักษาบิตไว้ ทั้งนี้เพราะบิต SUID ผูกกับเจ้าของไฟล์ การเปลี่ยนเจ้าของจึงเท่ากับเปลี่ยนผู้ที่ได้รับสิทธิ์เมื่อโปรแกรมทำงาน

คำสั่ง chown -R และ chmod -R ทำงานแบบเรียกซ้ำทั้งลำดับชั้น ซึ่งสะดวกแต่มีอันตรายสูงหากพิมพ์เส้นทางผิดเพียงตัวอักษรเดียว การใช้คำสั่งเหล่านี้จึงควรตรวจเส้นทางให้แน่ใจก่อนทุกครั้ง

บิตพิเศษสามบิต

บิตสิทธิ์เก้าบิตปกติควบคุมว่าใครทำอะไรได้ แต่ยังมีบิตอีกสามบิตที่อยู่นอกเหนือจากนั้นและมีผลพิเศษ บิตทั้งสามนี้คือจุดที่ระบบสิทธิ์แบบดั้งเดิมเริ่มไม่เพียงพอ และเป็นจุดที่ผู้ตรวจสอบระบบให้ความสนใจมากที่สุด

ตาราง 2.10 บิตพิเศษทั้งสามและความหมาย
บิตค่าใช้กับผลเมื่อตั้งไว้
SUID4000ไฟล์ที่เรียกใช้ได้โปรแกรมทำงานด้วยสิทธิ์ของเจ้าของไฟล์ ไม่ใช่ของผู้เรียก
SGID2000ไฟล์ที่เรียกใช้ได้โปรแกรมทำงานด้วยสิทธิ์กลุ่มของไฟล์
SGID2000ไดเรกทอรีไฟล์ใหม่ที่สร้างภายในสืบทอดกลุ่มของไดเรกทอรี
Sticky Bit1000ไดเรกทอรีลบหรือเปลี่ยนชื่อไฟล์ได้เฉพาะเจ้าของไฟล์ เจ้าของไดเรกทอรี หรือผู้ดูแลระบบ

SUID เป็นบิตที่ถูกพูดถึงมากที่สุดในงานทดสอบเจาะระบบ เพราะมันสร้างสถานการณ์ที่ผู้ใช้ธรรมดาเรียกโปรแกรมหนึ่งแล้วได้รับสิทธิ์ของอีกผู้ใช้หนึ่งชั่วคราว ตัวอย่างคลาสสิกคือคำสั่งเปลี่ยนรหัสผ่านของตนเอง ซึ่งต้องเขียนไฟล์ /etc/shadow ที่ผู้ใช้ทั่วไปเขียนไม่ได้ โปรแกรมนี้จึงถูกตั้ง SUID และเป็นของ root เพื่อให้ผู้ใช้ทั่วไปเปลี่ยนรหัสผ่านของตนเองได้โดยไม่ต้องเป็น root

ประโยชน์ของ SUID มาพร้อมความเสี่ยงเสมอ หากโปรแกรมที่ตั้ง SUID ไว้มีช่องโหว่ หรือยอมให้ผู้เรียกกำหนดค่าบางอย่างที่ส่งผลต่อการทำงานภายใน ผู้เรียกก็อาจใช้สิทธิ์ที่ได้รับชั่วคราวนั้นทำสิ่งอื่นนอกเหนือจากที่โปรแกรมตั้งใจไว้ วิธีป้องกันที่สำคัญที่สุดในทางปฏิบัติคือการจำกัดจำนวนโปรแกรม SUID ให้เหลือน้อยที่สุด และตรวจสอบโปรแกรมเหล่านั้นอย่างสม่ำเสมอ ผู้ทดสอบเจาะระบบจึงมักเริ่มต้นค้นหาไฟล์ SUID ทันทีที่ได้ foothold บนเครื่องหนึ่ง เพราะรายการนี้คือรายการประตูที่อาจเปิดไปสู่สิทธิ์สูงกว่า

ข้อเท็จจริงทางเทคนิคที่ควรรู้คือลินุกซ์ไม่ยอมให้บิต SUID ทำงานบนสคริปต์ที่เขียนด้วยเชลล์ มาตรการนี้มีมาแต่เดิมเพื่อป้องกันช่องโหว่จากการตีความสคริปต์ เคอร์เนลจะเพิกเฉยต่อบิต SUID บนไฟล์สคริปต์ ดังนั้นการพบสคริปต์ที่ตั้ง SUID ไว้จึงมักเป็นสัญญาณของผู้ที่เข้าใจระบบไม่ลึกพอ มากกว่าจะเป็นช่องโหว่ที่ใช้งานได้จริง

SGID มีสองหน้าที่ตามชนิดของสิ่งที่ติดบิต เมื่อติดบนไฟล์ที่เรียกใช้ได้ โปรแกรมจะทำงานด้วยสิทธิ์กลุ่มของไฟล์ ซี่งมีประโยชน์เมื่อต้องการให้โปรแกรมเข้าถึงไฟล์ที่กลุ่มหนึ่งใช้ร่วมกัน เมื่อติดบนไดเรกทอรี ไฟล์ใหม่ทุกไฟล์ที่สร้างภายในจะสืบทอดกลุ่มของไดเรกทอรีแทนกลุ่มหลักของผู้สร้าง ไดเรกทอรีแบบนี้ใช้ในพื้นที่ทำงานร่วมกันของทีม เพื่อให้สมาชิกทุกคนในกลุ่มเข้าถึงไฟล์ของกันและกันได้โดยไม่ต้องเปลี่ยนกลุ่มทีละไฟล์

Sticky Bit ใช้กับไดเรกทอรีที่ทุกคนเขียนได้ เพื่อแก้ปัญหาว่าเมื่อทุกคนเขียนได้ ทุกคนก็ลบของกันและกันได้ เมื่อตั้งบิตนี้ ระบบจะอนุญาตให้ลบหรือเปลี่ยนชื่อไฟล์ได้เฉพาะเจ้าของไฟล์นั้น เจ้าของไดเรกทอรี หรือผู้ดูแลระบบ ตัวอย่างที่คุ้นเคยที่สุดคือ /tmp ซึ่งมีสิทธิ์ 1777 และเป็นเหตุผลว่าทำไมผู้ใช้คนหนึ่งจึงลบไฟล์ชั่วคราวของอีกคนหนึ่งไม่ได้ แม้โฟลเดอร์จะเปิดให้ทุกคนเขียนก็ตาม

บิตพิเศษในฐานะเส้นทางยกระดับสิทธิ์

ในมุมของผู้ตรวจสอบ บิตทั้งสามไม่ได้เป็นเพียงกลไกการทำงานร่วมกัน แต่เป็นเส้นทางที่อาจนำไปสู่สิทธิ์สูงกว่า ตารางต่อไปนี้สรุปสถานการณ์ที่ควรสงสัย

ไฟล์ SUID ที่เจ้าของสามารถเขียนทับได้ผู้ใช้ที่เขียนไฟล์ได้ย่อมแก้โค้ดให้ทำสิ่งที่ตนต้องการ

โปรแกรม SUID ซึ่งเปิดให้ผู้เรียกกำหนดค่าสภาพแวดล้อมอาจถูกใช้ชักจูงให้โหลดไลบรารีหรือโปรแกรมอื่น

เพื่อค้นหาไฟล์เหล่านี้ คำสั่ง find มีตัวเลือกที่ตรงกับงานนี้โดยเฉพาะ เช่น find / -perm -4000 -type f 2>/dev/null สำหรับหาไฟล์ SUID ทั้งระบบ และ find / -perm -0002 -type d สำหรับหาไดเรกทอรีที่ทุกคนเขียนได้ การส่งข้อผิดพลาดไปยัง /dev/null เป็นสิ่งจำเป็นเพราะการค้นหาทั่วทั้งระบบจะพยายามเข้าถึงโฟลเดอร์ที่ผู้ใช้ไม่มีสิทธิ์และสร้างข้อความรบกวนจำนวนมาก

ทางเลือกสมัยใหม่: ความสามารถของโปรแกรม

ระบบลินุกซ์รุ่นใหม่มีกลไกที่ละเอียดกว่า SUID เรียกว่า ความสามารถของโปรแกรม (Capabilities) ซึ่งแทนที่จะให้สิทธิ์ทั้งหมดของผู้ดูแลระบบ แยกสิทธิ์ออกเป็นหน่วยย่อย เช่น ความสามารถในการผูกพอร์ตต่ำกว่า 1024 ความสามารถในการเปลี่ยนเจ้าของไฟล์ หรือความสามารถในการโหลดโมดูลเคอร์เนล โปรแกรมหนึ่งจะได้รับเฉพาะความสามารถที่ต้องการจริงๆ

กลไกนี้ช่วยลดความเสียหายเมื่อโปรแกรมถูกใช้ในทางที่ผิด แต่ก็สร้างความเสี่ยงรูปแบบใหม่เมื่อผู้ดูแลระบบให้ความสามารถที่กว้างเกินจำเป็น โดยเฉพาะความสามารถ cap_setuid ซึ่งยอมให้โปรแกรมเปลี่ยน UID ของตนเองได้ ซึ่งเทียบเท่ากับการมีสิทธิ์ของผู้ดูแลระบบเต็มรูปแบบในทางปฏิบัติ ผู้ตรวจสอบจึงควรตรวจสอบด้วยคำสั่ง getcap -r / 2>/dev/null ควบคู่กับการค้นหาไฟล์ SUID เสมอ

ชั้นป้องกันเพิ่มเติม: ACL และส่วนขยายความปลอดภัย

นอกจากสิทธิ์เก้าบิตพื้นฐาน ลินุกซ์ยังรองรับ รายการควบคุมการเข้าถึง (Access Control List) ซึ่งกำหนดสิทธิ์รายบุคคลได้ละเอียดกว่าสิทธิ์สามชุดปกติ คำสั่ง getfacl ใช้ดูและ setfacl ใช้ตั้งค่า การมี ACL หมายความว่าการดูสิทธิ์ด้วย ls -l เพียงอย่างเดียวอาจไม่ครบถ้วน เพราะ ls -l แสดงเพียงสิทธิ์พื้นฐาน สังเกตได้จากเครื่องหมาย + ต่อท้ายสตริงสิทธิ์ ซึ่งบอกว่ายังมีรายการ ACL ซ่อนอยู่

เหนือจาก ACL ยังมีระบบควบคุมการเข้าถึงภาคบังคับ (Mandatory Access Control) เช่น SELinux ในตระกูลเรดแฮต และ AppArmor ในตระกูลเดเบียน ระบบเหล่านี้เพิ่มนโยบายอีกรอบที่แม้ผู้ดูแลระบบก็ไม่สามารถข้ามได้โดยไม่ตั้งใจ ตัวอย่างเช่น แม้โปรเซสเว็บเซิร์ฟเวอร์จะถูกลักลอบสั่งงานให้อ่านไฟล์ /etc/shadow นโยบายของ SELinux หรือ AppArmor อาจปฏิเสธไม่ให้อ่านก็ได้

สำหรับผู้เรียนในบทนี้ สิ่งที่ต้องจำคือระบบสิทธิ์มีหลายชั้น และชั้นที่เห็นด้วยตาเปล่าจาก ls -l เป็นเพียงชั้นแรก ในบทต่อๆ ไปเมื่อศึกษาการยกระดับสิทธิ์ ผู้เรียนจะได้เห็นว่าการประเมินเส้นทางยกระดับสิทธิ์ต้องพิจารณาทั้งสิทธิ์พื้นฐาน บิตพิเศษ ความสามารถของโปรแกรม ACL และนโยบายความปลอดภัยภาคบังคับประกอบกัน

2.4 ผู้ใช้ กลุ่ม และการยกระดับสิทธิ์

ประเภทของบัญชีในระบบ

บัญชีในลินุกซ์ไม่ได้มีไว้สำหรับมนุษย์เท่านั้น แต่มีไว้สำหรับโปรแกรมที่ต้องทำงานภายใต้สิทธิ์จำกัดด้วย การแยกประเภทบัญชีจึงอาศัยช่วงของ UID เป็นหลัก

บัญชีที่มี UID เป็น 0 คือผู้ดูแลระบบสูงสุด ตามธรรมเนียมมีชื่อว่า root และมีอำนาจเหนือทุกสิ่งในระบบ บัญชีในช่วง 1 ถึง 999 ในตระกูลเดเบียน หรือ 1 ถึง 200 ในตระกูลเรดแฮต เป็นบัญชีของระบบ (System Account) ซึ่งสร้างขึ้นเพื่อให้บริการแต่ละตัวทำงานด้วยสิทธิ์ของตนเอง เช่น บริการเว็บทำงานในนาม www-data หรือ apache และบริการฐานข้อมูลทำงานในนาม mysql การแยกเช่นนี้จำกัดความเสียหายหากบริการใดถูกเจาะ เพราะผู้บุกรุกจะได้เพียงสิทธิ์ของบัญชีนั้น ไม่ใช่สิทธิ์ของผู้ดูแลระบบ

บัญชีของผู้ใช้จริงเริ่มที่ UID 1000 ขึ้นไปในระบบรุ่นใหม่ ค่าเริ่มต้นนี้กำหนดไว้ในไฟล์ /etc/login.defs ซึ่งเป็นไฟล์ที่ผู้ตรวจสอบมักเปิดอ่านเพื่อทำความเข้าใจนโยบายบัญชีของเครื่องนั้น

นอกเหนือจากสามประเภทนี้ยังมีบัญชี nobody ซึ่งมี UID 65534 ใช้สำหรับงานที่ไม่ต้องการสิทธิ์ใดๆ เลย และบัญชีที่ฟิลด์เชลล์เป็น /usr/sbin/nologin ซึ่งเข้าสู่ระบบไม่ได้แต่ยังทำงานเป็นเจ้าของไฟล์หรือโปรเซสได้

คำสั่งพื้นฐานสำหรับตรวจสอบบัญชี

ก่อนจะพูดถึงการยกระดับสิทธิ์ ควรรู้จักคำสั่งที่ใช้ตอบคำถามว่า "ตอนนี้เราคือใคร และอยู่ในกลุ่มใด" เสียก่อน คำสั่ง id แสดง UID, GID และกลุ่มเสริมทั้งหมดของผู้ใช้ปัจจุบัน คำสั่ง whoami แสดงเพียงชื่อบัญชี และคำสั่ง groups แสดงรายชื่อกลุ่ม หากต้องการดูข้อมูลของผู้ใช้อื่น ให้ระบุชื่อต่อท้าย เช่น id alice

คำสั่ง getent passwd และ getent group แสดงข้อมูลบัญชีจากแหล่งข้อมูลทั้งหมดที่ระบบกำหนดไว้ ซึ่งอาจไม่ใช่เพียงไฟล์ในเครื่อง แต่รวมถึงบริการค้นหาบัญชีกลางอย่าง LDAP หรือ Active Directory ในองค์กร ขณะที่การเปิดไฟล์ /etc/passwd ตรงๆ จะเห็นเฉพาะบัญชีที่เก็บไว้ในเครื่องเท่านั้น ความแตกต่างนี้สำคัญในสภาพแวดล้อมองค์กรซึ่งผู้ใช้ส่วนใหญ่อาจไม่ได้อยู่ในไฟล์ท้องถิ่นเลย

ส่วนคำสั่ง last, who, w และ lastlog ใช้ดูประวัติการเข้าสู่ระบบ ซึ่งจะกล่าวถึงในหัวข้อ 2.6 ร่วมกับบันทึกเหตุการณ์

su: การสลับผู้ใช้

คำสั่ง su ย่อมาจาก substitute user ใช้เปลี่ยนผู้ใช้ปัจจุบันเป็นผู้ใช้อีกคน โดยค่าเริ่มต้นคือ root รูปแบบที่ใช้บ่อยคือ su - ซึ่งเครื่องหมายขีดกลางมีความหมายสำคัญ เพราะมันบอกให้ su เริ่มเชลล์แบบเข้าสู่ระบบใหม่ (Login Shell) ซึ่งจะไปอ่านไฟล์ปรับแต่งของบัญชีปลายทาง เช่น /etc/profile และ ~/.bash_profile และย้ายโฟลเดอร์ทำงานไปยังโฟลเดอร์บ้านของบัญชีนั้น หากไม่ใส่เครื่องหมายขีดกลาง ตัวแปรสภาพแวดล้อมและโฟลเดอร์ทำงานบางส่วนจะยังคงเป็นของผู้ใช้เดิม ซึ่งอาจทำให้คำสั่งที่รันต่อมาทำงานไม่เหมือนกับการเข้าสู่ระบบจริง

นอกจากนี้ su ยังรับคำสั่งเดียวผ่านตัวเลือก -c เช่น su -c "id" alice ซึ่งมีประโยชน์เมื่อต้องการรันคำสั่งในนามของผู้ใช้อีกคนโดยไม่ต้องเปิดเชลล์ค้างไว้

ในระบบที่ตั้งค่าไว้รัดกุม การใช้ su เพื่อเป็น root ถูกจำกัดให้เฉพาะสมาชิกของกลุ่ม wheel ผ่านโมดูล PAM ชื่อ pam_wheel ซึ่งตั้งค่าใน /etc/pam.d/su การจำกัดนี้ทำให้ผู้ใช้ทั่วไปไม่สามารถลองรหัสผ่านของ root ผ่าน su ได้ แม้จะรู้รหัสผ่านก็ตาม

sudo: การสั่งงานด้วยสิทธิ์ที่ได้รับมอบหมาย

คำสั่ง sudo แก้ปัญหาพื้นฐานของ su สองข้อ ข้อแรกคือ su ต้องแลกมาด้วยการรู้รหัสผ่านของบัญชีปลายทาง ซึ่งหมายความว่าผู้ใช้หลายคนต้องรู้รหัสผ่านของ root ข้อที่สองคือเมื่อเข้าเป็น root แล้ว ผู้ใช้จะทำอะไรก็ได้โดยไม่มีขอบเขต ระบบจึงไม่มีทางบันทึกว่าแท้จริงแล้วใครเป็นผู้สั่งงานใด

sudo เปลี่ยนแนวคิดจากการ "กลายเป็น" ผู้ใช้อื่นเป็นการ "ได้รับอนุญาตให้รันคำสั่งหนึ่งในนามของผู้ใช้อื่น" ผู้ใช้ยังคงเป็นตัวเอง แต่ละคำสั่งที่รันผ่าน sudo จะถูกบันทึกพร้อมชื่อผู้ใช้จริง และผู้ใช้ต้องพิสูจน์ตัวด้วยรหัสผ่านของตนเอง ไม่ใช่ของ root

ความเสี่ยงหลักแชร์รหัสผ่าน rootตั้งนโยบายกว้างเกินไป

นโยบายของ sudo เก็บอยู่ในไฟล์ /etc/sudoers และไฟล์เพิ่มเติมในไดเรกทอรี /etc/sudoers.d/ การแก้ไขไฟล์นี้ต้องทำผ่านคำสั่ง visudo เท่านั้น เพราะ visudo ตรวจสอบไวยากรณ์ก่อนบันทึก หากแก้ด้วยโปรแกรมแก้ข้อความธรรมดาแล้วพิมพ์ผิดเพียงบรรทัดเดียว อาจทำให้นโยบายทั้งหมดใช้ไม่ได้และไม่มีใครยกระดับสิทธิ์ได้อีกเลย ซึ่งเป็นสถานการณ์ที่กู้คืนได้ยากบนเซิร์ฟเวอร์ที่เข้าถึงได้ทางไกลเท่านั้น

โครงสร้างของบรรทัดนโยบายหนึ่งบรรทัดมีสี่ส่วน คือ ผู้ที่ได้รับสิทธิ์ เครื่องที่ใช้ได้ ผู้ใช้ปลายทาง และคำสั่งที่อนุญาต ตัวอย่างเช่น alice ALL=(ALL:ALL) ALL หมายความว่าผู้ใช้ alice บนเครื่องใดก็ได้ สามารถรันคำสั่งใดก็ได้ในนามของผู้ใช้ใดก็ได้ ส่วน %developers ALL=(root) /usr/bin/systemctl หมายความว่าสมาชิกทุกคนของกลุ่ม developers รันได้เฉพาะคำสั่ง systemctl ในนามของ root

กลไกเบื้องหลังที่ควรรู้

sudo ไม่ได้ตรวจรหัสผ่านทุกครั้ง แต่จำผลการพิสูจน์ตัวไว้ชั่วครู่ตามค่าเริ่มต้นประมาณ 15 นาทีต่อเทอร์มินัลหนึ่งเครื่อง การจำนี้ทำให้ผู้ใช้ไม่ต้องพิมพ์รหัสผ่านซ้ำถี่เกินไป แต่ก็หมายความว่าผู้ที่เข้าถึงเทอร์มินัลที่ยังไม่หมดอายุการจำสามารถใช้สิทธิ์ต่อได้โดยไม่ต้องรู้รหัสผ่าน คำสั่ง sudo -k ใช้ล้างการจำนี้ทันที

นอกจากนี้ sudo ยังอนุญาตให้ผู้ใช้เปิดเชลล์ในนามของผู้อื่นผ่านตัวเลือก -i และ -s และอนุญาตให้ระบุผู้ใช้ปลายทางผ่าน -u การเข้าใจตัวเลือกเหล่านี้ช่วยให้ผู้ตรวจสอบอ่านผลลัพธ์ของ sudo -l ได้ครบถ้วนขึ้น เพราะบางนโยบายอนุญาตเฉพาะการรันเชลล์ ซึ่งมีผลเท่ากับการอนุญาตทุกอย่าง

ควรระลึกไว้ด้วยว่า sudo เองก็เป็นโปรแกรมที่มีช่องโหว่ได้ ในปี พ.ศ. 2564 มีการค้นพบช่องโหว่ร้ายแรงชื่อ CVE-2021-3156 ซึ่งรู้จักกันในชื่อ Baron Samedit ทำให้ผู้ใช้ทั่วไปยกระดับเป็น root ได้บนระบบที่ยังไม่อัปเดต ช่องโหว่ลักษณะนี้เตือนว่าการพึ่งพาโปรแกรมใดโปรแกรมหนึ่งเป็นด่านป้องกันเพียงด่านเดียวไม่เพียงพอ การอัปเดตระบบจึงเป็นมาตรการที่สำคัญพอกับการตั้งนโยบายให้รัดกุม

นโยบายรหัสผ่านและอายุบัญชี

แม้บทนี้จะไม่ลงลึกถึงการจัดการรหัสผ่าน แต่ควรรู้ว่าอายุของรหัสผ่านและการหมดอายุของบัญชีถูกกำหนดไว้ใน /etc/shadow และตรวจสอบได้ด้วยคำสั่ง chage -l ชื่อผู้ใช้ ซึ่งแสดงวันที่เปลี่ยนรหัสผ่านครั้งล่าสุด จำนวนวันก่อนหมดอายุ และวันที่บัญชีจะถูกปิด

การตั้งค่าที่สำคัญอีกจุดหนึ่งคือ /etc/login.defs ซึ่งกำหนดอายุรหัสผ่านเริ่มต้นและช่วง UID ของบัญชีผู้ใช้ และ /etc/security/pwquality.conf ซึ่งกำหนดความยาวและความซับซ้อนขั้นต่ำของรหัสผ่าน ผู้ตรวจสอบมักอ่านสองไฟล์นี้เพื่อประเมินว่านโยบายรหัสผ่านของเครื่องอ่อนเกินไปหรือไม่ ก่อนจะตัดสินใจว่าการเดารหัสผ่านเป็นแนวทางที่คุ้มค่าหรือไม่

2.5 กระบวนการ บริการ systemd และงานตามกำหนดเวลา

กระบวนการคืออะไร

เมื่อโปรแกรมถูกเรียกใช้ ลินุกซ์จะสร้างสิ่งที่เรียกว่า กระบวนการ (Process) ขึ้นมา กระบวนการหนึ่งมีหมายเลขประจำตัว (PID) มีหมายเลขของกระบวนการผู้ให้กำเนิด (PPID) มีผู้ใช้เจ้าของ มีสถานะการทำงาน และมีพื้นที่หน่วยความจำของตนเอง

กระบวนการแรกที่ถูกสร้างขึ้นเมื่อระบบเริ่มทำงานมี PID เป็น 1 และทำหน้าที่เป็นแม่ของกระบวนการทั้งหมด ในลินุกซ์รุ่นใหม่ กระบวนการนี้คือ systemd ซึ่งทำหน้าที่ทั้งเริ่มบริการ ดูแลบริการที่ล้มเหลว และจัดการงานตามกำหนดเวลา เมื่อใดก็ตามที่ระบบสร้างกระบวนการใหม่ จะเกิดลำดับการทำงานสองขั้นคือการแยกตัว (fork) เพื่อสร้างสำเนาของกระบวนการปัจจุบัน แล้วจึงเปลี่ยนเนื้อหาของสำเนานั้นให้เป็นโปรแกรมใหม่ (exec) เข้าใจลำดับนี้แล้วจะอ่านความสัมพันธ์แบบพ่อลูกในรายการกระบวนการได้ง่ายขึ้น

กระบวนการที่ไม่มีคู่ควบคุมและทำงานเบื้องหลังตั้งแต่เริ่มระบบเรียกว่า ดีมอน (Daemon) ตามธรรมเนียมมักลงท้ายชื่อด้วยตัวอักษร d เช่น sshd หรือ cron ดีมอนเหล่านี้คือบริการที่ระบบให้บริการตลอดเวลา ซึ่งในระบบรุ่นใหม่จะถูกจัดการโดย systemd แทนการเริ่มด้วยสคริปต์เองเหมือนในอดีต

ข้อมูลกระบวนการใน /proc

สำหรับงานที่ต้องการรายละเอียดลึก คำสั่งทั่วไปอาจไม่พอ เพราะไฟล์ใน /proc/<PID>/ ให้ข้อมูลที่โปรแกรมไม่ได้แสดง เช่น รายการตัวแปรสภาพแวดล้อมทั้งหมด รายการไฟล์ที่เปิดอยู่ และคำสั่งเต็มที่ใช้เปิดโปรแกรม ซึ่งมีประโยชน์เมื่อชื่อโปรเซสถูกปลอมแปลงให้ดูเหมือนโปรแกรมปกติ

ไฟล์ /proc/<PID>/maps แสดงแผนที่หน่วยความจำของกระบวนการ ซึ่งใช้ตรวจหาว่ามีโค้ดที่ถูกโหลดเข้ามาโดยไม่มีไฟล์ต้นทางบนดิสก์หรือไม่ เป็นเทคนิคสำคัญในการตรวจจับมัลแวร์แบบไม่เขียนไฟล์ (Fileless Malware) ที่จะกล่าวถึงในบทหลังๆ

บริการภายใต้ systemd

ในลินุกซ์รุ่นเก่า การเริ่มบริการทำผ่านสคริปต์ใน /etc/init.d ซึ่งต่างคนต่างเขียนแตกต่างกัน ทำให้การควบคุมบริการไม่เป็นมาตรฐาน systemd เข้ามาแก้ปัญหานี้โดยกำหนดให้ทุกสิ่งที่ระบบจัดการได้ต้องอธิบายด้วยไฟล์รูปแบบเดียวกันที่เรียกว่า ยูนิต (Unit)

ยูนิตมีหลายชนิด แต่ละชนิดแทนสิ่งที่ระบบต้องจัดการต่างกัน ชนิดที่พบบ่อยที่สุดคือ .service ซึ่งแทนบริการ .socket ซึ่งแทนช่องทางรับการเชื่อมต่อ .timer ซึ่งแทนงานตามกำหนดเวลา .target ซึ่งใช้จัดกลุ่มยูนิตให้เริ่มพร้อมกัน และ .mount ซึ่งแทนจุดเชื่อมต่อระบบไฟล์

ตำแหน่งที่เก็บไฟล์ยูนิตมีสามระดับ และระดับที่มีลำดับความสำคัญสูงสุดคือระดับที่ผู้ดูแลระบบแก้ไข

cron ทำงานในสภาพแวดล้อมที่จำกัดกว่าที่ผู้ใช้คาดคิด ตัวแปร PATH มีค่าเริ่มต้นเพียงไม่กี่ไดเรกทอรี มักเป็น /usr/bin:/bin และไม่มีการอ่านไฟล์ .bashrc หรือ .profile เลย คำสั่งที่เคยทำงานในเชลล์จึงอาจล้มเหลวเมื่อย้ายมาไว้ใน cron เพราะหาโปรแกรมไม่พบ หรือเพราะตัวแปรที่ตั้งไว้ในเชลล์ไม่มีอยู่ในสภาพแวดล้อมของ cron การเขียนเส้นทางเต็มของโปรแกรมทุกตัวและกำหนดตัวแปรที่จำเป็นไว้ตอนต้นตารางจึงเป็นแนวปฏิบัติที่ควรทำเสมอ

นอกจากนี้ ผลลัพธ์ของคำสั่งใน cron จะถูกส่งเป็นจดหมายถึงเจ้าของตารางผ่านระบบไปรษณีย์ภายในเครื่อง หากไม่ได้กำหนดปลายทางไว้ อาจเกิดไฟล์จดหมายสะสมใน /var/mail ซึ่งเป็นตำแหน่งที่ผู้ตรวจสอบมักพบข้อมูลที่ไม่ควรอยู่ในเครื่อง การเปลี่ยนเส้นทางผลลัพธ์ไปยังไฟล์บันทึกหรือ /dev/null จึงเป็นการจัดการที่เหมาะสมกว่า

ความเสี่ยงเชิงความปลอดภัยของงานตามกำหนดเวลา

ในมุมของผู้บุกรุก งานตามกำหนดเวลาคือกลไกการคงอยู่ (Persistence) ที่มีประสิทธิภาพ เพราะมันทำงานซ้ำโดยไม่ต้องมีใครสั่ง และมักไม่ถูกตรวจสอบหลังการติดตั้งครั้งแรก

จุดที่ควรสงสัยมีสามลักษณะ ลักษณะแรกคืองานที่รันด้วยสิทธิ์ของ root แต่เรียกสคริปต์หรือโปรแกรมซึ่งผู้ใช้ทั่วไปแก้ไขได้ ลักษณะที่สองคืองานที่ใช้เครื่องหมายแทนหลายไฟล์ (Wildcard) ในคำสั่ง ซึ่งอาจถูกใช้สร้างชื่อไฟล์ที่ตีความกลายเป็นตัวเลือกของคำสั่งได้ ลักษณะที่สามคืองานที่มาจากแพ็กเกจหรือบริการซึ่งไม่ควรมีอยู่เลย

การตรวจสอบทำได้ด้วยการอ่าน crontab -l ของผู้ใช้ปัจจุบัน การดู /etc/crontab และไดเรกทอรี /etc/cron.d/ และหากมีสิทธิ์เพียงพอ การอ่านตารางของผู้ใช้อื่นผ่าน crontab -l -u ชื่อผู้ใช้ ตำแหน่งที่ผู้ตรวจสอบควรอ่านก่อนคือ /var/spool/cron/crontabs/ ซึ่งเก็บตารางจริงทั้งหมด

ทางเลือกอื่น: at และ systemd timer

นอกจาก cron ยังมีกลไกอีกสองแบบที่ควรรู้จัก at ใช้สำหรับงานที่ต้องการรันครั้งเดียวในเวลาที่กำหนด คำสั่ง at 23:00 เปิดให้พิมพ์คำสั่ง แล้วปิดด้วย Ctrl+D งานจะถูกจัดคิวและแสดงด้วย atq และยกเลิกด้วย atrm งานชนิดนี้เหมาะกับการรันครั้งเดียว ซึ่ง cron ไม่ถนัดเพราะออกแบบมาสำหรับงานซ้ำ

ส่วน systemd timer คือยูนิตชนิด .timer ที่ทำงานคู่กับ .service ชื่อเดียวกัน ข้อดีเหนือ cron คือบันทึกผลลัพธ์ลง journal โดยอัตโนมัติ สามารถตั้งให้ทำงานชดเชยเมื่อเครื่องถูกปิดในเวลาที่กำหนดผ่านตัวเลือก Persistent=true และกำหนดเวลาได้ละเอียดถึงระดับวินาที การมีอยู่ของสองกลไกพร้อมกันหมายความว่าผู้ตรวจสอบต้องตรวจทั้งสองที่ ไม่ใช่เพียง cron

2.6 บันทึกระบบ: แหล่งข้อมูลที่ผู้ตรวจสอบอ่านก่อนใคร

สองระบบบันทึกที่ทำงานคู่กัน

ลินุกซ์รุ่นใหม่มีระบบบันทึกเหตุการณ์สองระบบทำงานคู่กัน ระบบแรกคือ syslog ซึ่งเป็นมาตรฐานเก่าแก่ที่กำหนดรูปแบบข้อความและระดับความรุนแรงของเหตุการณ์ ระบบที่สองคือ systemd-journald ซึ่งเก็บข้อมูลในรูปแบบไบนารีและรวมบันทึกจากหลายแหล่งไว้ที่เดียว

syslog แบ่งเหตุการณ์ตาม แหล่งกำเนิด (Facility) เช่น auth สำหรับการพิสูจน์ตัว cron สำหรับงานตามกำหนดเวลา และ kern สำหรับเคอร์เนล และแบ่งตาม ระดับความรุนแรง (Severity) ตั้งแต่ debug ไปจนถึง emerg การแบ่งสองชั้นนี้ทำให้ผู้ดูแลระบบกำหนดได้ว่าเหตุการณ์ประเภทใดควรไปลงไฟล์ใด เช่น เหตุการณ์ระดับรุนแรงเท่านั้นที่ส่งไปแจ้งเตือน ส่วนเหตุการณ์ระดับทั่วไปให้เก็บไว้ในไฟล์

การกำหนดเส้นทางเหล่านี้อยู่ใน /etc/rsyslog.conf และไฟล์ใน /etc/rsyslog.d/ ส่วน journald เก็บข้อมูลแยกต่างหากและมีไฟล์ปรับแต่งของตนเองที่ /etc/systemd/journald.conf

บันทึกสามไฟล์สุดท้ายมีลักษณะพิเศษคือเป็นไฟล์ไบนารี ไม่สามารถเปิดอ่านด้วยโปรแกรมแก้ข้อความธรรมดาได้ ต้องใช้คำสั่งเฉพาะ ไฟล์ wtmp เก็บประวัติการเข้าสู่ระบบสำเร็จและอ่านได้ด้วย last ไฟล์ btmp เก็บประวัติการเข้าสู่ระบบที่ล้มเหลวและอ่านได้ด้วย lastb ส่วน lastlog แสดงเวลาที่แต่ละบัญชีเข้าสู่ระบบครั้งล่าสุด

ความแตกต่างของชื่อไฟล์ระหว่างสองตระกูลลินุกซ์เป็นกับดักที่ผู้เริ่มต้นมักติด คำสั่งค้นหาข้อมูลจึงควรตรวจทั้งสองชื่อ หรือใช้ journalctl ซึ่งทำงานเหมือนกันทุกตระกูล

การหมุนและอายุของบันทึก

บันทึกเหตุการณ์ไม่สามารถโตขึ้นไม่จำกัด ระบบจึงใช้บริการ logrotate หมุนไฟล์เมื่อถึงเงื่อนไข เช่น เมื่อไฟล์ใหญ่เกินขนาดที่กำหนด หรือเมื่อครบรอบเวลา แล้วเปลี่ยนชื่อไฟล์เดิมเติมวันที่ จากนั้นจึงสร้างไฟล์ใหม่ว่างและบีบอัดไฟล์เก่าตามนโยบาย

การตั้งค่าอยู่ใน /etc/logrotate.conf และ /etc/logrotate.d/ โดยปกติระบบจะเก็บไฟล์ย้อนหลังเพียงไม่กี่สัปดาห์ ตำแหน่งนี้จึงเป็นทั้งประโยชน์และข้อจำกัดของผู้ตรวจสอบ ประโยชน์คือทำให้เห็นประวัติย้อนหลังได้ในระยะหนึ่ง ข้อจำกัดคือเหตุการณ์ที่เก่ากว่านั้นจะหายไปอย่างถาวร

บันทึกในฐานะหลักฐาน

บันทึกเหตุการณ์มีคุณค่าเพราะมันถูกเขียนขึ้นโดยระบบ ไม่ใช่โดยมนุษย์ จึงไม่ขึ้นกับความจำของผู้ใด แต่คุณค่านี้ขึ้นอยู่กับเงื่อนไขสามข้อ

ข้อแรกคือความถูกต้องของเวลา ในองค์กรที่มีเครื่องจำนวนมาก ระบบมักตั้งเวลาให้ตรงกันผ่านบริการเทียบเวลาให้ตรงกันตามมาตรฐาน ถ้าเครื่องหนึ่งมีเวลาเหลื่อมจากเครื่องอื่นเป็นชั่วโมง การเรียงลำดับเหตุการณ์ข้ามเครื่องจะผิดทั้งหมด การตรวจสอบเวลาของระบบจึงเป็นขั้นตอนแรกของการสอบสวนทุกครั้ง

ข้อที่สองคือความครบถ้วน ผู้บุกรุกที่มีสิทธิ์สูงมักลบบันทึกเพื่อกลบร่องรอย การที่บันทึกขาดหายในช่วงเวลาหนึ่งอาจเป็นหลักฐานว่ามีการกระทำเกิดขึ้น ไม่ใช่หลักฐานว่าไม่มีอะไรเกิดขึ้น การส่งบันทึกไปยังเครื่องอื่นแบบทันที (Remote Logging) จึงเป็นมาตรการป้องกันที่สำคัญ เพราะผู้บุกรุกบนเครื่องเป้าหมายไม่สามารถลบสำเนาที่อยู่บนเครื่องอื่นได้

ข้อที่สามคือความเกี่ยวเนื่องทางกฎหมาย ในประเทศไทย ผู้ให้บริการซึ่งให้บริการแก่ประชาชนทั่วไปมีหน้าที่เก็บรักษาข้อมูลจราจรทางคอมพิวเตอร์ไว้ไม่น้อยกว่าเก้าสิบวันตามมาตรา 26 แห่งพระราชบัญญัติว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ ซึ่งเป็นข้อกำหนดที่ทำให้หลายองค์กรต้องวางระบบเก็บบันทึกอย่างเป็นทางการ ไม่ใช่เพียงเพื่อการตรวจสอบภายในเท่านั้น

พร้อมกันนั้นบันทึกเหตุการณ์มักมีข้อมูลส่วนบุคคลปะปนอยู่ เช่น ชื่อบัญชี ที่อยู่ไอพี และพฤติกรรมการใช้งาน จึงต้องถูกจัดการภายใต้พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคลด้วย หลักการที่ใช้คือเก็บเท่าที่จำเป็น ใช้ตามวัตถุประสงค์ที่แจ้งไว้ และลบเมื่อพ้นระยะที่จำเป็น ซึ่งหมายความว่าระยะเวลาการเก็บบันทึกต้องมีเหตุผลรองรับทั้งจากข้อกำหนดทางกฎหมายและจากความจำเป็นทางธุรกิจ

2.7 ชุดเครื่องมือบรรทัดคำสั่ง

ปรัชญาของเครื่องมือขนาดเล็ก

เครื่องมือในหัวข้อนี้มีลักษณะร่วมกันสามข้อ คือทำงานอย่างเดียวให้ดี รับข้อมูลจากช่องทางมาตรฐานและส่งผลออกทางช่องทางมาตรฐาน และพิมพ์ผลลัพธ์เป็นข้อความธรรมดา คุณสมบัติสามข้อนี้ทำให้เครื่องมือแต่ละตัวสามารถต่อกันเป็นท่อ (Pipeline) เพื่อทำงานที่ซับซ้อนได้โดยไม่ต้องมีโปรแกรมใหญ่เพียงตัวเดียว

การคิดแบบท่อคือทักษะที่สำคัญที่สุดของหัวข้อนี้ ผู้ใช้ที่คิดเป็นท่อจะมองงานหนึ่งงานว่าประกอบด้วยขั้นตอนย่อยอะไรบ้าง แล้วเลือกเครื่องมือที่ตรงกับแต่ละขั้นตอน มากกว่าจะพยายามหาคำสั่งเดียวที่ทำทุกอย่าง

find: ค้นหาไฟล์ตามเงื่อนไข

find เริ่มค้นจากไดเรกทอรีที่ระบุ แล้วไล่ลงไปทุกระดับภายใต้เงื่อนไขที่กำหนด รูปแบบคำสั่งคือ find เส้นทาง เงื่อนไข การกระทำ

เงื่อนไขที่ใช้บ่อยแบ่งเป็นสี่กลุ่ม กลุ่มแรกเกี่ยวกับชนิดและชื่อ ได้แก่ -type f สำหรับไฟล์ปกติ -type d สำหรับไดเรกทอรี -name สำหรับชื่อที่ตรงตามรูปแบบ และ -iname สำหรับชื่อที่ไม่สนใจตัวพิมพ์ กลุ่มที่สองเกี่ยวกับเจ้าของและสิทธิ์ ได้แก่ -user -group และ -perm กลุ่มที่สามเกี่ยวกับเวลา ได้แก่ -mtime ซึ่งนับเป็นวัน และ -mmin ซึ่งนับเป็นนาที กลุ่มที่สี่เกี่ยวกับขนาด ได้แก่ -size ซึ่งรับหน่วยอย่าง k M หรือ G

ตัวอย่างที่ผู้ตรวจสอบใช้บ่อยคือการหาไฟล์ SUID ทั้งระบบ

find / -type f -perm -4000 2>/dev/null

คำสั่งนี้เริ่มจากรากของระบบ จำกัดเฉพาะไฟล์ปกติที่มีบิต SUID อย่างน้อยหนึ่งบิต และส่งข้อความข้อผิดพลาดทั้งหมดไปยัง /dev/null เพราะการค้นหาทั่วระบบจะพยายามเข้าสู่โฟลเดอร์ที่ไม่มีสิทธิ์และสร้างข้อความจำนวนมาก

ตัวอย่างที่สองคือการหาไฟล์ที่แก้ไขภายในเจ็ดวันที่ผ่านมา ซึ่งใช้ตอบคำถามว่า "เกิดอะไรขึ้นบนเครื่องนี้เมื่อเร็วๆ นี้"

find /var/www -type f -mtime -7 -ls

ตัวเลือก -ls สั่งให้แสดงผลในรูปแบบคล้าย ls -l พร้อมหมายเลขไอโหนด ซึ่งมีประโยชน์เมื่อต้องบันทึกหลักฐานว่าพบไฟล์ใดบ้าง

ส่วนการกระทำที่ทรงพลังที่สุดคือ -exec ซึ่งสั่งให้รันคำสั่งกับไฟล์ที่พบทีละไฟล์ โดยใช้ {} แทนชื่อไฟล์ และปิดท้ายด้วย \; เช่น

find /home -name "*.txt" -exec chmod 600 {} \;

ข้อควรระวังคือ -exec จะรันคำสั่งหนึ่งครั้งต่อหนึ่งไฟล์ ซึ่งช้าถ้าไฟล์มีจำนวนมาก ทางเลือกที่เร็วกว่าคือใช้ {} + ซึ่งรวมไฟล์หลายไฟล์เป็นคำสั่งเดียว แต่วิธีนี้ใช้ได้เฉพาะคำสั่งที่รับชื่อไฟล์หลายชื่อพร้อมกันเท่านั้น

อีกตัวเลือกที่ควรรู้คือ -prune ซึ่งสั่งให้ข้ามไดเรกทอรีที่ไม่ต้องการ เช่นการค้นหาทั่วระบบแต่ข้าม /proc และ /sys ซึ่งเป็นระบบไฟล์เสมือนที่ไม่มีประโยชน์ต่อการค้นหาและทำให้ช้าลงมาก

grep: ค้นหาข้อความ

grep อ่านข้อมูลทีละบรรทัดและพิมพ์บรรทัดที่ตรงกับรูปแบบที่กำหนด รูปแบบที่รับเป็นนิพจน์ปรกติ (Regular Expression) ซึ่งให้ความยืดหยุ่นมากกว่าการค้นหาข้อความตรงตัว

ตาราง 2.25 ตัวเลือกของ grep ที่ใช้บ่อย
ตัวเลือกความหมาย
-rค้นแบบเรียกซ้ำในไดเรกทอรี
-iไม่สนใจตัวพิมพ์เล็กใหญ่
-nแสดงหมายเลขบรรทัด
-vแสดงบรรทัดที่ไม่ตรงกับรูปแบบ
-lแสดงเฉพาะชื่อไฟล์ ไม่แสดงเนื้อหา
-cนับจำนวนบรรทัดที่ตรง
-oแสดงเฉพาะส่วนที่ตรง ไม่แสดงทั้งบรรทัด
-Eใช้ไวยากรณ์นิพจน์ปรกติแบบขยาย
-A, -B, -Cแสดงบรรทัดถัดไป ก่อนหน้า หรือรอบข้าง
--includeจำกัดเฉพาะไฟล์ที่ตรงรูปแบบชื่อ

ตัวอย่างการใช้งานที่ตรงกับงานตรวจสอบคือการค้นหาคำที่บ่งชี้ข้อมูลอ่อนไหวในโฟลเดอร์เว็บไซต์

grep -rn --include="*.php" -i "password" /var/www 2>/dev/null

คำสั่งนี้ค้นแบบเรียกซ้ำ เฉพาะไฟล์ .php ไม่สนใจตัวพิมพ์ และแสดงหมายเลขบรรทัด เพื่อให้ผู้ตรวจสอบเปิดไปดูบริบทของแต่ละจุดได้ทันที

ตัวเลือก -v มีประโยชน์เมื่อต้องการกรองสิ่งรบกวนออก ตัวอย่างคลาสสิกคือการดูรายการกระบวนการแล้วตัดบรรทัดของ grep เองออก ซึ่งเป็นเทคนิคที่ผู้เริ่มต้นมักลืมและทำให้ผลลัพธ์มีบรรทัดแปลกปลอมติดมาหนึ่งบรรทัดเสมอ

awk: ประมวลผลข้อมูลแบบแบ่งคอลัมน์

awk เป็นเครื่องมือที่ทรงพลังที่สุดในกลุ่มนี้ เพราะมันเป็นภาษาโปรแกรมขนาดเล็กที่มีโครงสร้างการทำงานชัดเจน รูปแบบคำสั่งพื้นฐานคือ เงื่อนไข { การกระทำ } โดย awk จะอ่านข้อมูลทีละบรรทัด แบ่งบรรทัดออกเป็นคอลัมน์ตามตัวคั่น แล้วทำงานตามที่กำหนดเมื่อเงื่อนไขเป็นจริง

ตัวแปรภายในที่ใช้บ่อยมีสี่ตัว $1 ถึง $NF คือค่าของคอลัมน์ตามลำดับ โดย $NF คือคอลัมน์สุดท้าย NF คือจำนวนคอลัมน์ทั้งหมด NR คือหมายเลขบรรทัดปัจจุบัน และ FS คือตัวคั่นซึ่งกำหนดได้ด้วยตัวเลือก -F หรือในบล็อก BEGIN

ตัวอย่างการหาบัญชีผู้ใช้จริงทั้งหมดในระบบ ซึ่งแยกจากบัญชีของระบบด้วยช่วง UID

awk -F: '$3 >= 1000 { print $1, $3 }' /etc/passwd

คำสั่งนี้ใช้เครื่องหมายทวิภาคเป็นตัวคั่น ตรวจว่าคอลัมน์ที่สามซึ่งเป็น UID มีค่าตั้งแต่ 1000 ขึ้นไป แล้วพิมพ์ชื่อบัญชีกับ UID ออกมา

ตัวอย่างการหาบัญชีที่มี UID เป็นศูนย์ ซึ่งเป็นสิ่งที่ควรตรวจสอบเสมอ

awk -F: '$3 == 0 { print $1 }' /etc/passwd

นอกจากนี้ awk ยังทำงานแบบสรุปยอดได้ด้วยบล็อก END ซึ่งทำงานครั้งเดียวหลังอ่านข้อมูลครบทุกบรรทัด ตัวอย่างการนับจำนวนผู้ใช้ที่ใช้เชลล์แต่ละชนิด

awk -F: '{ count[$7]++ } END { for (s in count) print count[s], s }' /etc/passwd

ความสามารถในการนับและสรุปนี้ทำให้ awk แทนที่คำสั่งหลายตัวที่ต้องต่อกันได้ในคำสั่งเดียว และเป็นเหตุผลที่ awk ปรากฏบ่อยในสคริปต์ตรวจสอบระบบ

sed: แก้ไขข้อความตามรูปแบบ

sed ย่อมาจาก stream editor ทำหน้าที่อ่านข้อมูลทีละบรรทัด แก้ไขตามคำสั่ง แล้วพิมพ์ผลออก คำสั่งที่ใช้บ่อยที่สุดคือการแทนที่ ซึ่งมีรูปแบบ s/สิ่งที่หา/สิ่งที่แทน/ตัวเลือกระบุขอบเขต

ตัวเลือก g ที่ต่อท้ายหมายถึงแทนที่ทุกตำแหน่งในบรรทัด ไม่ใช่เพียงตำแหน่งแรก ตัวอย่างการแทนที่คำหนึ่งด้วยอีกคำหนึ่งในไฟล์

sed 's/localhost/127.0.0.1/g' config.txt

คำสั่งนี้ไม่แก้ไฟล์ต้นฉบับ แต่พิมพ์ผลลัพธ์ออกทางหน้าจอ การแก้ไฟล์จริงต้องใช้ตัวเลือก -i ซึ่งควรใช้พร้อมการสำรองข้อมูล เช่น -i.bak เพื่อให้มีไฟล์เดิมเก็บไว้เผื่อผิดพลาด

นอกจากนี้ sed ยังใช้ลบบรรทัดหรือเลือกแสดงบางบรรทัดได้ ตัวอย่างการลบบรรทัดที่เป็นความคิดเห็นและบรรทัดว่างออกจากไฟล์ปรับแต่ง เพื่อให้เห็นเฉพาะค่าที่มีผลจริง

sed '/^#/d; /^$/d' sshd_config

หรือการแสดงเฉพาะช่วงบรรทัดที่กำหนด

sed -n '20,40p' access.log

ด้วยเหตุที่ sed ทำงานกับข้อความโดยไม่สนใจโครงสร้างของไฟล์ มันจึงเหมาะกับการแก้ไขไฟล์ปรับแต่งจำนวนมากพร้อมกัน แต่ก็ต้องระวังเพราะการแทนที่แบบ g อาจไปโดนข้อความที่ไม่ตั้งใจได้หากรูปแบบกว้างเกินไป การทดลองโดยไม่ใช้ -i ก่อนทุกครั้งจึงเป็นนิสัยที่ควรสร้าง

cut: ตัดเฉพาะคอลัมน์

cut เป็นเครื่องมือง่ายที่สุดในกลุ่มนี้ หน้าที่เดียวคือตัดเอาบางส่วนของแต่ละบรรทัด รูปแบบที่ใช้บ่อยคือ -d กำหนดตัวคั่น และ -f ระบุคอลัมน์ที่ต้องการ

cut -d: -f1,3 /etc/passwd

คำสั่งนี้ดึงเฉพาะชื่อบัญชีและ UID จาก /etc/passwd ซึ่งให้ผลเหมือนตัวอย่าง awk ก่อนหน้า แต่สั้นกว่า

ข้อจำกัดสำคัญของ cut คือตัวคั่นต้องเป็นอักขระเดียว และไม่สามารถจัดการช่องว่างหลายตัวติดกันได้ดีนัก ในกรณีที่ข้อมูลคั่นด้วยช่องว่างจำนวนไม่แน่นอน เช่นผลลัพธ์ของ ps การใช้ awk จะให้ผลที่ถูกต้องกว่าเสมอ นี่คือตัวอย่างของหลักการเลือกเครื่องมือให้ตรงกับลักษณะข้อมูล ไม่ใช่เลือกเครื่องมือที่คุ้นเคยที่สุด

ss: ดูการเชื่อมต่อเครือข่าย

ss ย่อมาจาก socket statistics ใช้แสดงการเชื่อมต่อเครือข่ายและพอร์ตที่เปิดรับการเชื่อมต่อในเครื่อง ปัจจุบันมันแทนที่คำสั่ง netstat ซึ่งมาจากแพ็กเกจ net-tools ที่ระบบรุ่นใหม่มักไม่ติดตั้งไว้แล้ว

ตาราง 2.26 ตัวเลือกของ ss ที่ใช้บ่อย
ตัวเลือกความหมาย
-tแสดงเฉพาะการเชื่อมต่อ TCP
-uแสดงเฉพาะการเชื่อมต่อ UDP
-lแสดงเฉพาะพอร์ตที่เปิดรับการเชื่อมต่อ
-aแสดงทั้งที่เปิดรับและที่เชื่อมต่ออยู่
-nแสดงหมายเลขพอร์ตแทนชื่อบริการ
-pแสดงชื่อโปรแกรมและ PID เจ้าของ
-sแสดงสรุปสถิติ

ชุดตัวเลือกที่ใช้บ่อยที่สุดในงานตรวจสอบคือ ss -tulpn ซึ่งรวมสี่ความต้องการไว้ในคำสั่งเดียว คือดูทั้ง TCP และ UDP ดูเฉพาะพอร์ตที่เปิดอยู่ แสดงหมายเลขพอร์ตเป็นตัวเลข และแสดงโปรแกรมเจ้าของ

ss -tulpn

การอ่านผลลัพธ์ต้องอาศัยความเข้าใจเรื่องที่อยู่ ที่อยู่ 0.0.0.0 หมายถึงพอร์ตนั้นเปิดรับจากทุกที่อยู่เครือข่ายของเครื่อง ขณะที่ 127.0.0.1 หมายถึงเปิดรับเฉพาะการเชื่อมต่อจากภายในเครื่องเดียวกันเท่านั้น ความแตกต่างนี้สำคัญมาก เพราะบริการที่ฟังเฉพาะ 127.0.0.1 อาจไม่ใช่เป้าหมายที่เข้าถึงได้จากภายนอกโดยตรง แต่กลับเป็นเป้าหมายที่มีคุณค่าสำหรับผู้ที่อยู่ในเครื่องแล้ว

นอกจากนี้ ss ยังกรองตามสถานะได้ เช่น ss -tan state established แสดงเฉพาะการเชื่อมต่อที่อยู่ในสถานะ established แล้ว ซึ่งใช้หาเซสชันที่ค้างอยู่ หรือตรวจสอบว่ามีการเชื่อมต่อไปยังที่อยู่ที่ผิดปกติหรือไม่

ข้อจำกัดที่ควรรู้คือตัวเลือก -p แสดงข้อมูลโปรแกรมเจ้าของได้เฉพาะกระบวนการของผู้ใช้ปัจจุบัน เว้นแต่จะรันด้วยสิทธิ์ของผู้ดูแลระบบ ในสถานการณ์ที่ไม่มีสิทธิ์สูง ผู้ตรวจสอบจึงอาจเห็นเพียงพอร์ตโดยไม่รู้ว่าโปรแกรมใดเป็นเจ้าของ และต้องใช้วิธีอื่น เช่นการอ่าน /proc/net/tcp ประกอบ

การต่อเครื่องมือเข้าด้วยกัน

คุณค่าที่แท้จริงของเครื่องมือเหล่านี้ปรากฏเมื่อนำมาต่อกันเป็นท่อ ตัวอย่างต่อไปนี้แสดงการต่อท่อสามตัวอย่างที่ใช้บ่อยในงานตรวจสอบ

ตัวอย่างแรก ค้นหาไฟล์ SUID ทั้งระบบแล้วนับว่ามีกี่ไฟล์

find / -type f -perm -4000 2>/dev/null | wc -l

ตัวอย่างที่สอง ดูว่ามีกระบวนการใดใช้หน่วยประมวลผลสูงผิดปกติ

ps aux | awk '$3 > 50 { print $2, $3, $11 }'

ตัวอย่างที่สาม ตรวจหาที่อยู่ต้นทางที่มีการเข้าสู่ระบบล้มเหลวมากที่สุดจากบันทึกการพิสูจน์ตัว

grep "Failed password" /var/log/auth.log | awk '{ print $(NF-3) }' | sort | uniq -c | sort -rn | head

คำสั่งนี้ทำงานเป็นห้าขั้น ขั้นแรกกรองเฉพาะบรรทัดที่บ่งชี้การเข้าสู่ระบบล้มเหลว ขั้นที่สองดึงที่อยู่ไอพีออกมาจากตำแหน่งคงที่ในบรรทัด ขั้นที่สามเรียงลำดับให้ค่าที่เหมือนกันอยู่ติดกัน ขั้นที่สี่นับจำนวนที่ซ้ำและรวมเป็นบรรทัดเดียว และขั้นที่ห้าเรียงจากมากไปน้อยเพื่อให้เห็นต้นทางที่พยายามมากที่สุดก่อน ทั้งนี้ตำแหน่งของที่อยู่ไอพีในบรรทัดอาจต่างกันตามรูปแบบบันทึกของแต่ละระบบ จึงควรตรวจผลลัพธ์ในขั้นกลางก่อนนำไปใช้สรุป

แม้ตัวอย่างนี้จะดูซับซ้อน แต่ละขั้นตอนล้วนเป็นงานง่ายๆ ที่เครื่องมือหนึ่งตัวทำได้ดี การคิดแบบท่อจึงเป็นการแบ่งปัญหายากออกเป็นปัญหาง่ายหลายข้อ ซึ่งง่ายต่อการตรวจสอบและแก้ไขเมื่อผลลัพธ์ไม่ตรงกับที่คาด

ข้อควรระวังในการต่อท่อคือไม่ควรส่งผลลัพธ์ไปยังคำสั่งที่ทำลายข้อมูลโดยตรง เช่นการต่อท่อไปยัง xargs rm หรือ sh โดยไม่ตรวจผลลัพธ์ก่อน เพราะข้อผิดพลาดเพียงจุดเดียวในท่ออาจทำให้คำสั่งที่ทำลายข้อมูลทำงานกับไฟล์ผิดชุดได้ หลักปฏิบัติคือให้แสดงผลลัพธ์ดูก่อนทุกครั้ง แล้วจึงเพิ่มขั้นตอนที่ลงมือทำจริง

2.8 Bash scripting เพื่อทำงานอัตโนมัติ

เหตุใดผู้ตรวจสอบจึงต้องเขียนสคริปต์

งานตรวจสอบระบบมีลักษณะซ้ำและมีปริมาณมาก การพิมพ์คำสั่งชุดเดิมซ้ำบนเครื่องสิบเครื่องย่อมเกิดความผิดพลาดได้ง่าย และเมื่อเกิดข้อผิดพลาดก็ยากที่จะทราบว่าผิดที่ขั้นตอนใด การเขียนสคริปต์แก้ปัญหานี้ได้สามด้าน

ด้านแรกคือความสม่ำเสมอ สคริปต์ทำงานชุดคำสั่งเดิมทุกครั้งด้วยลำดับเดิม ทำให้ผลลัพธ์เทียบกันได้ระหว่างเครื่อง ด้านที่สองคือความสามารถในการบันทึก สคริปต์เขียนผลลัพธ์ลงไฟล์ได้อัตโนมัติ จึงมีหลักฐานว่าตรวจอะไรไปแล้วและได้ผลอย่างไร ด้านที่สามคือการขยายขอบเขต งานที่ทำกับเครื่องเดียวสามารถทำกับเครื่องจำนวนมากได้ด้วยการเรียกสคริปต์ซ้ำหรือส่งไปยังเครื่องอื่น

ข้อควรระวังที่สำคัญคือสคริปต์ที่เขียนไม่รัดกุมอาจทำลายข้อมูลได้เร็วกว่าการพิมพ์คำสั่งด้วยมือ เพราะมันทำซ้ำได้เร็วและทำกับทุกอย่างที่เจอ การเรียนรู้หลักความปลอดภัยของสคริปต์จึงสำคัญพอกับการเรียนรู้ไวยากรณ์

โครงร่างของสคริปต์ที่ดี

สคริปต์ Bash ที่ดีเริ่มด้วยบรรทัดบอกเชลล์ที่ใช้ ที่เรียกว่า ชีแบน (Shebang) ซึ่งต้องอยู่บรรทัดแรกเสมอ

#!/usr/bin/env bash

การใช้ /usr/bin/env bash แทนการระบุ /bin/bash โดยตรงทำให้สคริปต์ทำงานได้บนระบบที่ติดตั้ง Bash ไว้ที่ตำแหน่งอื่นด้วย ซึ่งพบได้ในระบบที่จัดการแพ็กเกจต่างกัน

บรรทัดถัดมาที่ควรมีในสคริปต์ทุกตัวคือการตั้งโหมดเข้มงวด

set -euo pipefail

ตัวเลือกทั้งสามมีความหมายต่างกัน -e สั่งให้สคริปต์หยุดทันทีเมื่อคำสั่งใดคำสั่งหนึ่งล้มเหลว -u สั่งให้ถือว่าการอ้างถึงตัวแปรที่ยังไม่ได้กำหนดเป็นข้อผิดพลาด และ -o pipefail สั่งให้ท่อถือว่าล้มเหลวหากคำสั่งใดในท่อล้มเหลว ไม่ใช่ดูเพียงคำสั่งสุดท้าย การตั้งสามข้อนี้ทำให้ข้อผิดพลาดปรากฏขึ้นทันที ณ จุดที่เกิด แทนที่จะปล่อยให้สคริปต์ทำงานต่อด้วยข้อมูลผิดพลาด

ตัวแปรและการอ้างอิงค่า

ตัวแปรใน Bash กำหนดได้ด้วยชื่อ เครื่องหมายเท่ากับ และค่า โดยไม่มีช่องว่างรอบเครื่องหมายเท่ากับ การอ้างถึงค่าทำได้ด้วยเครื่องหมายดอลลาร์นำหน้าชื่อ

target="/var/log"
files=$(find "$target" -type f -name "*.log")

บรรทัดที่สองแสดงการรับผลลัพธ์ของคำสั่งมาเก็บในตัวแปร เรียกว่า การแทนที่คำสั่ง (Command Substitution) รูปแบบ $(...) เป็นวิธีที่แนะนำมากกว่ารูปแบบเก่าที่ใช้เครื่องหมายอัญประกาศกลับ เพราะอ่านง่ายและซ้อนกันได้

หลักการที่สำคัญที่สุดข้อหนึ่งของ Bash คือการใส่เครื่องหมายอัญประกาศคู่คร่อมตัวแปรเสมอ "$target" เพราะหากไม่ใส่ ระบบจะแบ่งค่าตามช่องว่างและตีความอักขระพิเศษ เช่น * หรือ ? เป็นรูปแบบชื่อไฟล์ ซึ่งอาจทำให้คำสั่งได้รับจำนวนอาร์กิวเมนต์ผิดจากที่ตั้งใจ กรณีนี้เป็นสาเหตุของข้อผิดพลาดที่อันตรายที่สุดในสคริปต์ Bash และเป็นสิ่งที่เครื่องมือตรวจสคริปต์อย่าง ShellCheck เตือนเป็นอันดับต้นๆ

นอกจากนี้ยังมีรูปแบบกำหนดค่าเริ่มต้น ${1:-ค่าเริ่มต้น} ซึ่งหมายความว่า "ใช้ค่าของพารามิเตอร์ตัวแรก หรือใช้ค่าเริ่มต้นหากไม่ได้ระบุ" รูปแบบนี้มีประโยชน์เมื่อสคริปต์รับพารามิเตอร์และต้องการทำงานได้แม้ผู้ใช้ไม่ระบุ

พารามิเตอร์ของสคริปต์

สคริปต์รับอาร์กิวเมนต์ได้ด้วยตัวแปรพิเศษ $1 ถึง $9 สำหรับอาร์กิวเมนต์ตามลำดับ $# สำหรับจำนวนอาร์กิวเมนต์ทั้งหมด และ "$@" สำหรับอาร์กิวเมนต์ทั้งหมดในรูปที่รักษาการแยกแต่ละรายการไว้

ความแตกต่างระหว่าง "$@" กับ $* สำคัญเมื่ออาร์กิวเมนต์มีช่องว่างอยู่ข้างใน "$@" จะรักษาขอบเขตของแต่ละอาร์กิวเมนต์ไว้ครบถ้วน ขณะที่ $* จะรวมทุกอย่างเป็นสตริงเดียว ทำให้คำสั่งที่รับต่อไม่สามารถแยกได้ว่าอะไรคืออาร์กิวเมนต์ใด

การตรวจจำนวนอาร์กิวเมนต์ก่อนทำงานเป็นนิสัยที่ดี เพราะช่วยให้สคริปต์แจ้งวิธีใช้อย่างชัดเจนแทนที่จะทำงานต่อด้วยค่าที่ขาดหาย

if [ "$#" -lt 1 ]; then
    echo "วิธีใช้: $0 โฟลเดอร์เป้าหมาย" >&2
    exit 1
fi

ข้อสังเกตคือข้อความแจ้งข้อผิดพลาดถูกส่งไปยังช่องทางข้อผิดพลาดมาตรฐาน (>&2) ไม่ใช่ช่องทางปกติ เพื่อให้ผู้ใช้แยกออกจากผลลัพธ์จริงได้ และการจบด้วยรหัส 1 บอกระบบว่าสคริปต์ล้มเหลว

การตรวจเงื่อนไข

Bash มีรูปแบบการตรวจสองแบบคือ [ ... ] แบบเก่าและ [[ ... ]] แบบใหม่ รูปแบบใหม่ปลอดภัยกว่าเพราะไม่ต้องใส่เครื่องหมายอัญประกาศรอบตัวแปรในทุกกรณี และรองรับการจับคู่รูปแบบได้ในตัวเอง

ตาราง 2.27 การตรวจเงื่อนไขที่ใช้บ่อย
รูปแบบความหมาย
[[ -f "$p" ]]เป็นไฟล์ปกติหรือไม่
[[ -d "$p" ]]เป็นไดเรกทอรีหรือไม่
[[ -r "$p" ]]อ่านได้หรือไม่
[[ -x "$p" ]]เรียกใช้ได้หรือไม่
[[ -z "$s" ]]สตริงว่างหรือไม่
[[ -n "$s" ]]สตริงไม่ว่างหรือไม่
[[ "$a" == "$b" ]]สตริงเท่ากันหรือไม่
[[ "$a" =~ ^[0-9]+$ ]]ตรงกับนิพจน์ปรกติหรือไม่
(( a > b ))เปรียบเทียบตัวเลข

ข้อผิดพลาดที่พบบ่อยคือการใช้ == กับตัวเลข หรือใช้ -eq กับสตริง ทั้งสองกรณีทำให้ผลลัพธ์ผิดโดยไม่มีข้อความเตือน การแยกให้ชัดว่าข้อมูลเป็นตัวเลขหรือสตริงจึงเป็นสิ่งจำเป็น

ลูป

ลูปใน Bash มีสามรูปแบบหลัก รูปแบบแรกคือ for ที่วนตามรายการ ซึ่งเหมาะเมื่อรู้รายการล่วงหน้า

for name in alice bob carol; do
    printf '%s\n' "$name"
done

รูปแบบที่สองคือ for แบบนับจำนวน ซึ่งเหมาะเมื่อต้องการทำซ้ำตามจำนวนครั้ง

for (( i = 1; i <= 5; i++ )); do
    printf 'รอบที่ %d\n' "$i"
done

รูปแบบที่สามคือ while ที่อ่านข้อมูลทีละบรรทัด ซึ่งเป็นรูปแบบที่สำคัญที่สุดในงานตรวจสอบ เพราะผลลัพธ์ของคำสั่งมักมีจำนวนบรรทัดไม่แน่นอนและมีช่องว่างปะปน

find /var/log -type f -name "*.log" 2>/dev/null |
while IFS= read -r line; do
    printf '%s\n' "$line"
done

การอ่านแบบนี้กำหนด IFS= ว่างเพื่อไม่ให้ตัดช่องว่างหัวท้าย และใช้ -r เพื่อไม่ให้ตีความเครื่องหมายแบ็กสแลช ซึ่งเป็นวิธีที่ปลอดภัยที่สุดในการอ่านชื่อไฟล์ที่อาจมีอักขระพิเศษ

ฟังก์ชัน

ฟังก์ชันช่วยแบ่งสคริปต์ยาวออกเป็นส่วนที่ทำหน้าที่เดียว และทำให้เรียกใช้ซ้ำได้โดยไม่ต้องเขียนโค้ดซ้ำ

count_lines() {
    local file="$1"
    wc -l < "$file"
}

total=$(count_lines /var/log/syslog)

คำสั่ง local จำกัดขอบเขตของตัวแปรให้อยู่ภายในฟังก์ชัน ป้องกันการเขียนทับตัวแปรชื่อเดียวกันในส่วนอื่นของสคริปต์โดยไม่ตั้งใจ ส่วนการรับผลลัพธ์ทำได้ด้วยการแทนที่คำสั่งตามตัวอย่าง ซึ่งหมายความว่าฟังก์ชันควรส่งออกเฉพาะข้อมูลที่ต้องการให้ผู้เรียกนำไปใช้ และส่งข้อความแจ้งเตือนไปยังช่องทางข้อผิดพลาดแทน

การจัดการผลลัพธ์และรหัสออก

ทุกคำสั่งในลินุกซ์ส่งค่ากลับเป็นตัวเลขเมื่อทำงานจบ เรียกว่า รหัสออก (Exit Code) โดย 0 หมายถึงสำเร็จ และค่าอื่นหมายถึงล้มเหลว ค่านี้เก็บไว้ในตัวแปร $? และสามารถใช้ตัดสินใจในสคริปต์ได้

if ! grep -q "error" "$logfile"; then
    printf 'ไม่พบข้อผิดพลาด\n'
fi

การเปลี่ยนเส้นทางผลลัพธ์มีสามรูปแบบหลักที่ต้องแยกให้ออก เครื่องหมาย > เขียนทับไฟล์ปลายทาง เครื่องหมาย >> ต่อท้ายไฟล์เดิม และเครื่องหมาย 2> เปลี่ยนเส้นทางข้อผิดพลาดแยกจากผลลัพธ์ปกติ ส่วน 2>&1 รวมข้อผิดพลาดเข้าไปในช่องทางเดียวกับผลลัพธ์ ซึ่งมีประโยชน์เมื่อต้องการเก็บทุกอย่างไว้ในไฟล์เดียวตามลำดับเวลา

คำสั่ง tee ใช้เมื่อต้องการเห็นผลบนหน้าจอและบันทึกลงไฟล์พร้อมกัน

ss -tulpn | tee listening-ports.txt

ตัวอย่างสคริปต์ที่ประกอบทุกส่วนเข้าด้วยกัน

สคริปต์ต่อไปนี้รวบรวมหลักการที่กล่าวมาไว้ในงานเดียว คือสร้างรายงานไฟล์ SUID พร้อมเจ้าของและสิทธิ์

#!/usr/bin/env bash
set -euo pipefail

output="${1:-./suid-report.csv}"

write_header() {
    printf 'path,owner,mode\n'
}

scan() {
    find / -xdev -type f -perm -4000 2>/dev/null |
    while IFS= read -r file; do
        printf '%s,%s,%s\n' \
            "$file" \
            "$(stat -c '%U' "$file")" \
            "$(stat -c '%a' "$file")"
    done
}

write_header > "$output"
scan >> "$output"
printf 'บันทึกผลลัพธ์ไปยัง %s แล้ว\n' "$output"

จุดที่ควรสังเกตในสคริปต์นี้มีห้าจุด จุดแรกคือการใช้ -xdev กับ find เพื่อจำกัดการค้นหาไว้เฉพาะระบบไฟล์เดียว ไม่ไล่เข้าไปในระบบไฟล์ที่ต่อเพิ่มซึ่งอาจทำให้ช้ามาก จุดที่สองคือการใช้ลูปอ่านทีละบรรทัดแทนการปล่อยให้ชื่อไฟล์ถูกแบ่งด้วยช่องว่าง จุดที่สามคือการใช้ printf แทน echo เพราะควบคุมรูปแบบได้แม่นยำกว่า จุดที่สี่คือการแยกส่วนเขียนหัวตารางและส่วนค้นหาออกเป็นฟังก์ชัน ทำให้อ่านและแก้ไขง่าย และจุดที่ห้าคือการรับชื่อไฟล์ผลลัพธ์จากพารามิเตอร์แรกโดยมีค่าเริ่มต้นสำรองไว้

ข้อจำกัดที่ควรรู้คือคำสั่ง stat มีไวยากรณ์ต่างกันระหว่างระบบ ตระกูลลินุกซ์ใช้ -c ขณะที่ระบบตระกูล BSD ใช้ -f สคริปต์ที่ต้องทำงานข้ามระบบจึงควรตรวจชนิดของระบบก่อน หรือเลือกใช้วิธีที่พกพาได้มากกว่า

หลักความปลอดภัยในการเขียนสคริปต์

สคริปต์ที่ทำงานด้วยสิทธิ์สูงเป็นเป้าหมายที่ดีของผู้ไม่หวังดี เพราะการแก้ไฟล์เดียวอาจส่งผลต่อทุกครั้งที่สคริปต์ทำงาน หลักปฏิบัติที่ควรยึดมีดังนี้

ประการแรก ตรวจสอบข้อมูลนำเข้าทุกครั้ง โดยเฉพาะค่าที่มาจากผู้ใช้หรือจากไฟล์ภายนอก และไม่ควรใช้ eval กับข้อมูลเหล่านั้นเด็ดขาด เพราะ eval จะตีความเป็นคำสั่ง Bash ซึ่งเปิดช่องให้ผู้ใช้สั่งงานใดก็ได้

ประการที่สอง ใส่เครื่องหมายอัญประกาศรอบตัวแปรทุกครั้งที่นำไปใช้เป็นอาร์กิวเมนต์ เพื่อป้องกันการแบ่งคำและการขยายรูปแบบชื่อไฟล์

ประการที่สาม ใช้ mktemp สร้างไฟล์ชั่วคราวแทนการตั้งชื่อเองใน /tmp เพราะชื่อที่คาดเดาได้เปิดช่องให้ผู้อื่นสร้างลิงก์สัญลักษณ์ดักไว้ก่อน

ประการที่สี่ ตั้ง trap เพื่อลบไฟล์ชั่วคราวเมื่อสคริปต์จบไม่ว่าด้วยเหตุใด

tmp=$(mktemp)
trap 'rm -f "$tmp"' EXIT

ประการที่ห้า ไม่เก็บรหัสผ่านหรือคีย์ไว้ในสคริปต์ เพราะไฟล์สคริปต์มักถูกคัดลอก สำรอง และอ่านโดยผู้ที่ไม่มีสิทธิ์ และประการที่หก ใช้สิทธิ์ต่ำสุดที่เพียงพอในการรันสคริปต์ ไม่ควรสั่งให้สคริปต์ทำงานด้วยสิทธิ์ root หากงานนั้นไม่ต้องการ

ในทางกลับกัน ผู้ตรวจสอบควรใช้หลักเดียวกันนี้ย้อนกลับเมื่อตรวจระบบของผู้อื่น คือมองหาสคริปต์ที่ถูกเรียกโดยงานอัตโนมัติหรือบริการ แล้วตรวจว่าสคริปต์นั้นเขียนได้โดยใคร และใช้ข้อมูลนำเข้าที่ควบคุมได้หรือไม่ จุดอ่อนจำนวนมากในระบบจริงไม่ได้อยู่ในโปรแกรมสำเร็จรูป แต่อยู่ในสคริปต์เล็กๆ ที่เขียนขึ้นเพื่อความสะดวกและถูกลืมไปแล้ว

✓ สรุปท้ายบท

บทนี้สร้างพื้นฐานสี่ชั้นซึ่งผู้เรียนจะใช้ตลอดรายวิชา

ชั้นแรกคือแผนที่ของระบบ ระบบไฟล์ของลินุกซ์เป็นต้นไม้เดียวที่จัดวางตามหน้าที่ ไม่ใช่ตามความสะดวกของผู้ใช้ การรู้ว่าไฟล์ใดอยู่ที่ใดจึงเท่ากับรู้ว่าไฟล์นั้นทำหน้าที่อะไร และสี่ตำแหน่งอย่าง /etc/passwd, /etc/shadow, /etc/sudoers และ /var/log/ คือที่เก็บความจริงเรื่องอำนาจและร่องรอยของผู้ใช้

ชั้นที่สองคือกติกาว่าใครแตะอะไรได้ ระบบสิทธิ์แบบ rwx ดูเรียบง่ายแต่มีความหมายต่างกันเมื่อใช้กับไฟล์และไดเรกทอรี โดยเฉพาะสิทธิ์เขียนบนไดเรกทอรีซึ่งควบคุมการลบไฟล์ ขณะที่บิตพิเศษสามบิตคือ SUID, SGID และ Sticky Bit คือจุดที่ระบบสิทธิ์แบบดั้งเดิมเริ่มไม่เพียงพอ และเป็นจุดที่ผู้ตรวจสอบให้ความสนใจมากที่สุด เพราะมันสร้างเส้นทางจากสิทธิ์ต่ำไปสู่สิทธิ์สูง

ชั้นที่สามคือภาพของสิ่งที่กำลังทำงานอยู่บนเครื่อง ทั้งกระบวนการที่ทำงานอยู่ในขณะนี้ บริการที่ systemd ดูแล และงานที่ถูกตั้งเวลาไว้ล่วงหน้า ทั้งสามส่วนนี้คือพื้นที่ที่ผู้บุกรุกใช้คงอยู่ และเป็นพื้นที่ที่ผู้ตรวจสอบต้องอ่านให้ครบก่อนสรุปว่าเครื่องหนึ่งสะอาด

ชั้นที่สี่คือเครื่องมือและวิธีประกอบมันเข้าด้วยกัน find, grep, awk, sed, cut และ ss เป็นโปรแกรมเล็กที่ทำหน้าที่เดียว แต่เมื่อต่อกันเป็นท่อก็ตอบคำถามที่ซับซ้อนได้ และเมื่อห่อหุ้มด้วยสคริปต์ Bash ที่รัดกุม งานที่ต้องทำซ้ำก็กลายเป็นงานที่ทำครั้งเดียวแล้วเชื่อถือผลได้

สิ่งที่ควรจำให้แม่นจากบทนี้ไม่ใช่รายละเอียดของตัวเลือกคำสั่งทุกตัว แต่เป็นวิธีคิดสามข้อ ข้อแรกคือทุกอย่างในระบบลินุกซ์คือไฟล์ที่มีเจ้าของและสิทธิ์ ข้อที่สองคือทุกการกระทำทิ้งร่องรอยไว้ในที่ใดที่หนึ่งเสมอ และข้อที่สามคือเครื่องมือที่ทรงพลังที่สุดในมือของผู้ตรวจสอบมักเป็นเครื่องมือที่มีอยู่แล้วในระบบ ไม่ใช่เครื่องมือที่ต้องติดตั้งเพิ่ม

สัปดาห์ถัดไปจะย้ายไปยังระบบปฏิบัติการอีกตระกูลหนึ่งซึ่งครองส่วนแบ่งใหญ่ในองค์กร นั่นคือวินโดวส์ ผู้เรียนจะเห็นว่าแนวคิดหลายอย่างในบทนี้ ทั้งสิทธิ์ เจ้าของ บริการ และงานตามกำหนดเวลา มีคู่เทียบในวินโดวส์ แต่ถูกนำไปใช้ด้วยกลไกที่ต่างออกไปโดยสิ้นเชิง การเทียบความเหมือนและความต่างระหว่างสองระบบนี้จะช่วยให้เข้าใจทั้งสองระบบลึกขึ้น

? ประเด็นทบทวนท้ายบท

ประเด็นต่อไปนี้ใช้ทบทวนความเข้าใจของผู้เรียนเองหลังจบบท คำตอบทั้งหมดอยู่ในเนื้อหาของบทนี้

ข้อ 1เหตุใด /etc/passwd จึงเปิดให้ผู้ใช้ทุกคนอ่านได้ ขณะที่ /etc/shadow ถูกจำกัดสิทธิ์ และการแยกเช่นนี้ป้องกันความเสี่ยงอะไร
ข้อ 2จงอธิบายความหมายของสิทธิ์เขียน (w) เมื่ออยู่บนไดเรกทอรี และอธิบายว่าเหตุใด /tmp จึงต้องมี Sticky Bit ประกอบ
ข้อ 3บิต SUID ทำให้โปรแกรมทำงานต่างจากปกติอย่างไร และเหตุใดการตั้ง SUID บนสคริปต์เชลล์จึงไม่เกิดผลบนลินุกซ์
ข้อ 4su กับ sudo ต่างกันในเรื่องรหัสผ่านที่ใช้และขอบเขตอำนาจอย่างไร และเหตุใด sudo -l จึงมักเป็นคำสั่งแรกๆ ที่ผู้ตรวจสอบรัน
ข้อ 5จงอธิบายความแตกต่างระหว่าง cron กับ systemd timer อย่างน้อยสามข้อ และเหตุใดผู้ตรวจสอบจึงต้องตรวจทั้งสองกลไก
ข้อ 6เหตุใดบันทึกของ journald อาจหายไปหลังการรีบูต และผู้ดูแลระบบต้องทำอะไรเพื่อให้เก็บไว้ได้ถาวร
ข้อ 7หากต้องดึงเฉพาะชื่อบัญชีจาก /etc/passwd จะเลือกใช้เครื่องมือใด เพราะเหตุใดจึงไม่เลือกเครื่องมืออื่นที่ให้ผลคล้ายกัน
ข้อ 8เหตุใดการไม่ใส่เครื่องหมายอัญประกาศรอบตัวแปรในสคริปต์ Bash จึงเป็นความเสี่ยง และความเสี่ยงนั้นเกิดขึ้นได้อย่างไร

Aa คำศัพท์สำคัญของบท

คำศัพท์ความหมายในบริบทของบทนี้
Filesystem Hierarchy Standard (FHS)มาตรฐานที่กำหนดว่าไดเรกทอรีใดควรบรรจุข้อมูลชนิดใด
Root (/)จุดเริ่มต้นเดียวของลำดับชั้นระบบไฟล์ทั้งหมด
Mount Point (จุดเชื่อมต่อ)ตำแหน่งที่ระบบไฟล์อื่นถูกต่อเข้าในต้นไม้เดียว
inode (ไอโหนด)โครงสร้างข้อมูลที่เก็บเมทาดาทาของไฟล์
Hard Link (ลิงก์แข็ง)ชื่อเพิ่มเติมที่ชี้ไปยังไอโหนดเดียวกัน
Symbolic Link (ลิงก์สัญลักษณ์)ไฟล์ที่เก็บเส้นทางไปยังไฟล์ปลายทาง
UID / GIDรหัสประจำตัวของผู้ใช้และกลุ่มซึ่งระบบใช้ตัดสินสิทธิ์
GECOSฟิลด์คำอธิบายใน /etc/passwd
Shadow Fileไฟล์เก็บแฮชรหัสผ่านที่อ่านได้เฉพาะผู้มีสิทธิ์
Hash (แฮช)ค่าที่คำนวณทางเดียวจากรหัสผ่าน ใช้ยืนยันโดยย้อนกลับไม่ได้
umaskค่าที่กำหนดว่าบิตสิทธิ์ใดจะถูกตัดออกเมื่อสร้างไฟล์ใหม่
SUIDบิตที่ทำให้โปรแกรมทำงานด้วยสิทธิ์ของเจ้าของไฟล์
SGIDบิตที่ให้สิทธิ์ตามกลุ่มของไฟล์ หรือบังคับกลุ่มของไฟล์ใหม่ในไดเรกทอรี
Sticky Bitบิตที่จำกัดการลบไฟล์ในไดเรกทอรีร่วมให้ทำได้เฉพาะเจ้าของ
Capabilityสิทธิ์ย่อยที่ให้แก่โปรแกรมแทนการใช้ SUID เต็มรูปแบบ
ACLรายการควบคุมการเข้าถึงรายบุคคลที่นอกเหนือจากสิทธิ์พื้นฐาน
sudoersไฟล์นโยบายกำหนดว่าใครรันคำสั่งใดด้วยสิทธิ์ใดได้
visudoโปรแกรมแก้ไขไฟล์ sudoers ที่ตรวจไวยากรณ์ก่อนบันทึก
PAMกรอบการพิสูจน์ตัวที่ใช้ร่วมกันโดยบริการหลายชนิด
Process (กระบวนการ)โปรแกรมที่กำลังทำงานอยู่พร้อมสถานะและทรัพยากรของตน
PID / PPIDหมายเลขประจำตัวกระบวนการ และหมายเลขของกระบวนการผู้ให้กำเนิด
Daemon (ดีมอน)กระบวนการที่ทำงานเบื้องหลังตั้งแต่ระบบเริ่มทำงาน
Signal (สัญญาณ)ข้อความแจ้งเหตุที่ส่งให้กระบวนการเพื่อให้เปลี่ยนพฤติกรรม
systemdระบบจัดการบริการและทรัพยากรหลักของลินุกซ์รุ่นใหม่
Unit (ยูนิต)ไฟล์อธิบายสิ่งที่ systemd จัดการ เช่น บริการหรือไทม์เมอร์
Drop-inไฟล์ส่วนเพิ่มที่ใช้แก้ไขยูนิตโดยไม่แตะไฟล์ต้นฉบับ
crontabตารางงานตามกำหนดเวลาของ cron
logrotateบริการหมุนและบีบอัดไฟล์บันทึกตามนโยบาย
journaldบริการเก็บบันทึกเหตุการณ์ในรูปแบบไบนารีของ systemd
Pipeline (ท่อ)การส่งผลลัพธ์ของคำสั่งหนึ่งเป็นข้อมูลนำเข้าของอีกคำสั่ง
Exit Code (รหัสออก)ค่าที่คำสั่งส่งกลับเพื่อบอกผลสำเร็จหรือล้มเหลว
Shebangบรรทัดแรกของสคริปต์ที่ระบุโปรแกรมแปลคำสั่ง
Word Splittingการแบ่งค่าตัวแปรตามช่องว่างซึ่งก่อให้เกิดข้อผิดพลาดได้
