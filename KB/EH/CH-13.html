เชื่อมโยงกับบทก่อนหน้าต่อยอดจากบทที่ 12 ซึ่งจบที่การได้สิทธิ์ระดับผู้ดูแลระบบบนเครื่องเดี่ยว บทนี้ขยายขอบเขตจากเครื่องหนึ่งไปสู่ระบบยืนยันตัวตนที่ควบคุมทั้งองค์กร
เชื่อมโยงกับบทถัดไปบทที่ 14 (Active Directory II) ซึ่งนำข้อมูลที่สำรวจได้ในบทนี้ไปใช้ในการโจมตี credential การเคลื่อนที่ในเครือข่าย และการรักษาการเข้าถึง

เอกสารประกอบการบรรยายฉบับนี้เรียบเรียงจากเนื้อหาต้นฉบับของบทโดยตรง จุดประสงค์การเรียนรู้ในหัวข้อถัดไปทำเครื่องหมายได้เมื่อทำสำเร็จ และความคืบหน้าจะถูกจำไว้ในเบราว์เซอร์ของเครื่องนี้

บทที่แล้วจบลงที่การได้สิทธิ์ระดับผู้ดูแลระบบบนเครื่องหนึ่งเครื่อง ผู้เรียนเห็นแล้วว่าการได้สิทธิ์นั้นต้องอาศัยการอ่านเงื่อนไขหลายชั้น และผลลัพธ์ที่ได้ก็จำกัดอยู่เพียงเครื่องนั้น แต่ในองค์กรจริง เครื่องแม่ข่ายแทบไม่เคยทำงานเดี่ยว การเข้าสู่ระบบ การเข้าถึงแชร์ไฟล์ การติดตั้งซอฟต์แวร์ และการกำหนดนโยบาย ล้วนอ้างอิงระบบกลางระบบหนึ่งซึ่งเก็บรายชื่อผู้ใช้และสิทธิ์ของทุกคนไว้

ระบบกลางนั้นคือ Active Directory ซึ่งทำหน้าที่สามอย่างพร้อมกัน คือเป็นฐานข้อมูลวัตถุขององค์กร เป็นผู้ให้บริการยืนยันตัวตน และเป็นผู้กระจายนโยบายไปยังเครื่องลูกข่าย คุณสมบัติทั้งสามนี้ทำให้มันมีคุณค่ามหาศาลต่อทั้งผู้ดูแลระบบและผู้โจมตี ผู้ดูแลระบบเห็นมันเป็นเครื่องมือลดงานและรวมศูนย์การจัดการ ส่วนผู้โจมตีเห็นมันเป็นกุญแจดอกเดียวที่เปิดประตูได้หลายพันบาน

ความเสี่ยงที่สำคัญที่สุดของ Active Directory ไม่ได้อยู่ที่ช่องโหว่ในซอฟต์แวร์ แต่อยู่ที่การออกแบบให้ผู้ใช้ยืนยันตัวตนครั้งเดียวแล้วเข้าถึงทรัพยากรได้หลายแห่ง เมื่อบัญชีหนึ่งถูกยึด ผู้โจมตีจึงไม่ต้องเจาะเครื่องทีละเครื่อง แต่ใช้สิทธิ์ของบัญชีนั้นสอบถามข้อมูลทั้งโดเมนและหาเส้นทางไปยังบัญชีที่มีสิทธิ์สูงกว่า

บทนี้จึงให้น้ำหนักกับการเข้าใจโครงสร้างและการอ่านข้อมูลมากกว่าการโจมตี ผู้เรียนจะได้ฝึกตอบคำถามว่าโดเมนนี้มีวัตถุอะไรบ้าง ใครเป็นสมาชิกกลุ่มใด เครื่องใดมีใครเข้าสู่ระบบบ้าง และข้อมูลใดที่บ่งชี้ว่ามีเส้นทางจากบัญชีธรรมดาไปสู่สิทธิ์สูง การอ่านข้อมูลเหล่านี้ให้ถูกต้องเป็นพื้นฐานที่ขาดไม่ได้ของบทถัดไป ซึ่งจะนำข้อมูลไปใช้ในการโจมตี

13.1 ทำไม Active Directory จึงเป็นสมรภูมิหลัก

กรณีศึกษาที่ต่อเนื่องจากบทที่แล้ว

กรณีศึกษาในบทนี้ยังคงใช้เครื่อง APP01 ที่หมายเลข 10.10.10.41 ซึ่งบทที่แล้วจบลงด้วยการยกระดับสิทธิ์จากบัญชี www-data ขึ้นเป็น root บนเครื่องนั้นได้สำเร็จ ระหว่างสำรวจไฟล์ของแอปพลิเคชันด้วยสิทธิ์ www-data ก่อนการยกระดับ ผู้ทดสอบพบไฟล์ตั้งค่าที่เก็บชื่อบัญชีและรหัสผ่านของบัญชีบริการชื่อ svc-backup ซึ่งใช้สำหรับเชื่อมต่อกับเครื่องแม่ข่ายเพื่อสำรองข้อมูล

การเป็น root บน APP01 ทำให้อ่านไฟล์ได้ทุกไฟล์บนเครื่อง แต่ไม่ได้เพิ่มสิทธิ์ใดบนเครื่องอื่นเลย สิ่งที่มีค่ากว่าคือข้อมูลยืนยันตัวตนที่พบในไฟล์เหล่านั้น บัญชี svc-backup ไม่ได้มีสิทธิ์บนเครื่อง APP01 มากไปกว่าบัญชีผู้ใช้ทั่วไป แต่เมื่อตรวจสอบการเป็นสมาชิกโดเมนแล้วพบว่า APP01 ถูกเพิ่มเข้าโดเมน corp.local และบัญชี svc-backup เป็นบัญชีของโดเมน ไม่ใช่บัญชีท้องถิ่น

จุดนี้คือจุดเปลี่ยนของภาพรวม ความรู้จากบทที่แล้วบอกผู้ทดสอบว่าอะไรทำให้ได้สิทธิ์บนเครื่องหนึ่ง แต่ความรู้จากบทนี้บอกว่าสิทธิ์ของบัญชีนั้นเปิดประตูไปที่ใดในองค์กร และข้อมูลใดที่ต้องเก็บก่อนตัดสินใจเคลื่อนที่

เหตุใดระบบเดียวจึงควบคุมได้ทั้งองค์กร

Active Directory ทำงานแบบ single sign-on คือผู้ใช้ยืนยันตัวตนครั้งเดียวแล้วได้รับตั๋วที่ใช้เข้าถึงบริการต่างๆ ได้โดยไม่ต้องกรอกรหัสผ่านซ้ำ ตั๋วนี้ไม่ผูกกับเครื่องใดเครื่องหนึ่งโดยเฉพาะ เมื่อผู้ใช้เข้าสู่ระบบเครื่องใดก็สามารถใช้ตั๋วเดียวกันเข้าถึงแชร์ไฟล์ เว็บภายใน ฐานข้อมูล และบริการอื่นที่เชื่อถือโดเมนเดียวกัน

การออกแบบเช่นนี้ลดภาระของผู้ใช้และผู้ดูแลระบบอย่างมาก แต่ก็ทำให้บัญชีเดียวมีอำนาจกว้างกว่าที่ผู้ใช้ส่วนใหญ่ตระหนัก บัญชีของฝ่ายบุคคลอาจเข้าถึงแชร์เงินเดือน บัญชีของฝ่ายไอทีอาจเข้าถึงเครื่องทุกเครื่อง และบัญชีของผู้ดูแลระบบอาจเข้าถึงทุกอย่างในโดเมน

ผลคือการยึดบัญชีเดียวไม่ใช่การได้เครื่องเดียว แต่เป็นการได้สิทธิ์ที่ติดไปกับบัญชีนั้นทุกที่ที่มันถูกยอมรับ ผู้โจมตีที่ได้บัญชีของผู้ดูแลระบบคนหนึ่งสามารถเข้าถึงเครื่องแม่ข่ายทุกเครื่องที่โดเมนควบคุม ซึ่งในองค์กรขนาดใหญ่อาจมีหลายพันเครื่อง

ตาราง 13.2 เปรียบเทียบขอบเขตการจัดการระหว่างเครื่องเดี่ยวกับระบบโดเมน
ประเด็นกลุ่มงานแบบเครื่องเดี่ยวระบบโดเมน
บัญชีผู้ใช้เก็บแยกในแต่ละเครื่องเก็บรวมที่โดเมนคอนโทรลเลอร์
การยืนยันตัวตนตรวจกับฐานข้อมูลของเครื่องนั้นตรวจกับระบบกลางและออกตั๋ว
การกำหนดนโยบายตั้งค่าเครื่องทีละเครื่องกระจายผ่านนโยบายกลุ่ม
การเข้าถึงแชร์ไฟล์ใช้บัญชีท้องถิ่นใช้บัญชีโดเมนและสิทธิ์จากกลุ่ม
การติดตั้งซอฟต์แวร์ทำที่เครื่องหรือใช้เครื่องมือแยกมอบหมายผ่านนโยบายกลุ่ม
การบริหารสิทธิ์กระจายและซ้ำซ้อนรวมศูนย์แต่ซับซ้อนขึ้น
ผลเมื่อบัญชีรั่วกระทบเครื่องเดียวกระทบทุกทรัพยากรที่บัญชียอมรับ

ตารางนี้แสดงเหตุผลทางเทคนิคที่ทำให้ Active Directory เป็นเป้าหมายที่มีมูลค่าสูง แต่ยังมีเหตุผลเชิงปฏิบัติอีกหลายข้อที่ทำให้มันยังคงเป็นจุดอ่อนในองค์กรจริง

เหตุผลเชิงปฏิบัติที่ทำให้ยังพบช่องทางอยู่เสมอ

เหตุผลข้อแรกคือระบบที่ใช้งานมานาน หลายองค์กรเริ่มใช้ Active Directory เมื่อสองทศวรรษก่อน และยังคงโครงสร้างเดิมไว้เพราะการเปลี่ยนมีต้นทุนสูง บัญชีที่สร้างไว้เพื่อโครงการที่จบไปแล้วยังคงเปิดอยู่ และกลุ่มที่ให้สิทธิ์กว้างเพื่อแก้ปัญหาเฉพาะหน้าก็ยังไม่ถูกทบทวน

เหตุผลข้อที่สองคือความสะดวกในการทำงาน ผู้ดูแลระบบจำเป็นต้องเข้าถึงเครื่องจำนวนมากเพื่อติดตั้งและแก้ไขปัญหา หากต้องยืนยันตัวตนใหม่ทุกครั้งงานจะช้าลงมาก องค์กรจึงมักสร้างบัญชีที่มีสิทธิ์กว้างและใช้ร่วมกัน ซึ่งทำให้การตรวจสอบย้อนหลังทำได้ยาก

เหตุผลข้อที่สามคือบัญชีบริการ บริการจำนวนมากต้องรันด้วยบัญชีโดเมนเพื่อเข้าถึงแชร์ไฟล์หรือฐานข้อมูล และบัญชีเหล่านี้มักตั้งรหัสผ่านแบบไม่หมดอายุเพื่อไม่ให้บริการหยุดทำงาน รหัสผ่านจึงไม่เคยเปลี่ยนและอาจถูกจดไว้ในไฟล์ตั้งค่าที่ผู้ใช้ทั่วไปอ่านได้

เหตุผลข้อที่สี่คือความซับซ้อนของสิทธิ์ Active Directory มีกลไกสิทธิ์หลายชั้น ทั้งกลุ่มที่ซ้อนกันหลายระดับ สิทธิ์บนวัตถุแต่ละชิ้น และสิทธิ์ที่สืบทอดตามหน่วยองค์กร ผู้ดูแลระบบจึงยากที่จะตอบได้ทันทีว่าใครมีสิทธิ์อะไรจริง ซึ่งเป็นช่องว่างที่เครื่องมืออย่าง BloodHound ถูกสร้างขึ้นมาเพื่อตอบ

เหตุผลข้อที่ห้าคือการย้ายระบบขึ้นคลาวด์ องค์กรจำนวนมากเชื่อมระบบภายในกับบริการยืนยันตัวตนบนคลาวด์ และสร้างการซิงโครไนซ์บัญชีระหว่างสองฝั่ง ความผิดพลาดในการตั้งค่าการซิงโครไนซ์อาจทำให้บัญชีที่มีสิทธิ์สูงปรากฏในที่ที่ไม่ควรมี

ผลกระทบทางธุรกิจ

เมื่อผู้โจมตีได้สิทธิ์ระดับโดเมน ผลกระทบไม่ได้จำกัดอยู่ที่ข้อมูล แต่รวมถึงความสามารถในการหยุดระบบทั้งหมด ผู้ที่มีสิทธิ์ระดับโดเมนสามารถเปลี่ยนนโยบายกลุ่มเพื่อรันคำสั่งบนทุกเครื่องที่โดเมนควบคุม ซึ่งเป็นกลไกเดียวกับที่องค์กรใช้ติดตั้งซอฟต์แวร์ตามปกติ

ผลกระทบอีกประการคือความน่าเชื่อถือของระบบยืนยันตัวตน หากผู้โจมตีสามารถออกตั๋วปลอมได้ องค์กรจะไม่สามารถแยกความแตกต่างระหว่างผู้ใช้จริงกับผู้ใช้ปลอมได้ด้วยวิธีปกติ การกู้คืนจึงต้องเปลี่ยนกุญแจหลักของโดเมนและทำให้ตั๋วที่ออกไปแล้วทั้งหมดใช้ไม่ได้

ด้วยเหตุนี้ งานทดสอบเจาะระบบในสภาพแวดล้อมที่มี Active Directory จึงต้องวางขอบเขตให้ชัดเจนตั้งแต่ต้น ทั้งเครื่องที่อนุญาตให้ทดสอบ บัญชีที่อนุญาตให้ใช้ และระดับการเข้าถึงที่ยอมรับได้ เพราะผลกระทบของการทดสอบอาจใกล้เคียงกับการโจมตีจริงมาก

ขอบเขตของบทนี้

บทนี้กล่าวถึงแนวคิด โครงสร้าง และการสำรวจข้อมูลใน Active Directory เท่านั้น การใช้ข้อมูลเพื่อขอตั๋วบริการ การทดลองรหัสผ่านแบบกระจาย การใช้แฮชแทนรหัสผ่าน และการเคลื่อนที่ระหว่างเครื่อง จะกล่าวถึงในบทที่ 14

การสำรวจในบทนี้เน้นการอ่านข้อมูลที่ผู้ใช้มีสิทธิ์อ่านอยู่แล้วเป็นหลัก ซึ่งเป็นการกระทำที่ไม่เปลี่ยนสถานะของระบบ แต่ก็ยังถูกบันทึกโดยระบบตรวจสอบขององค์กร ผู้เรียนจึงต้องเข้าใจว่าการสำรวจไม่ใช่การกระทำที่ปราศจากร่องรอย

เครื่องมือที่กล่าวถึงในบทนี้ได้แก่ ldapsearch, enum4linux, PowerView และ BloodHound ตามที่ระบุไว้ในโครงรายวิชา ผู้เรียนควรใช้เครื่องมือเหล่านี้ในห้องแล็บหรือระบบที่ได้รับอนุญาตเท่านั้น และควรเริ่มจากคำสั่งที่ให้ข้อมูลมากที่สุดก่อนใช้เครื่องมืออัตโนมัติ

13.2 โครงสร้างของ Active Directory

วัตถุ แอตทริบิวต์ และสคีมา

Active Directory เป็นฐานข้อมูลที่เก็บวัตถุ (Object) แต่ละวัตถุมีชนิดและมีแอตทริบิวต์ (Attribute) ที่อธิบายคุณสมบัติของมัน ตัวอย่างวัตถุชนิดผู้ใช้มีแอตทริบิวต์เช่นชื่อที่แสดง ชื่อเข้าสู่ระบบ และหมายเลขประจำตัว ส่วนวัตถุชนิดเครื่องมีแอตทริบิวต์เช่นชื่อเครื่องและระบบปฏิบัติการ

สคีมา (Schema) คือคำนิยามว่าวัตถุแต่ละชนิดมีแอตทริบิวต์ใดได้บ้าง และแอตทริบิวต์แต่ละตัวเก็บข้อมูลชนิดใด สคีมาจึงเป็นตัวกำหนดว่าฐานข้อมูลยอมรับข้อมูลแบบใด การเปลี่ยนแปลงสคีมาเป็นงานที่ต้องระวังเพราะมีผลทั้งป่าและย้อนกลับได้ยาก

แอตทริบิวต์บางตัวมีหลายค่า (Multi-valued) เช่นรายชื่อสมาชิกของกลุ่ม ซึ่งทำให้กลุ่มหนึ่งมีสมาชิกได้หลายรายโดยไม่ต้องสร้างแอตทริบิวต์ใหม่ การเข้าใจความแตกต่างนี้สำคัญเมื่ออ่านผลจากเครื่องมือ เพราะเครื่องมือบางตัวแสดงเฉพาะค่าแรกของแอตทริบิวต์

ชื่อวัตถุแบบ Distinguished Name

วัตถุทุกชิ้นมีชื่อเฉพาะที่เรียกว่า Distinguished Name หรือ DN ซึ่งบอกตำแหน่งของวัตถุในโครงสร้างทั้งหมด DN ประกอบด้วยส่วนย่อยที่เชื่อมด้วยเครื่องหมายจุลภาค โดยแต่ละส่วนมีรูปแบบ ตัวย่อ=ค่า

ตัวย่อที่พบบ่อยได้แก่ DC สำหรับองค์ประกอบชื่อโดเมน OU สำหรับหน่วยองค์กร CN สำหรับชื่อทั่วไป และ CN ที่ใช้กับวัตถุส่วนใหญ่ที่ไม่ใช่หน่วยองค์กร ตัวอย่างเช่นผู้ใช้ชื่อ Somchai ในหน่วยองค์กร Staff ของโดเมน corp.local มี DN เป็น CN=Somchai,OU=Staff,DC=corp,DC=local

ตาราง 13.3 ตัวอย่าง Distinguished Name และความหมาย
DNความหมาย
DC=corp,DC=localโดเมน corp.local
OU=Staff,DC=corp,DC=localหน่วยองค์กรชื่อ Staff ภายในโดเมน
CN=Somchai,OU=Staff,DC=corp,DC=localวัตถุชื่อ Somchai ในหน่วยองค์กร Staff
CN=Domain Admins,CN=Users,DC=corp,DC=localกลุ่ม Domain Admins ในคอนเทนเนอร์ Users
CN=DC01,OU=Servers,DC=corp,DC=localบัญชีเครื่องของโดเมนคอนโทรลเลอร์ DC01

การอ่าน DN จากมากไปน้อยทำให้เห็นลำดับชั้นของวัตถุ แต่การอ่านจากซ้ายไปขวาคือการอ่านจากวัตถุไปยังโดเมน การเขียน DN ผิดหนึ่งตัวอักษรจะทำให้สอบถามไม่พบวัตถุ ซึ่งเป็นข้อผิดพลาดที่พบบ่อยเมื่อพิมพ์คำสั่งด้วยมือ

โดเมน ทรี และฟอเรสต์

โดเมนคือขอบเขตการบริหารที่เก็บวัตถุและมีฐานข้อมูลของตัวเอง โดเมนหนึ่งมีโดเมนคอนโทรลเลอร์อย่างน้อยหนึ่งเครื่องที่ทำหน้าที่ให้บริการยืนยันตัวตนและเก็บสำเนาฐานข้อมูล โดเมนมีชื่อในรูปแบบ DNS เช่น corp.local และมีชื่อแบบ NetBIOS เช่น CORP สำหรับระบบรุ่นเก่า

ทรีคือกลุ่มของโดเมนที่ใช้ชื่อต่อเนื่องกัน เช่น corp.local, asia.corp.local และ europe.corp.local โดยโดเมนลูกมีความสัมพันธ์กับโดเมนแม่แบบอัตโนมัติสองทาง ฟอเรสต์คือกลุ่มของทรีที่แชร์สคีมาและแคตตาล็อกกลางร่วมกัน ฟอเรสต์จึงเป็นขอบเขตความปลอดภัยที่ใหญ่ที่สุดของ Active Directory

ระหว่างฟอเรสต์จะเชื่อมกันด้วยความเชื่อถือ (Trust) ซึ่งอนุญาตให้ผู้ใช้ของฟอเรสต์หนึ่งเข้าถึงทรัพยากรของอีกฟอเรสต์หนึ่งได้ตามที่กำหนด ความเชื่อถือเป็นจุดที่ต้องตรวจในการสำรวจ เพราะอาจเปิดทางข้ามขอบเขตที่องค์กรคิดว่าปิดอยู่

ตาราง 13.4 องค์ประกอบโครงสร้างและหน้าที่
องค์ประกอบหน้าที่สิ่งที่ควรตรวจ
โดเมนขอบเขตการบริหารและฐานข้อมูลวัตถุชื่อโดเมน ระดับการทำงาน
ทรีกลุ่มโดเมนที่ใช้ชื่อต่อเนื่องกันความสัมพันธ์ระหว่างโดเมนลูกและแม่
ฟอเรสต์ขอบเขตความปลอดภัยสูงสุดและสคีมากลางจำนวนโดเมนและความเชื่อถือ
ความเชื่อถืออนุญาตการเข้าถึงข้ามโดเมนหรือฟอเรสต์ทิศทาง ชนิด และการกรอง SID
โดเมนคอนโทรลเลอร์ให้บริการยืนยันตัวตนและเก็บฐานข้อมูลชื่อ เครื่อง บริการที่เปิด
แคตตาล็อกกลางค้นหาวัตถุข้ามโดเมนขอบเขตข้อมูลที่เก็บ
หน่วยองค์กรจัดกลุ่มวัตถุเพื่อบริหารและใช้นโยบายโครงสร้างและการมอบสิทธิ์
ไซต์แบ่งตามที่ตั้งเครือข่ายการจำลองข้อมูลและบริการใกล้เคียง

โดเมนคอนโทรลเลอร์และบทบาทพิเศษ

โดเมนคอนโทรลเลอร์ทุกเครื่องเก็บสำเนาฐานข้อมูลที่เขียนได้และให้บริการยืนยันตัวตน การเปลี่ยนแปลงที่เครื่องหนึ่งจะถูกจำลองไปยังเครื่องอื่นภายในเวลาไม่กี่วินาทีถึงไม่กี่นาที ขึ้นกับที่ตั้งเครือข่ายและภาระของระบบ

บทบาทพิเศษห้าบทบาทถูกกำหนดให้เครื่องใดเครื่องหนึ่งในแต่ละโดเมนหรือป่า เพื่อป้องกันความขัดแย้งเมื่อมีการเปลี่ยนแปลงบางประเภท บทบาทเหล่านี้ได้แก่ผู้ดูแลสคีมา ผู้ดูแลชื่อโดเมน ผู้จัดสรรรหัสภายใน ผู้เลียนแบบผู้ควบคุมโดเมนหลัก และผู้ดูแลโครงสร้างพื้นฐาน

บทบาทที่เกี่ยวข้องกับการสำรวจมากที่สุดคือผู้จัดสรรรหัสภายใน (RID Master) ซึ่งเป็นผู้แจกช่วงหมายเลขให้โดเมนคอนโทรลเลอร์แต่ละเครื่องใช้สร้างหมายเลขประจำวัตถุใหม่ และบทบาทผู้เลียนแบบผู้ควบคุมโดเมนหลัก (PDC Emulator) ซึ่งเป็นเครื่องที่ระบบอื่นสอบถามเมื่อต้องการข้อมูลล่าสุดเกี่ยวกับรหัสผ่านและการล็อกบัญชี

ในมุมของผู้ทดสอบ การรู้ว่าเครื่องใดถือบทบาทใดช่วยให้เข้าใจว่าข้อมูลบางอย่างอาจล่าช้าเมื่ออ่านจากเครื่องอื่น และช่วยให้วางแผนการสำรวจโดยไม่สร้างภาระเกินจำเป็นกับเครื่องหลัก

หมายเลข SID และ RID

วัตถุด้านความปลอดภัยทุกชิ้นใน Active Directory มีหมายเลขระบุตัวตนที่เรียกว่า Security Identifier หรือ SID ซึ่งระบบใช้ตัดสินสิทธิ์แทนชื่อ SID ของวัตถุในโดเมนมีรูปแบบ S-1-5-21- ตามด้วยตัวเลขสามชุดที่ระบุโดเมน และปิดท้ายด้วยหมายเลข RID ของวัตถุนั้น

หมายเลข RID ถูกแจกจากช่วงที่โดเมนจองไว้ และไม่ซ้ำกันภายในโดเมน วัตถุที่สร้างขึ้นใหม่จะได้ RID ถัดไปเรื่อยๆ ซึ่งทำให้ผู้ทดสอบสามารถประมาณได้ว่าวัตถุใดถูกสร้างก่อนหรือหลัง แต่ไม่สามารถใช้ระบุเวลาได้แน่นอน

บัญชี krbtgt เป็นบัญชีที่สำคัญที่สุดในโดเมน เพราะกุญแจของบัญชีนี้ใช้เข้ารหัสตั๋ว TGT ทุกใบ ผู้ที่ได้ค่าแฮชของบัญชีนี้สามารถสร้างตั๋วปลอมที่ระบบยอมรับได้ ซึ่งเป็นกลไกของ Golden Ticket ที่จะกล่าวถึงในบทถัดไปในระดับแนวคิด

การเห็น RID 500 ในผลการสำรวจเป็นสัญญาณให้ตรวจต่อ เพราะบัญชีผู้ดูแลระบบเริ่มต้นมักถูกใช้เป็นเป้าหมายของการทดลองรหัสผ่าน และหลายองค์กรไม่ได้เปลี่ยนชื่อหรือปิดบัญชีนี้

บัญชี ผู้ใช้ กลุ่ม และคอมพิวเตอร์

วัตถุชนิดผู้ใช้ (User) เก็บข้อมูลบัญชีและแอตทริบิวต์ที่เกี่ยวข้อง เช่นชื่อเข้าสู่ระบบ ชื่อที่แสดง หมายเลขโทรศัพท์ และวันที่สร้าง วัตถุชนิดคอมพิวเตอร์ (Computer) ก็เป็นบัญชีประเภทหนึ่งซึ่งมีรหัสผ่านของตัวเองและต้องเปลี่ยนเป็นระยะตามนโยบายของโดเมน

กลุ่ม (Group) ใช้รวมวัตถุเพื่อมอบสิทธิ์พร้อมกัน กลุ่มมีสองประเภทคือกลุ่มความปลอดภัย (Security Group) ซึ่งใช้กำหนดสิทธิ์ได้ และกลุ่มแจกจ่าย (Distribution Group) ซึ่งใช้สำหรับรายชื่ออีเมลเท่านั้น กลุ่มความปลอดภัยยังมีขอบเขตสามแบบที่กำหนดว่าสมาชิกสามารถมาจากที่ใดและใช้สิทธิ์ได้ที่ใด

ขอบเขตโกลบอลจากโดเมนของกลุ่มเท่านั้นใช้ได้ทุกโดเมนในป่า

การออกแบบที่พบบ่อยคือใช้กลุ่มโกลบอลรวมผู้ใช้ตามหน้าที่ แล้วเพิ่มกลุ่มโกลบอลเหล่านั้นเข้าเป็นสมาชิกของกลุ่มโดเมนท้องถิ่นซึ่งมีสิทธิ์บนทรัพยากร วิธีนี้ทำให้การบริหารสิทธิ์ทำได้โดยเปลี่ยนสมาชิกกลุ่มเพียงจุดเดียว

ปัญหาที่พบคือกลุ่มที่ซ้อนกันหลายชั้นจนไม่มีใครรู้ว่าสมาชิกที่แท้จริงคือใคร และกลุ่มที่เหลือจากโครงการเก่าซึ่งยังมีสิทธิ์อยู่ การสำรวจจึงต้องอ่านทั้งสมาชิกโดยตรงและสมาชิกที่ได้มาทางกลุ่มซ้อน

หน่วยองค์กรและนโยบายกลุ่ม

หน่วยองค์กร (Organizational Unit หรือ OU) ใช้จัดกลุ่มวัตถุเพื่อการบริหารและใช้เป็นจุดผูกนโยบายกลุ่ม หน่วยองค์กรต่างจากกลุ่มตรงที่มันไม่ให้สิทธิ์ด้วยตัวเอง แต่เป็นภาชนะที่ใส่ทั้งวัตถุและนโยบาย

ความสับสนที่พบบ่อยคือการคิดว่าการใส่ผู้ใช้ไว้ในหน่วยองค์กรเท่ากับการให้สิทธิ์ สิ่งที่ให้สิทธิ์คือนโยบายที่ผูกกับหน่วยองค์กรและสิทธิ์ที่มอบให้วัตถุหรือกลุ่ม ในทางกลับกัน การใส่ผู้ใช้ในกลุ่มให้สิทธิ์ทันทีโดยไม่ต้องมีนโยบายใดๆ

นโยบายกลุ่ม (Group Policy) คือกลไกที่ใช้กำหนดค่าเครื่องและผู้ใช้จากส่วนกลาง ตัวอย่างเช่นการกำหนดนโยบายรหัสผ่าน การติดตั้งซอฟต์แวร์ การแมปไดรฟ์ และการปิดความสามารถบางอย่างของระบบ

นโยบายกลุ่มถูกเก็บไว้ในโฟลเดอร์ SYSVOL ซึ่งจำลองไปยังโดเมนคอนโทรลเลอร์ทุกเครื่อง และถูกเรียกใช้โดยไคลเอนต์เมื่อเข้าสู่ระบบหรือเมื่อรีเฟรชตามรอบเวลา โฟลเดอร์นี้จึงเป็นแหล่งข้อมูลที่มีประโยชน์ในการสำรวจ เพราะบอกรายละเอียดการตั้งค่าที่องค์กรใช้อยู่

รูปแบบบัญชีที่พบได้บ่อย

นอกจากบัญชีผู้ใช้ทั่วไป องค์กรยังมีบัญชีประเภทอื่นที่ต้องตรวจแยก บัญชีบริการ (Service Account) ใช้รันบริการและมักมีสิทธิ์เข้าถึงฐานข้อมูลหรือแชร์ไฟล์ บัญชีกลุ่มบริการแบบจัดการ (Group Managed Service Account) เป็นรูปแบบที่ระบบจัดการรหัสผ่านให้อัตโนมัติและปลอดภัยกว่าบัญชีบริการแบบเดิม

บัญชีผู้ดูแลระบบแยกส่วน (Administrative Tiering) เป็นแนวปฏิบัติที่แยกบัญชีสำหรับงานผู้ดูแลระบบออกจากบัญชีสำหรับงานประจำวัน เพื่อไม่ให้รหัสผ่านของผู้ดูแลระบบถูกใช้บนเครื่องที่เสี่ยงต่อการถูกยึด องค์กรที่ทำได้ดีจะไม่ให้บัญชีผู้ดูแลระบบเข้าสู่ระบบเครื่องของผู้ใช้ทั่วไป

บัญชีที่ถูกปิดใช้งานแล้วแต่ยังมีสิทธิ์อยู่ก็เป็นสิ่งที่ต้องตรวจ เพราะการปิดใช้งานไม่ได้ลบสิทธิ์ออกจากกลุ่ม และการเปิดใช้งานอีกครั้งจะคืนสิทธิ์เดิมทั้งหมดโดยไม่มีใครสังเกต การสำรวจจึงต้องดูทั้งสถานะการใช้งานและสิทธิ์ที่ถืออยู่

เมื่อเข้าใจโครงสร้างและภาษาที่ใช้เรียกวัตถุแล้ว ขั้นต่อไปคือการเข้าใจกลไกที่ทำให้ผู้ใช้ได้รับสิทธิ์เหล่านั้น นั่นคือการยืนยันตัวตนด้วย Kerberos ซึ่งเป็นหัวข้อของส่วนถัดไป

13.3 การยืนยันตัวตนด้วย Kerberos

เหตุใดต้องเข้าใจ Kerberos ก่อนการสำรวจ

ผู้เรียนอาจสงสัยว่าเหตุใดบทที่ว่าด้วยการสำรวจข้อมูลจึงต้องอธิบายกลไกการยืนยันตัวตนด้วย คำตอบคือข้อมูลที่สำคัญที่สุดใน Active Directory หลายอย่างเกี่ยวข้องกับตั๋วและกุญแจ การรู้ว่าตั๋วใบใดถูกเข้ารหัสด้วยกุญแจใดทำให้เข้าใจว่าข้อมูลใดมีค่าเมื่อได้มา และการโจมตีในบทถัดไปเกือบทั้งหมดอาศัยกลไกนี้

นอกจากนี้ การอ่านบันทึกเหตุการณ์ของโดเมนคอนโทรลเลอร์ต้องอาศัยความรู้เรื่อง Kerberos เพราะบันทึกเหล่านี้บอกเพียงว่ามีการขอตั๋ว การขอถูกปฏิเสธ หรือการขอใช้ตั๋ว ถ้าไม่เข้าใจลำดับปกติก็แยกไม่ได้ว่าสิ่งใดผิดปกติ

Kerberos เป็นโปรโตคอลมาตรฐานที่พัฒนามาจากโครงการ Athena ของสถาบันเทคโนโลยีแมสซาชูเซตส์ และถูกใช้เป็นกลไกหลักของ Active Directory ตั้งแต่ระบบรุ่นแรก จุดออกแบบสำคัญคือไม่ส่งรหัสผ่านไปตามเครือข่ายแม้แต่ครั้งเดียว และใช้ตั๋วที่มีอายุจำกัดแทน

องค์ประกอบของระบบ

ผู้ใช้แต่ละรายเป็นตัวตน (Principal) ที่มีชื่อเฉพาะในรูป ชื่อ@ขอบเขต เช่น somchai@CORP.LOCAL ฝั่งบริการก็มีชื่อเฉพาะในรูปแบบเดียวกัน และมีชื่อบริการ (Service Principal Name หรือ SPN) ที่ใช้ระบุว่าบริการใดต้องการตั๋ว

ศูนย์กระจายกุญแจ (Key Distribution Center หรือ KDC) เป็นบริการที่รันบนโดเมนคอนโทรลเลอร์และทำหน้าที่สองอย่าง คือบริการยืนยันตัวตน (Authentication Service) และบริการออกตั๋ว (Ticket Granting Service) ทั้งสองอย่างทำงานร่วมกันแต่มีหน้าที่ต่างกัน

ลำดับการขอตั๋วห้าขั้น

การเข้าสู่ระบบหนึ่งครั้งมีลำดับที่ชัดเจน ผู้เรียนควรเข้าใจลำดับนี้เพราะการอ่านบันทึกเหตุการณ์และการตีความผลของเครื่องมือต้องอ้างอิงกับขั้นเหล่านี้

ขั้นแรก ผู้ใช้พิมพ์ชื่อและรหัสผ่าน ไคลเอนต์สร้างข้อมูลเวลาที่เข้ารหัสด้วยกุญแจที่คำนวณจากรหัสผ่าน แล้วส่งคำขอตั๋วเริ่มต้นไปยัง AS การส่งข้อมูลเวลานี้เรียกว่าการยืนยันตัวตนล่วงหน้า (Pre-authentication) และเป็นกลไกที่ป้องกันไม่ให้ใครขอตั๋วแทนผู้ใช้ได้โดยไม่รู้รหัสผ่าน

ขั้นที่สอง AS ตรวจข้อมูลเวลาและค้นหาผู้ใช้ในฐานข้อมูล หากถูกต้องจะสร้างตั๋ว TGT ซึ่งเข้ารหัสด้วยกุญแจของบัญชี krbtgt และสร้างกุญแจเซสชันซึ่งเข้ารหัสด้วยกุญแจของผู้ใช้ ทั้งสองอย่างถูกส่งกลับในข้อความตอบรับ

ขั้นที่สาม ไคลเอนต์เก็บ TGT และกุญแจเซสชันไว้ในหน่วยความจำ เมื่อต้องเข้าถึงบริการใด มันสร้างข้อมูลยืนยันตัวตนที่เข้ารหัสด้วยกุญแจเซสชัน แล้วส่ง TGT พร้อมข้อมูลนั้นไปยัง TGS พร้อมระบุ SPN ของบริการที่ต้องการ

ขั้นที่สี่ TGS ตรวจ TGT และข้อมูลยืนยันตัวตน หากถูกต้องจะสร้างตั๋วบริการซึ่งเข้ารหัสด้วยกุญแจของบัญชีที่รันบริการนั้น แล้วส่งกลับพร้อมกุญแจเซสชันใหม่

ขั้นที่ห้า ไคลเอนต์ส่งตั๋วบริการไปยังบริการปลายทาง บริการถอดรหัสตั๋วด้วยกุญแจของตัวเอง ตรวจข้อมูลสิทธิ์ใน PAC และตัดสินใจอนุญาตหรือปฏิเสธตามสิทธิ์นั้น

ตั๋ว TGT ไม่ได้เก็บรหัสผ่านของผู้ใช้ แต่เก็บข้อมูลที่ใช้ยืนยันตัวตนและกุญแจเซสชัน ซึ่งเพียงพอต่อการขอตั๋วบริการในนามของผู้ใช้ ตั๋วนี้จึงมีค่าเทียบเท่ารหัสผ่านในช่วงอายุของมัน และเป็นเหตุผลที่การป้องกันไม่ให้ตั๋วรั่วไหลสำคัญเท่ากับการป้องกันรหัสผ่าน

ตั๋วบริการถูกเข้ารหัสด้วยกุญแจของบัญชีที่รันบริการ ซึ่งหมายความว่าผู้ที่ได้ตั๋วใบนี้สามารถนำไปทดลองเดารหัสผ่านของบัญชีนั้นแบบไม่จำกัดจำนวนครั้งได้ กลไกนี้เป็นพื้นฐานของ Kerberoasting ในบทถัดไป และเป็นเหตุผลที่รหัสผ่านของบัญชีบริการต้องยาวและสุ่มเพียงพอ

ข้อมูลสิทธิ์ของผู้ใช้ถูกบรรจุใน PAC ซึ่งลงนามโดย KDC บริการปลายทางใช้ PAC ตัดสินสิทธิ์โดยไม่ต้องสอบถามโดเมนคอนโทรลเลอร์ทุกครั้ง การปลอมแปลง PAC จึงต้องใช้กุญแจของ KDC ซึ่งเป็นสิ่งที่ผู้โจมตีต้องการที่สุด

เวลาและอายุของตั๋ว

Kerberos อาศัยการเทียบเวลาอย่างเคร่งครัด เพราะข้อมูลยืนยันตัวตนมีเวลากำกับและถูกปฏิเสธหากต่างจากเวลาของ KDC เกินค่าที่กำหนด ซึ่งโดยทั่วไปคือห้านาที ความคลาดเคลื่อนนี้เกิดได้จากนาฬิกาของเครื่องที่ไม่ซิงโครไนซ์ และเป็นสาเหตุที่พบบ่อยของการเข้าสู่ระบบล้มเหลวในห้องแล็บ

ตั๋ว TGT มีอายุเริ่มต้นสิบชั่วโมงและต่ออายุได้ไม่เกินเจ็ดวันตามค่าเริ่มต้นของโดเมน ตั๋วบริการมีอายุเท่ากัน องค์กรสามารถปรับค่าเหล่านี้ได้ผ่านนโยบายกลุ่ม การอ่านค่าอายุจากตั๋วช่วยให้ผู้ทดสอบรู้ว่าตนมีเวลาเท่าใดก่อนต้องยืนยันตัวตนใหม่

เวลายังใช้ในการตรวจจับด้วย เพราะตั๋วที่ถูกนำกลับมาใช้ใหม่หลังเวลาที่ควรหมดอายุ หรือตั๋วที่ออกให้ผู้ใช้ในเวลาที่ผู้ใช้ไม่ได้ทำงาน เป็นสัญญาณที่ควรตรวจ

ชนิดการเข้ารหัสและความสำคัญต่อการทดสอบ

Kerberos รองรับการเข้ารหัสหลายชนิด แต่ที่พบบ่อยใน Active Directory คือ RC4-HMAC และ AES-128 กับ AES-256 ระบบรุ่นใหม่มักใช้ AES เป็นหลัก แต่ยังคงเปิด RC4 ไว้เพื่อความเข้ากันได้กับระบบรุ่นเก่า

ความแตกต่างนี้สำคัญเพราะตั๋วที่เข้ารหัสด้วย RC4 ใช้เวลาในการทดลองรหัสผ่านน้อยกว่าตั๋วที่เข้ารหัสด้วย AES มาก ผู้ทดสอบจึงมักขอตั๋วที่ใช้ RC4 เมื่อทำได้ และฝ่ายป้องกันควรปิด RC4 ในระบบที่ไม่มีเหตุจำเป็นต้องใช้

การกำหนดชนิดการเข้ารหัสทำได้ทั้งระดับโดเมนและระดับบัญชีผ่านแอตทริบิวต์ msDS-SupportedEncryptionTypes การเห็นบัญชีที่อนุญาตเฉพาะ RC4 เป็นสัญญาณว่าระบบอาจมีซอฟต์แวร์เก่าที่ผูกกับชนิดนี้

การมอบสิทธิ์และการเคลื่อนที่ในภาพรวม

Kerberos มีกลไกมอบสิทธิ์ (Delegation) ที่อนุญาตให้บริการหนึ่งเข้าถึงบริการอื่นในนามของผู้ใช้ กลไกนี้มีสามรูปแบบคือแบบไม่จำกัด แบบจำกัด และแบบอิงทรัพยากร แต่ละรูปแบบมีเงื่อนไขและความเสี่ยงต่างกัน

การมอบสิทธิ์แบบไม่จำกัดอนุญาตให้บริการที่ได้รับความเชื่อถือขอตั๋วให้บริการใดก็ได้ในนามผู้ใช้ หากบริการนั้นถูกยึด ผู้โจมตีสามารถใช้สิทธิ์ของผู้ใช้ทุกคนที่เคยเข้ามาใช้บริการนั้นได้ ซึ่งเป็นความเสี่ยงระดับสูงที่บทถัดไปจะกล่าวถึง

การมอบสิทธิ์แบบจำกัดระบุรายชื่อบริการปลายทางที่อนุญาต และการมอบสิทธิ์แบบอิงทรัพยากรกำหนดที่ตัวทรัพยากรแทนที่จะกำหนดที่บริการต้นทาง องค์กรที่จำเป็นต้องใช้กลไกนี้ควรเลือกแบบที่แคบที่สุดและตรวจรายการที่อนุญาตเป็นระยะ

Kerberos กับ NTLM

แม้ Kerberos เป็นกลไกหลัก แต่ Active Directory ยังรองรับ NTLM เพื่อความเข้ากันได้กับระบบเก่าและการเข้าถึงด้วยชื่อเครื่องโดยตรง NTLM ทำงานต่างจาก Kerberos โดยใช้การท้าทายและตอบกลับด้วยค่าแฮชของรหัสผ่าน ไม่มีการออกตั๋ว

การมี NTLM อยู่ในระบบทำให้เกิดความเสี่ยงที่ Kerberos ไม่มี เช่น การใช้แฮชแทนรหัสผ่านได้โดยตรง หากผู้โจมตีได้ค่าแฮชก็สามารถยืนยันตัวตนได้โดยไม่ต้องรู้รหัสผ่านจริง กลไกนี้จะกล่าวถึงในบทถัดไป

ฝ่ายป้องกันจึงพยายามลดการใช้ NTLM โดยปิดในระบบที่ไม่จำเป็น เปิดการบังคับใช้การลงนาม และตรวจระบบที่ยังพึ่งพา NTLM อยู่ การสำรวจที่ดีควรบันทึกด้วยว่าระบบใดยังอนุญาต NTLM เพราะเป็นข้อมูลที่ใช้ประเมินความเสี่ยงได้

รหัสข้อผิดพลาดที่ใช้ในการอ่านบันทึก

เมื่อการยืนยันตัวตนล้มเหลว KDC จะส่งรหัสข้อผิดพลาดกลับมา รหัสเหล่านี้ปรากฏในบันทึกเหตุการณ์ของโดเมนคอนโทรลเลอร์และช่วยแยกสาเหตุได้ เช่นแยกระหว่างรหัสผ่านผิดกับบัญชีถูกล็อกหรือบัญชีถูกปิด

13.4 การสำรวจผ่าน LDAP

LDAP คืออะไรและทำไมจึงเป็นช่องทางหลัก

LDAP (Lightweight Directory Access Protocol) เป็นโปรโตคอลมาตรฐานสำหรับสอบถามและแก้ไขข้อมูลในไดเรกทอรี Active Directory เปิดให้เข้าถึงผ่าน LDAP ตามมาตรฐานนี้โดยตรง จึงไม่จำเป็นต้องใช้เครื่องมือเฉพาะของผู้ผลิตก็สามารถอ่านข้อมูลได้

โครงสร้างข้อมูลของ LDAP เป็นลำดับชั้นแบบต้นไม้ แต่ละโหนดเรียกว่ารายการ (Entry) และมีแอตทริบิวต์กำกับ รายการหนึ่งมี DN เป็นชื่อเฉพาะ และการสอบถามจะระบุจุดเริ่มต้น (Base DN) ขอบเขตการค้นหา และตัวกรอง (Filter)

ความได้เปรียบของ LDAP เหนือวิธีอื่นคือมันเป็นช่องทางที่ถูกออกแบบมาให้ระบบภายนอกใช้ จึงมักเปิดไว้ในทุกโดเมน และให้ข้อมูลมากกว่าที่ผู้ใช้ทั่วไปคาด เช่นรายชื่อผู้ใช้ กลุ่ม คอมพิวเตอร์ นโยบาย และความเชื่อถือระหว่างโดเมน

จุดเริ่มต้นของโครงสร้าง

เมื่อเชื่อมต่อกับเซิร์ฟเวอร์ LDAP แล้ว ผู้ทดสอบสามารถสอบถามรายการพิเศษชื่อ rootDSE ซึ่งให้ข้อมูลเกี่ยวกับเซิร์ฟเวอร์และตำแหน่งของฐานข้อมูลแต่ละส่วน รายการนี้ไม่ต้องยืนยันตัวตนในระบบส่วนใหญ่และเป็นจุดเริ่มต้นที่ดีที่สุด

ค่าที่สำคัญใน rootDSE ได้แก่ defaultNamingContext ซึ่งบอก DN ของโดเมนหลัก configurationNamingContext ซึ่งบอกตำแหน่งของข้อมูลการตั้งค่า และ rootDomainNamingContext ซึ่งบอก DN ของโดเมนรากของป่า

ในห้องแล็บ ผู้ทดสอบมักเริ่มด้วยการอ่าน rootDSE เพื่อยืนยันว่าบริการ LDAP ตอบสนองและได้ DN ที่ถูกต้อง ก่อนจะเขียนคำสั่งสอบถามที่มีตัวกรองซับซ้อนขึ้น

โครงสร้างคำสั่ง ldapsearch

ldapsearch เป็นเครื่องมือบรรทัดคำสั่งที่มากับแพ็กเกจไคลเอนต์ LDAP บนลินุกซ์และแมคโอเอส รูปแบบคำสั่งประกอบด้วยที่อยู่เซิร์ฟเวอร์ วิธียืนยันตัวตน จุดเริ่มต้น ตัวกรอง และรายชื่อแอตทริบิวต์ที่ต้องการ

ldapsearch -x -H ldap://10.10.10.10:389 \
  -D "svc-backup@corp.local" -W \
  -b "DC=corp,DC=local" \
  "(objectCategory=person)" sAMAccountName displayName memberOf

ตัวเลือก -x หมายถึงใช้การยืนยันตัวตนแบบง่าย (Simple Bind) ซึ่งส่งชื่อและรหัสผ่านในคำขอ ตัวเลือก -H ระบุที่อยู่ของเซิร์ฟเวอร์ และ -W ให้โปรแกรมถามรหัสผ่านแทนการพิมพ์ในบรรทัดคำสั่ง ซึ่งป้องกันรหัสผ่านถูกบันทึกในประวัติคำสั่ง

ตัวเลือก -D ระบุชื่อที่ใช้ยืนยันตัวตน ซึ่งอาจเป็นรูปแบบ ชื่อ@โดเมน หรือ DN เต็ม ตัวเลือก -b ระบุ Base DN และตัวกรองอยู่ในวงเล็บตามด้วยรายชื่อแอตทริบิวต์ที่ต้องการ หากไม่ระบุแอตทริบิวต์ โปรแกรมจะคืนค่าทั้งหมดของรายการซึ่งทำให้ผลยาวเกินจำเป็น

การใช้การยืนยันตัวตนแบบง่ายผ่านการเชื่อมต่อที่ไม่เข้ารหัสเป็นความเสี่ยง เพราะรหัสผ่านเดินทางในเครือข่ายแบบอ่านได้ องค์กรที่ดีจึงเปิดการบังคับใช้การลงนาม LDAP หรือใช้ LDAPS บนพอร์ต 636 ผู้ทดสอบควรใช้ LDAPS เมื่อระบบรองรับ และควรใช้บัญชีที่ได้รับอนุญาตสำหรับการทดสอบเท่านั้น

ค่าของ lastLogonTimestamp และ pwdLastSet ถูกเก็บในรูปแบบเวลาแบบ FILETIME ซึ่งนับจำนวนช่วง 100 นาโนวินาทีตั้งแต่ปี ค.ศ. 1601 การอ่านค่าจึงต้องแปลงก่อนจึงจะเข้าใจ หรือใช้เครื่องมือที่แปลงให้

ข้อจำกัดที่ทำให้ผลไม่ครบ

การสอบถาม LDAP มักไม่คืนผลทั้งหมดในครั้งเดียว เพราะ Active Directory จำกัดจำนวนรายการต่อการค้นหา โดยค่าเริ่มต้นอยู่ที่หนึ่งพันรายการ หากผลมีมากกว่านั้น เซิร์ฟเวอร์จะส่งเพียงบางส่วนและแจ้งว่าถึงขีดจำกัด

การแก้ไขคือใช้การแบ่งหน้า (Paged Results) ซึ่ง ldapsearch รองรับผ่านตัวเลือก -E pr=1000/noprompt การไม่ใช้ตัวเลือกนี้เป็นสาเหตุที่พบบ่อยที่สุดของการสรุปผิดว่าองค์กรมีผู้ใช้เพียงหนึ่งพันคน

ข้อจำกัดอีกประการคือสิทธิ์ในการอ่านแอตทริบิวต์บางตัว ผู้ใช้ทั่วไปอาจอ่านแอตทริบิวต์พื้นฐานได้ แต่ไม่สามารถอ่านแอตทริบิวต์ที่เกี่ยวกับสิทธิ์หรือข้อมูลส่วนบุคคล การเห็นค่าว่างจึงไม่ได้แปลว่าไม่มีข้อมูล

การอ่านผลให้เป็นระบบ

ผลของ ldapsearch อยู่ในรูปแบบข้อความที่แยกแต่ละรายการด้วยบรรทัดว่าง แต่ละรายการเริ่มด้วย dn: ตามด้วยแอตทริบิวต์ที่ร้องขอ การอ่านด้วยตาทำได้เมื่อผลสั้น แต่เมื่อผลยาวควรแปลงเป็นรูปแบบที่จัดการได้ง่ายกว่า

วิธีที่ตรงไปตรงมาคือใช้ grep เพื่อดึงเฉพาะบรรทัดที่สนใจ เช่นการนับจำนวนบัญชีหรือดูรายชื่อกลุ่ม แต่การนับด้วยวิธีนี้อาจผิดหากแอตทริบิวต์บางตัวมีหลายบรรทัด วิธีที่ปลอดภัยกว่าคือใช้เครื่องมือแปลงเป็น JSON หรือ CSV แล้วประมวลผลด้วยสคริปต์

การบันทึกผลควรเก็บทั้งคำสั่งเต็ม วันที่ และบัญชีที่ใช้ยืนยันตัวตน เพราะผลเดียวกันอาจต่างกันเมื่อใช้บัญชีต่างกัน และเมื่อนำไปรายงานต้องอธิบายได้ว่าข้อมูลได้มาอย่างไร

ในทางปฏิบัติ การสอบถามด้วย LDAP ให้ข้อมูลที่แม่นยำและควบคุมขอบเขตได้ดีกว่าการใช้เครื่องมืออัตโนมัติ จึงควรใช้เป็นวิธีหลักในการยืนยันผลที่เครื่องมืออื่นรายงาน และใช้เครื่องมืออัตโนมัติเป็นเพียงตัวช่วยหาว่าควรสอบถามอะไร

13.5 เครื่องมือสำรวจ: enum4linux และ PowerView

บทบาทของเครื่องมืออัตโนมัติ

เครื่องมืออัตโนมัติช่วยลดเวลาที่ต้องพิมพ์คำสั่งซ้ำและช่วยให้เห็นภาพรวมเร็วขึ้น แต่ข้อเสียคือมันรวมการสอบถามหลายอย่างไว้ด้วยกันและรายงานผลในรูปแบบที่ผู้ใช้ต้องตีความเอง ผู้เรียนจึงต้องเข้าใจว่าผลแต่ละส่วนมาจากการสอบถามใด เพื่อแยกได้ว่าสิ่งใดเป็นข้อเท็จจริงและสิ่งใดเป็นข้อสันนิษฐาน

หลักที่ควรยึดคือใช้เครื่องมืออัตโนมัติเพื่อหาว่าควรถามอะไร จากนั้นใช้คำสั่งพื้นฐานยืนยันคำตอบทีละข้อ วิธีนี้ทำให้ผลในรายงานมีน้ำหนักและลดข้อผิดพลาดจากการเชื่อผลของเครื่องมือโดยตรง

enum4linux

enum4linux เป็นสคริปต์ที่รวมคำสั่งหลายตัวไว้ด้วยกันเพื่อสำรวจระบบผ่าน SMB และ RPC โดยอาศัยเครื่องมือในระบบเช่น rpcclient, net และ nmblookup มันถูกออกแบบมาในยุคที่ระบบจำนวนมากเปิดให้เข้าถึงแบบไม่ต้องยืนยันตัวตน (Null Session) ซึ่งทำให้ได้ข้อมูลรายชื่อผู้ใช้และกลุ่มโดยไม่ต้องมีบัญชี

ใน Active Directory รุ่นใหม่ การเข้าถึงแบบไม่ต้องยืนยันตัวตนมักถูกปิด จึงได้ข้อมูลเพียงบางส่วน เช่นชื่อโดเมน ชื่อเครื่อง และเวอร์ชันระบบ แต่ในระบบที่ยังอนุญาต อาจได้รายชื่อผู้ใช้ กลุ่ม แชร์ไฟล์ และนโยบายรหัสผ่าน

การเรียกใช้พื้นฐานที่สุดคือสั่งให้ตรวจทุกอย่างที่ทำได้แล้วบันทึกผลลงไฟล์ เพื่อให้ย้อนอ่านและอ้างอิงในรายงานได้

enum4linux -a 10.10.10.10 | tee enum4linux-dc01.txt

ผลลัพธ์ถูกแบ่งเป็นหัวข้อตามตัวเลือกย่อย ผู้ทดสอบควรอ่านหัวข้อ Domain Name, Domain Sid, Users on 10.10.10.10 และ Password Policy Information ก่อน เพราะสี่ส่วนนี้ตอบคำถามว่าโดเมนชื่ออะไร มีบัญชีใดบ้าง และทดลองรหัสผ่านได้กี่ครั้ง ส่วนหัวข้อที่แสดงข้อความแจ้งข้อผิดพลาด เช่น RPC call failed หรือ Access denied ไม่ใช่ข้อมูลที่ใช้สรุปผลได้ แต่เป็นสัญญาณว่าระบบปิดการเข้าถึงแบบไม่ต้องยืนยันตัวตน

หากติดตั้ง enum4linux-ng ไว้ สามารถใช้คำสั่งเดียวที่ให้ผลเทียบเท่าและเขียนออกเป็น JSON เพื่อประมวลผลต่อได้

enum4linux-ng -A 10.10.10.10 -oJ enum4linux-dc01

ข้อควรระวังคือ enum4linux จะรายงานสิ่งที่พบโดยไม่แยกว่าสิ่งใดเป็นสิทธิ์จริง สิ่งใดเป็นเพียงข้อมูลที่อ่านได้ และสิ่งใดเป็นข้อความแจ้งข้อผิดพลาด การนำผลไปสรุปว่า "พบบัญชีผู้ใช้จำนวนมาก" โดยไม่ตรวจว่าบัญชีเหล่านั้นยังใช้งานหรือไม่เป็นข้อผิดพลาดที่พบบ่อย

PowerView

PowerView เป็นชุดคำสั่ง PowerShell สำหรับสอบถาม Active Directory โดยเรียกใช้ API ของระบบโดยตรง มันให้ข้อมูลที่ละเอียดกว่าเครื่องมือทั่วไปเพราะสามารถอ่านแอตทริบิวต์ สิทธิ์บนวัตถุ และความสัมพันธ์ระหว่างวัตถุได้ในคำสั่งเดียว

PowerView ต้องรันบนเครื่องที่สามารถติดต่อโดเมนได้ และต้องมีสิทธิ์อ่านข้อมูลตามที่บัญชีนั้นมี คำสั่งส่วนใหญ่ทำงานในหน่วยความจำและไม่เขียนไฟล์ลงดิสก์ แต่ก็ยังถูกบันทึกโดยระบบตรวจสอบของวินโดวส์

สองคำสั่งแรกยืนยันว่าผู้ทดสอบติดต่อโดเมนได้และโดเมนคอนโทรลเลอร์เครื่องใดให้บริการอยู่ คำสั่งที่สามแสดงบัญชีที่มีชื่อบริการผูกอยู่ ซึ่งเป็นรายการเป้าหมายของ Kerberoasting ในบทถัดไป ผู้ทดสอบควรบันทึกทั้งชื่อบัญชีและชื่อบริการ เพราะชื่อบริการบอกว่าบริการนั้นรันบนเครื่องใดและใช้ซอฟต์แวร์อะไร

เมื่อต้องการดูว่าใครมีสิทธิ์แก้ไขบัญชีใด ให้เรียก Get-ObjectAcl กับวัตถุนั้นแล้วกรองเฉพาะสิทธิ์ที่ให้อำนาจเขียนหรือควบคุม

Get-ObjectAcl -SamAccountName svc-backup -ResolveGUIDs | Where-Object { $_.ActiveDirectoryRights -match 'Write|GenericAll|GenericWrite' }

ผลที่ได้จะบอกว่าวัตถุใดมีสิทธิ์บนบัญชีนี้และสิทธิ์นั้นคืออะไร ซึ่งเป็นข้อมูลตั้งต้นของการอ่านเส้นทางในหัวข้อ 13.6 การกรองด้วยชื่อสิทธิ์แทนการอ่านทั้งรายการช่วยลดปริมาณผลลัพธ์ที่ต้องตรวจด้วยตา

ข้อจำกัดและร่องรอยของเครื่องมือ

เครื่องมือสำรวจทุกตัวทิ้งร่องรอย เพราะการอ่านข้อมูลจากโดเมนต้องมีการยืนยันตัวตนและการสอบถามที่เซิร์ฟเวอร์บันทึกไว้ ระดับของร่องรอยต่างกันตามวิธีที่เครื่องมือใช้

enum4linux สร้างการเชื่อมต่อ SMB หลายครั้งและอาจทำให้เกิดการบันทึกการเข้าสู่ระบบล้มเหลวจำนวนมากหากระบบปิดการเข้าถึงแบบไม่ยืนยันตัวตน ผลคือผู้ดูแลระบบอาจเห็นความพยายามเข้าถึงที่ผิดปกติและระงับบัญชีที่ใช้

PowerView ทำงานผ่าน PowerShell จึงถูกบันทึกในบันทึกสคริปต์บล็อก (Event ID 4104) และบันทึกโมดูล (Event ID 4103) หากองค์กรเปิดการบันทึกเหล่านี้ ผลิตภัณฑ์ป้องกันบางตัวมีลายเซ็นที่ตรวจจับชื่อคำสั่งของ PowerView โดยตรง การเปลี่ยนชื่อคำสั่งไม่ใช่การอำพรางที่มีประสิทธิผล

BloodHound ซึ่งจะกล่าวถึงในหัวข้อถัดไป สร้างการเชื่อมต่อมากที่สุดเพราะต้องเก็บข้อมูลจากหลายแหล่ง การเก็บข้อมูลแบบสมบูรณ์อาจใช้เวลานานและสร้างภาระต่อโดเมนคอนโทรลเลอร์อย่างเห็นได้ชัด

ตาราง 13.18 ร่องรอยและข้อจำกัดของเครื่องมือแต่ละชนิด

enum4linuxSMB และ RPCการเข้าสู่ระบบและการสอบถาม RPCมักถูกจำกัดด้วยการปิด Null Session
PowerViewAPI ของระบบผ่าน PowerShellบันทึกสคริปต์บล็อกและโมดูลต้องรันบนเครื่องที่ติดต่อโดเมนได้

คำสั่ง netRPC และ SMBการสอบถามบัญชีและกลุ่มให้ข้อมูลน้อยและตีความง่าย

การเลือกใช้เครื่องมือตามสถานการณ์

เมื่อมีเวลาไม่จำกัดและต้องการข้อมูลครบ การใช้ ldapsearch กับตัวกรองที่ออกแบบเองให้ผลที่ควบคุมได้และตรวจสอบได้ง่ายที่สุด เมื่อต้องการภาพรวมเร็ว การใช้ PowerView หรือ BloodHound ช่วยชี้จุดที่ควรตรวจต่อ แต่ควรยืนยันผลด้วยคำสั่งพื้นฐานทุกครั้ง

ในระบบที่การเชื่อมต่อภายนอกถูกจำกัด ควรใช้เครื่องมือที่ทำงานผ่านช่องทางที่ได้รับอนุญาต เช่นผ่านเครื่องกระโดด (Jump Host) ที่องค์กรจัดไว้ให้ และควรแจ้งผู้ดูแลระบบก่อนเริ่มเก็บข้อมูลจำนวนมาก เพื่อไม่ให้กิจกรรมถูกเข้าใจผิดว่าเป็นการบุกรุก

เมื่อได้ข้อมูลดิบครบแล้ว ขั้นต่อไปคือการแปลงข้อมูลเหล่านั้นเป็นภาพของความสัมพันธ์ ซึ่งเป็นสิ่งที่ BloodHound ทำและเป็นหัวข้อของส่วนถัดไป

13.6 BloodHound และการอ่านเส้นทางการโจมตี

แนวคิดฐานข้อมูลกราฟ

เครื่องมือสำรวจทั่วไปตอบคำถามแบบตรงไปตรงมา เช่น "ผู้ใช้คนนี้เป็นสมาชิกกลุ่มใด" แต่คำถามที่สำคัญกว่าในงานทดสอบคือ "จากบัญชีที่ฉันถืออยู่ ไปถึงสิทธิ์ระดับโดเมนได้ด้วยเส้นทางใด" คำถามนี้ต้องอาศัยการเชื่อมความสัมพันธ์หลายทอด ซึ่งเป็นสิ่งที่ฐานข้อมูลกราฟทำได้ดี

ฐานข้อมูลกราฟเก็บข้อมูลเป็นสองชนิดคือโหนด (Node) ซึ่งแทนวัตถุ เช่นผู้ใช้ กลุ่ม หรือคอมพิวเตอร์ และเส้นเชื่อม (Edge) ซึ่งแทนความสัมพันธ์ระหว่างวัตถุ เช่นการเป็นสมาชิก การมีสิทธิ์ผู้ดูแล หรือการมีเซสชันอยู่ เส้นเชื่อมมีทิศทางและมีชนิดที่บอกความหมาย

BloodHound เป็นเครื่องมือที่เก็บข้อมูลจาก Active Directory แล้วสร้างกราฟจากข้อมูลนั้น จากนั้นผู้ใช้สามารถถามเส้นทางที่สั้นที่สุดจากโหนดหนึ่งไปยังอีกโหนดหนึ่งได้ ซึ่งช่วยให้เห็นเส้นทางที่ตาเปล่ามองไม่เห็นเพราะข้อมูลกระจายอยู่หลายที่

การเก็บข้อมูล

ข้อมูลเข้าสู่ BloodHound ผ่านตัวเก็บข้อมูล (Collector) ที่ทำงานบนเครื่องในโดเมน ตัวหลักคือ SharpHound ซึ่งเป็นโปรแกรมที่รวบรวมข้อมูลผ่าน LDAP, SMB, RPC และ WMI แล้วส่งออกเป็นไฟล์บีบอัดที่มีข้อมูลแบบ JSON

การเก็บข้อมูลมีหลายระดับตามความครบถ้วน ระดับที่เบาที่สุดอ่านเฉพาะข้อมูลจากโดเมนคอนโทรลเลอร์ เช่นผู้ใช้ กลุ่ม สิทธิ์บนวัตถุ และนโยบาย ซึ่งให้ข้อมูลเพียงพอต่อการวิเคราะห์เส้นทางเชิงโครงสร้าง แต่ไม่มีข้อมูลว่าใครเข้าสู่ระบบที่ใด

ระดับที่ครบกว่ารวมการตรวจสิทธิ์ผู้ดูแลท้องถิ่นบนเครื่องลูกข่าย การอ่านเซสชันที่เปิดอยู่ และการอ่านผู้ใช้ที่เข้าสู่ระบบ ซึ่งต้องอาศัยสิทธิ์ผู้ดูแลบนเครื่องเหล่านั้นและสร้างการเชื่อมต่อจำนวนมาก

การเก็บข้อมูลด้วย SharpHound และ bloodhound-python

การเก็บข้อมูลแบบสมบูรณ์ทำได้ด้วยคำสั่งเดียวบนเครื่องที่เข้าสู่โดเมนและมีสิทธิ์ตามที่ต้องการ

SharpHound.exe -c All --zipfilename corp-local.zip

ตัวเลือก -c All สั่งให้เก็บทุกหมวดหมู่ที่บัญชีนั้นเข้าถึงได้ รวมถึงเซสชันและสิทธิ์ผู้ดูแลท้องถิ่น ซึ่งใช้เวลานานและสร้างการเชื่อมต่อมาก หากต้องการเฉพาะข้อมูลเชิงโครงสร้างที่อ่านได้จากโดเมนคอนโทรลเลอร์ ให้ใช้ -c DCOnly ซึ่งเร็วและเบากว่า แต่จะไม่เห็นว่าใครมีเซสชันอยู่บนเครื่องใด

ในสภาพแวดล้อมที่ไม่มีเครื่องวินโดวส์สำหรับรัน SharpHound สามารถเก็บข้อมูลจากลินุกซ์ด้วย bloodhound-python โดยระบุโดเมน โดเมนคอนโทรลเลอร์ และบัญชีที่ใช้

bloodhound-python -d corp.local -ns 10.10.10.10 -u svc-backup -p '<รหัสผ่าน>' -c All

ผลลัพธ์จากทั้งสองวิธีเป็นไฟล์ ZIP ที่บรรจุ JSON ชุดเดียวกัน ซึ่งนำเข้าสู่หน้าจอ BloodHound ผ่านเมนูอัปโหลด หลังนำเข้าแล้วจึงเริ่มถามเส้นทางจากบัญชีที่ถืออยู่ไปยังกลุ่มผู้ดูแลโดเมน และบันทึกเส้นทางที่พบลงในบันทึกผลพร้อมหลักฐานว่าข้อมูลส่วนใดเป็นข้อเท็จจริงจากโดเมน

ตัวอย่างที่ผู้เริ่มต้นมักเข้าใจผิดคือ HasSession ซึ่งบอกว่าผู้ใช้มีเซสชันอยู่บนเครื่อง ไม่ได้หมายความว่าผู้ใช้คนนั้นเป็นผู้ดูแลเครื่อง แต่หมายความว่าหากยึดเครื่องได้ อาจได้ข้อมูลยืนยันตัวตนของผู้ใช้คนนั้นจากหน่วยความจำ ซึ่งเป็นจุดเชื่อมไปสู่สิทธิ์ที่ผู้ใช้ถืออยู่

การอ่านเส้นทางจากบัญชีธรรมดาไปสู่สิทธิ์สูง

BloodHound มีคำสั่งสำเร็จรูปที่ตอบคำถามที่พบบ่อย ที่มีประโยชน์ที่สุดคือการหาเส้นทางที่สั้นที่สุดจากบัญชีที่ผู้ทดสอบถืออยู่ไปยังกลุ่มที่มีสิทธิ์สูง เช่น Domain Admins หรือ Enterprise Admins

เส้นทางหนึ่งทอดอาจเป็น svc-backup → GenericAll → Helpdesk → MemberOf → Domain Admins ซึ่งแปลว่าบัญชีบริการสามารถแก้ไขสิทธิ์ของกลุ่ม Helpdesk และกลุ่มนั้นเป็นสมาชิกของ Domain Admins การอ่านเส้นทางต้องอ่านทีละเส้นเชื่อมและตรวจว่าเงื่อนไขของแต่ละเส้นเป็นจริง

เส้นทางที่ยาวไม่ได้แปลว่าใช้ไม่ได้ แต่ละขั้นต้องมีเงื่อนไขครบ เช่นต้องมีสิทธิ์บนเครื่อง ต้องมีเซสชัน ต้องรู้รหัสผ่าน หรือต้องรอให้ผู้ใช้เข้าสู่ระบบ ความเป็นไปได้จริงจึงขึ้นกับสภาพแวดล้อมและเวลา

ตาราง 13.21 ตัวอย่างการอ่านเส้นทางและคำถามที่ต้องตอบ
เส้นทางสิ่งที่ต้องตรวจความเป็นไปได้
ผู้ใช้ → MemberOf → กลุ่มที่มีสิทธิ์สูงกลุ่มนั้นมีสิทธิ์อะไรจริงสูง หากกลุ่มมีสิทธิ์ผู้ดูแล
ผู้ใช้ → GenericAll → บัญชีอื่นบัญชีปลายทางมีสิทธิ์อะไรสูง หากปลายทางมีสิทธิ์มากกว่า
ผู้ใช้ → AdminTo → เครื่องเครื่องนั้นมีเซสชันของใครกลาง ขึ้นกับผู้ใช้ที่เข้าสู่ระบบ
ผู้ใช้ → HasSession → เครื่องเครื่องนั้นถูกยึดได้หรือไม่กลาง ต้องยึดเครื่องก่อน
ผู้ใช้ → DCSync → โดเมนสิทธิ์นั้นมาจากกลุ่มใดสูงมาก หากทำได้จริง
ผู้ใช้ → ReadLAPSPassword → เครื่องรหัสผ่านยังใช้ได้หรือไม่กลาง ขึ้นกับการเปลี่ยนรหัส

ข้อจำกัดของกราฟ

กราฟแสดงความสัมพันธ์จากข้อมูลที่เก็บ ณ เวลาหนึ่ง จึงมีข้อจำกัดที่ผู้ใช้ต้องตระหนัก ข้อแรกคือข้อมูลเซสชันเก่าได้เร็ว เพราะผู้ใช้เข้าออกเครื่องตลอดวัน การวิเคราะห์จากข้อมูลที่เก็บเมื่อหลายวันก่อนอาจชี้เส้นทางที่ใช้ไม่ได้แล้ว

ข้อที่สองคือการเก็บข้อมูลบางประเภทต้องมีสิทธิ์ผู้ดูแล หากเก็บจากบัญชีที่มีสิทธิ์น้อย ข้อมูลสิทธิ์ผู้ดูแลท้องถิ่นและเซสชันจะไม่ครบ กราฟจึงดูเหมือนไม่มีเส้นทางทั้งที่อาจมีอยู่

ข้อที่สามคือเส้นเชื่อมบางอย่างเกิดจากพฤติกรรมปกติของระบบ เช่นสมาชิกกลุ่ม Domain Users ที่เป็นผู้ดูแลเครื่องบางเครื่องตามนโยบายเริ่มต้น การเห็นเส้นทางจึงไม่ได้แปลว่าองค์กรมีช่องโหว่ แต่ต้องประเมินว่าสภาพนั้นยอมรับได้หรือไม่

ข้อที่สี่คือกราฟไม่รู้ว่าบริการใดทำงานอยู่จริง หรือไฟล์ใดถูกป้องกันด้วยระบบบังคับนโยบาย การยืนยันจึงต้องทำด้วยการทดสอบในขอบเขตที่อนุญาต ไม่ใช่สรุปจากกราฟเพียงอย่างเดียว

ตาราง 13.22 ข้อจำกัดของ BloodHound และวิธีชดเชย
ข้อจำกัดผลต่อการวิเคราะห์วิธีชดเชย
ข้อมูลเซสชันเก่าเส้นทางที่เห็นอาจใช้ไม่ได้แล้วเก็บข้อมูลใหม่ก่อนสรุป
สิทธิ์ของบัญชีที่ใช้เก็บจำกัดข้อมูลไม่ครบใช้บัญชีที่ได้รับอนุญาตและระบุข้อจำกัด
เส้นทางจากพฤติกรรมปกติเข้าใจผิดว่าเป็นช่องโหว่ตรวจบริบทและนโยบายขององค์กร
ไม่รู้สถานะบริการจริงประเมินผลกระทบคลาดเคลื่อนตรวจพอร์ตและบริการประกอบ
ไม่รู้การป้องกันระดับวัตถุเส้นทางอาจถูกบล็อกทดสอบในขอบเขตที่กำหนด
ข้อมูลขนาดใหญ่วิเคราะห์ไม่ครบใช้คำสั่งเจาะจงแทนการดูทั้งกราฟ

การใช้กราฟอย่างมีความรับผิดชอบ

การเก็บข้อมูลด้วย BloodHound สร้างการเชื่อมต่อจำนวนมากและอาจกระทบสมรรถนะของโดเมนคอนโทรลเลอร์ หากเก็บในช่วงเวลาทำงานขององค์กร ควรแจ้งผู้ดูแลระบบและเลือกช่วงเวลาที่เหมาะสม

ข้อมูลที่ได้มีข้อมูลส่วนบุคคลและข้อมูลสิทธิ์ของทั้งองค์กร จึงต้องเก็บอย่างปลอดภัย จำกัดผู้เข้าถึง และลบเมื่อจบงานตามข้อตกลง ไฟล์ข้อมูลของ BloodHound ไม่ควรถูกทิ้งไว้ในเครื่องเป้าหมายหรือเครื่องที่ใช้ร่วมกัน

สุดท้าย การรายงานเส้นทางต้องแยกให้ชัดระหว่างสิ่งที่พิสูจน์แล้วกับสิ่งที่ยังไม่ได้ทดสอบ การเขียนว่า "สามารถยกระดับเป็น Domain Admin ได้" โดยไม่มีหลักฐานการทดสอบทำให้รายงานขาดความน่าเชื่อถือ และอาจทำให้ทีมแก้ไขลงทุนกับเส้นทางที่ใช้ไม่ได้จริง

13.7 Password spraying และความเสี่ยงการล็อกบัญชี

หลักการของ password spraying

การทดลองรหัสผ่านแบบตรงไปตรงมาคือลองหลายรหัสกับบัญชีเดียว ซึ่งจะทำให้บัญชีถูกล็อกอย่างรวดเร็วหากองค์กรตั้งนโยบายล็อกไว้ password spraying กลับทิศทาง โดยใช้รหัสผ่านไม่กี่รหัสทดลองกับบัญชีจำนวนมาก เพื่อให้แต่ละบัญชีมีจำนวนครั้งล้มเหลวไม่ถึงขีดล็อก

วิธีนี้ได้ผลเพราะผู้ใช้จำนวนมากยังตั้งรหัสผ่านที่คาดเดาได้ เช่นชื่อบริษัทตามด้วยปี รหัสผ่านเริ่มต้นที่ผู้ดูแลระบบตั้งให้ และรูปแบบที่ใช้ซ้ำกันในองค์กร แม้แต่ละรหัสจะไม่น่าจะถูก แต่เมื่อลองกับบัญชีหลายร้อยบัญชี โอกาสที่จะมีบางบัญชีใช้รหัสนั้นก็สูง

password spraying ไม่ใช่การโจมตีทางเทคนิคที่อาศัยช่องโหว่ของซอฟต์แวร์ แต่เป็นการใช้พฤติกรรมของมนุษย์และนโยบายที่ผ่อนปรนเกินไป จึงป้องกันได้ด้วยนโยบายรหัสผ่าน การศึกษาผู้ใช้ และการเฝ้าดูพฤติกรรมการยืนยันตัวตน

พารามิเตอร์การล็อกบัญชี

นโยบายล็อกบัญชีของโดเมนกำหนดสามค่าที่ทำงานร่วมกัน ค่าแรกคือจำนวนครั้งที่ล้มเหลวก่อนล็อก (Lockout threshold) ค่าที่สองคือระยะเวลาที่บัญชีถูกล็อก (Lockout duration) และค่าที่สามคือช่วงเวลาที่ระบบนับจำนวนครั้งล้มเหลว (Lockout observation window)

เมื่อผู้ใช้พิมพ์รหัสผิด ระบบจะเพิ่มตัวนับความล้มเหลวของบัญชีนั้น หากจำนวนถึงขีดที่กำหนด บัญชีจะถูกล็อกทันทีและไม่ยอมรับรหัสผ่านใดๆ จนกว่าจะพ้นระยะเวลาที่กำหนดหรือผู้ดูแลระบบปลดล็อก

ตัวนับนี้ถูกรีเซ็ตเมื่อมีการยืนยันตัวตนสำเร็จ หรือเมื่อพ้นช่วงเวลาสังเกตการณ์นับตั้งแต่ความล้มเหลวครั้งล่าสุด ค่าเหล่านี้จึงกำหนดว่าผู้ทดสอบมีโอกาสกี่ครั้งและต้องเว้นระยะนานเท่าใด

ตาราง 13.23 พารามิเตอร์การล็อกบัญชีและผลต่อการทดสอบ
พารามิเตอร์ความหมายผลต่อการวางแผน
Lockout thresholdจำนวนครั้งล้มเหลวก่อนล็อกกำหนดจำนวนครั้งสูงสุดต่อบัญชี
Lockout durationระยะเวลาที่บัญชีถูกล็อกกำหนดผลกระทบหากล็อกโดยไม่ตั้งใจ
Observation windowช่วงเวลาที่นับความล้มเหลวกำหนดระยะห่างระหว่างความพยายาม
badPwdCountตัวนับความล้มเหลวของบัญชีใช้ตรวจสถานะก่อนทดลอง
Fine-grained policyนโยบายแยกตามกลุ่มอาจเข้มกว่าหรือผ่อนกว่าหลัก

การอ่านค่านโยบายบนเครื่องที่อยู่ในโดเมนจะแสดงทั้งขีดล็อก ระยะเวลา และช่วงสังเกตการณ์ หากค่าขีดล็อกเป็นศูนย์หมายความว่าไม่มีการล็อกบัญชี ซึ่งเป็นสภาพที่อันตรายเพราะเปิดโอกาสให้ทดลองรหัสผ่านได้ไม่จำกัด

ก่อนทดลองจริงควรอ่านค่านโยบายด้วยคำสั่งนี้และจดค่าทั้งสามไว้ในบันทึกผล

net accounts /domain

จากนั้นตรวจว่านโยบายเดียวกันนี้เปิดให้สอบถามผ่าน SMB ได้หรือไม่ และยืนยันว่ารหัสผ่านที่เตรียมไว้ใช้ได้จริงกับบัญชีทดสอบเพียงบัญชีเดียวก่อนเริ่มรอบแรก

nxc smb 10.10.10.10 -u svc-backup -p '<รหัสผ่าน>' --pass-pol

ตัวอย่างการทดลองแบบกระจายที่ควบคุมจำนวนครั้งได้ ใช้รายชื่อบัญชีจากขั้นสำรวจและรหัสผ่านเดียวต่อรอบ ตัวเลือก --continue-on-success สั่งให้ทำต่อแม้พบบัญชีที่สำเร็จ เพื่อไม่ให้การหยุดกลางทางทำให้รอบนั้นไม่ครบและต้องเริ่มนับใหม่

nxc smb 10.10.10.10 -u users.txt -p 'Summer2026!' --continue-on-success

หลังจบแต่ละรอบต้องตรวจว่ามีบัญชีใดมีค่า badPwdCount เพิ่มขึ้นหรือถูกล็อก แล้วเว้นระยะให้พ้น observation window ที่อ่านได้ในขั้นแรกก่อนเริ่มรอบถัดไป การเปลี่ยนรหัสผ่านเพียงตัวเดียวต่อรอบทำให้ตรวจย้อนได้ว่าบัญชีใดได้ผลจากรหัสใด

นอกจากนโยบายหลัก องค์กรอาจมีนโยบายรหัสผ่านแยกสำหรับกลุ่มเฉพาะ เช่นบัญชีผู้ดูแลระบบหรือบัญชีบริการ ซึ่งอาจเข้มกว่านโยบายหลัก การอ่านเฉพาะนโยบายหลักจึงไม่พอ

เงื่อนไขที่ทำให้การทดลองมีความหมาย

การทดลองรหัสผ่านจะได้ผลเมื่อมีเงื่อนไขครบสามข้อ ข้อแรกคือต้องมีรายชื่อบัญชีที่ถูกต้อง ซึ่งได้จากการสำรวจในหัวข้อก่อนหน้า ข้อที่สองคือต้องมีรายการรหัสผ่านที่มีโอกาสถูก ซึ่งอาศัยบริบทขององค์กร เช่นชื่อบริษัท ผลิตภัณฑ์ หรือปี ข้อที่สามคือต้องมีช่องทางยืนยันตัวตนที่ยอมรับรหัสผ่านโดยไม่ถูกล็อกหรือจำกัดอัตรา

ช่องทางที่ใช้ได้มีหลายแบบ เช่น SMB, LDAP, WinRM หรือบริการเว็บที่ใช้การยืนยันตัวตนแบบโดเมน แต่ละช่องทางมีผลต่อการบันทึกเหตุการณ์ต่างกัน และบางช่องทางอาจถูกจำกัดด้วยนโยบายความปลอดภัยของระบบ

การทดลองผ่าน Kerberos ก็เป็นไปได้ แต่ต้องระวังว่าการยืนยันตัวตนล่วงหน้าที่ล้มเหลวจะถูกนับในตัวนับเดียวกัน และอาจทำให้บัญชีถูกล็อกได้เช่นกัน การเลือกช่องทางจึงต้องคำนึงถึงผลข้างเคียง ไม่ใช่เพียงความสะดวก

ความเสี่ยงต่อการล็อกบัญชี

ความเสี่ยงที่ชัดที่สุดคือการล็อกบัญชีของผู้ใช้จริง หากบัญชีที่ถูกล็อกเป็นบัญชีบริการที่ระบบใช้อยู่ การหยุดชะงักอาจเกิดขึ้นทันทีและกระทบผู้ใช้ทั้งองค์กร หากเป็นบัญชีผู้ดูแลระบบ อาจทำให้ไม่มีผู้มีสิทธิ์เข้าถึงระบบแก้ไขเหตุการณ์

ความเสี่ยงอีกประการคือการถูกเข้าใจผิดว่าเป็นการโจมตีจริง ระบบตรวจจับขององค์กรอาจแจ้งเตือนและทีมตอบสนองอาจดำเนินการกักกันเครื่องที่ใช้ทดสอบ หรือระงับบัญชีที่ใช้ ซึ่งทำให้งานหยุดชะงักและต้องใช้เวลาแก้ไข

ความเสี่ยงประการที่สามคือผลลัพธ์บวกลวง บัญชีที่ถูกล็อกอาจทำให้ผู้ทดสอบเข้าใจผิดว่าได้รหัสผ่านที่ถูกต้อง หรือทำให้ตัวนับความล้มเหลวของบัญชีอื่นเปลี่ยนไป การตีความผลจึงต้องอาศัยการตรวจสอบรหัสข้อผิดพลาดอย่างระมัดระวัง

ด้วยเหตุนี้ การทดลองรหัสผ่านจึงต้องมีข้อตกลงล่วงหน้าอย่างชัดเจน ทั้งบัญชีที่ยกเว้น ช่วงเวลาที่อนุญาต จำนวนครั้งสูงสุด และช่องทางติดต่อเมื่อเกิดเหตุไม่คาดคิด

การวางแผนอย่างระมัดระวัง

ขั้นแรกคืออ่านนโยบายล็อกและตรวจว่ามีบัญชีใดอยู่ภายใต้นโยบายแยก ขั้นที่สองคือจัดทำรายชื่อบัญชีที่จะทดลองและตัดบัญชีบริการกับบัญชีผู้ดูแลระบบออก ขั้นที่สามคือกำหนดจำนวนครั้งต่อบัญชีให้ต่ำกว่าขีดล็อกอย่างน้อยหนึ่งครั้ง และเว้นระยะให้พ้นช่วงสังเกตการณ์ก่อนเริ่มรอบใหม่

ขั้นที่สี่คือเตรียมรายการรหัสผ่าน ชุดเล็กที่อิงบริบทองค์กร และหลีกเลี่ยงรหัสผ่านที่ทำให้เกิดการล็อกง่าย เช่นรหัสผ่านที่ผู้ใช้มักพิมพ์ผิดซ้ำๆ ขั้นที่ห้าคือแจ้งทีมตรวจสอบขององค์กรล่วงหน้าและตกลงสัญญาณหยุดเมื่อพบการล็อก

ระหว่างทดลองควรเฝ้าดูจำนวนบัญชีที่ถูกล็อกและหยุดทันทีเมื่อถึงเกณฑ์ที่ตกลงไว้ การทดลองที่ได้ผลบางส่วนแต่ทำให้ระบบหยุดทำงานไม่ใช่ผลลัพธ์ที่ยอมรับได้ในงานทดสอบมืออาชีพ

การตรวจจับและการป้องกัน

ฝ่ายป้องกันตรวจจับ password spraying ได้จากรูปแบบการล้มเหลวที่กระจายไปยังบัญชีจำนวนมากจากแหล่งเดียวหรือแหล่งไม่กี่แหล่ง ซึ่งต่างจากการเดารหัสผ่านปกติที่กระจุกอยู่ที่บัญชีเดียว

บันทึกที่เกี่ยวข้องได้แก่เหตุการณ์การเข้าสู่ระบบล้มเหลว (Event ID 4625) ซึ่งมีรหัสสถานะที่บอกรหัสผ่านผิดหรือบัญชีถูกล็อก เหตุการณ์การล็อกบัญชี (Event ID 4740) และเหตุการณ์การยืนยันตัวตนด้วย Kerberos ที่ล้มเหลว (Event ID 4771)

ตาราง 13.24 เหตุการณ์ที่ใช้ตรวจจับการทดลองรหัสผ่าน
เหตุการณ์ความหมายสิ่งที่ควรสังเกต
4625การเข้าสู่ระบบล้มเหลวบัญชีจำนวนมากจากแหล่งเดียวในช่วงสั้น

4771การยืนยันตัวตน Kerberos ล้มเหลวรหัสผ่านผิดซ้ำกับหลายบัญชี
4768การขอตั๋ว TGTการขอตั๋วจำนวนมากผิดปกติ
4648การเข้าสู่ระบบด้วยข้อมูลที่ระบุชัดการใช้บัญชีหนึ่งเข้าถึงหลายเครื่อง

มาตรการป้องกันเริ่มจากนโยบายรหัสผ่านที่เหมาะสม การบังคับความยาวและห้ามรหัสผ่านที่คาดเดาง่าย การใช้ระบบกรองรหัสผ่านต้องห้าม และการเปิดใช้การยืนยันตัวตนหลายขั้นสำหรับบริการที่สำคัญ

นอกจากนี้ควรมีบัญชีล่อ (Honeytoken Account) ที่ไม่มีผู้ใช้จริงและมีสิทธิ์ดูน่าสนใจ การล็อกหรือการพยายามเข้าสู่ระบบบัญชีนี้เป็นสัญญาณที่มีความแม่นยำสูงเพราะไม่มีเหตุผลปกติใดที่จะเกิด

การปรับขีดล็อกให้สูงขึ้นเพื่อลดการล็อกโดยไม่ตั้งใจเป็นแนวทางที่ใช้กัน แต่ก็เพิ่มโอกาสที่การทดลองรหัสผ่านจะสำเร็จ องค์กรจึงต้องชั่งน้ำหนักร่วมกับการเฝ้าดูและการยืนยันตัวตนหลายขั้น ไม่ใช่ปรับค่าตัวใดตัวหนึ่งโดยไม่ดูผลรวม

ข้อผิดพลาดที่พบบ่อย

ตาราง 13.25 ข้อผิดพลาดในการทดลองรหัสผ่านและผลที่เกิดขึ้น
ข้อผิดพลาดผลที่เกิดขึ้นวิธีหลีกเลี่ยง
ไม่ตรวจขีดล็อกก่อนเริ่มบัญชีถูกล็อกโดยไม่ตั้งใจอ่านนโยบายและทดสอบในแล็บก่อน
ใช้หลายรหัสกับบัญชีเดียวล็อกบัญชีทันทีใช้หนึ่งรหัสต่อบัญชีต่อรอบ
รวมบัญชีบริการไว้ในรายการบริการหยุดทำงานตัดบัญชีบริการออกและประสานเจ้าของระบบ
ไม่เว้นช่วงตาม observation windowตัวนับไม่รีเซ็ตและล็อกในรอบถัดไปเว้นระยะให้พ้นช่วงสังเกตการณ์
ไม่แจ้งทีมตรวจสอบถูกเข้าใจว่าเป็นการบุกรุกแจ้งล่วงหน้าและตกลงช่องทางติดต่อ
ทดลองในช่วงเวลาทำงานหลักกระทบผู้ใช้และเพิ่มความสนใจเลือกช่วงเวลาที่ตกลงไว้
สรุปผลจากข้อความผิดพลาดเข้าใจผิดว่าได้รหัสผ่านตรวจรหัสสถานะและทดสอบซ้ำอย่างถูกวิธี

ข้อผิดพลาดข้อสุดท้ายเป็นสาเหตุของรายงานที่ผิดพลาดมากที่สุด เพราะข้อความตอบกลับของการยืนยันตัวตนอาจแยกไม่ออกระหว่างรหัสผ่านผิด บัญชีถูกล็อก และบัญชีถูกปิดใช้งาน การตรวจรหัสสถานะจึงเป็นสิ่งจำเป็นก่อนสรุปผลใดๆ

13.8 การบันทึกผลและการจัดลำดับเส้นทาง

เหตุผลที่การบันทึกต้องทำระหว่างสำรวจ

ผลการสำรวจ Active Directory มีปริมาณมากและมาจากหลายแหล่ง หากบันทึกเฉพาะตอนจบ ข้อมูลสำคัญจะสูญหายและตรวจสอบย้อนกลับไม่ได้ ผู้ทดสอบจึงควรบันทึกทุกคำสั่งที่รันพร้อมเวลาและบัญชีที่ใช้ เพราะผลเดียวกันอาจต่างกันเมื่อใช้สิทธิ์ต่างกัน

การบันทึกยังมีผลต่อความน่าเชื่อถือของรายงาน ผู้อ่านที่ต้องการตรวจสอบว่าผลสรุปมาจากข้อมูลใดสามารถย้อนกลับไปยังคำสั่งและเวลาที่ระบุไว้ได้ ซึ่งเป็นสิ่งที่แยกงานมืออาชีพออกจากงานที่อาศัยความจำ

ตาราง 13.26 ข้อมูลที่ต้องบันทึกในการสำรวจ Active Directory
หมวดตัวอย่างเหตุผล
ขอบเขตโดเมนชื่อโดเมน โดเมนคอนโทรลเลอร์ที่ใช้ระบุแหล่งข้อมูลและข้อจำกัด
บัญชีที่ใช้ชื่อบัญชีและที่มาของสิทธิ์อธิบายว่าผลใดได้จากสิทธิ์ใด
เวลาวันและเวลาของแต่ละคำสั่งใช้เทียบกับบันทึกเหตุการณ์
คำสั่งเต็มคำสั่งและตัวเลือกทั้งหมดทำซ้ำและตรวจสอบได้
ผลดิบไฟล์ข้อความหรือ JSONใช้วิเคราะห์ซ้ำโดยไม่ต้องรันใหม่
ข้อสังเกตสิ่งที่ผิดปกติและยังไม่ได้ตรวจไม่ให้ข้อมูลสำคัญหาย
การคืนสภาพไฟล์ที่สร้างและลบแล้วยืนยันว่าไม่ทิ้งการเปลี่ยนแปลง

การจัดลำดับเส้นทาง

เมื่อได้เส้นทางหลายเส้นทาง ผู้ทดสอบต้องจัดลำดับก่อนเลือกดำเนินการต่อ การจัดลำดับที่ดีไม่ได้ดูที่ความสั้นของเส้นทางเพียงอย่างเดียว แต่ดูที่ความน่าเชื่อถือ ผลกระทบ และความเสี่ยงต่อระบบ

เกณฑ์แรกคือผลกระทบ หากเส้นทางนำไปสู่สิทธิ์ระดับโดเมน ผลกระทบย่อมสูงกว่าเส้นทางที่ได้เพียงสิทธิ์ผู้ดูแลเครื่องเดียว แต่ผลกระทบที่สูงกว่าก็ต้องใช้ความระมัดระวังมากกว่า

เกณฑ์ที่สองคือความน่าเชื่อถือ เส้นทางที่อาศัยสิทธิ์ที่ตรวจสอบแล้วว่ามีจริงและใช้ได้ทันทีมีความน่าเชื่อถือสูงกว่าเส้นทางที่ต้องรอเงื่อนไข เช่นรอให้ผู้ใช้เข้าสู่ระบบเครื่องที่กำหนด

เกณฑ์ที่สามคือจำนวนขั้นตอน เส้นทางที่ต้องผ่านหลายขั้นมีโอกาสล้มเหลวมากกว่าและทิ้งร่องรอยมากกว่า การเลือกเส้นทางที่สั้นที่สุดจึงมักเป็นทางเลือกแรกเมื่อผลกระทบเท่ากัน

เกณฑ์ที่สี่คือผลข้างเคียง เส้นทางที่ต้องหยุดบริการหรือแก้ไขไฟล์ระบบมีความเสี่ยงต่อการทำงานขององค์กรสูงกว่าเส้นทางที่อ่านข้อมูลเท่านั้น

ตาราง 13.27 เกณฑ์การจัดลำดับเส้นทาง
เกณฑ์คำถามที่ใช้ประเมินน้ำหนัก
ผลกระทบได้สิทธิ์ระดับใดและเข้าถึงข้อมูลใดสูง
ความน่าเชื่อถือเงื่อนไขครบและตรวจสอบแล้วหรือไม่สูง
จำนวนขั้นตอนต้องผ่านกี่ขั้นและมีจุดล้มเหลวกี่จุดกลาง
ผลข้างเคียงกระทบบริการหรือข้อมูลหรือไม่สูง
การตรวจจับมีโอกาสถูกจับได้มากน้อยเพียงใดกลาง
ความสามารถย้อนกลับคืนสภาพได้ง่ายเพียงใดกลาง

การส่งต่อข้อมูลไปยังบทถัดไป

ข้อมูลที่ได้จากบทนี้จะถูกใช้ในบทที่ 14 ในสามลักษณะ ลักษณะแรกคือรายชื่อบัญชีที่มีคุณสมบัติเหมาะแก่การขอตั๋วบริการ เช่นบัญชีที่มี SPN และบัญชีที่ไม่ต้องยืนยันตัวตนล่วงหน้า ลักษณะที่สองคือความสัมพันธ์เชิงสิทธิ์ที่ชี้ว่าบัญชีใดควบคุมบัญชีใดได้ และลักษณะที่สามคือข้อมูลเครื่องและเซสชันที่ใช้ประกอบการวางแผนเคลื่อนที่

การส่งต่อข้อมูลควรทำในรูปแบบที่ผู้อ่านคนอื่นเข้าใจได้ ไม่ใช่ไฟล์ดินที่ต้องใช้เครื่องมือเดิมจึงจะอ่านได้ ตารางสรุปที่ระบุชื่อบัญชี ชนิดของหลักฐาน และระดับความน่าเชื่อถือช่วยให้ทีมตัดสินใจได้เร็วและลดการทำงานซ้ำ

ข้อผิดพลาดในการสรุปผล

ข้อผิดพลาดที่พบบ่อยที่สุดคือการสรุปจากชื่อบัญชีหรือชื่อกลุ่มโดยไม่ตรวจสิทธิ์จริง เช่นเห็นกลุ่มชื่อ Helpdesk Admins แล้วสรุปว่ามีสิทธิ์ระดับโดเมน ทั้งที่กลุ่มนั้นอาจมีสิทธิ์เพียงรีเซ็ตรหัสผ่านของผู้ใช้ทั่วไป

ข้อผิดพลาดอีกประการคือการถือว่าเส้นทางในกราฟใช้ได้เสมอโดยไม่ตรวจเวลาและเงื่อนไข ซึ่งทำให้รายงานระบุความเสี่ยงที่ไม่มีอยู่จริง และทำให้ทีมแก้ไขเสียเวลาไปกับสิ่งที่ไม่ใช่ปัญหา

ข้อผิดพลาดประการที่สามคือการรายงานจำนวนวัตถุโดยไม่แยกประเภท เช่นรายงานว่าพบ "ผู้ใช้ 1,200 บัญชี" ทั้งที่ผลรวมนั้นปนบัญชีเครื่องและบัญชีที่ปิดใช้งานแล้ว การแยกประเภททำให้ตัวเลขสื่อความหมายได้จริง

ข้อผิดพลาดผลที่เกิดขึ้นวิธีแก้ไข
สรุปจากชื่อกลุ่มประเมินสิทธิ์สูงเกินจริงตรวจสิทธิ์และสมาชิกจริง
เชื่อกราฟโดยไม่ตรวจเวลารายงานเส้นทางที่ใช้ไม่ได้ระบุเวลาเก็บข้อมูลและตรวจซ้ำ
นับวัตถุปนประเภทตัวเลขสื่อความหมายผิดแยกผู้ใช้ คอมพิวเตอร์ และกลุ่ม
ไม่ระบุบัญชีที่ใช้สำรวจผู้อ่านประเมินข้อจำกัดไม่ได้บันทึกบัญชีและสิทธิ์ทุกครั้ง
ละเลยการล็อกบัญชีกระทบผู้ใช้จริงตรวจและบันทึกสถานะบัญชี
ไม่ลบข้อมูลที่เก็บไว้ข้อมูลองค์กรตกค้างลบตามข้อตกลงเมื่อจบงาน

เมื่อบันทึกและจัดลำดับครบแล้ว ผู้ทดสอบจะมีทั้งภาพของโดเมนและรายการเส้นทางที่พร้อมตรวจสอบต่อในบทถัดไป ซึ่งจะเริ่มจากการใช้ข้อมูลยืนยันตัวตนที่ได้มาเพื่อเข้าถึงทรัพยากรอื่น

✓ สรุป

Active Directory เป็นทั้งฐานข้อมูลกลาง ผู้ให้บริการยืนยันตัวตน และผู้กระจายนโยบายขององค์กร คุณสมบัติทั้งสามนี้ทำให้มันมีมูลค่าสูงต่อผู้โจมตี เพราะการยึดบัญชีเดียวอาจเปิดทางไปยังทรัพยากรนับพันเครื่อง

โครงสร้างของ Active Directory มีลำดับชั้นชัดเจน โดเมนเก็บวัตถุและมีโดเมนคอนโทรลเลอร์ให้บริการ ทรีรวมโดเมนที่ใช้ชื่อต่อเนื่องกัน และฟอเรสต์เป็นขอบเขตความปลอดภัยที่ใหญ่ที่สุดซึ่งแชร์สคีมาร่วมกัน

วัตถุทุกชิ้นมี Distinguished Name บอกตำแหน่ง และมี SID บอกตัวตนในระบบสิทธิ์ การเข้าใจทั้งสองรูปแบบช่วยให้ผู้ทดสอบอ้างอิงวัตถุได้ถูกต้องและตีความผลจากเครื่องมือได้แม่นยำขึ้น

หน่วยองค์กรกับกลุ่มมีหน้าที่ต่างกัน หน่วยองค์กรใช้จัดโครงสร้างและผูกนโยบาย แต่ไม่ให้สิทธิ์ด้วยตัวเอง ส่วนกลุ่มให้สิทธิ์ทันทีและสามารถซ้อนกันได้หลายชั้นจนยากต่อการติดตาม

Kerberos เป็นกลไกยืนยันตัวตนหลักของโดเมน ผู้ใช้ได้ตั๋ว TGT จากนั้นใช้ตั๋วนั้นขอตั๋วบริการสำหรับแต่ละบริการ ตั๋ว TGT เข้ารหัสด้วยกุญแจของบัญชี krbtgt และตั๋วบริการเข้ารหัสด้วยกุญแจของบัญชีที่รันบริการ ซึ่งเป็นเหตุผลที่ตั๋วบริการมีค่าในมุมของผู้โจมตี

LDAP เป็นช่องทางมาตรฐานสำหรับอ่านข้อมูลจากไดเรกทอรี การใช้ ldapsearch กับตัวกรองที่เหมาะสมให้ข้อมูลที่ควบคุมขอบเขตได้ และสามารถตรวจสอบได้ง่ายกว่าการใช้เครื่องมืออัตโนมัติ

เครื่องมืออัตโนมัติอย่าง enum4linux และ PowerView ช่วยลดเวลาในการสำรวจ แต่ผลที่ได้ต้องตรวจซ้ำด้วยคำสั่งพื้นฐานเสมอ เพราะเครื่องมืออาจรายงานข้อมูลเก่า ข้อมูลที่ไม่ครบ หรือข้อมูลที่ตีความผิดได้

BloodHound เปลี่ยนข้อมูลที่กระจัดกระจายให้เป็นกราฟของความสัมพันธ์ ทำให้เห็นเส้นทางจากบัญชีธรรมดาไปสู่สิทธิ์สูง แต่กราฟมีข้อจำกัดเรื่องความสดของข้อมูล สิทธิ์ที่ใช้เก็บ และบริบทขององค์กร จึงต้องอ่านอย่างระมัดระวัง

password spraying อาศัยการกระจายความพยายามไปยังบัญชีจำนวนมากเพื่อหลบขีดล็อก ความเสี่ยงหลักคือการล็อกบัญชีจริงซึ่งอาจกระทบระบบทั้งองค์กร การวางแผนจึงต้องอ่านนโยบายล็อก ตัดบัญชีบริการออก และประสานงานกับทีมตรวจสอบล่วงหน้า

การบันทึกผลและการจัดลำดับเส้นทางเป็นขั้นตอนที่ขาดไม่ได้ เพราะงานสำรวจที่ไม่ได้บันทึกไว้จะตรวจสอบย้อนกลับไม่ได้ และเส้นทางที่ไม่ได้จัดลำดับจะทำให้ทีมแก้ไขลงทุนผิดจุด ข้อมูลที่ดีจึงต้องมาพร้อมบริบท เวลา และข้อจำกัดอย่างชัดเจน

โดเมนคอนโทรลเลอร์เครื่องที่ให้บริการยืนยันตัวตนและเก็บสำเนาฐานข้อมูล

สิ่งที่ผู้เรียนควรเตรียมจากบทนี้คือรายการบัญชีที่มีคุณสมบัติเหมาะสม แผนที่ความสัมพันธ์ที่ตรวจสอบแล้ว และความเข้าใจว่าการกระทำใดถูกบันทึกไว้ที่ใด เพราะการโจมตีในบทถัดไปจะทิ้งร่องรอยมากกว่าการสำรวจ และการรู้ล่วงหน้าว่าร่องรอยนั้นอยู่ที่ใดคือสิ่งที่ทำให้งานทดสอบยังอยู่ในขอบเขตและตรวจสอบได้
