เชื่อมโยงกับบทก่อนหน้าต่อยอดจากบทที่ 11 ซึ่งอธิบายการยกระดับสิทธิ์บนวินโดวส์ บทนี้ใช้ระเบียบวิธีเดียวกัน แต่เปลี่ยนไปอ่านแบบจำลองสิทธิ์ของลินุกซ์ซึ่งมีกลไกและจุดผิดพลาดต่างออกไป
เชื่อมโยงกับบทถัดไปบทที่ 13 (Active Directory I) ซึ่งขยายขอบเขตจากเครื่องเดียวไปสู่ระบบยืนยันตัวตนของทั้งองค์กร ผู้เรียนจะเห็นว่าสิทธิ์ในระดับเครื่องเป็นเพียงจุดเริ่มต้นของการเคลื่อนที่ในเครือข่าย

เอกสารประกอบการบรรยายฉบับนี้เรียบเรียงจากเนื้อหาต้นฉบับของบทโดยตรง จุดประสงค์การเรียนรู้ในหัวข้อถัดไปทำเครื่องหมายได้เมื่อทำสำเร็จ และความคืบหน้าจะถูกจำไว้ในเบราว์เซอร์ของเครื่องนี้

บทที่แล้วจบลงที่การยกระดับสิทธิ์บนวินโดวส์ ซึ่งผู้เรียนได้เห็นว่าการเปลี่ยนจากบัญชีผู้ใช้ทั่วไปไปสู่บัญชีระบบต้องอาศัยการอ่านเงื่อนไขให้ครบก่อนลงมือ บทนี้ทำสิ่งเดียวกันบนระบบปฏิบัติการอีกตระกูลหนึ่ง แต่ผู้อ่านจะพบว่าแม้หลักคิดจะเหมือนกัน รายละเอียดกลับต่างกันมากพอที่จะทำให้ข้อสรุปจากบทก่อนใช้แทนกันไม่ได้

ลินุกซ์ไม่ได้มีรายการควบคุมการเข้าถึงยาวๆ แบบวินโดวส์ แต่ใช้แบบจำลองที่เรียบง่ายกว่าคือเจ้าของ กลุ่ม และผู้อื่น พร้อมบิตพิเศษอีกสามชนิดที่เปลี่ยนพฤติกรรมของโปรแกรมหรือโฟลเดอร์ ความเรียบง่ายนี้ทำให้ระบบอ่านได้เร็ว แต่ก็ทำให้ผู้ดูแลระบบละเลยรายละเอียดได้ง่ายเช่นกัน ไฟล์หนึ่งไฟล์ที่ตั้งบิตผิดจึงกลายเป็นช่องทางยกระดับสิทธิ์ที่คงอยู่ได้นานหลายปีโดยไม่มีใครสังเกต

นอกจากบิตสิทธิ์แล้ว ลินุกซ์ยังมีกลไกอีกสองชั้นที่ผู้เรียนต้องเข้าใจ คือการมอบสิทธิ์ผ่าน sudo ซึ่งกำหนดว่าใครรันคำสั่งใดในนามใครได้ และ capabilities ซึ่งแบ่งอำนาจของบัญชี root ออกเป็นชิ้นย่อยแล้วมอบเฉพาะบางชิ้นให้โปรแกรม กลไกทั้งสองถูกออกแบบมาเพื่อลดความเสี่ยง แต่การตั้งค่าที่ผ่อนปรนเกินจำเป็นก็ให้ผลตรงกันข้าม

งานที่ถูกตั้งเวลาและตัวแปรสภาพแวดล้อมเป็นอีกกลุ่มที่พบบ่อยในระบบจริง เพราะสคริปต์ของผู้ดูแลระบบมักถูกเขียนไว้หลายปีก่อนและไม่มีการตรวจทานซ้ำ เมื่อโฟลเดอร์ที่เก็บสคริปต์เปิดให้ผู้ใช้ทั่วไปเขียนได้ หรือเมื่อสคริปต์เรียกคำสั่งโดยไม่ระบุเส้นทางเต็ม ผู้ใช้ทั่วไปก็สามารถแทรกโปรแกรมของตนเข้าไปทำงานในนามของเจ้าของงานได้

บทนี้จึงให้น้ำหนักกับการอ่านระบบมากกว่าการท่องจำรายการช่องโหว่ ผู้เรียนจะได้ฝึกตอบคำถามว่าใครเป็นเจ้าของไฟล์ ใครเขียนได้ โปรแกรมใดเรียกไฟล์นั้นด้วยสิทธิ์ใด และเงื่อนไขใดที่ยังขาดอยู่ การตอบคำถามเหล่านี้ได้จะทำให้ผู้เรียนปรับตัวเข้ากับระบบที่ไม่เคยเห็นได้เร็วกว่าการจำชื่อเครื่องมือ

12.1 ทำไมการยกระดับสิทธิ์บนลินุกซ์จึงมีลักษณะเฉพาะ

จุดที่เซสชันหยุดอยู่

กรณีศึกษาสมมติที่ใช้ตลอดบทนี้คือเครื่อง APP01 ที่หมายเลข 10.10.10.41 ซึ่งเป็นแม่ข่ายแอปพลิเคชันภายในขององค์กร ผู้เรียนได้เซสชันจากช่องโหว่ในแอปพลิเคชันเว็บ และเซสชันนั้นทำงานด้วยบัญชี www-data ซึ่งเป็นบัญชีมาตรฐานของเว็บเซิร์ฟเวอร์

เมื่อตรวจด้วยคำสั่งพื้นฐาน ผู้ทดสอบพบว่าบัญชีนี้มี UID และ GID ที่ไม่ใช่ศูนย์ ไม่ได้อยู่ในกลุ่ม sudo หรือ wheel และไม่มีสิทธิ์อ่านไฟล์ในโฟลเดอร์บ้านของผู้ใช้คนอื่น บัญชีนี้เขียนไฟล์ได้เฉพาะในโฟลเดอร์ชั่วคราวและโฟลเดอร์เนื้อหาของเว็บแอปพลิเคชัน

ถ้าหยุดอยู่ตรงนี้ รายงานจะบอกได้เพียงว่ามีช่องโหว่ที่ทำให้รันคำสั่งในนามของบัญชีเว็บ ซึ่งเป็นข้อความจริงแต่ยังไม่ตอบว่าองค์กรเสี่ยงต่ออะไร การยกระดับสิทธิ์คือการพิสูจน์ว่าจากจุดนี้ไปถึงสิทธิ์ของผู้ดูแลระบบได้หรือไม่ และต้องใช้เงื่อนไขใด

คำถามสามข้อที่ใช้ได้กับทุกระบบ

ระเบียบวิธีในบทนี้ยังคงใช้คำถามสามข้อจากบทที่แล้ว เพราะเป็นคำถามที่ไม่ได้ผูกกับระบบปฏิบัติการใดระบบหนึ่ง คำถามแรกคือ "ตอนนี้ฉันเป็นใคร" ซึ่งบนลินุกซ์หมายถึงหมายเลขผู้ใช้ หมายเลขกลุ่ม กลุ่มเสริม และสิทธิ์ที่ได้รับผ่าน sudo หรือ capabilities

คำถามที่สองคือ "ฉันมีอะไร" หมายถึงไฟล์ที่อ่านได้ คีย์ส่วนตัวที่ตกค้าง ไฟล์ตั้งค่าที่มีรหัสผ่าน และโฟลเดอร์ที่เขียนได้ ข้อมูลเหล่านี้ไม่มีเสียงดังและไม่ทำให้ระบบเปลี่ยนแปลง จึงเป็นส่วนที่ผู้ทดสอบมักมองข้ามทั้งที่ให้ผลได้บ่อยที่สุด

คำถามที่สามคือ "ระบบอนุญาตอะไร" หมายถึงสิ่งที่ระบบเปิดไว้โดยไม่ตั้งใจ เช่น ไฟล์ที่ตั้งบิต SUID งานที่ถูกตั้งเวลาและเรียกสคริปต์ที่แก้ไขได้ หรือคำสั่งที่ sudo อนุญาตให้รันโดยไม่ต้องยืนยันรหัสผ่าน

เมื่อตอบครบทั้งสามข้อ ผู้ทดสอบจะเห็นเส้นทางหลายเส้นทางและสามารถเลือกเส้นทางที่กระทบระบบน้อยที่สุด คำถามข้อที่สามต้องอาศัยการสำรวจจริง ไม่ใช่การเดาจากชื่อระบบปฏิบัติการหรือรุ่นของเคอร์เนล

ความแตกต่างเชิงโครงสร้างจากวินโดวส์

สิทธิ์สูงสุดบัญชี SYSTEM และผู้ดูแลระบบที่ยืนยันแล้วบัญชี root ซึ่งมีหมายเลขผู้ใช้เป็นศูนย์

งานอัตโนมัติงานที่ถูกตั้งเวลาและบริการงานที่ถูกตั้งเวลาและยูนิตของ systemd
จุดผิดพลาดที่พบบ่อยสิทธิ์บนวัตถุบริการและไฟล์โปรแกรมไฟล์ที่ตั้งบิตพิเศษและคำสั่งในสคริปต์
ร่องรอยการตรวจสอบบันทึกเหตุการณ์ของวินโดวส์และ Sysmonบันทึกของระบบ auditd และ journald

ความแตกต่างที่สำคัญที่สุดคือลินุกซ์ไม่มีโทเคนที่ต้องรีเฟรชเมื่อกลุ่มเปลี่ยน สิทธิ์ของกระบวนการถูกกำหนดตั้งแต่สร้างกระบวนการจากหมายเลขผู้ใช้และกลุ่มในขณะนั้น การเพิ่มผู้ใช้เข้ากลุ่มจึงมีผลกับเซสชันที่เปิดใหม่ แต่ไม่เปลี่ยนสิทธิ์ของกระบวนการที่กำลังทำงานอยู่ เช่นเดียวกับกรณีของวินโดวส์ในแง่ผลลัพธ์ แต่กลไกเบื้องหลังต่างกัน

อีกความแตกต่างคือลินุกซ์เปิดโอกาสให้ผู้ใช้ทั่วไปรันคำสั่งในนามของผู้อื่นได้ผ่าน sudo โดยไม่ต้องสลับบัญชีทั้งเซสชัน การตั้งค่า sudo จึงเป็นพื้นที่ที่มีความเสี่ยงสูง เพราะการอนุญาตเกินหนึ่งคำสั่งอาจเทียบเท่าการให้สิทธิ์ root ทั้งหมดโดยที่ผู้ดูแลระบบไม่รู้ตัว

เหตุใดช่องโหว่ประเภทนี้จึงยังพบมาก

สาเหตุแรกคือระบบที่ใช้งานมานาน สคริปต์สำหรับสำรองข้อมูล ตรวจสอบบันทึก และหมุนเวียนไฟล์มักถูกเขียนไว้ก่อนที่องค์กรจะมีมาตรฐานความปลอดภัย และไม่มีการแก้ไขเพราะยังทำงานได้ดี

สาเหตุที่สองคือความสะดวกในการติดตั้งโปรแกรมบางประเภท ผู้ให้บริการซอฟต์แวร์อาจแนะนำให้ตั้งบิต SUID หรือให้สิทธิ์ใน sudoers เพื่อให้โปรแกรมทำงานได้ทันที โดยไม่แจ้งผลกระทบด้านความปลอดภัย

สาเหตุที่สามคือการให้สิทธิ์ในวงกว้างเพื่อลดจำนวนปัญหาที่ผู้ใช้แจ้ง เช่น การให้กลุ่มผู้ใช้ทั้งหมดเขียนโฟลเดอร์ที่ใช้ร่วมกัน หรือการให้ sudo กับคำสั่งตีความเช่น less, vim และ python เพราะคิดว่าเป็นเพียงโปรแกรมอ่านหรือแก้ไขไฟล์ คำสั่งเหล่านี้มักมีความสามารถซ่อนอยู่ที่ใช้เปิดเชลล์หรืออ่านไฟล์ใดก็ได้

สาเหตุที่สี่คือภาชนะและเครื่องเสมือนที่ถูกโคลนบ่อย ภาพสำเร็จรูปภาพหนึ่งอาจมีไฟล์ที่ตั้งบิตพิเศษหรือบัญชีที่ตั้งรหัสผ่านอ่อนติดไปด้วย และเมื่อนำไปใช้หลายสิบเครื่อง ปัญหาเดียวก็กลายเป็นปัญหาระดับองค์กร

การรู้สาเหตุมีผลต่อการรายงาน เพราะการแก้ที่ตัวเลข เช่น การลบบิต SUID ออกจากไฟล์หนึ่ง จะไม่ป้องกันการเกิดซ้ำหากกระบวนการติดตั้งยังสร้างไฟล์นั้นขึ้นมาใหม่ทุกครั้ง

ขอบเขตของบทนี้

บทนี้กล่าวถึงการยกระดับสิทธิ์ภายในเครื่องเดียวจากบัญชีผู้ใช้ทั่วไปไปจนถึง root เนื้อหาไม่ได้ครอบคลุมการโจมตีระดับโดเมน ซึ่งจะกล่าวถึงในบทที่ 13 และ 14 และไม่ได้สอนการเขียนโปรแกรมโจมตีเคอร์เนลใหม่ เพราะงานจริงส่วนใหญ่ใช้ช่องโหว่ที่รู้จักแล้วร่วมกับการอ่านการตั้งค่าของระบบ

สิ่งที่บทนี้ให้น้ำหนักมากกว่าคำสั่งคือการอ่านเงื่อนไข ผู้เรียนที่ท่องจำคำสั่ง find ได้แต่ไม่เข้าใจว่าไฟล์ที่พบนั้นทำงานอย่างไรหรือใครเป็นเจ้าของ จะไม่สามารถแยกช่องโหว่จริงออกจากรายการที่เครื่องมือรายงานเกินจริงได้

เมื่อจบบท ผู้เรียนควรมีกรอบความคิดที่ใช้ได้กับทุกระบบลินุกซ์ ตั้งแต่เครื่องแม่ข่ายที่ติดตั้งมานานจนถึงคอนเทนเนอร์ที่เพิ่งสร้างขึ้น คือเริ่มจากสิทธิ์ปัจจุบัน เก็บข้อมูลอย่างเป็นระบบ ตรวจเงื่อนไขของแต่ละเส้นทาง เลือกเส้นทางที่เสี่ยงน้อยที่สุด และพิสูจน์ผลด้วยหลักฐานที่ตรวจสอบได้

12.2 แบบจำลองสิทธิ์ของลินุกซ์

หมายเลขผู้ใช้และหมายเลขกลุ่ม

ลินุกซ์ไม่ได้ตัดสินสิทธิ์จากชื่อบัญชี แต่ตัดสินจากหมายเลขผู้ใช้ (User Identifier หรือ UID) และหมายเลขกลุ่ม (Group Identifier หรือ GID) ชื่อบัญชีเป็นเพียงป้ายที่ใช้ให้มนุษย์อ่านง่าย ระบบจึงยอมให้มีชื่อต่างกันแต่หมายเลขเดียวกันได้ และการเปลี่ยนชื่อบัญชีไม่เปลี่ยนสิทธิ์ที่บัญชีนั้นถืออยู่

บัญชี root มี UID เป็นศูนย์ ซึ่งเป็นค่าพิเศษที่ระบบถือว่ามีสิทธิ์ทุกอย่างโดยไม่ต้องตรวจบัญชีเพิ่ม บัญชีระบบอื่นๆ มักมี UID ในช่วงตั้งแต่ 1 ถึง 999 ขึ้นกับผู้ผลิตระบบ และบัญชีผู้ใช้ทั่วไปมักเริ่มที่ 1000 ตัวเลขช่วงเหล่านี้อาจต่างกันในแต่ละระบบ จึงไม่ควรใช้เป็นข้อสรุปโดยไม่ตรวจสอบ

ตาราง 12.3 ชนิดบัญชีบนลินุกซ์และลักษณะสำคัญ
ชนิดบัญชีช่วง UID โดยทั่วไปใช้ทำอะไรข้อควรระวัง
root0ควบคุมระบบทั้งหมดไม่ควรใช้เป็นบัญชีสำหรับงานประจำวัน
บัญชีระบบ1–999รันบริการและงานเบื้องหลังมักไม่มีรหัสผ่านและไม่ควรเข้าสู่ระบบได้
บัญชีผู้ใช้ทั่วไป1000 ขึ้นไปงานของผู้ใช้แต่ละคนสิทธิ์เสริมอาจสูงกว่าที่คาด
บัญชีบริการของแอปพลิเคชันขึ้นกับผู้ติดตั้งรันเว็บเซิร์ฟเวอร์หรือฐานข้อมูลอาจถูกสร้างโดยไม่มีการจัดการรหัสผ่าน
บัญชีที่ผูกกับไดเรกทอรีบริการขึ้นกับระบบใช้ระบุตัวตนของบริการชื่อรูปแบบ systemd-* หรือลงท้ายด้วยเครื่องหมายบวก

ข้อมูลบัญชีถูกเก็บในไฟล์สามไฟล์หลักคือ /etc/passwd ซึ่งเก็บชื่อ หมายเลข และโฟลเดอร์บ้าน /etc/shadow ซึ่งเก็บค่ารหัสผ่านที่เข้ารหัสแล้ว และ /etc/group ซึ่งเก็บรายชื่อกลุ่มและสมาชิก ไฟล์แรกอ่านได้โดยทุกคน ส่วนสองไฟล์ที่เหลืออ่านได้เฉพาะผู้ดูแลระบบตามค่าเริ่มต้น

คำสั่ง id แสดงหมายเลขผู้ใช้ หมายเลขกลุ่มหลัก และกลุ่มเสริมทั้งหมดของผู้ใช้ปัจจุบัน คำสั่งนี้เป็นจุดเริ่มต้นของการสำรวจทุกครั้ง เพราะบอกทั้งตัวตนและขอบเขตสิทธิ์ที่ได้จากกลุ่มในคำสั่งเดียว

id
uid=33(www-data) gid=33(www-data) groups=33(www-data)

ผลลัพธ์ข้างต้นบอกว่าบัญชีนี้ไม่มีกลุ่มเสริมใดเลย ซึ่งหมายความว่าเส้นทางยกระดับผ่านกลุ่มจะไม่เกิดจากกลุ่มที่ผู้ใช้เป็นสมาชิกอยู่แล้ว แต่ต้องมาจากไฟล์หรือการตั้งค่าที่อนุญาตให้ "ผู้อื่น" เข้าถึง

บิตสิทธิ์และการอ่านผลจาก ls -l

สิทธิ์บนไฟล์และโฟลเดอร์ถูกแทนด้วยบิตเก้าบิต แบ่งเป็นสามชุดสำหรับเจ้าของ กลุ่ม และผู้อื่น แต่ละชุดมีบิตอ่าน (r) เขียน (w) และรัน (x) ค่าตัวเลขประจำบิตคือ 4, 2 และ 1 ตามลำดับ ผลรวมของแต่ละชุดจึงเป็นตัวเลขฐานแปดหนึ่งหลัก เช่น 7 หมายถึงอ่าน เขียน และรันครบทั้งสามอย่าง

ตาราง 12.4 ความหมายของบิตสิทธิ์เมื่อใช้กับไฟล์และโฟลเดอร์
บิตค่าผลกับไฟล์ผลกับโฟลเดอร์
อ่าน (r)4เปิดอ่านเนื้อหาได้แสดงรายชื่อไฟล์ภายในได้
เขียน (w)2แก้ไขหรือตัดทอนเนื้อหาได้สร้าง ลบ หรือเปลี่ยนชื่อไฟล์ภายในได้
รัน (x)1เรียกโปรแกรมให้ทำงานได้เข้าไปในโฟลเดอร์หรือผ่านเส้นทางได้

ความแตกต่างที่ผู้เริ่มต้นมักสับสนคือบิตเขียนบนโฟลเดอร์ไม่ได้หมายถึงแก้ไขไฟล์ภายในได้ แต่หมายถึงสร้างหรือลบรายชื่อไฟล์ในโฟลเดอร์นั้นได้ หากโฟลเดอร์เปิดให้เขียน ผู้ใช้สามารถลบไฟล์ที่ไม่ใช่ของตนได้แม้จะอ่านเนื้อหาไฟล์นั้นไม่ได้ และสามารถเปลี่ยนไฟล์ด้วยไฟล์ของตนได้หากชื่อเดียวกัน

การอ่านผลจาก ls -l ทำได้โดยดูอักขระสิบตัวแรก ตัวแรกบอกชนิดของไฟล์ ส่วนเก้าตัวที่เหลือคือชุดสิทธิ์สามชุด ตามด้วยชื่อเจ้าของ ชื่อกลุ่ม ขนาด และเวลาแก้ไขล่าสุด

ตัวอย่างความหมาย

-rwxr-xr-x 1 root rootไฟล์โปรแกรมที่ทุกคนรันได้ แต่แก้ไขได้เฉพาะเจ้าของ
-rwsr-xr-x 1 root rootไฟล์ที่มีบิต SUID เปิดอยู่ เจ้าของคือ root
drwxrwxrwt 1 root rootโฟลเดอร์ที่ทุกคนเขียนได้และมีบิต sticky
-rw-r----- 1 root shadowไฟล์ที่เจ้าของอ่านและเขียนได้ กลุ่มอ่านได้ ผู้อื่นไม่มีสิทธิ์

ค่า t ในตำแหน่งท้ายของชุดสิทธิ์คือบิต sticky ส่วนตัว s ในตำแหน่งรันของเจ้าของคือบิต SUID และตัว s ในตำแหน่งรันของกลุ่มคือบิต SGID หากตัวอักษรเป็นตัวพิมพ์ใหญ่ เช่น S แปลว่าบิตนั้นถูกตั้งไว้แต่บิตรันถูกปิด ซึ่งเป็นสภาพที่มักเกิดจากการตั้งค่าผิดและควรตรวจสอบ

สิทธิ์เริ่มต้นของไฟล์ใหม่ไม่ได้มาจากการตั้งค่าไฟล์ต้นแบบเพียงอย่างเดียว แต่มาจากค่า umask ซึ่งเป็นค่าที่ระบบใช้ลบสิทธิ์บางส่วนออกจากสิทธิ์เต็ม ค่า umask ที่พบบ่อยคือ 022 ทำให้โฟลเดอร์ใหม่ได้สิทธิ์ 755 และไฟล์ใหม่ได้สิทธิ์ 644 องค์กรที่ตั้งค่า umask เป็น 000 หรือ 002 อาจสร้างไฟล์ที่กลุ่มหรือผู้อื่นเขียนได้โดยไม่ตั้งใจ

การตรวจสิทธิ์ของไฟล์ต้องดูโฟลเดอร์ตามเส้นทางทั้งหมด ไม่ใช่ดูเฉพาะไฟล์ปลายทาง คำสั่ง namei -l แสดงสิทธิ์ของทุกองค์ประกอบในเส้นทางให้เห็นในครั้งเดียว

namei -l /opt/backup/run.sh

หากโฟลเดอร์ใดในเส้นทางเปิดให้ผู้ใช้เขียนได้ ผู้ใช้สามารถเปลี่ยนชื่อไฟล์หรือวางไฟล์ใหม่แทนที่ได้ แม้ตัวไฟล์ปลายทางจะอนุญาตเฉพาะเจ้าของก็ตาม การตรวจเฉพาะไฟล์จึงเป็นข้อผิดพลาดที่พบบ่อย

บิตพิเศษสามชนิด

นอกจากบิตเก้าบิตปกติ ลินุกซ์ยังมีบิตพิเศษอีกสามบิตที่เปลี่ยนพฤติกรรมของโปรแกรมหรือโฟลเดอร์ บิตเหล่านี้คือสาเหตุของช่องโหว่ยกระดับสิทธิ์ที่พบบ่อยที่สุด และเป็นสิ่งที่ผู้ทดสอบต้องเข้าใจก่อนใช้เครื่องมือใดๆ

บิต SUID (Set User ID) ตั้งบนไฟล์โปรแกรม เมื่อผู้ใช้รันโปรแกรมนั้น กระบวนการจะได้รับหมายเลขผู้ใช้ที่มีผล (Effective UID) เท่ากับเจ้าของไฟล์ ไม่ใช่ผู้ใช้ที่รัน ผลคือโปรแกรมที่เจ้าของเป็น root จะทำงานด้วยสิทธิ์ root แม้ผู้ใช้ทั่วไปเป็นผู้สั่งรัน

บิต SGID (Set Group ID) ตั้งบนไฟล์โปรแกรมเพื่อให้กระบวนการได้รับกลุ่มที่มีผลเท่ากับกลุ่มของไฟล์ หรือตั้งบนโฟลเดอร์เพื่อให้ไฟล์ใหม่ภายในสืบทอดกลุ่มของโฟลเดอร์ การใช้บนโฟลเดอร์เป็นวิธีที่ถูกต้องสำหรับโฟลเดอร์ทำงานร่วมกัน แต่การใช้บนโปรแกรมอาจให้สิทธิ์กลุ่มที่มากเกินจำเป็น

บิต sticky ตั้งบนโฟลเดอร์เพื่อจำกัดการลบหรือเปลี่ยนชื่อไฟล์ให้ทำได้เฉพาะเจ้าของไฟล์ เจ้าของโฟลเดอร์ หรือผู้ดูแลระบบ โฟลเดอร์ /tmp ใช้บิตนี้เพื่อไม่ให้ผู้ใช้คนหนึ่งลบไฟล์ชั่วคราวของอีกคนหนึ่ง

ข้อเท็จจริงที่สำคัญคือเคอร์เนลลินุกซ์ไม่สนับสนุนบิต SUID บนสคริปต์ที่ขึ้นต้นด้วยบรรทัดระบุตัวแปลภาษา สคริปต์ที่ตั้งบิตนี้จึงไม่ทำงานตามที่ผู้ตั้งคาด แต่ไบน์นารีที่คอมไพล์แล้วเท่านั้นที่ได้รับผล การเห็นสคริปต์ที่มีสิทธิ์ rws จึงไม่ใช่ช่องโหว่โดยตัวเอง แต่สะท้อนว่าผู้ดูแลระบบเข้าใจกลไกผิด และอาจมีปัญหาอื่นในระบบเดียวกัน

การมีบิต SUID ไม่ได้แปลว่าเป็นช่องโหว่ทุกไฟล์ โปรแกรมจำนวนหนึ่งจำเป็นต้องใช้บิตนี้เพื่อทำงาน เช่น โปรแกรมเปลี่ยนรหัสผ่านต้องเขียนไฟล์ /etc/shadow ซึ่งผู้ใช้ทั่วไปเขียนไม่ได้ การประเมินจึงต้องดูว่าโปรแกรมนั้นยอมให้ผู้ใช้ทำอะไรได้บ้าง ไม่ใช่ดูที่บิตเพียงอย่างเดียว

การมอบสิทธิ์ผ่าน sudo

sudo คือกลไกที่อนุญาตให้ผู้ใช้รันคำสั่งในนามของอีกบัญชี โดยทั่วไปคือนามของ root โดยไม่ต้องรู้รหัสผ่านของ root การตั้งค่าอยู่ในไฟล์ /etc/sudoers และไฟล์เพิ่มเติมในโฟลเดอร์ /etc/sudoers.d/ ซึ่งควรมีสิทธิ์อ่านได้เฉพาะผู้ดูแลระบบ

รูปแบบของบรรทัดในไฟล์ sudoers ประกอบด้วยสี่ส่วนคือ ผู้ใช้หรือกลุ่ม ระบบที่ใช้ได้ ผู้ใช้ที่รันแทน และคำสั่งที่อนุญาต

Linux capabilities

capabilities คือกลไกที่แบ่งอำนาจของ root ออกเป็นหน่วยย่อยหลายสิบหน่วย แล้วมอบเฉพาะหน่วยที่จำเป็นให้โปรแกรมหรือกระบวนการ ตัวอย่างเช่น โปรแกรมที่ต้องเปิดพอร์ตต่ำกว่า 1024 อาจได้รับเฉพาะ cap_net_bind_service โดยไม่ต้องเป็น root ทั้งหมด

capabilities ถูกเก็บไว้กับไฟล์ในรูปแบบคุณลักษณะเพิ่มเติมของระบบไฟล์ และแสดงได้ด้วยคำสั่ง getcap การค้นหาทั้งระบบทำได้ด้วย getcap -r / 2>/dev/null ส่วนกระบวนการปัจจุบันแสดง capabilities ที่ถืออยู่ด้วย capsh --print

ตาราง 12.8 capabilities ที่เกี่ยวข้องกับการยกระดับสิทธิ์และความเสี่ยง
capabilityความสามารถความเสี่ยง
cap_setuidเปลี่ยนหมายเลขผู้ใช้ของกระบวนการสูงมาก หากโปรแกรมยอมให้เรียกฟังก์ชันนี้ได้
cap_setgidเปลี่ยนหมายเลขกลุ่มของกระบวนการสูง หากกลุ่มปลายทางมีสิทธิ์มาก
cap_dac_overrideข้ามการตรวจสิทธิ์อ่าน เขียน และรันสูงมาก เข้าถึงไฟล์ใดก็ได้
cap_dac_read_searchข้ามการตรวจสิทธิ์อ่านและค้นหาโฟลเดอร์สูง อ่านไฟล์ใดก็ได้
cap_chownเปลี่ยนเจ้าของไฟล์ปานกลาง ใช้ยึดไฟล์สำคัญ
cap_fownerข้ามการตรวจสิทธิ์เมื่อเปลี่ยนสิทธิ์ไฟล์ปานกลาง ใช้แก้สิทธิ์ไฟล์
cap_sys_adminทำงานดูแลระบบหลายอย่าง เช่น การเมานต์สูงมาก อาจเข้าถึงระบบไฟล์ทั้งระบบ
cap_net_rawเปิดใช้ดิบของเครือข่ายต่ำถึงปานกลาง ใช้ดักจับแพ็กเก็ต

ตัวอักษรต่อท้ายที่แสดงในผลของ getcap บอกสถานะของ capability เช่น ep หมายถึงเปิดใช้ทั้งในชุดที่อนุญาตและชุดที่มีผลจริง หาก capability ถูกตั้งแบบ p เพียงอย่างเดียว โปรแกรมอาจยังใช้ไม่ได้จนกว่าจะเรียกใช้เอง ซึ่งขึ้นกับว่าโปรแกรมนั้นทำได้หรือไม่

ความเสี่ยงของ capabilities คล้ายกับ SUID คือมันให้ความสามารถที่ผู้ใช้ทั่วไปไม่มี แต่ไม่ได้แปลว่าใช้ประโยชน์ได้ทุกกรณี ตัวอย่างเช่น ไบน์นารีที่ได้รับ cap_dac_read_search แต่ไม่ยอมให้ผู้ใช้ระบุไฟล์ที่จะอ่าน ก็ไม่อาจใช้ประโยชน์ได้จริง การประเมินจึงต้องดูทั้ง capability และพฤติกรรมของโปรแกรม

การอ่านสิทธิ์ให้ครบทั้งเส้นทาง

การตัดสินว่ากระบวนการหนึ่งเข้าถึงไฟล์ได้หรือไม่ขึ้นกับหลายชั้น ชั้นแรกคือบิตสิทธิ์แบบดั้งเดิม ชั้นที่สองคือรายการควบคุมการเข้าถึงเพิ่มเติมหรือ ACL ซึ่งกำหนดสิทธิ์ให้ผู้ใช้หรือกลุ่มเฉพาะ ชั้นที่สามคือระบบบังคับนโยบายเช่น SELinux และ AppArmor ซึ่งอาจปฏิเสธการเข้าถึงแม้สิทธิ์แบบดั้งเดิมจะอนุญาต

เมื่อเข้าใจแบบจำลองสิทธิ์ครบทั้งสี่ชั้นแล้ว การสำรวจระบบจะไม่ใช่การไล่ค้นหาคำว่า SUID ในไฟล์ใดไฟล์หนึ่ง แต่เป็นการถามว่าใครถือสิทธิ์อะไร ที่ใด และด้วยกลไกใด ซึ่งเป็นพื้นฐานของหัวข้อถัดไป

12.3 ระเบียบวิธี: การสำรวจก่อนวางแผน

ลำดับสี่ขั้นที่ใช้ได้กับทุกเครื่อง

เช่นเดียวกับบทที่แล้ว การสำรวจที่ดีไม่ใช่การรันเครื่องมือหลายตัวพร้อมกัน แต่เป็นลำดับงานที่ชัดเจนซึ่งทำให้ผลลัพธ์ตรวจสอบได้ ลำดับนี้มีสี่ขั้นและใช้เวลาไม่นานหากทำอย่างเป็นระบบ

ขั้นแรกคือยืนยันบริบท ผู้ทดสอบต้องรู้ว่ากำลังทำงานในนามของบัญชีใด มีกลุ่มเสริมใดบ้าง มีสิทธิ์ผ่าน sudo อะไร และกำลังอยู่บนเครื่องใด ขั้นนี้ใช้คำสั่งสั้นๆ สองสามคำสั่งแต่ป้องกันความเข้าใจผิดที่เสียเวลามากที่สุด

ขั้นที่สองคือเก็บข้อมูลระบบอย่างเป็นระบบ ทั้งรุ่นของระบบปฏิบัติการ ระดับแพตช์ ผู้ใช้และกลุ่ม บริการที่เปิดพอร์ต งานที่ถูกตั้งเวลา โฟลเดอร์ที่เมานต์ และไฟล์ที่ตั้งบิตพิเศษ ขั้นนี้ควรเก็บให้ครบก่อนวิเคราะห์ เพราะข้อมูลที่ขาดทำให้เห็นเส้นทางไม่ครบและต้องกลับมาเก็บใหม่

ขั้นที่สามคือหาเส้นทาง ผู้ทดสอบนำข้อมูลจากขั้นที่สองมาจับคู่กับเงื่อนไขของช่องโหว่แต่ละประเภท แล้วจัดลำดับเส้นทางตามความน่าเชื่อถือ ผลกระทบ และความเสี่ยงต่อระบบ

ขั้นที่สี่คือตรวจสอบและพิสูจน์ ผู้ทดสอบยืนยันเงื่อนไขด้วยคำสั่งที่ไม่เปลี่ยนแปลงระบบก่อน จากนั้นจึงเลือกวิธีพิสูจน์ที่เบาที่สุด ซึ่งอาจเป็นการรันคำสั่งอ่านค่าภายในบริบทใหม่โดยไม่ต้องเปิดเชลล์ค้างไว้

ผู้ทดสอบมือใหม่มักข้ามขั้นที่สองและสาม แล้วกระโดดไปรันสคริปต์ตรวจหาอัตโนมัติทันที ผลคือได้รายการยาวที่อ่านไม่ออกและเสียเวลากับรายการที่ตรวจแล้วว่าใช้ไม่ได้ ลำดับสี่ขั้นจึงไม่ใช่พิธีการ แต่เป็นการประหยัดเวลาที่ดีที่สุด

ข้อมูลที่ต้องเก็บและเหตุผล

คำสั่ง ps aux แสดงกระบวนการทั้งหมดพร้อมผู้ใช้ที่เป็นเจ้าของ แม้จะไม่เห็นรายละเอียดภายในของกระบวนการ แต่ก็บอกได้ว่าบริการใดรันด้วย root และมีคำสั่งแบบใด การเห็นกระบวนการที่รันสคริปต์จากโฟลเดอร์ที่ผู้ใช้เขียนได้เป็นสัญญาณที่ควรตรวจต่อทันที

สำหรับไฟล์ที่ตั้งบิตพิเศษ คำสั่งค้นหามาตรฐานคือ

find / -perm -4000 -type f 2>/dev/null
find / -perm -2000 -type f 2>/dev/null
getcap -r / 2>/dev/null

ตัวเลือก -perm -4000 หมายถึงต้องมีบิต SUID อย่างน้อยหนึ่งบิต ไม่ใช่มีค่าสิทธิ์เท่ากับ 4000 ทั้งหมด ส่วน 2>/dev/null ตัดข้อความแจ้งข้อผิดพลาดจากโฟลเดอร์ที่ผู้ใช้ไม่มีสิทธิ์อ่านออก เพื่อให้เห็นเฉพาะผลลัพธ์ที่ต้องการ

การค้นหาทั้งระบบอาจใช้เวลานานและสร้างภาระต่อดิสก์ วิธีที่เหมาะสมในงานจริงคือจำกัดขอบเขตด้วย -xdev เพื่อไม่ข้ามไปยังระบบไฟล์อื่น และเริ่มจากโฟลเดอร์ที่มีความเสี่ยงสูง เช่น /usr/local, /opt, /home และ /tmp ก่อน

find / -xdev -perm -4000 -type f 2>/dev/null

การค้นหาโฟลเดอร์ที่เขียนได้ทั้งระบบมักให้ผลยาวเกินกว่าจะอ่านไหว และทำให้ระบบทำงานหนักโดยไม่จำเป็น วิธีที่มีประโยชน์กว่าคือตรวจโฟลเดอร์ที่เกี่ยวข้องกับเส้นทางยกระดับโดยตรง เช่น โฟลเดอร์ของบริการ โฟลเดอร์สคริปต์ และโฟลเดอร์ที่อยู่ใน PATH

การบันทึกผลให้ตรวจสอบย้อนกลับได้

ผลการสำรวจที่ไม่ได้บันทึกไว้คือข้อมูลที่สูญหาย เมื่อเวลาผ่านไปแม้แต่ผู้ทดสอบเองก็จำไม่ได้ว่าคำสั่งใดให้ผลอะไร และเมื่อต้องเขียนรายงานก็ต้องกลับไปรันซ้ำซึ่งเพิ่มร่องรอยโดยไม่จำเป็น

วิธีที่ง่ายและได้ผลคือเปิดการบันทึกทั้งเซสชันด้วยคำสั่ง script ซึ่งเก็บทุกอย่างที่พิมพ์และทุกผลลัพธ์ลงไฟล์

script -q -c "bash" /home/www-data/session-$(date +%F).txt

ไฟล์บันทึกที่ได้ควรตั้งชื่อตามเครื่องและหัวข้อ และควรคำนวณค่าแฮชเมื่อจะใช้เป็นหลักฐาน

sha256sum session-2026-11-12.txt

การบันทึกด้วย script มีข้อจำกัดคือเก็บอักขระควบคุมที่ใช้จัดรูปแบบหน้าจอไว้ด้วย ทำให้ไฟล์ที่ได้มีอักขระแปลกปลอมปนอยู่ ผู้อ่านจึงควรใช้โปรแกรมอ่านที่รองรับหรือแปลงไฟล์ก่อนแนบในรายงาน

นอกจากไฟล์บันทึก ควรจดสรุปสั้นๆ ว่าพบอะไรในแต่ละขั้น เพราะไฟล์บันทึกยาวหลายพันบรรทัดไม่เหมาะกับการอ่านเพื่อทำความเข้าใจภาพรวม สรุปนี้ไม่ใช่หลักฐานแต่เป็นดัชนีที่ช่วยให้ผู้ตรวจทานกลับไปยังจุดที่ต้องการได้

ข้อผิดพลาดในการสำรวจที่พบบ่อย

ตาราง 12.12 ข้อผิดพลาดในการสำรวจและวิธีหลีกเลี่ยง
ข้อผิดพลาดผลที่เกิดขึ้นวิธีหลีกเลี่ยง
ค้นหาไฟล์ทั้งระบบโดยไม่จำกัดระบบไฟล์ระบบหน่วงและผลยาวเกินอ่านใช้ -xdev และเริ่มจากโฟลเดอร์เสี่ยง
สรุปจากชื่อไฟล์เข้าใจผิดว่าเป็นช่องโหว่ตรวจเจ้าของ สิทธิ์ และพฤติกรรมจริง
ไม่บันทึกเวลาและคำสั่งเต็มตรวจสอบย้อนกลับไม่ได้เปิด script และจดเวลา
อ่านผลเครื่องมือโดยไม่ตรวจซ้ำรายงานเต็มไปด้วยผลบวกลวงยืนยันด้วยคำสั่งพื้นฐานทุกครั้ง
สำรวจเฉพาะโฟลเดอร์บ้านพลาดไฟล์ใน /opt และ /usr/localตรวจเส้นทางของบริการและสคริปต์
ลืมตรวจสิทธิ์ของโฟลเดอร์แม่มองข้ามการเปลี่ยนไฟล์ใช้ namei -l กับทุกเส้นทางสำคัญ
ใช้เครื่องมือที่ต้องติดตั้งเพิ่มโดยไม่แจ้งผิดขอบเขตและถูกกักกันขออนุญาตและใช้เครื่องมือที่มีอยู่ก่อน

ข้อผิดพลาดข้อสุดท้ายมีผลต่อความน่าเชื่อถือของงานมากกว่าที่คิด การดาวน์โหลดสคริปต์จากอินเทอร์เน็ตเข้าไปในเครื่องของลูกค้าเป็นการเปลี่ยนแปลงระบบ และอาจถูกผลิตภัณฑ์ป้องกันกักกันจนได้ผลที่ไม่ครบ ผู้ทดสอบจึงควรเริ่มจากคำสั่งที่มีอยู่ในระบบ แล้วจึงขออนุญาตใช้เครื่องมือเพิ่มเมื่อจำเป็น

เมื่อเก็บข้อมูลครบแล้ว ขั้นต่อไปคือการอ่านข้อมูลเหล่านั้นทีละกลุ่ม โดยเริ่มจากกลุ่มที่ให้ผลชัดที่สุดคือไฟล์ที่ตั้งบิตพิเศษ ซึ่งเป็นหัวข้อของส่วนถัดไป

12.4 SUID และ SGID: กลไกและการตรวจหา

สิทธิ์ที่มีผลและสิทธิ์ที่แท้จริง

กระบวนการบนลินุกซ์มีหมายเลขผู้ใช้สามค่าที่เกี่ยวข้องกัน ค่าแรกคือ UID จริง (Real UID) ซึ่งเป็นบัญชีที่สั่งรันโปรแกรม ค่าที่สองคือ UID ที่มีผล (Effective UID) ซึ่งเป็นค่าที่ระบบใช้ตัดสินสิทธิ์ในการเข้าถึงไฟล์ และค่าที่สามคือ UID ที่บันทึกไว้ (Saved UID) ซึ่งใช้กู้คืนสิทธิ์เดิมหลังจากเปลี่ยนชั่วคราว

ในโปรแกรมปกติ ค่าทั้งสามจะเท่ากัน แต่เมื่อโปรแกรมที่มีบิต SUID ถูกเรียก เคอร์เนลจะตั้ง Effective UID ของกระบวนการให้เท่ากับเจ้าของไฟล์ โปรแกรมจึงทำงานด้วยสิทธิ์ของเจ้าของแม้ผู้ใช้ที่สั่งรันจะเป็นบัญชีอื่น

กลไกนี้มีไว้เพื่อให้โปรแกรมที่ต้องการสิทธิ์สูงทำงานได้โดยไม่ต้องให้ผู้ใช้เป็น root ตัวอย่างที่คุ้นเคยคือโปรแกรมเปลี่ยนรหัสผ่าน ซึ่งต้องเขียนไฟล์ /etc/shadow ที่ผู้ใช้ทั่วไปเขียนไม่ได้ โปรแกรมนี้จึงถูกตั้งบิต SUID และตรวจสอบเองว่าผู้ใช้ที่เรียกมีสิทธิ์เปลี่ยนรหัสผ่านของบัญชีใด

ความเสี่ยงเกิดเมื่อโปรแกรมนั้นไม่ได้จำกัดสิ่งที่ผู้ใช้ทำได้อย่างรัดกุม หากโปรแกรมยอมให้ผู้ใช้ระบุคำสั่งที่จะรัน ระบุไฟล์ที่จะอ่าน หรือโหลดไลบรารีจากตำแหน่งที่ผู้ใช้ควบคุม ผู้ใช้ก็จะได้สิทธิ์ของเจ้าของไฟล์ไปโดยปริยาย

การค้นหาไฟล์ที่ตั้งบิตพิเศษ

การค้นหาไฟล์ SUID ใช้คำสั่ง find ตามที่กล่าวในหัวข้อก่อนหน้า และควรบันทึกผลไว้เทียบกับรายการมาตรฐานของระบบ การเปรียบเทียบนี้ช่วยแยกไฟล์ที่มากับแพ็กเกจออกจากไฟล์ที่ถูกเพิ่มเข้ามาภายหลัง

find / -xdev -perm -4000 -type f 2>/dev/null | sort > suid-found.txt
dpkg -S $(cat suid-found.txt) 2>/dev/null

คำสั่ง dpkg -S ใช้ตรวจว่าไฟล์ใดเป็นของแพ็กเกจใด ในระบบที่ใช้ตระกูลเรดแฮตจะใช้ rpm -qf แทน ไฟล์ที่ไม่เป็นของแพ็กเกจใดเลยคือไฟล์ที่ควรตรวจเป็นลำดับแรก เพราะอาจถูกติดตั้งโดยผู้รับเหมาหรือถูกวางไว้โดยผู้บุกรุก

ตาราง 12.13 โปรแกรม SUID มาตรฐานและสิ่งที่ต้องพิจารณา
โปรแกรมเหตุผลที่มีบิต SUIDสิ่งที่ต้องตรวจ
passwdเขียนไฟล์รหัสผ่านจำกัดว่าผู้ใช้แก้รหัสผ่านของใคร
suเปลี่ยนบัญชีผู้ใช้ต้องยืนยันรหัสผ่านหรือไม่

โปรแกรมในตารางนี้ไม่ใช่ช่องโหว่โดยตัวเอง แต่เป็นรายการที่ต้องตรวจทุกครั้งว่าการตั้งค่าและเวอร์ชันยังปลอดภัย หากระบบมีโปรแกรมรุ่นเก่าที่มีช่องโหว่ที่รู้จัก การมีบิต SUID จะทำให้ช่องโหว่นั้นยกระดับสิทธิ์ได้ทันที

การวิเคราะห์โปรแกรมที่พบ

เมื่อพบไฟล์ SUID ที่ไม่คุ้นเคย ลำดับการวิเคราะห์มีสี่ขั้น ขั้นแรกคือตรวจชนิดไฟล์และสถาปัตยกรรมด้วย file เพื่อแยกว่าเป็นไบน์นารีจริงหรือสคริปต์ ขั้นที่สองคือตรวจเจ้าของและสิทธิ์ด้วย ls -l และ stat เพื่อยืนยันว่าเจ้าของเป็น root จริง

ขั้นที่สามคือดูว่าภายในโปรแกรมมีข้อความที่บอกการทำงานหรือไม่ คำสั่ง strings แสดงข้อความที่ฝังอยู่ในไบน์นารี ซึ่งอาจเผยชื่อคำสั่ง ไฟล์ตั้งค่า หรือข้อความแจ้งข้อผิดพลาดที่บอกว่าตัวโปรแกรมทำอะไร

ขั้นที่สี่คือตรวจว่าคำสั่งนั้นมีอยู่ในฐานข้อมูล GTFOBins หรือไม่ ฐานข้อมูลนี้รวบรวมโปรแกรมมาตรฐานที่เมื่อได้รับสิทธิ์สูงแล้วยอมให้ผู้ใช้ทำสิ่งที่เป็นอันตราย เช่น เปิดเชลล์ อ่านไฟล์ หรือเขียนไฟล์

ฐานข้อมูล GTFOBins และข้อจำกัด

GTFOBins เป็นฐานข้อมูลที่จัดกลุ่มความสามารถของโปรแกรมตามชนิดของผลลัพธ์ เช่น การเปิดเชลล์ การอ่านไฟล์ การเขียนไฟล์ และการข้ามสิทธิ์ แต่ละรายการอธิบายเงื่อนไขที่ต้องเป็นจริง เช่น ต้องรันผ่าน sudo หรือต้องเป็นไฟล์ SUID และต้องใช้ตัวเลือกใด

ประโยชน์ของฐานข้อมูลนี้คือช่วยลดเวลาค้นหาว่าโปรแกรมที่ดูไม่น่ามีอันตรายนั้นมีพฤติกรรมอะไรซ่อนอยู่ ตัวอย่างเช่นโปรแกรมค้นหาไฟล์ที่ดูเรียบง่ายอาจมีตัวเลือกให้รันคำสั่ง arbitrary ได้ หรือโปรแกรมอ่านเอกสารอาจมีคำสั่งเปิดเชลล์จากภายใน

ข้อจำกัดมีสามประการ ประการแรกคือรายการในฐานข้อมูลอาจไม่ตรงกับเวอร์ชันที่ติดตั้งในเครื่อง เพราะตัวเลือกอาจถูกถอดออกหรือเพิ่มเข้ามาในรุ่นใหม่ ประการที่สองคือการตั้งค่าของระบบอาจจำกัดอาร์กิวเมนต์ที่อนุญาต ทำให้วิธีในฐานข้อมูลใช้ไม่ได้ ประการที่สามคือฐานข้อมูลบอกว่าทำได้ แต่ไม่ได้บอกว่าควรทำหรือไม่ การทดสอบในระบบจริงต้องเลือกวิธีที่ไม่ทำลายข้อมูล

ตัวอย่างการยืนยันผลอย่างไม่ทำลายระบบ

สมมติว่าผู้ทดสอบพบไฟล์ SUID ที่เป็นโปรแกรมค้นหาไฟล์และโปรแกรมนั้นยอมให้รันคำสั่งได้ การยืนยันว่ากระบวนการได้สิทธิ์จริงทำได้โดยรันคำสั่งที่ไม่เปลี่ยนแปลงอะไรและเขียนผลลงไฟล์ชั่วคราว

/usr/local/bin/find /tmp -maxdepth 0 -exec id \; 2>/dev/null

หากผลลัพธ์แสดง uid=0(root) แปลว่าคำสั่งที่ถูกเรียกทำงานด้วยสิทธิ์ของเจ้าของไฟล์ ไม่ใช่สิทธิ์ของผู้ใช้ที่สั่ง การพิสูจน์แบบนี้ไม่เปิดเชลล์ค้างไว้ ไม่แก้ไขไฟล์ระบบ และลบร่องรอยได้ง่าย

ข้อควรระวังคือคำสั่งที่รันภายใต้โปรแกรม SUID อาจทำงานกับไฟล์จริงได้หากระบุเส้นทางผิด ผู้ทดสอบจึงควรจำกัดขอบเขตด้วยเส้นทางชั่วคราวและตรวจคำสั่งให้ดีก่อนรัน การทดสอบในเครื่องเสมือนก่อนลงมือกับระบบจริงเป็นแนวปฏิบัติที่ควรทำเสมอ

SGID และไลบรารีที่ถูกโหลด

บิต SGID บนโปรแกรมให้ผลคล้าย SUID แต่เปลี่ยนกลุ่มที่มีผลแทนหมายเลขผู้ใช้ ผลลัพธ์จึงขึ้นกับว่ากลุ่มนั้นมีสิทธิ์อะไร หากกลุ่มมีสิทธิ์อ่านไฟล์สำคัญหรือเขียนโฟลเดอร์ของบริการ ก็อาจใช้ยกระดับได้เช่นกัน

บิต SGID บนโฟลเดอร์เป็นเรื่องปกติในโฟลเดอร์ทำงานร่วมกัน เพราะทำให้ไฟล์ใหม่สืบทอดกลุ่มเดียวกับโฟลเดอร์ ปัญหาเกิดขึ้นเมื่อโฟลเดอร์นั้นถูกใช้เก็บไฟล์ที่โปรแกรมสิทธิ์สูงเรียกใช้ และผู้ใช้ทั่วไปสามารถสร้างไฟล์ในโฟลเดอร์นั้นได้

อีกเส้นทางที่เกี่ยวข้องคือการโหลดไลบรารีแบบพลวัต โปรแกรมส่วนใหญ่ไม่ได้บรรจุโค้ดทั้งหมดไว้ในไฟล์เดียว แต่เรียกใช้ไลบรารีร่วมจากตำแหน่งที่กำหนดไว้ในตัวโปรแกรมหรือจากตัวแปรสภาพแวดล้อม หากตำแหน่งที่ค้นหาอยู่ในโฟลเดอร์ที่ผู้ใช้เขียนได้ ผู้ใช้สามารถวางไลบรารีของตนให้ถูกโหลดแทนของจริงได้

อย่างไรก็ดี กลไกป้องกันของลินุกซ์จะล้างตัวแปรอย่าง LD_PRELOAD และ LD_LIBRARY_PATH เมื่อเรียกโปรแกรมที่มีบิต SUID หรือ SGID การใช้ตัวแปรเหล่านี้กับโปรแกรม SUID จึงมักไม่สำเร็จ เว้นแต่ระบบถูกตั้งค่าให้เก็บตัวแปรนั้นไว้เป็นกรณีพิเศษ ซึ่งเป็นความผิดพลาดที่พบได้น้อยแต่มีผลร้ายแรง

เส้นทางที่ได้ผลกว่าคือการวางไลบรารีในตำแหน่งที่โปรแกรมค้นหาตามค่าเริ่มต้นอยู่แล้ว เช่น โฟลเดอร์ของโปรแกรมเองหรือโฟลเดอร์ที่ระบุไว้ใน RPATH หากโฟลเดอร์เหล่านั้นเขียนได้ ผู้ใช้ก็สามารถแทรกไลบรารีได้โดยไม่ต้องพึ่งตัวแปรสภาพแวดล้อม

ตาราง 12.14 เงื่อนไขที่ทำให้ไฟล์ SUID กลายเป็นช่องโหว่ที่ใช้ได้
เงื่อนไขสิ่งที่ต้องเป็นจริงวิธีตรวจ
เจ้าของไฟล์เป็น root หรือบัญชีที่มีสิทธิ์สูงกว่าls -l, stat
พฤติกรรมโปรแกรมยอมให้รันคำสั่ง อ่านไฟล์ หรือเขียนไฟล์ตามที่ผู้ใช้กำหนดstrings, ทดลองในเครื่องเสมือน
ข้อจำกัดอาร์กิวเมนต์ไม่ได้จำกัดตัวเลือกที่อันตรายตรวจการตั้งค่าและคู่มือ
สิทธิ์ของโฟลเดอร์โฟลเดอร์ที่โปรแกรมเรียกใช้เขียนได้namei -l, ls -ld
สภาพแวดล้อมไม่มีนโยบายบังคับที่บล็อกการทำงานgetenforce, aa-status

การเห็นไฟล์ SUID ที่เป็นของ root จึงเป็นเพียงจุดเริ่มต้น ข้อสรุปจะเกิดได้ต่อเมื่อตรวจพฤติกรรมและเงื่อนไขครบทุกข้อในตารางนี้

การป้องกันและผลต่อการรายงาน

มาตรการป้องกันเริ่มจากการลบบิต SUID ออกจากไฟล์ที่ไม่จำเป็น และเพิ่มตัวเลือก nosuid ในการเมานต์ระบบไฟล์ที่ผู้ใช้ทั่วไปเขียนได้ เช่น /home และ /tmp ตัวเลือกนี้ทำให้บิต SUID บนระบบไฟล์นั้นไม่มีผลแม้ผู้ใช้พยายามสร้างไฟล์ของตน

นอกจากนี้ควรมีกระบวนการตรวจสอบไฟล์ที่ตั้งบิตพิเศษเป็นรอบ และเปรียบเทียบกับรายการมาตรฐานของแพ็กเกจ การเปลี่ยนแปลงที่ไม่มาจากการอัปเดตตามปกติควรได้รับการตรวจสอบทันที

ในรายงาน ข้อค้นพบเกี่ยวกับ SUID ต้องระบุชื่อไฟล์เต็ม เจ้าของ พฤติกรรมที่ทำให้ใช้ประโยชน์ได้ และเงื่อนไขที่ต้องครบ การรายงานเพียงว่า "พบไฟล์ SUID จำนวนมาก" ไม่ช่วยให้ทีมแก้ไขตัดสินใจได้ว่าควรลบไฟล์ใดก่อน

12.5 การตั้งค่า sudo ที่ผิดพลาด

การอ่านผลจาก sudo -l

คำสั่ง sudo -l แสดงกฎที่ใช้บังคับกับผู้ใช้ปัจจุบัน เป็นจุดเริ่มต้นที่ดีที่สุดของการตรวจสอบสิทธิ์เพราะบอกทั้งคำสั่งที่อนุญาต ผู้ใช้ปลายทาง และเงื่อนไขการยืนยันรหัสผ่านในครั้งเดียว

$ sudo -l
Matching Defaults entries for www-data on APP01:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

User www-data may run the following commands on APP01:
    (root) NOPASSWD: /usr/bin/systemctl restart app
    (root) /usr/bin/tee /var/log/app.log

ผลลัพธ์แบ่งเป็นสามส่วน ส่วนแรกคือค่าตั้งต้น (Defaults) ซึ่งกำหนดพฤติกรรมของ sudo เช่น การล้างตัวแปรสภาพแวดล้อม และเส้นทางค้นหาคำสั่งที่ปลอดภัย ส่วนที่สองคือรายการกฎ ซึ่งระบุผู้ใช้ปลายทางและคำสั่ง ส่วนที่สามอาจมีข้อความเตือนเกี่ยวกับรหัสผ่านหรือนโยบาย

ตาราง 12.15 สิ่งที่ต้องอ่านจากผลคำสั่ง sudo -l
ส่วนตัวอย่างความหมาย
ผู้ใช้ปลายทาง(root)คำสั่งจะถูกรันในนามของบัญชีใด
เงื่อนไขรหัสผ่านNOPASSWD:ไม่ต้องยืนยันรหัสผ่านก่อนรัน
คำสั่ง/usr/bin/systemctlโปรแกรมที่อนุญาตให้รัน
อาร์กิวเมนต์restart appขอบเขตของอาร์กิวเมนต์ที่อนุญาต
ค่าตั้งต้นsecure_path=...เส้นทางที่ sudo ใช้ค้นหาคำสั่ง
ตัวแปรที่คงไว้env_keep+=...ตัวแปรที่ส่งต่อไปยังคำสั่งปลายทาง

การอ่านกฎต้องดูทั้งบรรทัด ไม่ใช่ดูเฉพาะชื่อคำสั่ง หากคำสั่งเดียวกันถูกอนุญาตพร้อมอาร์กิวเมนต์ที่จำกัด การใช้ประโยชน์จะทำได้เพียงภายในขอบเขตนั้น แต่หากอาร์กิวเมนต์เป็นเครื่องหมายดาวหรือไม่ได้ระบุเลย ผู้ใช้มักเลือกอาร์กิวเมนต์เองได้

นอกจากกฎแล้ว ควรตรวจเวอร์ชันของ sudo ด้วยคำสั่ง sudo -V เพราะมีช่องโหว่ที่รู้จักในบางเวอร์ชันซึ่งทำให้ผู้ใช้ทั่วไปได้สิทธิ์ root โดยไม่ต้องมีกฎใดเลย การรู้เวอร์ชันช่วยให้เทียบกับประกาศความปลอดภัยได้ถูกต้อง

รูปแบบการตั้งค่าที่เสี่ยง

ตาราง 12.16 รูปแบบการตั้งค่า sudo ที่เสี่ยงและเหตุผล
รูปแบบตัวอย่างเหตุใดจึงเสี่ยง
อนุญาตโปรแกรมตีความ(root) NOPASSWD: /usr/bin/python3ผู้ใช้รันโค้ดใดก็ได้ในนาม root
อนุญาตโปรแกรมแก้ไข(root) /usr/bin/vimโปรแกรมแก้ไขเปิดเชลล์หรือเขียนไฟล์ใดก็ได้
อนุญาตคำสั่งอ่านไฟล์(root) /usr/bin/catอ่านไฟล์สำคัญเช่น /etc/shadow ได้
อนุญาตคำสั่งเขียนไฟล์(root) /usr/bin/teeเขียนทับไฟล์ระบบหรือเพิ่มบัญชีได้
ใช้อาร์กิวเมนต์แบบดาว/usr/bin/systemctl restart *เลือกบริการใดก็ได้ รวมถึงบริการที่แก้ไขได้
อนุญาตทั้งกลุ่ม%developers ALL=(ALL) ALLสมาชิกทุกคนได้สิทธิ์เต็มโดยไม่ต้องตรวจรายบุคคล
คงตัวแปรสภาพแวดล้อมenv_keep+=LD_PRELOADโหลดไลบรารีของผู้ใช้เข้าไปในคำสั่งที่รันด้วยสิทธิ์สูง
ไม่จำกัดคำสั่ง(ALL:ALL) ALLเทียบเท่าให้ root ทั้งหมด

รูปแบบแรกเป็นปัญหาที่พบบ่อยที่สุด เพราะผู้ดูแลระบบมักคิดว่าโปรแกรมตีความเช่นไพทอนเป็นเครื่องมือทำงาน ไม่ใช่ช่องทางโจมตี แต่โปรแกรมเหล่านี้ออกแบบมาให้รันโค้ดที่ผู้ใช้เขียนขึ้น จึงไม่มีความแตกต่างระหว่างการอนุญาตให้รันไพทอนกับการอนุญาตให้รันคำสั่งใดก็ได้

รูปแบบที่เกี่ยวกับโปรแกรมแก้ไขก็เช่นกัน โปรแกรมแก้ไขมาตรฐานมักมีคำสั่งภายในที่เรียกเชลล์หรืออ่านเขียนไฟล์อื่นได้ การอนุญาตให้แก้ไขไฟล์หนึ่งจึงไม่ได้จำกัดผลลัพธ์ไว้ที่ไฟล์นั้น เว้นแต่จะใช้กลไก sudoedit ที่แยกสิทธิ์อ่านและเขียนอย่างถูกต้อง

การใช้อาร์กิวเมนต์แบบดาวเป็นความผิดพลาดที่ตรวจพบได้ยาก เพราะดูเหมือนจำกัดคำสั่งไว้แล้ว แต่ดาวเปิดช่องให้เลือกอาร์กิวเมนต์ใดก็ได้ รวมถึงค่าที่ทำให้โปรแกรมทำงานนอกเหนือเจตนา การอนุญาตควรระบุอาร์กิวเมนต์ที่ต้องการจริงและปฏิเสธส่วนที่เหลือ

การใช้ GTFOBins กับสิทธิ์จาก sudo

ฐานข้อมูล GTFOBins ช่วยตอบคำถามว่าคำสั่งที่ถูกอนุญาตนั้นมีพฤติกรรมใดที่ใช้เปิดเชลล์หรืออ่านไฟล์ได้หรือไม่ การอ่านรายการควรดูบริบทกำกับ เพราะความสามารถเดียวกันอาจใช้ได้เฉพาะเมื่อรันผ่าน sudo หรือเฉพาะเมื่อเป็นไฟล์ SUID

สมมติว่ากฎอนุญาตคำสั่ง /usr/bin/awk โดยไม่จำกัดอาร์กิวเมนต์ การยืนยันว่าคำสั่งนั้นให้สิทธิ์จริงทำได้ด้วยคำสั่งที่ไม่เปิดเชลล์ค้างไว้

sudo /usr/bin/awk 'BEGIN{system("id")}'

หากผลลัพธ์แสดง uid=0(root) แปลว่าคำสั่งภายในถูกเรียกด้วยสิทธิ์ของ root การพิสูจน์ด้วย id ไม่เปลี่ยนสถานะระบบและไม่ทิ้งไฟล์ไว้ ต่างจากการเปิดเชลล์ซึ่งต้องจัดการ process ค้างและการบันทึกกิจกรรม

ข้อควรระวังคือการทดสอบกับคำสั่งที่เขียนไฟล์อาจทำให้ไฟล์ระบบเสียหายได้ ผู้ทดสอบควรทดสอบกับไฟล์ชั่วคราวก่อนเสมอ และควรตรวจว่ากฎที่เห็นนั้นใช้กับคำสั่งและอาร์กิวเมนต์ที่กำลังจะรันจริง ไม่ใช่กฎของบัญชีอื่น

sudoedit และตัวแปรสภาพแวดล้อม

sudoedit เป็นโหมดพิเศษของ sudo ที่ให้ผู้ใช้แก้ไขไฟล์ด้วยสิทธิ์ของตนเอง แต่ระบบจะเขียนไฟล์กลับด้วยสิทธิ์สูงเมื่อบันทึก กลไกนี้ออกแบบมาเพื่อลดความเสี่ยงจากการรันโปรแกรมแก้ไขด้วยสิทธิ์ root โดยตรง

ความเสี่ยงยังเกิดได้หากระบบตั้งค่าให้ผู้ใช้เลือกโปรแกรมแก้ไขเอง หรือคงตัวแปรที่เกี่ยวข้องกับโปรแกรมแก้ไขไว้ ผู้ใช้ก็อาจเปลี่ยนโปรแกรมแก้ไขเป็นคำสั่งอื่นได้ การตั้งค่าที่ปลอดภัยคือกำหนดโปรแกรมแก้ไขตายตัวและไม่คงตัวแปรที่ผู้ใช้ควบคุม

ตัวแปรสภาพแวดล้อมอีกกลุ่มที่ต้องตรวจคือ LD_PRELOAD และ LD_LIBRARY_PATH ตามที่กล่าวในหัวข้อก่อนหน้า โดยปกติ sudo จะล้างตัวแปรเหล่านี้ออกก่อนรันคำสั่ง แต่หากไฟล์ sudoers ระบุให้คงไว้ คำสั่งที่รันด้วยสิทธิ์ root จะโหลดไลบรารีที่ผู้ใช้กำหนด ซึ่งเทียบเท่าการรันโค้ดของตนในนาม root

การตรวจว่ามีการคงตัวแปรใดทำได้จากผล sudo -l ส่วนคำสั่ง sudo -V แสดงรายการความสามารถที่คอมไพล์เข้ามาในไบนารี ซึ่งช่วยในการประเมินเวอร์ชัน

การยืนยันผลและการป้องกัน

การยืนยันสิทธิ์จาก sudo ควรทำด้วยคำสั่งที่อ่านค่าอย่างเดียว เช่น id, hostname หรือการอ่านไฟล์ที่ไม่มีข้อมูลอ่อนไหว หากจำเป็นต้องอ่านไฟล์สำคัญเพื่อพิสูจน์ผล ควรอ่านเพียงบรรทัดแรกและบันทึกเฉพาะข้อมูลที่จำเป็นต่อการยืนยัน ไม่ควรคัดลอกเนื้อหาทั้งไฟล์ลงรายงาน

มาตรการป้องกันเริ่มจากการทบทวนกฎใน sudoers ทั้งหมดและลบกฎที่ไม่ได้ใช้ การอนุญาตควรระบุคำสั่งและอาร์กิวเมนต์ให้แคบที่สุด หลีกเลี่ยงโปรแกรมตีความและโปรแกรมแก้ไข และไม่ใช้เครื่องหมายดาวในอาร์กิวเมนต์

ควรเปิดการบันทึกคำสั่งที่รันผ่าน sudo ไว้ที่ส่วนกลาง และตรวจสอบเป็นระยะ การบันทึกนี้มีประโยชน์ทั้งต่อการตรวจสอบเหตุการณ์และการสอบสวนย้อนหลัง เพราะบอกว่าใครรันอะไรเมื่อใด

สุดท้าย ควรติดตามประกาศความปลอดภัยของ sudo และปรับปรุงให้เป็นเวอร์ชันล่าสุด ช่องโหว่ในตัว sudo เองเคยทำให้ผู้ใช้ทั่วไปได้สิทธิ์ root โดยไม่ต้องมีกฎใด ซึ่งแสดงให้เห็นว่าการตั้งค่าที่ดีเพียงอย่างเดียวไม่พอหากซอฟต์แวร์ไม่ได้ปรับปรุง

12.6 งานที่ถูกตั้งเวลาและการแทรกผ่าน PATH

ตำแหน่งของงานที่ถูกตั้งเวลา

ลินุกซ์มีงานที่ถูกตั้งเวลาได้หลายรูปแบบ แต่ละรูปแบบเก็บคำนิยามไว้ต่างตำแหน่งและรันด้วยบัญชีต่างกัน การรู้ตำแหน่งเหล่านี้เป็นพื้นฐานก่อนตรวจว่าใครแก้ไขได้

ตาราง 12.17 ตำแหน่งของงานที่ถูกตั้งเวลาและสิ่งที่ต้องตรวจ
ตำแหน่งรูปแบบบัญชีที่รันสิ่งที่ต้องตรวจ
/etc/crontabมีช่องระบุผู้ใช้ก่อนคำสั่งตามช่องผู้ใช้สิทธิ์ของไฟล์และสคริปต์ที่เรียก
/etc/cron.d/ไฟล์เดี่ยว มีช่องผู้ใช้ตามช่องผู้ใช้ไฟล์และสคริปต์ที่อ้างถึง
/etc/cron.hourly/, /etc/cron.daily/สคริปต์ที่ถูกเรียกผ่าน run-partsrootชื่อไฟล์และสิทธิ์เขียน
/var/spool/cron/crontabs/ไฟล์ของแต่ละผู้ใช้เจ้าของไฟล์สิทธิ์ของโฟลเดอร์และไฟล์
ไทเมอร์ของ systemdไฟล์ .timer และ .serviceตามยูนิตสิทธิ์ของยูนิตและคำสั่ง
atคิวงานครั้งเดียวตามผู้สั่งคิวที่ค้างอยู่และสิทธิ์

คำสั่ง crontab -l แสดงงานของผู้ใช้ปัจจุบัน ส่วนงานของระบบต้องอ่านจากไฟล์ในตารางข้างต้นโดยตรง การตรวจควรเริ่มจากรายการงานทั้งหมดแล้วจึงตรวจสคริปต์ที่แต่ละงานเรียก เพราะช่องโหว่มักอยู่ที่สคริปต์ ไม่ใช่ที่บรรทัด cron

ls -la /etc/cron.d /etc/cron.daily /etc/cron.hourly
cat /etc/crontab
systemctl list-timers --all

ในระบบที่ใช้ systemd ไทเมอร์อาจทำงานแทน cron ทั้งหมด การตรวจเฉพาะ cron จึงไม่พอ ต้องตรวจยูนิตที่เกี่ยวข้องด้วย โดยดูว่า ExecStart ชี้ไปยังไฟล์ใดและไฟล์นั้นแก้ไขได้หรือไม่

เงื่อนไขที่ทำให้งานที่ถูกตั้งเวลาเป็นช่องโหว่

ช่องโหว่เกิดเมื่อผู้ใช้ทั่วไปสามารถเปลี่ยนสิ่งที่งานจะรันได้ ไม่ว่าจะโดยแก้ไขสคริปต์โดยตรง เปลี่ยนไฟล์ที่สคริปต์เรียก หรือเปลี่ยนเส้นทางที่ใช้ค้นหาคำสั่ง

ตาราง 12.18 เงื่อนไขของช่องโหว่งานที่ถูกตั้งเวลา
เงื่อนไขสิ่งที่ต้องเป็นจริงวิธีตรวจ
งานรันด้วยสิทธิ์สูงผู้ใช้ในงานเป็น root หรือมีสิทธิ์มากกว่าอ่านบรรทัด cron หรือยูนิต
สคริปต์แก้ไขได้ไฟล์หรือโฟลเดอร์เขียนได้โดยผู้ใช้ls -l, namei -l
คำสั่งถูกเรียกโดยไม่ระบุเส้นทางใช้ชื่อคำสั่งล้วนอ่านเนื้อสคริปต์
PATH มีโฟลเดอร์ที่เขียนได้โฟลเดอร์นั้นอยู่ก่อนโฟลเดอร์ระบบตรวจ PATH ในสคริปต์และยูนิต
งานทำงานซ้ำมีรอบเวลาที่แน่นอนดูตารางเวลา

การแก้ไขสคริปต์เป็นวิธีที่ตรงไปตรงมาและตรวจพบได้ง่าย เพราะผู้ใช้ต้องเขียนไฟล์ที่เจ้าของเป็น root การกระทำนี้มักถูกบันทึกโดยระบบตรวจสอบไฟล์ แต่ในเครื่องที่ไม่มีระบบตรวจสอบไฟล์ ผู้ใช้สามารถแก้ไขและรอรอบถัดไปได้โดยไม่มีใครเห็น

วิธีที่แนบเนียนกว่าคือการไม่แตะสคริปต์เลย แต่เปลี่ยนไฟล์ที่สคริปต์เรียกใช้ เช่น ไฟล์ตั้งค่าที่สคริปต์อ่าน หรือไฟล์ข้อมูลที่สคริปต์ประมวลผล หากไฟล์เหล่านั้นอยู่ในโฟลเดอร์ที่ผู้ใช้เขียนได้ ผู้ใช้ก็เปลี่ยนพฤติกรรมของสคริปต์ได้โดยไม่ต้องแก้โค้ด

การสังเกตการทำงานของงานอัตโนมัติ

ในบางกรณีผู้ทดสอบไม่รู้ว่างานใดทำงานเมื่อใด และไม่สามารถอ่านไฟล์ cron ได้ทั้งหมด เครื่องมืออย่าง pspy ช่วยเฝ้าดูกระบวนการที่ถูกสร้างขึ้นโดยไม่ต้องมีสิทธิ์ root ทำให้เห็นว่างานใดทำงานและรันคำสั่งอะไร

การใช้เครื่องมือลักษณะนี้ต้องอยู่ในขอบเขตที่ตกลงไว้และควรแจ้งผู้ดูแลระบบก่อน เพราะเป็นการเฝ้าดูกระบวนการทั้งเครื่องซึ่งอาจเก็บข้อมูลของผู้ใช้คนอื่น การบันทึกผลควรจำกัดเฉพาะกระบวนการที่เกี่ยวข้องกับงานที่สงสัย

อีกวิธีที่ไม่ต้องใช้เครื่องมือเพิ่มคือการเดาจากรูปแบบเวลา งานสำรองข้อมูลมักทำงานตอนกลางคืน งานตรวจสอบบันทึกมักทำงานทุกชั่วโมง และงานทำความสะอาดไฟล์ชั่วคราวมักทำงานทุกวัน การรอรอบเวลาอาจใช้เวลาแต่ไม่ทิ้งร่องรอยเพิ่ม

การแทรกคำสั่งผ่าน PATH

เมื่อเชลล์ได้รับคำสั่งที่ไม่ระบุเส้นทางเต็ม เช่น tar หรือ backup มันจะค้นหาโปรแกรมตามลำดับโฟลเดอร์ในตัวแปร PATH และใช้โปรแกรมแรกที่พบ หากโฟลเดอร์ที่เขียนได้อยู่ก่อนโฟลเดอร์ระบบ ผู้ใช้สามารถวางโปรแกรมชื่อเดียวกันไว้ในโฟลเดอร์นั้นเพื่อให้ถูกเรียกแทน

ตาราง 12.19 เงื่อนไขที่ทำให้การแทรกผ่าน PATH สำเร็จ
เงื่อนไขสิ่งที่ต้องเป็นจริงวิธีตรวจ
คำสั่งไม่ระบุเส้นทางสคริปต์เรียกชื่อคำสั่งล้วนอ่านเนื้อสคริปต์
PATH มีโฟลเดอร์ที่เขียนได้โฟลเดอร์นั้นอยู่ก่อนโฟลเดอร์จริงecho $PATH, อ่านสคริปต์
โฟลเดอร์นั้นไม่อยู่ในรายการป้องกันไม่ได้ถูกเมานต์แบบอ่านอย่างเดียวmount, ls -ld
งานรันด้วยสิทธิ์สูงเจ้าของงานเป็น rootอ่านบรรทัด cron
ชื่อคำสั่งไม่ซ้ำกับของระบบในโฟลเดอร์ก่อนหน้าไม่มีโปรแกรมชื่อเดียวกันอยู่ก่อนแล้วตรวจตามลำดับ PATH

ปัญหานี้พบบ่อยในสคริปต์ที่ผู้ดูแลระบบเขียนเอง เพราะผู้เขียนมักทดสอบในเซสชันที่ PATH ต่างจาก PATH ของ cron ใน cron ค่า PATH มักสั้นกว่ามาก และอาจรวมโฟลเดอร์ของแอปพลิเคชันที่ผู้ใช้เขียนได้

ตัวอย่างสมมติคือสคริปต์สำรองข้อมูลที่เรียก tar โดยไม่ระบุเส้นทาง และมีบรรทัดกำหนด PATH=/opt/backup/bin:/usr/bin:/bin อยู่ตอนต้น หากโฟลเดอร์ /opt/backup/bin เปิดให้ผู้ใช้ทั่วไปเขียนได้ ผู้ใช้ก็สามารถวางไฟล์ชื่อ tar ไว้ในนั้นและรอให้งานทำงาน

การยืนยันทำได้โดยวางสคริปต์ทดสอบที่เขียนผลของ id ลงไฟล์ชั่วคราว รอรอบถัดไป แล้วลบไฟล์ทิ้ง วิธีนี้ไม่เปลี่ยนไฟล์ระบบและเห็นผลได้ชัดว่าโปรแกรมถูกเรียกด้วยบัญชีใด

การป้องกันงานอัตโนมัติ

มาตรการพื้นฐานมีสี่ข้อ ข้อแรก ไฟล์สคริปต์และโฟลเดอร์ที่เก็บต้องเป็นของ root และอนุญาตให้เฉพาะ root เขียน ข้อที่สอง สคริปต์ควรเรียกคำสั่งด้วยเส้นทางเต็มทุกครั้ง ข้อที่สาม ควรกำหนด PATH ไว้ตอนต้นสคริปต์ให้มีเฉพาะโฟลเดอร์ระบบ และข้อที่สี่ ควรตรวจรายการงานที่ถูกตั้งเวลาเป็นระยะและลบงานที่ไม่ได้ใช้

สำหรับยูนิตของ systemd ควรกำหนดผู้ใช้และกลุ่มให้ชัดเจน จำกัดสิทธิ์ด้วยตัวเลือกด้านความปลอดภัย เช่น NoNewPrivileges, ProtectSystem และ PrivateTmp และตรวจว่าไฟล์ยูนิตแก้ไขได้เฉพาะผู้ดูแลระบบ

ในรายงาน ข้อค้นพบด้านงานอัตโนมัติควรระบุชื่อไฟล์งาน เวลาที่ทำงาน บัญชีที่รัน และไฟล์ที่ผู้ใช้แก้ไขได้ พร้อมหลักฐานว่าไฟล์นั้นถูกเรียกจริง การระบุเพียงว่า "พบ cron ที่เขียนได้" ไม่พอให้ทีมแก้ไขประเมินความเสี่ยงได้

12.7 Wildcard injection, capabilities และเส้นทางอื่น

กลไกของ wildcard injection

ในบทที่แล้ว ผู้เรียนเห็นว่าการเรียกคำสั่งด้วยอาร์กิวเมนต์ที่ผู้ใช้ควบคุมเป็นต้นเหตุของช่องโหว่หลายประเภท บนลินุกซ์มีรูปแบบหนึ่งที่เกิดจากตัวอักขระแทน (wildcard) ซึ่งเชลล์ขยายให้ก่อนส่งให้โปรแกรม ความพิเศษอยู่ที่ผลของการขยายอาจกลายเป็นตัวเลือกของคำสั่ง ไม่ใช่เพียงชื่อไฟล์

เมื่อเชลล์พบเครื่องหมาย * ในอาร์กิวเมนต์ มันจะแทนที่ด้วยรายชื่อไฟล์ในโฟลเดอร์ปัจจุบัน เรียงตามตัวอักษร แล้วส่งทั้งหมดเป็นอาร์กิวเมนต์ให้โปรแกรม หากชื่อไฟล์ขึ้นต้นด้วยเครื่องหมายลบ โปรแกรมที่รับอาร์กิวเมนต์จะตีความว่าเป็นตัวเลือก ไม่ใช่ชื่อไฟล์

ตัวอย่างที่ใช้เป็นกรณีศึกษามาตรฐานคือคำสั่งสำรองข้อมูลที่เขียนไว้ในงาน cron

cd /var/www/app && tar -czf /backup/app.tar.gz *

เจตนาของผู้เขียนคือบีบอัดทุกไฟล์ในโฟลเดอร์ แต่ถ้าผู้ใช้ทั่วไปเขียนไฟล์ในโฟลเดอร์นั้นได้ ผู้ใช้สามารถสร้างไฟล์ชื่อ --checkpoint=1 และ --checkpoint-action=exec=sh run.sh ไว้ในโฟลเดอร์ เมื่อเชลล์ขยาย * รายชื่อไฟล์จะกลายเป็นอาร์กิวเมนต์ของ tar และ tar จะตีความสองไฟล์แรกว่าเป็นตัวเลือก สั่งให้รันคำสั่งในไฟล์ run.sh ด้วยสิทธิ์ของเจ้าของงาน

จุดสำคัญของกลไกนี้คือโปรแกรมไม่เคยเห็น * เลย มันเห็นเพียงรายชื่อไฟล์ ซึ่งบางรายการบังเอิญมีรูปแบบเหมือนตัวเลือก การป้องกันจึงไม่ได้อยู่ที่การตรวจชื่อไฟล์ในสคริปต์ แต่อยู่ที่การไม่ใช้ wildcard กับโฟลเดอร์ที่ผู้ใช้เขียนได้ หรือใช้ตัวเลือก -- เพื่อบอกว่าไม่มีตัวเลือกเพิ่มเติมอีก

ตาราง 12.20 ตัวอย่างคำสั่งที่ได้รับผลจาก wildcard injection
คำสั่งตัวเลือกที่ถูกแทรกได้ผลที่เกิดขึ้น
tar -czf ... *--checkpoint-action=exec=...รันคำสั่งระหว่างบีบอัด
rsync ... *-e หรือ --rshเปลี่ยนคำสั่งที่ใช้เชื่อมต่อ
chown ... *--reference=...เปลี่ยนเจ้าของตามไฟล์อ้างอิง
chmod ... *--reference=...เปลี่ยนสิทธิ์ตามไฟล์อ้างอิง
zip ... *-T และ -TTรันคำสั่งทดสอบไฟล์

ช่องโหว่นี้พบบ่อยในสคริปต์สำรองข้อมูลและสคริปต์ทำความสะอาดไฟล์ ซึ่งมักเขียนขึ้นเพื่อความสะดวกและไม่คาดคิดว่าจะมีไฟล์ที่ขึ้นต้นด้วยเครื่องหมายลบในโฟลเดอร์เนื้อหาของเว็บ

การตรวจหาเริ่มจากการอ่านสคริปต์ที่รันด้วยสิทธิ์สูง แล้วมองหาคำสั่งที่ใช้ * หรือ ? กับโฟลเดอร์ที่ผู้ใช้เขียนได้ จากนั้นตรวจว่าโฟลเดอร์นั้นอนุญาตให้สร้างไฟล์ที่ขึ้นต้นด้วยเครื่องหมายลบหรือไม่ ซึ่งโดยปกติระบบไฟล์ลินุกซ์อนุญาต

การยืนยันว่าช่องโหว่มีจริงทำได้โดยสร้างไฟล์ทดสอบที่เขียนผลของ id ลงไฟล์ชั่วคราว รอรอบของงาน แล้วตรวจไฟล์ผลลัพธ์ วิธีนี้ไม่แตะข้อมูลจริงและลบได้ง่าย แต่ต้องระวังว่าไฟล์ทดสอบอาจถูกบีบอัดหรือลบไปพร้อมงาน จึงควรใช้ชื่อที่ชัดเจนและเก็บไว้นอกโฟลเดอร์ที่ถูกประมวลผล

มาตรการป้องกันมีสามระดับ ระดับแรกคือเปลี่ยนสคริปต์ให้ใช้ ./* หรือระบุรายชื่อไฟล์เอง ระดับที่สองคือใส่ -- ก่อน wildcard เพื่อสิ้นสุดการอ่านตัวเลือก ระดับที่สามคือย้ายโฟลเดอร์ที่ถูกบีบอัดออกจากโฟลเดอร์ที่ผู้ใช้เขียนได้ ซึ่งเป็นวิธีที่แก้ที่ต้นเหตุมากที่สุด

Linux capabilities ในทางปฏิบัติ

หัวข้อ 12.2 อธิบายว่า capabilities แบ่งอำนาจของ root เป็นหน่วยย่อย ในทางปฏิบัติ ผู้ทดสอบต้องตรวจสองอย่างคู่กัน คือไฟล์ใดได้รับ capability และโปรแกรมนั้นยอมให้ผู้ใช้ควบคุมสิ่งที่อยู่ภายใต้ capability นั้นได้หรือไม่

การค้นหาทั้งระบบใช้คำสั่งเดียว

getcap -r / 2>/dev/null

ผลลัพธ์มักสั้นกว่ารายการ SUID มาก ซึ่งทำให้ตรวจได้ละเอียดขึ้น ตัวอย่างผลที่มักพบในระบบจริง ได้แก่ ไบนารีที่ให้ความสามารถในการดักจับแพ็กเก็ต การผูกพอร์ตต่ำ และการจัดการเวลา

ตาราง 12.21 capability ที่พบบ่อยและเงื่อนไขการใช้ประโยชน์
capabilityโปรแกรมที่มักพบเงื่อนไขที่ทำให้ใช้ประโยชน์ได้
cap_net_rawping, tcpdumpโปรแกรมยอมให้อ่านหรือเขียนไฟล์ตามที่ผู้ใช้กำหนด
cap_net_bind_serviceไบนารีของบริการบริการยอมรับโค้ดหรือโมดูลจากผู้ใช้
cap_dac_read_searchเครื่องมือสำรองข้อมูลผู้ใช้ระบุไฟล์ที่จะอ่านได้
cap_dac_overrideเครื่องมือจัดการไฟล์ผู้ใช้ระบุไฟล์ที่จะเขียนได้
cap_setuidไบนารีเฉพาะกิจโปรแกรมเรียกฟังก์ชันเปลี่ยนผู้ใช้ตามค่าที่รับมา
cap_sys_adminเครื่องมือเมานต์ผู้ใช้ควบคุมพารามิเตอร์การเมานต์
cap_chownเครื่องมือคัดลอกไฟล์ผู้ใช้กำหนดเจ้าของปลายทางได้

กรณีที่ชัดที่สุดคือไบนารีที่ได้รับ cap_setuid และยอมให้ระบุหมายเลขผู้ใช้ เช่นเดียวกับกรณี SUID ที่โปรแกรมยอมให้รันคำสั่ง การยืนยันทำได้ด้วยการรันคำสั่งอ่านค่าในบริบทใหม่ แล้วตรวจว่าหมายเลขผู้ใช้เปลี่ยนจริง

capabilities ต่างจาก SUID ในจุดสำคัญสองจุด จุดแรก capabilities ไม่ได้ผูกกับเจ้าของไฟล์ จึงไม่แสดงในผล ls -l ตามปกติ ผู้ตรวจที่ดูเพียงบิตสิทธิ์จะมองไม่เห็น จุดที่สอง capabilities ถูกจำกัดด้วยชุดขอบเขต (bounding set) ของกระบวนการ หาก capability ไม่อยู่ในชุดขอบเขต ก็ไม่สามารถใช้ได้แม้ไฟล์จะตั้งไว้

ด้วยเหตุนี้ ระบบที่ตั้ง capabilities อย่างระมัดระวังจึงลดความเสี่ยงได้มากกว่าการใช้ SUID แต่ระบบที่ติดตั้งไบนารีจากแหล่งภายนอกโดยไม่ตรวจสอบอาจมี capability ที่เกินจำเป็นและไม่มีใครสังเกต

ไฟล์สำคัญที่เขียนได้

เส้นทางที่ตรงไปตรงมาที่สุดคือการที่ผู้ใช้ทั่วไปเขียนไฟล์ซึ่งระบบใช้ตัดสินสิทธิ์ได้ ไฟล์ที่อันตรายที่สุดคือ /etc/passwd ซึ่งเก็บรายชื่อบัญชีและโฟลเดอร์บ้าน หากเขียนได้ ผู้ใช้สามารถเพิ่มบัญชีที่มี UID เป็นศูนย์และรหัสผ่านที่ตนรู้ได้

ไฟล์ /etc/shadow มักอ่านได้เฉพาะ root แต่หากสิทธิ์ผิดพลาดจนผู้ใช้ทั่วไปอ่านได้ ผู้ใช้สามารถนำค่าแฮชไปทดลองเดารหัสผ่านแบบไม่จำกัดจำนวนครั้ง ซึ่งเป็นการโจมตีที่ไม่ทำให้ระบบเปลี่ยนแปลงและตรวจพบได้ยาก

ไฟล์ตั้งค่าของบริการก็อยู่ในกลุ่มเดียวกัน เช่น ไฟล์ที่กำหนดคำสั่งที่บริการจะรัน ไฟล์กำหนดเส้นทางของไลบรารี หรือไฟล์กำหนดผู้ใช้ของบริการ การเขียนไฟล์เหล่านี้มักให้ผลเทียบเท่าการรันคำสั่งด้วยสิทธิ์ของบริการ

ตาราง 12.22 ไฟล์และโฟลเดอร์ที่ควรตรวจสิทธิ์เป็นพิเศษ
เป้าหมายผลหากเขียนได้วิธีตรวจ
/etc/passwdเพิ่มบัญชี UID 0ls -l /etc/passwd
/etc/shadowอ่านหรือแก้แฮชรหัสผ่านls -l /etc/shadow
/etc/sudoers และ /etc/sudoers.d/เพิ่มกฎให้สิทธิ์ rootls -lR /etc/sudoers.d
ยูนิตของ systemdเปลี่ยนคำสั่งที่บริการรันls -l /etc/systemd/system
ไฟล์ตั้งค่าบริการเปลี่ยนพารามิเตอร์หรือคำสั่งnamei -l ตามเส้นทาง
โฟลเดอร์ใน PATH ของ rootแทรกโปรแกรมชื่อซ้ำecho $PATH, ls -ld
โฟลเดอร์บ้านของผู้ดูแลระบบวางไฟล์ที่ถูกเรียกภายหลังls -la /root

การตรวจควรใช้ namei -l กับทุกเส้นทาง เพราะไฟล์ปลายทางอาจมีสิทธิ์ถูกต้องแต่โฟลเดอร์แม่เปิดให้เขียน ซึ่งทำให้เปลี่ยนไฟล์ได้ด้วยวิธีเปลี่ยนชื่อหรือสร้างไฟล์ใหม่

การเมานต์ที่ขาดตัวเลือกป้องกัน

ระบบไฟล์ที่เมานต์โดยไม่มีตัวเลือก nosuid จะยอมให้บิต SUID บนไฟล์ในระบบไฟล์นั้นมีผล หากผู้ใช้ทั่วไปเขียนระบบไฟล์นั้นได้ เช่น โฟลเดอร์บ้านที่แยกพาร์ทิชันหรือไดรฟ์ภายนอก ผู้ใช้ก็สามารถวางไบนารีของตนที่ตั้งบิต SUID และรันได้ทันที

กรณีที่พบบ่อยในห้องแล็บและในระบบจริงคือการแชร์ผ่าน NFS ที่ตั้งค่า no_root_squash ซึ่งทำให้ผู้ใช้ที่มีสิทธิ์ระดับ root บนเครื่องลูกค้าสามารถสร้างไฟล์ที่เจ้าของเป็น root บนเครื่องแม่ข่ายได้ หากแชร์นั้นถูกเมานต์ไว้ในเส้นทางที่ระบบอื่นเรียกใช้ ก็อาจใช้วางไบนารีหรือแก้ไฟล์ตั้งค่าได้

การตรวจทำได้ด้วยคำสั่ง mount และการอ่าน /etc/fstab โดยดูว่าระบบไฟล์ใดขาด nosuid, nodev หรือ noexec และระบบไฟล์ใดถูกแชร์ออกโดยไม่จำกัดสิทธิ์

กลุ่มที่ให้สิทธิ์เทียบเท่า root

บนลินุกซ์บางระบบ การเป็นสมาชิกกลุ่มหนึ่งอาจเทียบเท่าการเป็น root โดยไม่ต้องยกระดับสิทธิ์เพิ่ม ตัวอย่างที่พบบ่อยคือกลุ่ม docker ซึ่งสมาชิกสามารถสั่งให้บริการคอนเทนเนอร์รันคำสั่งใดก็ได้ และสามารถเมานต์ระบบไฟล์ของเครื่องแม่ข่ายเข้าไปในคอนเทนเนอร์ได้

กลุ่มอื่นที่มีลักษณะเดียวกันได้แก่กลุ่มที่ดูแลไฮเปอร์ไวเซอร์ กลุ่มที่ดูแลระบบสำรองข้อมูล และกลุ่มที่อ่านไฟล์บันทึกของระบบได้ทั้งหมด การตรวจกลุ่มเสริมจึงไม่ใช่เพียงดูว่ามีกลุ่ม sudo หรือไม่ แต่ต้องดูว่ากลุ่มที่พบมีสิทธิ์อะไรในทางปฏิบัติ

การประเมินกลุ่มเหล่านี้ต้องอธิบายให้ชัดว่าไม่ได้เป็นข้อบกพร่องของการตั้งค่ากลุ่มโดยตรง แต่เป็นผลจากการออกแบบที่ให้สิทธิ์กว้างแก่กลุ่มเพื่อความสะดวก มาตรการที่เหมาะสมคือจำกัดสมาชิกและแยกเครื่องที่ใช้ทำงานเหล่านี้ออกจากเครื่องที่ผู้ใช้ทั่วไปเข้าถึง

ช่องโหว่ระดับเคอร์เนล

ช่องโหว่ในเคอร์เนลให้ผลรุนแรงเพราะผู้ใช้ที่ใช้ประโยชน์ได้จะได้สิทธิ์ระดับ kernel ซึ่งเทียบเท่า root และมักหลบเลี่ยงการตรวจของโปรแกรมป้องกันได้ แต่ก็เป็นเส้นทางที่เสี่ยงที่สุดต่อเสถียรภาพของระบบ การใช้ประโยชน์ผิดพลาดอาจทำให้เครื่องหยุดทำงานหรือข้อมูลเสียหาย

การประเมินจึงควรทำเมื่อเส้นทางอื่นหมดแล้วเท่านั้น และควรตรวจรุ่นเคอร์เนลเทียบกับประกาศความปลอดภัยก่อนเสมอ การเห็นรุ่นที่เก่าไม่ได้แปลว่าใช้ประโยชน์ได้ เพราะผู้ผลิตการกระจายบางรายได้ใส่การแก้ไขย้อนหลังโดยไม่เปลี่ยนเลขรุ่นหลัก

ในบทนี้ไม่สอนการเขียนโปรแกรมใช้ประโยชน์จากเคอร์เนล เพราะงานจริงส่วนใหญ่ใช้โค้ดที่เผยแพร่แล้วและการเลือกใช้ต้องอาศัยการทดสอบในเครื่องเสมือนก่อน สิ่งที่ผู้เรียนต้องทำได้คือระบุว่ารุ่นที่พบมีความเสี่ยงหรือไม่ และรายงานให้ทีมตัดสินใจอัปเดต

การเลือกเส้นทางอย่างมีความรับผิดชอบ

เมื่อพบเส้นทางหลายเส้นทาง ผู้ทดสอบควรเลือกเส้นทางที่กระทบระบบน้อยที่สุดและพิสูจน์ผลได้ชัดที่สุด ลำดับที่เหมาะสมคือเริ่มจากสิทธิ์ที่ได้มาโดยไม่ต้องรันโค้ดใดๆ เช่น การอ่านไฟล์ที่ตกค้าง จากนั้นจึงใช้การตั้งค่าที่มีอยู่ เช่น กฎ sudo หรือไฟล์ที่เขียนได้ และเก็บเส้นทางที่ต้องรันโค้ดหรือแตะเคอร์เนลไว้เป็นทางเลือกสุดท้าย

การเลือกเช่นนี้ไม่ใช่เพียงเรื่องจริยธรรม แต่เป็นเรื่องเทคนิค เพราะเส้นทางที่แตะระบบมากจะทิ้งร่องรอยมากและทำให้การสอบสวนภายหลังแยกแยะได้ยากว่าอะไรคือการทดสอบและอะไรคือการบุกรุกจริง

เมื่อได้ผลแล้ว ขั้นต่อไปคือการยืนยันอย่างเป็นระบบและเก็บหลักฐานให้ตรวจสอบย้อนกลับได้ ซึ่งเป็นหัวข้อของส่วนถัดไป

12.8 การยืนยันผล การรายงาน และการป้องกัน

เกณฑ์การยืนยันผล

การยกระดับสิทธิ์ถือว่าสำเร็จเมื่อมีหลักฐานยืนยันสามอย่างครบ อย่างแรกคือหมายเลขผู้ใช้ที่มีผล (Effective UID) เป็นศูนย์ อย่างที่สองคือคำสั่งที่รันในบริบทใหม่ทำงานได้จริงตามที่อ้าง และอย่างที่สามคือหลักฐานนั้นตรวจสอบย้อนกลับได้ว่าได้มาจากการกระทำใด

เกณฑ์ข้อแรกฟังดูง่าย แต่มีกับดักหลายจุด ผู้ใช้ที่รันคำสั่ง id ผ่านโปรแกรม SUID อาจเห็น uid=0 ในผลลัพธ์ แต่กระบวนการที่เหลือยังทำงานด้วยสิทธิ์เดิม หากโปรแกรมนั้นเพียงเรียกคำสั่งแล้วจบลง การได้มาซึ่งสิทธิ์จึงเป็นเพียงชั่วคราวและอาจไม่เพียงพอต่อการอ้างว่ายกระดับได้จริง

การยืนยันที่ตรงกว่าคือรันคำสั่งที่ไม่เกี่ยวข้องกับโปรแกรมเดิมในบริบทใหม่ เช่น การอ่านไฟล์ที่ผู้ใช้ทั่วไปอ่านไม่ได้ หรือการเขียนไฟล์ในโฟลเดอร์ของ root แล้วตรวจว่าไฟล์นั้นมีเจ้าของเป็น root จริง จากนั้นจึงลบไฟล์ทิ้ง

ตาราง 12.23 เกณฑ์การยืนยันผลและหลักฐานที่ต้องเก็บ
เกณฑ์วิธีตรวจหลักฐานที่เก็บ
หมายเลขผู้ใช้เป็นศูนย์id ในบริบทใหม่ภาพหน้าจอหรือไฟล์บันทึกพร้อมเวลา
สิทธิ์ใช้งานจริงอ่านหรือเขียนไฟล์ที่จำกัดสิทธิ์ชื่อไฟล์ ผลของ ls -l ก่อนและหลัง
ที่มาของสิทธิ์ระบุกลไกที่ใช้คำสั่งเต็มและผลของ sudo -l หรือ getcap
ความสามารถทำซ้ำทำซ้ำได้ในเครื่องทดสอบบันทึกขั้นตอนและเงื่อนไข
การคืนสภาพระบบกลับสู่สภาพเดิมผลตรวจหลังลบไฟล์หรือคืนค่า

การเก็บหลักฐานอย่างมีวินัย

หลักฐานที่ดีต้องตอบได้ว่าใครทำ อะไร เมื่อใด ที่ใด และด้วยเครื่องมือใด การเก็บควรเริ่มก่อนลงมือ ไม่ใช่หลังได้ผล เพราะเมื่อได้สิทธิ์แล้วผู้ทดสอบมักเร่งทำงานต่อและลืมบันทึกขั้นตอนที่สำคัญ

วิธีที่ได้ผลคือเปิดการบันทึกเซสชันด้วย script ตั้งแต่ต้น ตั้งชื่อไฟล์ตามเครื่องและวันที่ และคำนวณค่าแฮชเมื่อจบงาน และเก็บไฟล์แยกจากเครื่องเป้าหมายเพื่อไม่ให้ผู้บุกรุกหรือผู้ดูแลระบบแก้ไขได้ภายหลัง

นอกจากไฟล์บันทึก ควรเก็บผลของคำสั่งสำคัญเป็นไฟล์แยก เช่น ผล sudo -l, ผล find สำหรับ SUID, ผล getcap และรายการงานที่ถูกตั้งเวลา การเก็บแยกช่วยให้ผู้ตรวจทานเห็นภาพรวมได้เร็วและลดความจำเป็นในการรันคำสั่งซ้ำ

สิ่งที่ไม่ควรเก็บคืองานเกินจำเป็น ไฟล์รหัสผ่านทั้งไฟล์ ข้อมูลส่วนบุคคลของผู้ใช้ และข้อมูลทางธุรกิจที่ไม่เกี่ยวกับการพิสูจน์สิทธิ์ การเก็บเกินความจำเป็นเพิ่มความเสี่ยงต่อองค์กรและทำให้รายงานมีข้อมูลที่ไม่ควรเผยแพร่

การคืนสภาพระบบ

การทดสอบที่ดียกระบบไว้ในสภาพที่ใช้งานได้เหมือนก่อนทดสอบ ผู้ทดสอบต้องลบไฟล์ที่สร้าง เพิ่ม หรือแก้ไขทั้งหมด และคืนค่าที่เปลี่ยนแปลงทุกจุด การคืนสภาพต้องทำก่อนจบงาน ไม่ใช่ปล่อยให้ทีมลูกค้าจัดการเอง

รายการที่ต้องตรวจก่อนจบงานมีดังนี้ ไฟล์ที่วางไว้ในโฟลเดอร์ที่เขียนได้ บัญชีที่เพิ่มใน /etc/passwd หรือ /etc/shadow กฎใน sudoers ที่แก้ไข ไฟล์ใน /tmp หรือโฟลเดอร์บ้าน ยูนิตของ systemd ที่สร้าง และงานที่ถูกตั้งเวลาที่เพิ่มเข้าไป

หากการทดสอบจำเป็นต้องเปลี่ยนไฟล์ระบบ ควรสำรองไฟล์เดิมไว้ก่อนและเก็บค่าแฮชของไฟล์เดิมไว้ด้วย เพื่อให้ตรวจได้ว่าคืนค่าได้ตรงต้นฉบับ การคืนค่าที่ไม่ตรงอาจทำให้บริการทำงานผิดและสร้างปัญหาใหม่ที่ซับซ้อนกว่าช่องโหว่เดิม

ในบางกรณีการคืนสภาพอาจไม่สามารถทำได้ทั้งหมด เช่น เมื่อการทดสอบทำให้เกิดการล็อกบัญชีหรือทำให้บริการหยุดทำงาน ในกรณีนี้ต้องแจ้งผู้ดูแลระบบทันทีและบันทึกเหตุการณ์ไว้ในรายงานอย่างชัดเจน

โครงของข้อค้นพบ

ข้อค้นพบที่ดีมีห้าส่วนเสมอ ส่วนแรกคือชื่อเรื่องที่ระบุกลไก ไม่ใช่ระบุเพียงผล เช่น "การเรียกคำสั่งผ่านอาร์กิวเมนต์ของ tar ในงาน cron" ไม่ใช่ "ยกระดับสิทธิ์ได้"

ส่วนที่สองคือตำแหน่งของปัญหา ระบุไฟล์ บรรทัด หรือยูนิตที่เกี่ยวข้องให้ชัดเจน พร้อมสิทธิ์และเจ้าของในขณะที่ตรวจพบ ส่วนที่สามคือเงื่อนไขที่ทำให้ใช้ประโยชน์ได้ ซึ่งต้องอธิบายว่าผู้ใช้ต้องมีสิทธิ์อะไรและต้องรอเงื่อนไขใด

ส่วนที่สี่คือหลักฐานสั้นๆ ที่พอให้ผู้ตรวจทานเห็นภาพ โดยปกติคือผลของคำสั่งที่ไม่เปิดเผยข้อมูลอ่อนไหว ส่วนที่ห้าคือผลกระทบและข้อเสนอแนะ ซึ่งต้องเชื่อมโยงกับสาเหตุ ไม่ใช่เป็นรายการทั่วไปที่ใช้กับทุกข้อค้นพบ

จากสาเหตุสู่มาตรการ

ข้อผิดพลาดที่พบบ่อยในการรายงานคือเสนอมาตรการที่ไม่ตรงกับสาเหตุ ทำให้ปัญหาเกิดซ้ำ ตัวอย่างเช่น เมื่อพบว่าโฟลเดอร์สคริปต์เปิดให้ผู้ใช้เขียนได้ การลบบิตเขียนของไฟล์เดียวจะไม่ช่วยเพราะผู้ใช้ยังสร้างไฟล์ใหม่แทนได้ มาตรการที่ตรงคือแก้สิทธิ์ของโฟลเดอร์และทบทวนกระบวนการติดตั้ง

ตาราง 12.24 การจับคู่สาเหตุกับมาตรการที่ตรงจุด
สาเหตุมาตรการที่ตรงจุดมาตรการที่ไม่พอ
ไฟล์ SUID ที่ไม่จำเป็นลบบิตและเพิ่มขั้นตอนตรวจตอนติดตั้งตรวจหาเป็นครั้งคราวโดยไม่แก้ไฟล์
กฎ sudo กว้างเกินระบุคำสั่งและอาร์กิวเมนต์ให้แคบเพิ่มการยืนยันรหัสผ่านแต่ยังอนุญาตคำสั่งเดิม
สคริปต์ใน cron แก้ไขได้เปลี่ยนเจ้าของและสิทธิ์ของโฟลเดอร์ลบงานนั้นทิ้งโดยไม่แก้สิทธิ์
PATH มีโฟลเดอร์ที่เขียนได้กำหนด PATH ในสคริปต์และย้ายโฟลเดอร์เปลี่ยนชื่อสคริปต์
wildcard กับโฟลเดอร์ที่เขียนได้ใช้ -- หรือเลี่ยง wildcardตรวจชื่อไฟล์ที่ขึ้นต้นด้วยเครื่องหมายลบเป็นครั้งคราว
capability เกินจำเป็นลบ capability และใช้วิธีอื่นเฝ้าดูบันทึกอย่างเดียว
ระบบไฟล์ไม่มี nosuidเพิ่มตัวเลือกในการเมานต์ลบบิต SUID เป็นรายไฟล์
บริการรันด้วย root โดยไม่จำเป็นลดสิทธิ์ของยูนิตจำกัดการเข้าถึงพอร์ต

การจับคู่เช่นนี้ทำให้รายงานมีน้ำหนัก เพราะผู้อ่านเห็นว่าข้อเสนอไม่ได้เป็นคำแนะนำทั่วไป แต่ตอบปัญหาเฉพาะที่ตรวจพบ

การตรวจจับและการเฝ้าดู

ฝ่ายป้องกันต้องการสัญญาณที่บอกว่ามีการยกระดับสิทธิ์เกิดขึ้นจริง ไม่ใช่เพียงการตั้งค่าที่ไม่ดี การตรวจจับจึงควรใช้ข้อมูลจากหลายแหล่งประกอบกัน

แหล่งแรกคือบันทึกของ sudo ซึ่งมักอยู่ใน /var/log/auth.log หรือ /var/log/secure ขึ้นกับการกระจาย บันทึกนี้แสดงว่าใครรันคำสั่งใดในนามใคร และถูกปฏิเสธหรือไม่ การเรียกคำสั่งที่ผิดปกติเช่นเชลล์หรือโปรแกรมตีความจากบัญชีบริการเป็นสัญญาณที่ควรตรวจ

แหล่งที่สองคือ auditd ซึ่งบันทึกการเรียกใช้ระบบและการเข้าถึงไฟล์ตามกฎที่ตั้งไว้ กฎที่ควรมีได้แก่การเฝ้าดูการเขียน /etc/passwd, /etc/shadow, /etc/sudoers และโฟลเดอร์ยูนิตของ systemd

แหล่งที่สามคือ journald ซึ่งรวมบันทึกของบริการและเคอร์เนลไว้ที่เดียว การค้นหาคำว่า error, denied หรือ segfault ในช่วงเวลาที่สงสัยช่วยชี้จุดที่ควรตรวจต่อ

แหล่งที่สี่คือระบบตรวจสอบความสมบูรณ์ของไฟล์ ซึ่งเทียบแฮชของไฟล์ระบบกับค่าฐานและแจ้งเมื่อเปลี่ยน การเปลี่ยนแปลงของไบนารีที่ตั้ง SUID หรือไฟล์ตั้งค่าของบริการควรได้รับการตรวจสอบทุกครั้ง

ตาราง 12.25 แหล่งข้อมูลตรวจจับและสัญญาณที่ควรสนใจ
แหล่งข้อมูลตำแหน่งโดยทั่วไปสัญญาณที่ควรสนใจ
บันทึก sudo/var/log/auth.log, /var/log/secureคำสั่งแปลกจากบัญชีบริการ
auditd/var/log/audit/audit.logการเขียนไฟล์สิทธิ์สำคัญ
journaldjournalctlข้อความปฏิเสธสิทธิ์หรือกระบวนการล้มเหลว
ความสมบูรณ์ของไฟล์ฐานข้อมูลของระบบไบนารีหรือไฟล์ตั้งค่าเปลี่ยนโดยไม่มีแพตช์
กระบวนการps, บันทึกการสร้างกระบวนการกระบวนการที่รันจากโฟลเดอร์ชั่วคราว
การเข้าสู่ระบบ/var/log/lastlog, wtmpการเข้าสู่ระบบของบัญชีที่ควรถูกปิด

การตรวจจับที่ดีต้องมีค่าฐาน (baseline) ของสิ่งที่ปกติก่อน เพราะการเห็นความผิดปกติต้องรู้ว่าปกติคืออะไร องค์กรที่ไม่มีค่าฐานจะได้รับแจ้งเตือนมากแต่แยกไม่ออกว่ารายการใดสำคัญ

มาตรการป้องกันเชิงชั้น

การป้องกันที่มีประสิทธิผลไม่ได้พึ่งมาตรการเดียว แต่ใช้หลายชั้นซ้อนกันเพื่อให้การพลาดชั้นหนึ่งยังถูกจับได้ในชั้นถัดไป

ชั้นแรกคือการลดพื้นผิวการโจมตี ลบโปรแกรมที่ไม่ใช้ ปิดบริการที่ไม่จำเป็น และลบบิต SUID ที่ไม่ต้องการ ชั้นที่สองคือการจำกัดสิทธิ์ ใช้บัญชีเฉพาะสำหรับแต่ละบริการ กำหนดสิทธิ์ของโฟลเดอร์อย่างเคร่งครัด และหลีกเลี่ยงการรันบริการด้วย root

ชั้นที่สามคือการควบคุมการยกระดับ ใช้ sudo แบบระบุคำสั่งและอาร์กิวเมนต์ จำกัดสมาชิกกลุ่มที่ได้สิทธิ์สูง และตรวจเวอร์ชันของซอฟต์แวร์ที่เกี่ยวข้อง ชั้นที่สี่คือการตรวจจับและตอบสนอง เปิดการบันทึกที่จำเป็น ตั้งกฎ audit สำหรับไฟล์สำคัญ และมีขั้นตอนตอบสนองเมื่อพบสัญญาณ

ชั้นที่ห้าคือการบริหารจัดการ กำหนดรอบตรวจสอบสิทธิ์ ทบทวนกฎ sudo และรายการงานอัตโนมัติทุกไตรมาส และผูกการเปลี่ยนแปลงกับการอนุมัติ เพื่อไม่ให้ข้อผิดพลาดเดิมกลับมาเมื่อมีผู้ติดตั้งซอฟต์แวร์ใหม่

การป้องกันเชิงชั้นมีต้นทุน ทั้งเวลาและความยุ่งยากในการทำงาน องค์กรจึงควรจัดลำดับตามความเสี่ยงของระบบ ไม่ใช่ใช้มาตรการเข้มที่สุดกับทุกเครื่อง เพราะมาตรการที่เข้มเกินไปมักถูกเลี่ยงด้วยวิธีที่แย่กว่า เช่น การให้สิทธิ์กว้างเพื่อให้งานเสร็จ

ข้อผิดพลาดในการรายงานที่ควรหลีกเลี่ยง

ข้อผิดพลาดแบบแรกคือรายงานผลของเครื่องมือโดยไม่ตรวจซ้ำ ทำให้รายงานเต็มไปด้วยรายการที่ใช้ไม่ได้ และทำให้ข้อค้นพบจริงถูกมองข้ามเพราะปนกับเสียงรบกวน

ข้อผิดพลาดแบบที่สองคือรายงานเฉพาะผลลัพธ์ ไม่อธิบายเงื่อนไข ผู้อ่านจึงไม่สามารถประเมินได้ว่าควรแก้ก่อนหรือหลัง และไม่รู้ว่าหากเงื่อนไขเปลี่ยน ปัญหาจะยังเกิดหรือไม่

ข้อผิดพลาดแบบที่สามคือเสนอมาตรการแบบกว้าง เช่น "ควรปรับปรุงความปลอดภัย" ซึ่งไม่ได้บอกว่าใครต้องทำอะไรภายในเมื่อใด ข้อเสนอที่ดีต้องระบุเจ้าของงานและกรอบเวลา

ข้อผิดพลาดแบบที่สี่คือเปิดเผยข้อมูลเกินจำเป็น เช่น การแนบไฟล์รหัสผ่านทั้งไฟล์หรือข้อมูลของผู้ใช้จริงลงในรายงาน ข้อมูลเหล่านี้ไม่จำเป็นต่อการพิสูจน์และเพิ่มความเสี่ยงให้องค์กร

ข้อผิดพลาดแบบที่ห้าคือไม่บันทึกการคืนสภาพ ผู้อ่านไม่รู้ว่าระบบกลับสู่สภาพเดิมแล้วหรือไม่ และอาจเข้าใจว่ายังมีไฟล์ที่ผู้ทดสอบวางไว้ตกค้าง

เมื่อเขียนรายงานครบทั้งห้าส่วนและตรวจการคืนสภาพแล้ว งานยกระดับสิทธิ์จึงถือว่าสมบูรณ์ สิ่งที่เหลือคือการทบทวนภาพรวมว่าความรู้จากบทนี้เชื่อมกับบทถัดไปอย่างไร

✓ สรุป

การยกระดับสิทธิ์บนลินุกซ์เริ่มจากความเข้าใจว่า�ระบบตัดสินสิทธิ์จากหมายเลขผู้ใช้และหมายเลขกลุ่ม ไม่ใช่จากชื่อบัญชี การอ่านค่าเหล่านี้ให้ถูกต้องเป็นพื้นฐานของการวิเคราะห์ทั้งหมด เพราะข้อสรุปที่ผิดตั้งแต่ต้นจะทำให้การตรวจขั้นต่อไปเสียเวลาโดยไม่จำเป็น

แบบจำลองสิทธิ์ของลินุกซ์เรียบง่ายแต่มีรายละเอียดที่มองข้ามได้ง่าย บิตเก้าบิตบอกสิทธิ์ของเจ้าของ กลุ่ม และผู้อื่น ส่วนบิตพิเศษอีกสามบิตเปลี่ยนพฤติกรรมของโปรแกรมและโฟลเดอร์ การเห็นอักขระ s ในผล ls -l จึงเป็นสัญญาณให้ตรวจต่อ ไม่ใช่ข้อสรุปว่าเป็นช่องโหว่

บิต SUID ให้กระบวนการทำงานด้วยสิทธิ์ของเจ้าของไฟล์ ซึ่งจำเป็นสำหรับโปรแกรมบางประเภท แต่กลายเป็นความเสี่ยงเมื่อโปรแกรมนั้นยอมให้ผู้ใช้ควบคุมคำสั่ง ไฟล์ หรือไลบรารีที่ถูกโหลด การประเมินจึงต้องดูพฤติกรรมของโปรแกรม ไม่ใช่ดูที่บิตเพียงอย่างเดียว

SGID และ capabilities ให้ผลคล้ายกันแต่ต่างกลไก capabilities แบ่งอำนาจของ root เป็นหน่วยย่อยและไม่แสดงในผล ls -l ตามปกติ ผู้ตรวจจึงต้องใช้ getcap ค้นหาแยก และต้องเข้าใจว่าความสามารถที่มีอยู่ไม่เท่ากับความสามารถที่ใช้ประโยชน์ได้

sudo เป็นพื้นที่เสี่ยงสูงเพราะการอนุญาตเกินหนึ่งคำสั่งอาจเทียบเท่าการให้สิทธิ์ root ทั้งหมด คำสั่งที่ดูไม่มีอันตรายเช่นโปรแกรมอ่านไฟล์หรือโปรแกรมแก้ไขมักมีความสามารถซ่อนอยู่ การอ่านผล sudo -l ต้องดูทั้งคำสั่ง อาร์กิวเมนต์ ผู้ใช้ปลายทาง และตัวแปรที่คงไว้

งานที่ถูกตั้งเวลาเป็นช่องทางที่พบบ่อยในระบบจริง เพราะสคริปต์มักถูกเขียนไว้นานและไม่มีการตรวจทานซ้ำ ช่องโหว่เกิดเมื่อผู้ใช้ทั่วไปเปลี่ยนสิ่งที่งานจะรันได้ ไม่ว่าจะโดยแก้สคริปต์ เปลี่ยนไฟล์ที่สคริปต์อ่าน หรือแทรกโปรแกรมผ่าน PATH

wildcard injection เป็นรูปแบบที่ผู้เริ่มต้นมักไม่คาดคิด เพราะโปรแกรมไม่ได้ถูกเรียกด้วย wildcard โดยตรง แต่ได้รับรายชื่อไฟล์ที่บางรายการมีรูปแบบเหมือนตัวเลือก การป้องกันจึงต้องเลี่ยง wildcard กับโฟลเดอร์ที่ผู้ใช้เขียนได้ หรือใช้เครื่องหมาย -- เพื่อสิ้นสุดการอ่านตัวเลือก

เส้นทางอื่นที่ควรตรวจได้แก่ไฟล์สำคัญที่เขียนได้ การเมานต์ที่ขาด nosuid กลุ่มที่ให้สิทธิ์เทียบเท่า root และช่องโหว่ระดับเคอร์เนล เส้นทางเหล่านี้มีผลกระทบต่างกันและมีความเสี่ยงต่อเสถียรภาพของระบบต่างกัน การเลือกใช้จึงต้องคำนึงถึงผลข้างเคียง ไม่ใช่เพียงความสำเร็จ

การยืนยันผลต้องมีหลักฐานที่ตรวจสอบย้อนกลับได้ ไม่ใช่เพียงการเห็นข้อความ uid=0 ครั้งเดียว หลักฐานที่ดีบอกคำสั่งเต็ม เวลา และเงื่อนไขที่ทำให้ได้ผล และต้องมาพร้อมการคืนสภาพระบบให้กลับสู่สภาพเดิม

การรายงานที่มีคุณค่าต้องเชื่อมสาเหตุกับมาตรการให้ตรงจุด ข้อค้นพบที่ระบุเพียงอาการจะนำไปสู่การแก้ที่ปลายเหตุ และปัญหาเดิมจะกลับมาเมื่อมีผู้ติดตั้งซอฟต์แวร์ใหม่หรือเปลี่ยนการตั้งค่า มาตรการเชิงชั้นและการตรวจจับที่อาศัยข้อมูลหลายแหล่งจึงเป็นสิ่งที่ทำให้การแก้คงอยู่

ท้ายที่สุด ระเบียบวิธียังคงสำคัญกว่าคำสั่ง ผู้เรียนที่เข้าใจคำถามสามข้อคือเป็นใคร มีอะไร และระบบอนุญาตอะไร จะปรับตัวเข้ากับระบบที่ไม่เคยเห็นได้ และจะรู้ว่าเมื่อใดควรหยุดตรวจและรายงาน แทนที่จะเร่งใช้ประโยชน์จากสิ่งที่พบ
