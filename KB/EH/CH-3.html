3.1 ทำไมวินโดวส์จึงเป็นเป้าหมายหลัก

บทที่แล้วปิดท้ายด้วยการชี้ว่าแนวคิดเรื่องสิทธิ์ เจ้าของ บริการ และงานตามกำหนดเวลามีคู่เทียบอยู่ในวินโดวส์ แต่ถูกนำไปใช้ด้วยกลไกที่ต่างออกไป บทนี้จึงเริ่มจากคำถามที่ตรงที่สุดก่อนว่า เหตุใดผู้ทดสอบเจาะระบบจึงต้องลงทุนเรียนรู้ระบบปฏิบัติการที่ดูเหมือนจะ "ใช้งานง่ายกว่า" ระบบลินุกซ์

คำตอบไม่ได้อยู่ที่ความง่ายหรือความยาก แต่อยู่ที่ตำแหน่งของระบบในองค์กร เครื่องปลายทางส่วนใหญ่ในองค์กรเป็นเครื่องวินโดวส์ เครื่องของผู้บริหาร เครื่องของฝ่ายการเงิน เครื่องของเจ้าหน้าที่ทรัพยากรบุคคล และเครื่องของเจ้าหน้าที่เทคนิค ล้วนเป็นเครื่องที่ผู้ใช้เปิดใช้งานทุกวันด้วยระบบนี้ ขณะที่เซิร์ฟเวอร์ของบริการภายในองค์กรจำนวนมากก็ทำงานบนวินโดวส์เซิร์ฟเวอร์ โดยเฉพาะบริการที่ผูกกับบัญชีผู้ใช้กลางอย่าง Active Directory ซึ่งจะกล่าวถึงในบทหลังๆ

ผลที่ตามมาคือข้อมูลที่มีค่าที่สุดในองค์กรไม่ได้อยู่ในเซิร์ฟเวอร์ฐานข้อมูลเพียงเครื่องเดียว แต่กระจายอยู่ในเครื่องปลายทางนับพันเครื่องที่ผู้ใช้แต่ละคนมีสิทธิ์เขียนไฟล์เอง ติดตั้งโปรแกรมเอง และเปิดไฟล์แนบจากอีเมลเอง ความสะดวกนี้คือคุณค่าของระบบ และในเวลาเดียวกันก็คือพื้นผิวโจมตีที่กว้างที่สุด

ห้าเหตุผลเชิงโครงสร้าง

เหตุผลข้อแรกคือความเข้ากันได้ย้อนหลัง วินโดวส์ต้องรันโปรแกรมที่เขียนขึ้นเมื่อสิบหรือยี่สิบปีก่อนให้ได้ เพื่อรักษาลูกค้าองค์กรที่ยังพึ่งพาโปรแกรมเหล่านั้น ความเข้ากันได้นี้ทำให้ระบบต้องแบกกลไกเก่าที่ไม่ทันสมัยไว้ เช่น ความสามารถในการรันสคริปต์แบบเก่า การรองรับโปรโตคอลรุ่นเก่าในบางบริการ และการอนุญาตให้โปรแกรมติดตั้งเขียนทับไฟล์ของระบบได้ในบางกรณี กลไกเหล่านี้ไม่ได้ผิดโดยตัวเอง แต่ละกลไกเพิ่มช่องทางที่ผู้โจมตีสามารถใช้ได้

เหตุผลข้อที่สองคือการรวมศูนย์การยืนยันตัวตน องค์กรที่ใช้ Active Directory จะมีบัญชีเดียวที่ใช้ได้กับทุกบริการ ตั้งแต่เข้าคอมพิวเตอร์ เปิดอีเมล เปิดแชร์ไฟล์ ไปจนถึงเข้าเซิร์ฟเวอร์ฐานข้อมูล การรวมศูนย์เช่นนี้สะดวกต่อผู้ใช้และผู้ดูแลระบบอย่างมาก แต่ก็หมายความว่ารหัสผ่านเดียวที่รั่วไหลอาจเปิดทางไปได้ไกลกว่าที่ผู้ใช้คาดคิด แนวคิดนี้จะกลับมาเป็นหัวข้อหลักในบทที่ว่าด้วยการโจมตี Active Directory

เหตุผลข้อที่สามคือบริการที่เปิดรับการเชื่อมต่อจากระยะไกล วินโดวส์มาพร้อมบริการสำหรับบริหารจัดการจากระยะไกลหลายชนิด ทั้ง Remote Desktop, SMB สำหรับแชร์ไฟล์, WinRM สำหรับรันคำสั่ง และ WMI สำหรับสอบถามข้อมูล บริการเหล่านี้มีประโยชน์และถูกเปิดใช้ในองค์กรจริงเป็นจำนวนมาก แต่ละบริการมีช่องทางยืนยันตัวตนและมีประวัติช่องโหว่ของตนเอง

เหตุผลข้อที่สี่คือผู้ใช้มักมีสิทธิ์สูงกว่าที่ควร ธรรมเนียมการใช้งานมายาวนานทำให้ผู้ใช้จำนวนมากคุ้นเคยกับการติดตั้งโปรแกรมเอง ซึ่งในทางปฏิบัติหมายถึงการเป็นสมาชิกกลุ่มผู้ดูแลระบบบนเครื่องของตน แม้องค์กรจะพยายามลดสิทธิ์นี้มาระยะหนึ่งแล้ว แต่เครื่องที่ผู้ใช้เป็นผู้ดูแลระบบเองยังพบได้ทั่วไป และเครื่องลักษณะนี้ทำให้การยกระดับสิทธิ์บนเครื่องนั้นไม่จำเป็นต้องใช้ช่องโหว่ที่ซับซ้อนเลย

เหตุผลข้อที่ห้าคือระบบมีเครื่องมือบริหารจัดการในตัวที่ทรงพลัง วินโดวส์มี PowerShell ติดตั้งมาให้ทุกเครื่องตั้งแต่รุ่น 7 เป็นต้นมา เครื่องมือนี้ถูกออกแบบมาให้ผู้ดูแลระบบทำงานอัตโนมัติได้เต็มรูปแบบ ซึ่งหมายความว่าผู้ที่ยึดเครื่องได้ก็ได้เครื่องมือชนิดเดียวกันไปด้วย แนวคิดการใช้เครื่องมือที่มีอยู่แล้วในระบบเพื่อทำงานของผู้บุกรุก ซึ่งบทที่แล้วเรียกว่าการอยู่กับเครื่องมือที่มีอยู่ จะกลับมาเป็นแกนของบทนี้อีกครั้ง

สิ่งที่ผู้ตรวจสอบมองหา

เมื่อเข้าถึงเครื่องวินโดวส์หนึ่งเครื่องได้ ผู้ตรวจสอบไม่ได้เปิดดูทุกอย่าง แต่ไล่ดูตามลำดับความสำคัญของคำถามสี่ข้อ คือ ใครอยู่ในระบบนี้ เครื่องนี้ทำอะไรอยู่ มีอะไรเริ่มทำงานเองบ้าง และมีอะไรที่ผิดปกติจากเครื่องทั่วไปหรือไม่

องค์ประกอบเหตุใดจึงน่าสนใจหลักฐานที่อ่านได้
บัญชีและกลุ่มบอกว่าใครมีสิทธิ์อะไร และมีบัญชีที่ถูกสร้างขึ้นโดยไม่ชอบหรือไม่net user, Get-LocalUser, กลุ่มผู้ดูแลระบบ
บริการบริการทำงานด้วยสิทธิ์สูงและเริ่มเองทุกครั้งที่บูตรีจิสทรีใต้ Services, Get-Service, sc qc
งานตามกำหนดเวลาทำงานซ้ำโดยไม่มีใครสั่ง และมักไม่ถูกตรวจภายหลังGet-ScheduledTask, schtasks, ไฟล์ XML ใน Tasks
จุด Autostartเป็นที่วางกลไกให้ทำงานทุกครั้งที่ผู้ใช้เข้าสู่ระบบคีย์ Run, โฟลเดอร์ Startup, Winlogon

ตารางนี้ไม่ใช่รายการที่ต้องตรวจครบทุกครั้ง แต่เป็นแผนที่ที่บอกว่าคำถามแต่ละข้อควรไปหาคำตอบที่ใด ผู้เรียนจะเห็นว่าเกือบทุกแถวในตารางชี้กลับไปที่รีจิสทรี ซึ่งเป็นเหตุผลที่หัวข้อถัดไปของบทนี้ให้เวลากับรีจิสทรีมากที่สุด

ขอบเขตของบทนี้

บทนี้ไม่ใช่คู่มือบริหารระบบวินโดวส์ และไม่ใช่คู่มือติดตั้งเครื่อง ผู้เรียนจะไม่ได้เรียนรู้วิธีตั้งค่าโดเมน วิธีปรับนโยบายกลุ่ม หรือวิธีติดตั้งโปรแกรมแบบครบวงจร สิ่งที่บทนี้ทำคือพาผู้เรียนอ่านเครื่องหนึ่งเครื่องในฐานะหลักฐาน คือเข้าใจว่าแต่ละองค์ประกอบเก็บข้อมูลอะไร ข้อมูลนั้นเชื่อถือได้แค่ไหน และการตั้งค่าที่ไม่รัดกุมหน้าตาเป็นอย่างไร

ความแตกต่างนี้สำคัญเพราะการอ่านหลักฐานกับการบริหารระบบใช้ความรู้ชุดเดียวกันแต่ใช้คนละทิศทาง ผู้ดูแลระบบถามว่า "จะตั้งค่าให้ถูกต้องได้อย่างไร" ส่วนผู้ตรวจสอบถามว่า "การตั้งค่าที่เป็นอยู่บอกอะไรกับเรา" ผู้เรียนที่เข้าใจทั้งสองทิศทางจะประเมินความเสี่ยงได้แม่นกว่าผู้ที่รู้เพียงทิศทางเดียว

3.2 สถาปัตยกรรมวินโดวส์ในมุมของผู้ตรวจสอบ

สองโหมดการทำงาน

วินโดวส์แบ่งการทำงานออกเป็นสองระดับอย่างเด็ดขาด ระดับแรกคือ โหมดผู้ใช้ (User Mode) ซึ่งโปรแกรมทั่วไปทำงานอยู่ โปรแกรมในระดับนี้แตะฮาร์ดแวร์โดยตรงไม่ได้ และต้องขอให้ระบบช่วยทุกครั้งที่ต้องการเข้าถึงทรัพยากรที่สำคัญ ระดับที่สองคือ โหมดเคอร์เนล (Kernel Mode) ซึ่งเป็นที่อยู่ของแกนกลางระบบ ทำหน้าที่จัดการหน่วยความจำ กระบวนการ อุปกรณ์ และการรักษาความปลอดภัย

การแบ่งสองระดับนี้มีผลโดยตรงต่องานตรวจสอบ เพราะมันกำหนดว่าสิ่งใดที่โปรแกรมของผู้บุกรุกทำได้และทำไม่ได้ หากผู้บุกรุกได้สิทธิ์ในโหมดผู้ใช้เพียงอย่างเดียว เขาจะยังถูกจำกัดด้วยกติกาของระบบ แต่หากเขาสามารถทำให้โค้ดของตนทำงานในโหมดเคอร์เนลได้ เขาจะอยู่เหนือกติกาเหล่านั้นทั้งหมด ทั้งนี้เพราะโค้ดในโหมดเคอร์เนลสามารถแก้โครงสร้างข้อมูลที่ระบบใช้ตัดสินใจได้ทุกอย่าง

โครงสร้างพื้นฐานที่ควรรู้คือ ชั้นที่ติดกับโปรแกรมผู้ใช้เป็นไลบรารีที่ทำหน้าที่เป็นตัวกลาง เช่น kernel32.dll และ advapi32.dll ซึ่งเรียกต่อไปยัง ntdll.dll ที่เป็นตัวแทนของส่วนติดต่อ native ของระบบ จากนั้นจึงเข้าสู่เคอร์เนลผ่านกลไกที่เรียกว่า system call ตัวเลขที่ใช้ระบุ system call ในแต่ละรุ่นของวินโดวส์ไม่เหมือนกัน ซึ่งเป็นเหตุผลว่าทำไมโค้ดที่เรียก native API โดยตรงจึงผูกกับรุ่นของระบบมากกว่าโค้ดที่เรียกผ่านไลบรารีมาตรฐาน

ตาราง 3.3 องค์ประกอบหลักของสถาปัตยกรรมวินโดวส์
องค์ประกอบอยู่ระดับใดหน้าที่
ntoskrnl.exeเคอร์เนลแกนกลางระบบ รวมตัวจัดการหน่วยความจำ กระบวนการ และไฟล์
hal.dllเคอร์เนลชั้นเชื่อมกับฮาร์ดแวร์เฉพาะเครื่อง
ตัวจัดการวัตถุเคอร์เนลจัดการวัตถุทุกชนิดและตัวนับการอ้างอิง
ตัวจัดการความปลอดภัยเคอร์เนลตรวจสิทธิ์ทุกครั้งที่เข้าถึงวัตถุ
ntdll.dllผู้ใช้ส่วนติดต่อ native ที่โปรแกรมอื่นเรียกใช้
kernel32.dll, advapi32.dllผู้ใช้ส่วนติดต่อมาตรฐานที่โปรแกรมทั่วไปเรียกใช้
csrss.exeผู้ใช้ส่วนผู้ใช้ของระบบย่อย จัดการหน้าต่างและเทอร์มินัล
lsass.exeผู้ใช้ผู้มีอำนาจด้านความปลอดภัย ตรวจรหัสผ่านและสร้างโทเคน

กระบวนการที่ต้องรู้จัก

เมื่อระบบเริ่มทำงาน จะมีกระบวนการชุดหนึ่งถูกสร้างขึ้นตามลำดับที่กำหนดไว้ตายตัว การรู้ลำดับนี้ช่วยให้ผู้เรียนแยกได้ว่ากระบวนการใดเป็นของระบบจริงและกระบวนการใดเพียงแค่ใช้ชื่อเดียวกัน

ตาราง 3.4 กระบวนการหลักและบทบาท
กระบวนการหน้าที่ข้อสังเกตด้านการตรวจสอบ
System (PID 4)เป็นตัวแทนของเคอร์เนลเอง ไม่มีไฟล์โปรแกรมไม่ควรมีเส้นทางไฟล์ และไม่ควรถูกอ้างว่ามี
smss.exeตัวจัดการเซสชัน สร้างเซสชันและเริ่มกระบวนการแรกของแต่ละเซสชันมีได้หลายอินสแตนซ์ชั่วคราวช่วงบูต
csrss.exeระบบย่อยฝั่งผู้ใช้ จัดการหน้าต่างและคอนโซลเป็นกระบวนการวิกฤต ถ้าถูกหยุดระบบจะหยุดทั้งเครื่อง
wininit.exeเตรียมเซสชันที่ศูนย์และเริ่มบริการหลักของระบบทำงานในเซสชัน 0 เท่านั้น
services.exeตัวจัดการบริการ ดูแลวงจรชีวิตของทุกบริการเป็นจุดที่ควบคุมบริการทั้งหมด
lsass.exeตรวจสอบการเข้าสู่ระบบและสร้างโทเคนการเข้าถึงเก็บข้อมูลรับรองและความลับของระบบ
svchost.exeตัวโฮสต์ที่รวมบริการหลายตัวไว้ในกระบวนการเดียวต้องดูพารามิเตอร์ -k หรือ -p เพื่อรู้ว่าถือบริการใด
winlogon.exeจัดการการเข้าสู่ระบบแบบมีหน้าจอเรียกกระบวนการสร้างเชลล์ของผู้ใช้
explorer.exeเชลล์ของหน้าจอ เดสก์ท็อป และแถบงานถูกรันด้วยสิทธิ์ของผู้ใช้ ไม่ใช่ของผู้ดูแลระบบ

ประเด็นที่ผู้เริ่มต้นมักเข้าใจผิดคือการเห็น svchost.exe หลายสิบอินสแตนซ์แล้วคิดว่าเป็นความผิดปกติ ความจริงคือการรวมบริการไว้ในโฮสต์เดียวเป็นพฤติกรรมปกติของวินโดวส์มาตั้งแต่รุ่นแรกๆ สิ่งที่ผิดปกติคือ svchost.exe ที่ไม่มีพารามิเตอร์กำกับ หรือทำงานจากโฟลเดอร์อื่นที่ไม่ใช่ System32 เพราะกระบวนการนี้ควรถูกเรียกจากตำแหน่งมาตรฐานเสมอ

อีกประเด็นคือแนวคิด กระบวนการวิกฤต (Critical Process) ซึ่งระบบจะหยุดทั้งเครื่องทันทีหากกระบวนการนั้นจบการทำงาน กระบวนการอย่าง csrss.exe, wininit.exe, lsass.exe, smss.exe และ services.exe ถูกตั้งค่าลักษณะนี้ไว้ การหยุดกระบวนการเหล่านี้จึงไม่ใช่การปิดบริการหนึ่งบริการ แต่เป็นการทำให้เครื่องล่ม ซึ่งผู้บุกรุกบางกลุ่มใช้เป็นกลไกข่มขู่หรือกลบร่องรอย

ลำดับการเริ่มระบบ

การเข้าใจลำดับการเริ่มระบบมีประโยชน์สองด้าน ด้านหนึ่งคือทำให้รู้ว่าการคงอยู่แบบใดทำงานก่อนที่ผู้ใช้จะเห็นหน้าจอ และอีกด้านหนึ่งคือทำให้รู้ว่าบันทึกเหตุการณ์ส่วนใดจะถูกเขียนก่อนใคร

ตาราง 3.5 ลำดับการเริ่มระบบวินโดวส์โดยย่อ
ลำดับขั้นตอนสิ่งที่เกิดขึ้น
1เฟิร์มแวร์ตรวจฮาร์ดแวร์แล้วส่งต่อให้ตัวจัดการบูตของวินโดวส์
2ตัวจัดการบูตเลือกระบบปฏิบัติการและโหลดตัวโหลดเคอร์เนล
3ตัวโหลดเคอร์เนลโหลดเคอร์เนล ฮาร์ดแวร์แอบสแตรกชัน และไดรเวอร์ที่ต้องเริ่มก่อน
4smss.exeสร้างเซสชัน เริ่ม csrss.exe และ wininit.exe
5services.exeเริ่มบริการที่ตั้งไว้ให้เริ่มอัตโนมัติ รวมถึงไดรเวอร์และบริการของระบบ
6lsass.exeเตรียมกลไกยืนยันตัวตนและนโยบายความปลอดภัย
7winlogon.exeแสดงหน้าจอเข้าสู่ระบบและรอผู้ใช้ยืนยันตัว
8userinit.exeเตรียมโปรไฟล์ผู้ใช้แล้วเริ่มเชลล์
9explorer.exeแสดงเดสก์ท็อปและเริ่มโปรแกรมที่ผู้ใช้ตั้งไว้

จุดที่ควรสังเกตคือขั้นตอนที่ 5 และ 6 เกิดขึ้นก่อนที่ผู้ใช้จะเห็นหน้าจอใดๆ เลย กลไกที่ทำงานในขั้นตอนเหล่านี้จึงมองไม่เห็นจากมุมของผู้ใช้ทั่วไป และเป็นเหตุผลว่าทำไมการคงอยู่ในรูปแบบบริการหรือไดรเวอร์จึงตรวจพบได้ยากกว่าการคงอยู่ในรูปแบบโปรแกรมที่ผู้ใช้ต้องเปิดเอง

ระบบวัตถุและตัวจัดการแฮนเดิล

วินโดวส์ไม่ได้ให้โปรแกรมแตะไฟล์ อุปกรณ์ หรือโครงสร้างข้อมูลภายในโดยตรง แต่จัดการทุกอย่างผ่านแนวคิดที่เรียกว่า วัตถุ (Object) ไม่ว่าจะเป็นไฟล์ คีย์รีจิสทรี กระบวนการ เทอร์มินัล หรือเหตุการณ์ที่ใช้ประสานงานระหว่างโปรแกรม ล้วนเป็นวัตถุที่เคอร์เนลสร้างขึ้นและดูแล

โปรแกรมเข้าถึงวัตถุผ่าน แฮนเดิล (Handle) ซึ่งเป็นตัวเลขที่แสดงถึงสิทธิ์ที่โปรแกรมได้รับบนวัตถุนั้น การได้แฮนเดิลมาหมายความว่าโปรแกรมผ่านการตรวจสิทธิ์แล้วครั้งหนึ่ง และสามารถใช้งานวัตถุนั้นได้ตามสิทธิ์ที่ระบุไว้ในแฮนเดิล สิทธิ์ในแฮนเดิลจึงไม่จำเป็นต้องเท่ากับสิทธิ์เต็มบนวัตถุ เช่น โปรแกรมอาจเปิดไฟล์ด้วยสิทธิ์อ่านเท่านั้นแม้ผู้ใช้จะมีสิทธิ์เขียนก็ตาม

แนวคิดนี้มีประโยชน์ในงานตรวจสอบสองทาง ทางแรกคือการดูรายการไฟล์และวัตถุที่กระบวนการหนึ่งเปิดอยู่ ซึ่งบอกได้ว่าโปรแกรมนั้นกำลังทำอะไรจริงๆ ไม่ใช่เพียงชื่อโปรแกรม ทางที่สองคือการดูวัตถุที่ตั้งชื่อไว้ในระบบ เพราะมัลแวร์จำนวนมากใช้การสร้างวัตถุชื่อเฉพาะเพื่อตรวจว่าเครื่องนี้ถูกบุกรุกไปแล้วหรือยัง เทคนิคนี้รู้จักกันในชื่อการตรวจข้อความต้องห้าม (Mutex) และเป็นหนึ่งในวิธีที่เครื่องมือวิเคราะห์มัลแวร์ใช้ระบุตระกูลของตัวอย่าง

ชื่อของวัตถุที่ตั้งชื่อไว้จะปรากฏในเนมสเปซของตัวจัดการวัตถุ ซึ่งเป็นโครงสร้างแบบต้นไม้ที่คล้ายระบบไฟล์ มีไดเรกทอรีอย่าง \Device, \BaseNamedObjects, \Sessions และ \RPC Control เนมสเปซนี้ไม่ได้ผูกกับไดรฟ์ใด จึงต้องใช้เครื่องมือเฉพาะในการสำรวจ และเป็นที่มาของเส้นทางรูปแบบพิเศษที่ผู้เรียนอาจพบในเอกสารทางเทคนิค

ระบบไฟล์ NTFS และสิ่งที่ผู้ตรวจสอบต้องรู้

ระบบไฟล์หลักของวินโดวส์คือ NTFS ซึ่งมีคุณสมบัติที่ต่างจากระบบไฟล์ของลินุกซ์ในหลายจุด จุดที่สำคัญที่สุดสำหรับงานตรวจสอบคือการเก็บข้อมูลในลักษณะที่ผู้ใช้ทั่วไปมองไม่เห็น และการเก็บประวัติการเปลี่ยนแปลงของไฟล์

ตาราง 3.6 คุณสมบัติของ NTFS ที่เกี่ยวกับงานตรวจสอบ
คุณสมบัติความหมายประโยชน์หรือความเสี่ยง
สตรีมข้อมูลทางเลือกไฟล์หนึ่งไฟล์เก็บข้อมูลได้หลายสตรีมใช้ซ่อนข้อมูลหรือโค้ดได้ และมองไม่เห็นในโปรแกรมทั่วไป
รายการควบคุมการเข้าถึงสิทธิ์รายบุคคลที่ผูกกับไฟล์หรือโฟลเดอร์ละเอียดกว่าสิทธิ์แบบเจ้าของและกลุ่มของลินุกซ์
ตารางไฟล์หลักทะเบียนไฟล์ทุกไฟล์พร้อมเวลาและที่อยู่แหล่งหลักฐานที่สำคัญที่สุดของระบบไฟล์
บันทึกการเปลี่ยนแปลงบันทึกทุกการสร้าง ลบ และเปลี่ยนชื่อใช้ยืนยันการกระทำได้แม้ไฟล์ถูกลบไปแล้ว
จุดเชื่อมต่อและลิงก์สัญลักษณ์ทางลัดระดับระบบไฟล์ใช้เปลี่ยนเส้นทางให้โปรแกรมเขียนทับไฟล์อื่นได้
การเข้ารหัสไฟล์เข้ารหัสไฟล์ผูกกับบัญชีผู้ใช้ป้องกันการอ่านไฟล์แม้ได้สิทธิ์ผู้ดูแลระบบ

คุณสมบัติที่ผู้เริ่มต้นมักมองข้ามมากที่สุดคือสตรีมข้อมูลทางเลือก หรือ Alternate Data Stream ไฟล์หนึ่งไฟล์ใน NTFS ไม่ได้เก็บข้อมูลก้อนเดียวเหมือนในระบบไฟล์อื่น แต่เก็บได้หลายสตรีมโดยใช้ชื่อกำกับ เช่น report.txt:hidden.exe ซึ่งเมื่อเปิดด้วยโปรแกรมทั่วไปจะเห็นเพียงเนื้อหาของสตรีมหลัก การตรวจหาสตรีมซ่อนทำได้ด้วยคำสั่ง Get-Item -Stream * ใน PowerShell หรือเครื่องมือเฉพาะทาง

คุณสมบัติอีกข้อที่ควรรู้คือ NTFS ไม่สนใจตัวพิมพ์เล็กใหญ่ในชื่อไฟล์ แต่เก็บชื่อจริงตามที่ผู้ใช้ตั้งไว้ ขณะที่ระบบไฟล์ของลินุกซ์สนใจตัวพิมพ์เล็กใหญ่ ผลคือไฟล์ชื่อ Report.txt กับ report.txt เป็นไฟล์เดียวกันในวินโดวส์ แต่เป็นคนละไฟล์ในลินุกซ์ ความแตกต่างนี้สำคัญเมื่อต้องย้ายเครื่องมือหรือสคริปต์ข้ามระบบ

ตัวระบุความปลอดภัย

วินโดวส์ไม่ได้ตัดสินสิทธิ์จากชื่อบัญชี แต่ตัดสินจากตัวเลขที่เรียกว่า ตัวระบุความปลอดภัย (Security Identifier) หรือ SID ซึ่งมีรูปแบบขึ้นต้นด้วย S-1-5-21 สำหรับบัญชีที่เครื่องสร้างเอง หรือ S-1-5-21-... สำหรับบัญชีในโดเมน ตามด้วยหมายเลขเครื่องหรือโดเมน และปิดท้ายด้วยหมายเลขสัมพัทธ์ที่เรียกว่า RID

หมายเลขที่ต่อท้าย SID ของบัญชีในเครื่องหรือในโดเมนเรียกว่า RID และมีบางค่าที่มีความหมายเฉพาะซึ่งผู้ตรวจสอบควรจำได้ ค่า 500 คือบัญชีผู้ดูแลระบบในตัวที่สร้างมาพร้อมระบบ ค่า 501 คือบัญชี guest และค่า 502 คือบัญชี krbtgt ซึ่งเป็นบัญชีบริการที่ใช้ในกลไก Kerberos ของโดเมน บัญชีที่มี RID ต่ำเหล่านี้มีมาก่อนบัญชีที่ผู้ใช้สร้างขึ้น จึงมักถูกมองข้ามและเป็นเป้าหมายที่ผู้บุกรุกให้ความสนใจ

การที่ระบบตัดสินจาก SID ไม่ใช่ชื่อ ทำให้เกิดสถานการณ์ที่ผู้ตรวจสอบต้องระวัง คือบัญชีที่ถูกเปลี่ยนชื่อยังคงมี SID เดิม และบัญชีที่ถูกสร้างใหม่ให้ชื่อเหมือนบัญชีเดิมก็ยังมี SID ใหม่ การตรวจสอบบัญชีจึงต้องดูทั้งชื่อและ SID ประกอบกันเสมอ

ตารางเวลาของไฟล์ใน NTFS

NTFS เก็บเวลาหลายค่าในโครงสร้างข้อมูลของไฟล์ สองค่าที่ผู้ตรวจสอบใช้บ่อยที่สุดคือเวลาสร้างและเวลาที่แก้ไขล่าสุด แต่ยังมีค่าอื่นที่สำคัญไม่แพ้กัน ได้แก่เวลาที่เข้าถึงล่าสุด เวลาที่บันทึกการเปลี่ยนแปลงเมทาดาทา และเวลาที่ไฟล์ถูกเปลี่ยนชื่อ

คุณสมบัติที่ควรรู้คือ NTFS เก็บเวลาสองชุดแยกจากกันคือชุดที่ผู้ใช้และโปรแกรมเห็น กับชุดที่ระบบไฟล์เก็บไว้เอง ชุดหลังนี้แก้ไขได้ยากกว่ามาก การปรับเวลาแก้ไขไฟล์เพื่อกลบร่องรอยจึงมักถูกจับได้เมื่อตรวจสอบชุดที่สอง ซึ่งเป็นหลักการเดียวกับที่บทที่แล้วอธิบายเรื่องเวลาเปลี่ยนแปลงเมทาดาทาในระบบลินุกซ์

นอกจากนี้ยังมีบันทึกเหตุการณ์ของระบบไฟล์อีกชั้นที่ทำงานอิสระจากตัวไฟล์ คือบันทึกการเปลี่ยนแปลงระดับโวลุ่ม ซึ่งเก็บเหตุการณ์การสร้าง ลบ และเปลี่ยนชื่อไฟล์ไว้ในฐานข้อมูลแยก บันทึกนี้มีประโยชน์อย่างยิ่งเมื่อไฟล์ที่ถูกอ้างถึงถูกลบไปแล้ว เพราะชื่อและเวลายังคงอยู่ในบันทึก การอ่านบันทึกนี้ต้องใช้เครื่องมือเฉพาะและต้องมีสิทธิ์ของผู้ดูแลระบบ

3.3 รีจิสทรี: โครงสร้างฮีฟและจุด Autostart

รีจิสทรีคืออะไรและทำไมจึงสำคัญ

รีจิสทรี (Registry) คือฐานข้อมูลแบบลำดับชั้นที่วินโดวส์ใช้เก็บค่าปรับแต่งของระบบแทบทั้งหมด ก่อนที่มันจะถูกนำมาใช้ในระบบรุ่นแรกๆ วินโดวส์เก็บค่าปรับแต่งไว้ในไฟล์ข้อความแยกกันหลายไฟล์ซึ่งกระจัดกระจายและควบคุมได้ยาก เมื่อระบบใหญ่ขึ้น การตามหาว่าโปรแกรมใดแก้ค่าอะไรจึงแทบเป็นไปไม่ได้ รีจิสทรีถูกสร้างขึ้นเพื่อรวมค่าปรับแต่งทั้งหมดไว้ในที่เดียวโดยมีโครงสร้างชัดเจน

สำหรับผู้ตรวจสอบ รีจิสทรีมีความสำคัญสามเหตุผล เหตุผลแรกคือมันเก็บคำตอบของคำถามว่า "เครื่องนี้ถูกตั้งค่าให้ทำอะไรบ้าง" ไว้เกือบทั้งหมด ทั้งโปรแกรมที่เริ่มพร้อมระบบ บริการที่ทำงาน นโยบายที่ถูกบังคับใช้ และโปรแกรมที่เคยถูกติดตั้ง เหตุผลที่สองคือมันเป็นที่ที่ผู้บุกรุกใช้คงอยู่ในระบบมากกว่าที่อื่นใด เพราะการเขียนค่าหนึ่งค่าในรีจิสทรีทำให้โปรแกรมทำงานทุกครั้งที่เครื่องบูตหรือทุกครั้งที่ผู้ใช้เข้าสู่ระบบ โดยไม่ต้องมีไฟล์โปรแกรมวางไว้ในตำแหน่งที่มองเห็นง่าย เหตุผลที่สามคือแต่ละคีย์มีบันทึกเวลาเขียนครั้งล่าสุด ซึ่งใช้จัดลำดับเหตุการณ์ได้

ข้อที่ต้องเข้าใจให้ถูกต้องตั้งแต่ต้นคือ รีจิสทรีไม่ใช่ไฟล์เดียว แต่เป็นมุมมองเชิงตรรกะที่ระบบประกอบขึ้นจากไฟล์หลายไฟล์ที่เรียกว่า ฮีฟ (Hive) เมื่อโปรแกรมถามค่าจากรีจิสทรี ระบบจะตอบจากฮีฟที่ถูกโหลดอยู่ในหน่วยความจำ ไม่ได้อ่านจากดิสก์ทุกครั้ง ผลคือการแก้ไขค่าในรีจิสทรีจะมีผลทันที แต่การเปลี่ยนแปลงจะถูกบันทึกลงดิสก์เมื่อระบบเขียนฮีฟกลับตามรอบของมัน

โครงสร้างสามชั้น

รีจิสทรีมีองค์ประกอบสามระดับที่ต้องแยกให้ออก คีย์ (Key) เป็นเหมือนโฟลเดอร์ที่ใช้จัดกลุ่ม รายการย่อย (Subkey) คือคีย์ที่อยู่ภายใต้คีย์หนึ่ง และ ค่า (Value) คือข้อมูลจริงที่เก็บในคีย์หนึ่งๆ แต่ละคีย์มีค่าได้หลายค่า และค่าแต่ละค่ามีชื่อกำกับ ชนิดข้อมูล และข้อมูลของตัวเอง

ความสับสนที่พบบ่อยคือการพูดว่า "คีย์" เมื่อหมายถึง "ค่า" ทั้งสองอย่างนี้ต่างกันและเครื่องมือจัดการต่างกันด้วย การสร้างคีย์ใหม่กับการตั้งค่าในคีย์ที่มีอยู่เป็นคนละการกระทำ และการอ่านค่าหนึ่งค่าจำเป็นต้องรู้ทั้งเส้นทางของคีย์และชื่อของค่า ไม่ใช่รู้เพียงอย่างใดอย่างหนึ่ง

ค่าทุกรายการมีชนิดข้อมูลกำกับ และชนิดข้อมูลนี้กำหนดว่าข้อมูลจะถูกตีความอย่างไร

HKEY_CURRENT_CONFIGHKCCมุมมองชั่วคราวของข้อมูลฮาร์ดแวร์

รายละเอียดที่ควรสังเกตมีสามข้อ ประการแรก HKLM\HARDWARE และ HKCC ไม่มีไฟล์บนดิสก์เลย ข้อมูลทั้งหมดสร้างขึ้นใหม่ทุกครั้งที่ระบบเริ่มทำงาน การค้นหาข้อมูลย้อนหลังในสองฮีฟนี้จึงเป็นไปไม่ได้ ประการที่สอง HKCU\Software\Classes ไม่ได้อยู่ในไฟล์ NTUSER.DAT แต่แยกไปอยู่ในไฟล์ UsrClass.dat ในโฟลเดอร์ของผู้ใช้ ซึ่งเป็นตำแหน่งที่ผู้บุกรุกใช้ซ่อนการเชื่อมโยงไฟล์ได้ ประการที่สาม HKCR ไม่ใช่ฮีฟจริง แต่เป็นมุมมองที่ระบบรวม HKLM\Software\Classes เข้ากับ HKCU\Software\Classes โดยให้ฝั่งของผู้ใช้มีลำดับความสำคัญสูงกว่า

ลำดับความสำคัญนี้เองคือช่องทางที่รู้จักกันในชื่อ การจี้การเชื่อมโยงคลาสออบเจกต์ (COM Hijacking) โปรแกรมจำนวนมากเรียกใช้ส่วนประกอบที่ลงทะเบียนไว้ในรีจิสทรีผ่านหมายเลขคลาส เมื่อระบบหาตัวอย่างส่วนประกอบนั้น มันจะตรวจฝั่งผู้ใช้ก่อนเสมอ ผู้ใช้ทั่วไปเขียนค่าในฝั่งของตนได้โดยไม่ต้องมีสิทธิ์ของผู้ดูแลระบบ จึงสามารถชี้ให้โปรแกรมที่ทำงานด้วยสิทธิ์สูงไปโหลดไลบรารีของตนได้ นี่เป็นตัวอย่างของหลักการที่ว่า ตำแหน่งที่ผู้ใช้เขียนได้ในรีจิสทรีไม่ใช่เรื่องเล็ก

นอกจากไฟล์ฮีฟแล้ว ยังมีไฟล์บันทึกธุรกรรมที่ลงท้ายด้วย .LOG1 และ .LOG2 อยู่ข้างกัน ไฟล์เหล่านี้ใช้ป้องกันข้อมูลเสียหายเมื่อระบบหยุดทำงานกลางคันระหว่างเขียนฮีฟ ในงานสืบสวน ไฟล์บันทึกธุรกรรมอาจเก็บข้อมูลที่ยังไม่ได้ถูกเขียนลงฮีฟหลัก และสามารถใช้ยืนยันการเปลี่ยนแปลงที่เพิ่งเกิดขึ้นได้

มุมมอง 32 บิตและ 64 บิต

ระบบวินโดวส์ 64 บิตต้องรองรับโปรแกรม 32 บิตที่ยังใช้อยู่ เพื่อไม่ให้โปรแกรมเหล่านั้นเห็นค่าปรับแต่งของโปรแกรม 64 บิตปนกัน ระบบจึงแยกส่วนหนึ่งของรีจิสทรีออกเป็นมุมมองต่างหาก โดยโปรแกรม 32 บิตที่อ่าน HKLM\SOFTWARE จะถูกเปลี่ยนเส้นทางไปยัง HKLM\SOFTWARE\WOW6432Node โดยอัตโนมัติ

ผลต่อการตรวจสอบคือค่าเดียวกันอาจปรากฏในสองตำแหน่งที่ต่างกัน และการค้นหาเพียงตำแหน่งเดียวอาจไม่พบรายการที่ตั้งใจหา คำสั่ง reg query มีตัวเลือก /reg:32 และ /reg:64 สำหรับระบุมุมมองที่ต้องการ ส่วน PowerShell จะเห็นทั้งสองตำแหน่งตามที่มีอยู่จริงในฮีฟ การตรวจสอบจุด Autostart จึงต้องตรวจทั้งสองมุมมองเสมอ

การอ่านรีจิสทรีด้วยเครื่องมือ

เครื่องมือที่ใช้บ่อยมีสองตัวคือคำสั่ง reg ซึ่งมีมาในทุกรุ่นของวินโดวส์ และ cmdlet ของ PowerShell ที่ทำงานผ่าน Registry Provider ทั้งสองวิธีให้ผลเหมือนกัน แต่ให้ความสะดวกต่างกัน

คำสั่งพื้นฐานของ reg มีสี่รูปแบบ คือ reg query สำหรับอ่าน reg add สำหรับสร้างหรือแก้ reg delete สำหรับลบ และ reg export สำหรับส่งออกทั้งคีย์ไปเป็นไฟล์ข้อความ ตัวอย่างการอ่านจุด Autostart ทั้งหมดของเครื่อง

reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" /s

ตัวเลือก /s สั่งให้ค้นรวมรายการย่อยทั้งหมด ซึ่งจำเป็นเพราะจุด Autostart หลายตำแหน่งมีรายการย่อยซ้อนอยู่ ตัวอย่างการอ่านค่าที่กำหนดโปรแกรมซึ่งทำงานตอนเข้าสู่ระบบ

reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /v Userinit

ใน PowerShell เส้นทางของรีจิสทรีเข้าถึงได้เหมือนไดรฟ์ทั่วไป เพราะระบบมีผู้ให้บริการข้อมูลชื่อ Registry ที่ติดตั้งมาให้ คำสั่ง Get-ItemProperty อ่านค่าทั้งหมดในคีย์เดียว ส่วน Get-ChildItem ใช้ไล่รายการย่อย

Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run'

ข้อแตกต่างที่ควรรู้คือ PowerShell แสดงค่าที่มีอยู่ในคีย์นั้นจริงๆ โดยไม่ต้องระบุชื่อค่า แต่ถ้าต้องการอ่านค่าที่อาจไม่มีอยู่ ควรใช้ -ErrorAction SilentlyContinue เพื่อไม่ให้เกิดข้อความผิดพลาดรบกวนสคริปต์

จุด Autostart ที่ผู้ตรวจสอบต้องตรวจ

คำว่า Autostart ในบทนี้หมายถึงทุกตำแหน่งที่ทำให้โปรแกรมทำงานเองโดยไม่ต้องมีผู้ใช้สั่ง ตำแหน่งเหล่านี้มีมากกว่าที่ผู้ใช้ทั่วไปคาดคิด และแต่ละตำแหน่งมีกลไกทำงานต่างกัน

ตาราง 3.10 ตำแหน่ง Autostart หลักและลักษณะการทำงาน
ตำแหน่งทำงานเมื่อใดสิทธิ์ที่ใช้
...\CurrentVersion\Runผู้ใช้เข้าสู่ระบบสิทธิ์ของผู้ใช้เจ้าของคีย์
...\CurrentVersion\RunOnceผู้ใช้เข้าสู่ระบบครั้งถัดไป แล้วถูกลบสิทธิ์ของผู้ใช้เจ้าของคีย์
...\CurrentVersion\RunServicesบริการของระบบเริ่มทำงานสิทธิ์ของระบบ
โฟลเดอร์ Startup ของผู้ใช้ผู้ใช้เข้าสู่ระบบสิทธิ์ของผู้ใช้
โฟลเดอร์ Startup ของทุกผู้ใช้ผู้ใช้ทุกคนเข้าสู่ระบบสิทธิ์ที่ผู้ใช้ทั่วไปเขียนไม่ได้
Winlogon\Shell และ Userinitระหว่างการเข้าสู่ระบบสิทธิ์ของระบบ
Image File Execution Optionsทุกครั้งที่โปรแกรมที่ระบุถูกเรียกสิทธิ์ของระบบ
AppInit_DLLsทุกครั้งที่โปรแกรมโหลดไลบรารีของหน้าจอสิทธิ์ของระบบ
บริการใน CurrentControlSet\Servicesระบบเริ่มทำงานตามบัญชีของบริการ
งานตามกำหนดเวลาตามเวลาหรือเหตุการณ์ที่กำหนดตามบัญชีที่กำหนดในงาน

ความแตกต่างที่สำคัญที่สุดในตารางนี้คือสิทธิ์ที่ใช้ ถ้ากลไกอยู่ในคีย์ของผู้ใช้ ค่าที่วางไว้จะทำงานด้วยสิทธิ์ของผู้ใช้คนนั้น ซึ่งจำกัดความเสียหายไว้ที่ระดับผู้ใช้ แต่ถ้ากลไกอยู่ในคีย์ของเครื่องหรือในบริการ ค่าที่วางไว้จะทำงานด้วยสิทธิ์ของระบบหรือของผู้ดูแลระบบ ความน่าสนใจของผู้บุกรุกจึงขึ้นอยู่กับว่ากลไกใดทำงานด้วยสิทธิ์สูง

คีย์ Run และ RunOnce เป็นตำแหน่งที่รู้จักกันแพร่หลายที่สุด ค่าแต่ละค่าในคีย์นี้ประกอบด้วยชื่อที่ใช้แสดงและเส้นทางของโปรแกรม ค่าที่มีเส้นทางแปลก เช่น อยู่ในโฟลเดอร์ชั่วคราว อยู่ในโฟลเดอร์ของผู้ใช้ หรือใช้ตัวแปลคำสั่งเป็นตัวกลาง ควรถูกตรวจสอบทุกครั้ง นอกจากคีย์มาตรฐานแล้วยังมีคีย์คู่ขนานใต้ WOW6432Node สำหรับโปรแกรม 32 บิต และคีย์ในส่วน Policies ซึ่งระบบก็ยอมรับค่าจากที่นั่นด้วย

โฟลเดอร์ Startup ทำหน้าที่เหมือนคีย์ Run แต่ใช้ไฟล์แทนการเขียนรีจิสทรี ตำแหน่งของผู้ใช้แต่ละคนอยู่ที่ %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup และตำแหน่งของทุกผู้ใช้อยู่ที่ %ProgramData%\Microsoft\Windows\Start Menu\Programs\Startup ข้อได้เปรียบของผู้บุกรุกคือการวางไฟล์ในโฟลเดอร์ของผู้ใช้ไม่ต้องแตะรีจิสทรีเลย จึงหลุดจากการตรวจที่ดูแต่รีจิสทรี

Winlogon เป็นตำแหน่งที่มีอันตรายสูงที่สุดในตาราง เพราะค่าอย่าง Shell และ Userinit ถูกเรียกใช้ในขั้นตอนที่ระบบกำลังเตรียมเชลล์ให้ผู้ใช้ ซึ่งเป็นขั้นตอนที่ทำงานด้วยสิทธิ์ของระบบ ค่าปกติของ Shell คือ explorer.exe และค่าปกติของ Userinit คือ C:\Windows\system32\userinit.exe, การเติมชื่อโปรแกรมอื่นต่อท้ายค่าปกติเป็นเทคนิคที่ทำให้ผู้ใช้ทั่วไปไม่สังเกตเห็นความผิดปกติ เพราะค่าที่เห็นยังดูคุ้นตา

Image File Execution Options เป็นกลไกที่ออกแบบไว้สำหรับนักพัฒนาที่ต้องการให้โปรแกรมดีบักเกอร์ทำงานแทนโปรแกรมหนึ่งๆ โดยตั้งค่าชื่อ Debugger ใต้คีย์ของโปรแกรมนั้น เมื่อใดก็ตามที่มีการเรียกโปรแกรมนั้น ระบบจะเรียกดีบักเกอร์แทน กลไกนี้กลายเป็นช่องทางคงอยู่ในระบบที่แนบเนียนมาก เพราะไม่มีการเพิ่มรายการใหม่ในตำแหน่ง Autostart ที่ใครๆ ตรวจ และยังใช้ปิดการทำงานของเครื่องมือป้องกันได้ด้วยการชี้ให้โปรแกรมป้องกันถูกแทนที่ด้วยโปรแกรมอื่น

AppInit_DLLs เป็นกลไกเก่าที่ระบบโหลดไลบรารีที่ระบุไว้เข้าทุกโปรแกรมที่โหลดไลบรารีของหน้าจอ ผู้บุกรุกใช้กลไกนี้เพื่อให้โค้ดของตนอยู่ทุกโปรแกรมโดยไม่ต้องแก้ไฟล์ใด ระบบรุ่นใหม่ปิดการทำงานของกลไกนี้โดยค่าเริ่มต้น แต่ค่าที่ถูกเปิดไว้ยังตรวจพบได้ และการพบว่าค่า LoadAppInit_DLLs ถูกตั้งเป็นหนึ่งคือสัญญาณที่ต้องอธิบายให้ได้ว่ามีเหตุผลอะไร

รีจิสทรีในฐานะหลักฐาน

นอกจากใช้หา Autostart แล้ว รีจิสทรียังเก็บร่องรอยการใช้งานที่ผู้ใช้ไม่ได้ตั้งใจทิ้งไว้ และร่องรอยเหล่านี้มีค่ามากเมื่อต้องตอบคำถามว่าเครื่องนี้ถูกใช้ทำอะไร

ตาราง 3.11 ตำแหน่งรีจิสทรีที่เป็นหลักฐานการใช้งาน
ตำแหน่งเก็บอะไรประโยชน์
Explorer\UserAssistโปรแกรมที่เคยถูกเรียก พร้อมจำนวนครั้งและเวลายืนยันการทำงานของโปรแกรมที่ถูกลบไปแล้ว
Services\bam\State\UserSettingsโปรแกรมที่ถูกเรียกและเวลาล่าสุดตรวจการเรียกโปรแกรมที่ผิดปกติ
Explorer\RunMRUคำสั่งที่ผู้ใช้พิมพ์ในช่องเรียกใช้เผยคำสั่งที่ผู้ใช้หรือผู้บุกรุกรัน
Explorer\TypedPathsเส้นทางที่ผู้ใช้พิมพ์ในแถบที่อยู่เผยโฟลเดอร์ที่ถูกเข้าถึง

คุณสมบัติที่ทำให้รีจิสทรีเป็นหลักฐานที่มีค่าไม่ใช่เพียงเนื้อหาของค่า แต่เป็น เวลาเขียนครั้งล่าสุดของคีย์ ซึ่งระบบบันทึกไว้ทุกครั้งที่มีการแก้ไขค่าในคีย์นั้น เวลานี้ช่วยจัดลำดับเหตุการณ์ได้ว่าการเปลี่ยนแปลงใดเกิดก่อนหรือหลัง และช่วยแยกการเปลี่ยนแปลงที่เกิดจากผู้ใช้จริงออกจากการเปลี่ยนแปลงที่เกิดจากโปรแกรมติดตั้งหรือระบบอัปเดต

ข้อจำกัดที่ต้องรู้คือเวลานี้เป็นเวลาของคีย์ ไม่ใช่ของค่าแต่ละค่า การแก้ค่าหนึ่งค่าจะอัปเดตเวลาของคีย์ทั้งคีย์ ผู้ที่ต้องการตรวจอย่างละเอียดจึงต้องดูทั้งเวลาของคีย์ ตารางเวลาไฟล์ของฮีฟ และบันทึกเหตุการณ์ของระบบประกอบกัน การอ่านค่าเวลาเพียงแหล่งเดียวไม่เพียงพอต่อการสรุป

สิทธิ์บนคีย์รีจิสทรี

รีจิสทรีมีระบบสิทธิ์ของตัวเองแยกจากระบบไฟล์ แต่ละคีย์มีรายการควบคุมการเข้าถึงที่กำหนดว่าใครอ่านเขียนได้ และสิทธิ์เหล่านี้สืบทอดลงไปยังรายการย่อยในลักษณะเดียวกับโฟลเดอร์

โดยทั่วไปผู้ใช้ทั่วไปเขียนได้เฉพาะส่วนของตนเองใต้ HKCU ขณะที่ HKLM จำกัดไว้ให้ผู้ดูแลระบบ อย่างไรก็ตาม มีข้อยกเว้นที่ควรรู้ คือคีย์บางส่วนถูกตั้งสิทธิ์ให้กลุ่มผู้ใช้ทั่วไปเขียนได้เพื่อรองรับการทำงานของโปรแกรมรุ่นเก่า และคีย์ของบริการบางตัวก็ถูกตั้งสิทธิ์หลวมเกินไปจนผู้ใช้ทั่วไปแก้ไขค่าของบริการที่ทำงานด้วยสิทธิ์สูงได้

การตรวจสอบทำได้ด้วยคำสั่ง PowerShell ที่อ่านรายการควบคุมการเข้าถึงของคีย์

Get-Acl 'HKLM:\SYSTEM\CurrentControlSet\Services\BackupSvc' |
    Format-List Path, Owner, AccessToString

ผลลัพธ์ที่ควรสงสัยคือรายการที่ให้สิทธิ์เขียนแก่กลุ่มอย่าง Users, Authenticated Users หรือ Everyone บนคีย์ที่ควบคุมบริการหรือโปรแกรมซึ่งทำงานด้วยสิทธิ์สูง เพราะการเขียนค่านี้ได้เท่ากับการกำหนดว่าโปรแกรมใดจะถูกเรียกด้วยสิทธิ์ใด

การจัดเก็บสำเนาเพื่อการวิเคราะห์

เมื่อต้องเก็บหลักฐานจากรีจิสทรี วิธีที่ตรงไปตรงมาที่สุดคือการส่งออกคีย์ที่สนใจเป็นไฟล์ข้อความด้วยคำสั่ง reg export ซึ่งได้ไฟล์นามสกุล .reg ที่เปิดอ่านได้ด้วยโปรแกรมแก้ข้อความ และนำกลับเข้าไปศึกษาในเครื่องทดสอบได้

reg export "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion" currentversion.reg /y

ข้อควรระวังคือการส่งออกเฉพาะคีย์ไม่ได้เก็บสิทธิ์และไม่ได้เก็บเวลาของคีย์อย่างครบถ้วน หากต้องการวิเคราะห์เชิงลึกควรทำสำเนาไฟล์ฮีฟทั้งไฟล์และเปิดด้วยเครื่องมือวิเคราะห์เฉพาะ ซึ่งจะแสดงเวลาของทุกคีย์และโครงสร้างข้อมูลภายในได้ครบกว่า

การอ่านรีจิสทรีในระหว่างการทดสอบต้องคำนึงถึงผลข้างเคียงด้วย คำสั่งอ่านไม่เปลี่ยนสถานะของระบบ แต่คำสั่งที่เขียนค่าจะเปลี่ยน และการเปลี่ยนค่าอาจทำให้ระบบทำงานผิดปกติหรือทำให้ผู้ใช้สังเกตเห็นความเปลี่ยนแปลง การบันทึกค่าก่อนแก้ไขและการคืนค่าให้เหมือนเดิมจึงเป็นขั้นตอนที่ต้องทำทุกครั้ง

3.4 บริการและงานตามกำหนดเวลา

บริการในวินโดวส์ต่างจากโปรแกรมทั่วไปอย่างไร

บริการ (Service) คือโปรแกรมที่ระบบเป็นผู้เริ่มและดูแล ไม่ใช่ผู้ใช้ บริการทำงานได้ตั้งแต่ก่อนที่ผู้ใช้คนใดจะเข้าสู่ระบบ และทำงานต่อไปได้แม้ไม่มีผู้ใช้เข้าสู่ระบบเลย คุณสมบัติข้อนี้คือเหตุผลที่ผู้บุกรุกให้ความสนใจบริการมากกว่ากลไกอื่น เพราะบริการที่เริ่มอัตโนมัติจะทำงานทุกครั้งที่เครื่องบูต โดยไม่ต้องรอให้ใครเปิดโปรแกรม และไม่ปรากฏเป็นหน้าต่างให้ผู้ใช้สังเกตเห็น

บริการทุกตัวถูกดูแลโดย ตัวจัดการบริการ (Service Control Manager) ซึ่งทำงานอยู่ในกระบวนการ services.exe ตัวจัดการนี้เป็นผู้รับคำสั่งเริ่ม หยุด และสอบถามสถานะของบริการทั้งหมด และเป็นผู้เก็บฐานข้อมูลบริการซึ่งอยู่ในรีจิสทรีใต้ HKLM\SYSTEM\CurrentControlSet\Services

คำว่า CurrentControlSet ในเส้นทางนี้เป็นสิ่งที่ต้องอธิบาย เพราะมันไม่ใช่คีย์จริงแต่เป็นลิงก์ที่ชี้ไปยังชุดควบคุมชุดหนึ่ง เช่น ControlSet001 ระบบเก็บชุดควบคุมสำรองไว้หลายชุดเพื่อให้กู้คืนได้หากชุดที่ใช้อยู่เสียหาย ผลต่อการตรวจสอบคือเส้นทางที่เขียนด้วย CurrentControlSet เป็นวิธีที่ปลอดภัยที่สุดในการอ้างถึงค่าที่ระบบใช้อยู่ในขณะนี้ เพราะมันชี้ตามชุดที่ใช้งานจริงเสมอ

ผู้เรียนที่มาจากบทที่แล้วจะเห็นความคล้ายกับ systemd ของลินุกซ์ทันที ทั้งสองระบบมีตัวจัดการกลางที่เริ่มบริการตามลำดับ ดูแลบริการที่ล้มเหลว และเก็บสถานะของบริการไว้ในที่เดียว ความต่างที่สำคัญคือ systemd อธิบายบริการด้วยไฟล์ข้อความในระบบไฟล์ ขณะที่ตัวจัดการบริการของวินโดวส์อ่านค่าจากรีจิสทรีเป็นหลัก ไฟล์จึงไม่ใช่แหล่งความจริงหลักของบริการในวินโดวส์

การอ่านค่าของบริการ

บริการหนึ่งตัวมีค่าปรับแต่งหลายสิบค่า แต่มีเพียงไม่กี่ค่าที่ผู้ตรวจสอบต้องอ่านทุกครั้ง

ค่าที่สำคัญที่สุดคือ ImagePath เพราะมันกำหนดโปรแกรมที่จะถูกเรียกและอาร์กิวเมนต์ที่ส่งให้โปรแกรมนั้น การอ่านค่านี้จึงตอบได้ทันทีว่าบริการทำงานจากไฟล์ใด และไฟล์นั้นอยู่ในตำแหน่งที่ควรอยู่หรือไม่ บริการของระบบส่วนใหญ่ชี้ไปยัง C:\Windows\System32 หรือโฟลเดอร์ของโปรแกรมที่ติดตั้งตามปกติ บริการที่ชี้ไปยังโฟลเดอร์ชั่วคราว โฟลเดอร์ของผู้ใช้ หรือโฟลเดอร์ที่ผู้ใช้ทั่วไปเขียนได้ คือสิ่งที่ต้องอธิบายให้ได้ว่ามาได้อย่างไร

ค่าที่สองที่สำคัญไม่แพ้กันคือ ObjectName เพราะมันกำหนดว่าบริการทำงานในนามของใคร บริการที่ทำงานในนามของบัญชีระบบมีสิทธิ์สูงกว่าบริการที่ทำงานในนามของบัญชีผู้ใช้ธรรมดา และบริการที่ทำงานในนามของบัญชีผู้ใช้ที่ระบุไว้อย่างชัดเจนจะเก็บรหัสผ่านของบัญชีนั้นไว้ในฐานข้อมูลความลับของระบบ ซึ่งเป็นสิ่งที่ผู้ตรวจสอบต้องระวังเป็นพิเศษ

ค่าที่สามคือ Start ซึ่งบอกว่าระบบจะเริ่มบริการนี้เมื่อใด

บริการที่ตั้งเป็น 2 คือบริการที่ทำงานทุกครั้งโดยไม่ต้องมีใครสั่ง จึงเป็นตำแหน่งที่ผู้บุกรุกเลือกใช้คงอยู่ในระบบมากที่สุด นอกจากนี้ยังมีค่า DelayedAutostart ซึ่งเมื่อตั้งเป็น 1 จะทำให้บริการเริ่มช้ากว่าบริการอัตโนมัติทั่วไปเล็กน้อย คุณสมบัตินี้มีไว้ลดภาระช่วงบูต แต่ในมุมของการตรวจสอบมันทำให้บริการที่เริ่มช้านี้ไม่ปรากฏในช่วงเวลาที่ผู้ดูแลระบบมักตรวจดูรายการบริการทันทีหลังบูต

บัญชีที่บริการใช้

วินโดวส์มีบัญชีสำเร็จรูปสำหรับบริการโดยเฉพาะสามบัญชี และอนุญาตให้ใช้บัญชีอื่นได้ตามต้องการ

ตาราง 3.14 บัญชีที่บริการใช้และระดับสิทธิ์
บัญชีสิทธิ์ในเครื่องสิทธิ์ในเครือข่ายข้อสังเกต
บัญชีระบบภายในสูงสุด เข้าถึงทรัพยากรได้เกือบทั้งหมดใช้บัญชีเครื่องของตนเองพบบ่อยที่สุดในบริการของระบบ
บริการเครือข่ายจำกัดใช้บัญชีเครื่องของตนเองเหมาะกับบริการที่ต้องออกเครือข่าย
บริการภายในเครื่องจำกัดเข้าถึงเครือข่ายแบบไม่ระบุตัวเหมาะกับงานที่ไม่ต้องออกเครือข่าย
บัญชีผู้ใช้ที่ระบุตามสิทธิ์ของบัญชีนั้นตามสิทธิ์ของบัญชีนั้นต้องเก็บรหัสผ่านไว้ในระบบ
บัญชีเสมือนของบริการจำกัดและแยกตามบริการใช้บัญชีเครื่องระบบสร้างให้อัตโนมัติ

บัญชีระบบภายในมีสิทธิ์สูงจนในทางปฏิบัติเทียบได้กับผู้ดูแลระบบเต็มรูปแบบ บริการที่ทำงานในนามของบัญชีนี้จึงเป็นเป้าหมายที่มีค่าที่สุดสำหรับผู้ที่ต้องการยกระดับสิทธิ์ เพราะการทำให้บริการลักษณะนี้เรียกโปรแกรมของตนได้เท่ากับได้สิทธิ์ของผู้ดูแลระบบโดยไม่ต้องรู้รหัสผ่านใดเลย

บัญชีประเภทที่สี่คือบัญชีผู้ใช้ที่ระบุไว้อย่างชัดเจน ซึ่งมักใช้เมื่อบริการต้องเข้าถึงแชร์ไฟล์หรือฐานข้อมูลในนามของผู้ใช้คนหนึ่ง การใช้บัญชีเช่นนี้ต้องเก็บรหัสผ่านไว้ในระบบ และรหัสผ่านนั้นถูกเก็บในฐานข้อมูลความลับของส่วนความปลอดภัยภายในเครื่อง ผู้ตรวจสอบจึงควรตรวจว่าบริการใดใช้บัญชีประเภทนี้ เพราะบัญชีเหล่านั้นมักเป็นบัญชีที่ตั้งรหัสผ่านแบบไม่เปลี่ยน และมักมีสิทธิ์กว้างกว่าที่จำเป็น

บัญชีประเภทสุดท้ายคือบัญชีเสมือนที่ระบบสร้างให้บริการแต่ละตัวโดยอัตโนมัติ ซึ่งมีข้อดีคือแยกสิทธิ์ของแต่ละบริการออกจากกัน แม้สองบริการจะทำงานในโฟลเดอร์เดียวกันหรือในโฮสต์เดียวกัน การแยกนี้ทำให้บริการหนึ่งไม่สามารถใช้สิทธิ์ของอีกบริการหนึ่งได้โดยตรง

จุดที่การตั้งค่าบริการกลายเป็นความเสี่ยง

บริการเกี่ยวข้องกับเส้นทางการยกระดับสิทธิ์ในหลายลักษณะ แต่ลักษณะที่พบบ่อยที่สุดมีสี่แบบ

แบบแรกคือ โฟลเดอร์ของไฟล์บริการเปิดให้ผู้ใช้เขียนได้ หากไฟล์ที่ ImagePath ชี้ไปอยู่ในโฟลเดอร์ที่ผู้ใช้ทั่วไปสร้างไฟล์ได้ ผู้ใช้สามารถแทนที่ไฟล์นั้นด้วยโปรแกรมของตน แล้วรอให้ระบบเริ่มบริการใหม่ด้วยสิทธิ์ของบัญชีที่บริการใช้ ผลคือได้สิทธิ์ของบัญชีนั้นทันทีโดยไม่ต้องใช้ช่องโหว่ใดๆ

แบบที่สองคือ เส้นทางที่ไม่มีเครื่องหมายอัญประกาศและมีช่องว่างในชื่อ เมื่อเส้นทางมีช่องว่างและไม่ได้ถูกครอบด้วยเครื่องหมายอัญประกาศ ระบบจะพยายามตีความเส้นทางนั้นหลายแบบตามลำดับ และอาจเรียกไฟล์ที่อยู่ผิดตำแหน่งได้ หากผู้ใช้สามารถสร้างไฟล์ชื่อที่ตรงกับส่วนแรกของเส้นทางในโฟลเดอร์ที่ค้นหาก่อนได้ ก็จะสามารถแทรกโปรแกรมของตนเข้าไปได้ รายละเอียดของกลไกนี้จะกล่าวถึงในบทที่ว่าด้วยการยกระดับสิทธิ์บนวินโดวส์

แบบที่สามคือ สิทธิ์บนคีย์บริการหลวมเกินไป การที่ผู้ใช้ทั่วไปมีสิทธิ์เปลี่ยนค่าของบริการเท่ากับสามารถเปลี่ยน ImagePath ให้ชี้ไปยังโปรแกรมใดก็ได้ สิทธิ์ที่ควรระวังคือสิทธิ์ที่อนุญาตให้เปลี่ยนการตั้งค่าบริการ เริ่มบริการ หรือเขียนรายการควบคุมการเข้าถึงของบริการเอง

แบบที่สี่คือ ไลบรารีของบริการที่ผู้ใช้แก้ไขได้ บริการจำนวนมากไม่ได้ทำงานเป็นโปรแกรมเดี่ยว แต่ทำงานเป็นไลบรารีที่โหลดเข้าไปในโฮสต์บริการร่วม ค่าที่ชี้ไปยังไลบรารีนี้จึงมีสถานะเดียวกับ ImagePath และต้องถูกจำกัดสิทธิ์เช่นเดียวกัน

งานตามกำหนดเวลา

งานตามกำหนดเวลา (Scheduled Task) คือกลไกที่ให้ระบบรันคำสั่งเมื่อถึงเงื่อนไขที่กำหนด เงื่อนไขอาจเป็นเวลา การเริ่มระบบ การเข้าสู่ระบบของผู้ใช้ หรือเหตุการณ์เฉพาะ เช่น การเชื่อมต่อเครือข่าย หรือการบันทึกเหตุการณ์บางชนิด

กลไกนี้มีที่มาจากเครื่องมือรุ่นเก่าชื่อ at ซึ่งรับงานครั้งเดียวในเวลาที่กำหนด วินโดวส์รุ่นใหม่ยังคงรองรับคำสั่ง at เพื่อความเข้ากันได้ แต่กลไกหลักที่ใช้จริงคืองานตามกำหนดเวลาซึ่งจัดการโดยบริการของตัวจัดกำหนดการ

ข้อมูลของงานถูกเก็บสองที่พร้อมกัน ที่แรกคือไฟล์ XML ใน C:\Windows\System32\Tasks ซึ่งเก็บคำนิยามของงานแต่ละงานแยกเป็นไฟล์ ที่สองคือรีจิสทรีใต้ HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache ซึ่งเก็บดัชนีและข้อมูลประกอบเพื่อให้ระบบค้นหางานได้เร็ว การตรวจสอบจึงต้องดูทั้งสองที่ เพราะผู้บุกรุกที่ลบไฟล์ XML อาจลบไม่ครบหรืออาจเหลือร่องรอยในรีจิสทรี

ปัญหาที่โทเคนถูกสร้างขึ้นมาแก้

ในระบบที่ผู้ใช้คนหนึ่งเป็นสมาชิกกลุ่มผู้ดูแลระบบ คำถามที่ต้องตอบให้ได้ก่อนคือ ระหว่างที่ผู้ใช้คนนั้นเปิดโปรแกรมอยู่ โปรแกรมนั้นมีสิทธิ์เท่ากับผู้ดูแลระบบตลอดเวลาหรือไม่ คำตอบคือไม่ และกลไกที่ทำให้เป็นเช่นนั้นคือโทเคนการเข้าถึง

ก่อนที่วินโดวส์รุ่นที่มี UAC จะถือกำเนิด ผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบจะได้สิทธิ์สูงสุดทันทีที่เข้าสู่ระบบ ทุกโปรแกรมที่ผู้ใช้เปิด ไม่ว่าจะเป็นโปรแกรมอ่านอีเมล โปรแกรมเล่นสื่อ หรือโปรแกรมที่ดาวน์โหลดมาจากอินเทอร์เน็ต ล้วนทำงานด้วยสิทธิ์นั้นทั้งหมด ผลคือโปรแกรมใดก็ตามที่ผู้ใช้เผลอเปิดสามารถแก้ไฟล์ระบบ ติดตั้งไดรเวอร์ หรือปิดเครื่องมือป้องกันได้โดยไม่ต้องมีใครอนุญาต ปัญหานี้ไม่ใช่ปัญหาของผู้ใช้ที่ตั้งใจทำสิ่งผิด แต่เป็นปัญหาของการที่ระบบมอบอำนาจสูงสุดให้ทุกอย่างโดยอัตโนมัติ

โทเคนการเข้าถึงและ UAC ถูกสร้างขึ้นมาเพื่อแก้ปัญหานี้ โดยแยกคำถามสองข้อที่เดิมรวมกันอยู่ออกจากกัน คำถามข้อแรกคือ "บัญชีนี้มีสิทธิ์อะไร" ซึ่งเป็นเรื่องของสมาชิกภาพในกลุ่ม คำถามข้อที่สองคือ "กระบวนการที่กำลังทำงานอยู่นี้มีสิทธิ์อะไรในขณะนี้" ซึ่งเป็นเรื่องของโทเคน ทั้งสองคำตอบไม่จำเป็นต้องเหมือนกัน และความเข้าใจว่าสองสิ่งนี้แยกจากกันคือหัวใจของหัวข้อนี้

โทเคนการเข้าถึงคืออะไร

โทเคนการเข้าถึง (Access Token) คือโครงสร้างข้อมูลที่ระบบสร้างขึ้นเมื่อผู้ใช้ยืนยันตัวสำเร็จ และผูกไว้กับทุกกระบวนการที่ทำงานในนามของผู้ใช้คนนั้น โทเคนทำหน้าที่เป็นบัตรประจำตัวของกระบวนการ กล่าวคือทุกครั้งที่กระบวนการขอเข้าถึงวัตถุใด ระบบจะตรวจสิทธิ์จากโทเคนของกระบวนการนั้น ไม่ได้ตรวจจากชื่อบัญชีที่ผู้ใช้พิมพ์ตอนเข้าสู่ระบบ

โทเคนถูกสร้างโดยส่วนความปลอดภัยของระบบซึ่งทำงานในกระบวนการ lsass.exe และถูกส่งต่อให้กับกระบวนการใหม่ทุกครั้งที่มีการสร้างกระบวนการในนามของผู้ใช้ ผลที่ตามมาคือการเปลี่ยนแปลงสมาชิกภาพในกลุ่มไม่ส่งผลต่อกระบวนการที่เปิดอยู่แล้ว เพราะโทเคนถูกสร้างไว้ก่อนการเปลี่ยนแปลงนั้น กระบวนการจะได้รับโทเคนใหม่ก็ต่อเมื่อผู้ใช้เข้าสู่ระบบใหม่หรือสร้างเซสชันการเข้าสู่ระบบใหม่เท่านั้น

ตาราง 3.19 องค์ประกอบสำคัญของโทเคนการเข้าถึง
องค์ประกอบเก็บอะไรนัยด้านความปลอดภัย
ตัวระบุผู้ใช้SID ของบัญชีเจ้าของโทเคนระบุว่าโทเคนนี้เป็นของใคร
รายการกลุ่มSID ของทุกกลุ่มที่ผู้ใช้เป็นสมาชิกกำหนดสิทธิ์ที่ได้จากกลุ่ม
รายการสิทธิ์พิเศษสิทธิ์ระดับระบบ เช่น สำรองข้อมูล หรือดีบักโปรแกรมใช้ได้แม้ไม่มีสิทธิ์บนวัตถุ
ระดับความสมบูรณ์ระดับที่กำหนดเพดานการเขียนจำกัดการเขียนทับวัตถุที่สูงกว่า
เซสชันการเข้าสู่ระบบตัวระบุเซสชันและวิธีที่ผู้ใช้เข้าสู่ระบบใช้แยกการเข้าสู่ระบบแบบมีหน้าจอกับแบบเครือข่าย
รายการควบคุมเริ่มต้นสิทธิ์เริ่มต้นของวัตถุที่กระบวนการสร้างกำหนดว่าวัตถุใหม่จะเปิดให้ใคร
แหล่งที่มาข้อมูลว่ากระบวนการนี้เกิดจากอะไรใช้ประกอบการตัดสินใจของนโยบาย

องค์ประกอบที่ผู้ตรวจสอบให้ความสนใจมากที่สุดคือรายการสิทธิ์พิเศษ เพราะสิทธิ์บางอย่างให้อำนาจที่เกินกว่าการเป็นสมาชิกกลุ่ม ตัวอย่างสิทธิ์ที่ควรรู้จักคือสิทธิ์ในการสำรองข้อมูลและกู้คืน ซึ่งอนุญาตให้อ่านไฟล์ได้โดยข้ามรายการควบคุมการเข้าถึง สิทธิ์ในการดีบักโปรแกรม ซึ่งอนุญาตให้เข้าถึงหน่วยความจำของกระบวนการอื่น และสิทธิ์ในการเป็นเจ้าของไฟล์ ซึ่งอนุญาตให้เปลี่ยนเจ้าของวัตถุแล้วจึงแก้สิทธิ์ของวัตถุนั้น สิทธิ์เหล่านี้ถูกออกแบบมาให้ผู้ดูแลระบบใช้ทำงาน แต่เมื่อใดก็ตามที่บัญชีทั่วไปมีสิทธิ์เหล่านี้ โทเคนนั้นก็มีอำนาจมากกว่าที่สมาชิกภาพในกลุ่มบอก

การอ่านโทเคนของตัวเองทำได้ด้วยคำสั่งเดียว

whoami /all

ผลลัพธ์ของคำสั่งนี้แบ่งเป็นสี่ส่วน คือข้อมูลผู้ใช้ รายการกลุ่ม รายการสิทธิ์พิเศษ และระดับความสมบูรณ์ สี่ส่วนนี้คือสิ่งที่ต้องอ่านประกอบกันเสมอ เพราะการดูเพียงชื่อบัญชีหรือเพียงรายการกลุ่มจะให้ภาพที่ไม่ครบ

โทเคนหลักและโทเคนแสดงตน

โทเคนมีสองประเภทที่ต้องแยกให้ออก โทเคนหลัก (Primary Token) คือโทเคนที่ผูกกับกระบวนการและใช้เป็นตัวตนหลักของกระบวนการนั้น โทเคนแสดงตน (Impersonation Token) คือโทเคนที่ผูกกับเธรดชั่วคราว เพื่อให้เธรดนั้นทำงานในนามของผู้อื่นได้ในระหว่างที่ให้บริการเขา

แนวคิดที่สองนี้จำเป็นเพราะบริการจำนวนมากต้องทำงานแทนผู้ใช้ที่เชื่อมต่อเข้ามา ตัวอย่างที่เข้าใจง่ายคือบริการแชร์ไฟล์ ซึ่งต้องตอบคำขออ่านไฟล์ตามสิทธิ์ของผู้ใช้ที่ร้องขอ ไม่ใช่ตามสิทธิ์ของบัญชีที่บริการใช้อยู่ หากไม่มีโทเคนแสดงตน บริการจะต้องเลือกอย่างใดอย่างหนึ่ง คือทำงานด้วยสิทธิ์ของตัวเองตลอดเวลาซึ่งเสี่ยงเกินไป หรือสร้างกระบวนการใหม่ในนามของผู้ใช้ทุกครั้งซึ่งสิ้นเปลืองเกินไป โทเคนแสดงตนจึงเป็นทางออกที่ให้บริการสลับตัวตนได้ชั่วคราว

ระดับของโทเคนแสดงตนมีสี่ระดับที่ให้อำนาจต่างกัน ระดับต่ำสุดอนุญาตให้ระบบรู้ว่าผู้ใช้เป็นใครแต่ไม่ยอมให้ทำอะไรในนามของเขา ระดับถัดมาอนุญาตให้ตรวจสอบสิทธิ์แต่ยังไม่ให้เข้าถึงทรัพยากร ระดับที่สามอนุญาตให้เข้าถึงทรัพยากรภายในเครื่องได้ ระดับสูงสุดอนุญาตให้ส่งต่อตัวตนไปยังเครื่องอื่นได้ ระดับสูงสุดนี้คือสิ่งที่ทำให้เกิดความเสี่ยงแบบหนึ่งที่เรียกว่า การส่งต่อตัวตน (Delegation) ซึ่งระบบที่ดีจะปิดไว้โดยค่าเริ่มต้น

ในมุมของการตรวจสอบ แนวคิดนี้สำคัญเพราะมันอธิบายว่าทำไมกระบวนการหนึ่งจึงมีสิทธิ์ต่างกันในแต่ละช่วงเวลา และทำไมเครื่องมือตรวจสอบบางตัวจึงรายงานสิทธิ์ของเธรดหนึ่งไม่เหมือนกับของกระบวนการทั้งกระบวนการ การอ่านสิทธิ์จึงต้องระบุให้ชัดว่ากำลังอ่านสิทธิ์ของสิ่งใด

ระดับความสมบูรณ์

กลไกที่สองที่ทำงานคู่กับโทเคนคือ ระดับความสมบูรณ์ (Integrity Level) ซึ่งเป็นป้ายที่ติดอยู่กับทั้งโทเคนและวัตถุทุกชนิดในระบบ ระบบใช้ป้ายนี้ตัดสินว่าโทเคนหนึ่งจะเขียนทับวัตถุหนึ่งได้หรือไม่ โดยใช้หลักที่เรียบง่ายว่าโทเคนที่ระดับต่ำกว่าเขียนทับวัตถุที่ระดับสูงกว่าไม่ได้

ตาราง 3.20 ระดับความสมบูรณ์ในวินโดวส์
ระดับค่าตัวเลขใช้กับอะไร
ไม่น่าเชื่อถือ0x0000กระบวนการที่ถูกจำกัดสิทธิ์อย่างรุนแรง เช่น โปรแกรมที่รันในแซนด์บ็อกซ์
ต่ำ0x1000กระบวนการของเบราว์เซอร์แบบแยกส่วน และโปรแกรมที่ถูกจำกัดสิทธิ์
ปานกลาง0x2000กระบวนการทั่วไปของผู้ใช้ รวมถึงเชลล์ที่เปิดตามปกติ
สูง0x3000กระบวนการที่ได้รับการยกระดับสิทธิ์แล้ว
ระบบ0x4000บริการและกระบวนการของระบบ
กระบวนการป้องกัน0x5000กระบวนการที่ระบบป้องกันไม่ให้แม้แต่ผู้ดูแลระบบแตะ

ค่าตัวเลขที่เห็นในผลลัพธ์ของเครื่องมือเป็นเลขฐานสิบหกที่แสดงเป็นตัวเลขฐานสิบในบางเครื่องมือ ตัวอย่างเช่น 0x2000 เขียนเป็น 8192 และ 0x3000 เขียนเป็น 12288 ตัวเลขเหล่านี้จะปรากฏใน SID รูปแบบ S-1-16-8192 ซึ่งผู้เรียนจะเห็นได้ในผลลัพธ์ของ whoami /all

หลักการทำงานของระดับความสมบูรณ์เรียกว่า นโยบายห้ามเขียนขึ้น (No-Write-Up) ซึ่งหมายความว่าโทเคนที่ระดับต่ำกว่าจะเขียนหรือลบวัตถุที่ระดับสูงกว่าไม่ได้ แต่ยังอ่านได้หากสิทธิ์ตามปกติอนุญาต นโยบายนี้ออกแบบมาเช่นนี้เพื่อไม่ให้โปรแกรมทั่วไปที่ต้องอ่านไฟล์ระบบหยุดทำงาน แต่จำกัดความเสียหายที่โปรแกรมระดับต่ำจะทำได้

ผลที่สำคัญที่สุดของนโยบายนี้คือ การป้องกันการแก้ไขค่าโดยไม่ตั้งใจจากโปรแกรมระดับต่ำ ซึ่งเป็นกรณีที่เกิดบ่อยในทางปฏิบัติ ตัวอย่างเช่นโปรแกรมที่ผู้ใช้ดาวน์โหลดมาซึ่งพยายามเขียนไฟล์ในโฟลเดอร์ของระบบจะล้มเหลวเพราะโทเคนของมันอยู่ระดับปานกลาง ขณะที่วัตถุปลายทางอยู่ระดับสูง นี่คือกลไกที่ทำให้มัลแวร์ทั่วไปไม่สามารถแก้ไฟล์ระบบได้ทันทีที่ผู้ใช้เปิดโปรแกรม

แต่ต้องเข้าใจข้อจำกัดด้วยว่า นโยบายนี้จำกัดการเขียนไปยังวัตถุที่ระบบติดป้ายไว้เท่านั้น วัตถุที่ผู้ใช้สร้างเอง ไฟล์ในโฟลเดอร์ของผู้ใช้ และคีย์รีจิสทรีในส่วนของผู้ใช้ ล้วนอยู่ระดับเดียวกับโทเคนของผู้ใช้ จึงเขียนได้ตามปกติ พื้นที่เหล่านี้คือพื้นที่ที่มัลแวร์ใช้ทำงาน และเป็นเหตุผลว่าทำไมการคงอยู่ในส่วนของผู้ใช้จึงยังเป็นเรื่องที่พบได้เสมอ

UAC ทำงานอย่างไร

การควบคุมบัญชีผู้ใช้ (User Account Control) คือกลไกที่ทำให้ผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบทำงานด้วยสิทธิ์ปานกลางเป็นปกติ และยกระดับสิทธิ์เฉพาะเมื่อจำเป็น กลไกนี้ทำงานโดย การแยกโทเคน (Token Splitting) กล่าวคือเมื่อผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบเข้าสู่ระบบ ระบบจะสร้างโทเคนสองชุด ชุดแรกคือโทเคนที่ถูกกรองแล้ว ซึ่งตัด SID ของกลุ่มผู้ดูแลระบบและสิทธิ์พิเศษส่วนใหญ่ออก และใช้กับเชลล์และโปรแกรมทั่วไป ชุดที่สองคือโทเคนเต็มที่ยังมีสิทธิ์ครบ และเก็บไว้รอใช้เมื่อผู้ใช้ยืนยันความประสงค์จะยกระดับ

เมื่อโปรแกรมที่ต้องการสิทธิ์สูงเริ่มทำงาน ระบบจะตรวจจากรายการแจ้งความต้องการของโปรแกรมว่าโปรแกรมนี้ขอสิทธิ์สูงหรือไม่ หากขอ ระบบจะแสดงกล่องยืนยันให้ผู้ใช้ตัดสินใจ เมื่อผู้ใช้ยืนยัน ระบบจะสร้างกระบวนการใหม่ด้วยโทเคนเต็ม ไม่ใช่การเพิ่มสิทธิ์ให้กระบวนการเดิม ข้อเท็จจริงข้อนี้สำคัญเพราะมันอธิบายว่าทำไมการยกระดับจึงได้กระบวนการใหม่เสมอ และทำไมค่าในตัวแปรของเชลล์เดิมจึงไม่ติดไปกับกระบวนการที่ยกระดับ

กล่องยืนยันที่ระบบแสดงมีสองแบบที่ต่างกันในระดับความเสี่ยง แบบแรกคือ การขอความยินยอม (Consent) ซึ่งแสดงเมื่อผู้ใช้ที่กำลังยกระดับเป็นสมาชิกกลุ่มผู้ดูแลระบบอยู่แล้ว ผู้ใช้เพียงกดยืนยันโดยไม่ต้องพิมพ์รหัสผ่าน แบบที่สองคือ การขอข้อมูลรับรอง (Credential Prompt) ซึ่งแสดงเมื่อผู้ใช้ที่กำลังยกระดับยังไม่ใช่สมาชิกกลุ่มผู้ดูแลระบบ ระบบจึงต้องให้ระบุบัญชีที่มีสิทธิ์ ตัวอย่างของผู้ใช้ประเภทที่สองคือผู้ใช้ทั่วไปที่ต้องการติดตั้งโปรแกรมซึ่งต้องใช้สิทธิ์ของผู้ดูแลระบบ

กล่องยืนยันทั้งสองแบบถูกแสดงบน เดสก์ท็อปที่ปลอดภัย (Secure Desktop) ซึ่งเป็นเดสก์ท็อปแยกที่โปรแกรมอื่นวาดทับไม่ได้ การออกแบบนี้มีไว้ป้องกันโปรแกรมที่พยายามปลอมหน้าตากล่องยืนยันเพื่อหลอกให้ผู้ใช้กรอกรหัสผ่าน

ค่าที่ผู้ตรวจสอบพบว่าถูกแก้บ่อยที่สุดคือ EnableLUA ซึ่งเมื่อตั้งเป็น 0 จะปิดกลไกทั้งหมด และทำให้ผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบได้โทเคนเต็มทันทีที่เข้าสู่ระบบ การตั้งค่านี้พบได้ในเครื่องที่ผู้ดูแลระบบปิดไว้เพื่อความสะดวกในการใช้งานโปรแกรมรุ่นเก่า ซึ่งในมุมของความปลอดภัยเท่ากับย้อนระบบกลับไปสู่สภาพก่อนมี UAC

ค่าที่สองคือ LocalAccountTokenFilterPolicy ซึ่งมีผลเฉพาะการเข้าถึงจากระยะไกล เมื่อตั้งเป็น 1 ระบบจะมอบโทเคนเต็มให้บัญชีในเครื่องที่เชื่อมต่อเข้ามาทางเครือข่าย การตั้งค่านี้ถูกใช้เพื่อให้เครื่องมือบริหารจัดการจากระยะไกลทำงานได้ แต่ผลข้างเคียงคือบัญชีผู้ดูแลระบบในเครื่องที่ถูกยึดรหัสผ่านไปแล้วจะใช้ได้เต็มสิทธิ์ทันทีโดยไม่ต้องผ่านกลไกใด

ค่าที่สามคือ FilterAdministratorToken ซึ่งควบคุมบัญชีผู้ดูแลระบบในตัวที่มี RID 500 โดยค่าเริ่มต้นบัญชีนี้จะไม่ถูกกรองโทเคน หมายความว่าผู้ที่เข้าสู่ระบบด้วยบัญชีนี้จะได้โทเคนเต็มทันที การตั้งค่านี้เป็น 1 คือการปิดข้อยกเว้นนี้ และเป็นสิ่งที่ควรทำในเครื่องที่ต้องการความรัดกุม

เหตุใด UAC จึงไม่ใช่เส้นแบ่งความปลอดภัย

มีข้อเข้าใจผิดที่พบบ่อยในหมู่ผู้เริ่มต้นว่า UAC เป็นกำแพงที่กั้นระหว่างสิทธิ์ผู้ใช้กับสิทธิ์ผู้ดูแลระบบ และการข้ามกำแพงนี้ต้องใช้ช่องโหว่ ความจริงคือผู้ผลิตระบบเองระบุชัดว่า UAC ไม่ใช่ขอบเขตความปลอดภัย (Security Boundary) แต่เป็นกลไกที่ออกแบบมาเพื่อลดโอกาสที่ผู้ใช้จะทำสิ่งที่มีผลกระทบโดยไม่ตั้งใจ

เหตุผลเชิงโครงสร้างที่ทำให้เป็นเช่นนั้นมีสามข้อ ข้อแรกคือกลไกนี้ทำงานอยู่ในโหมดผู้ใช้เดียวกับโปรแกรมอื่น กระบวนการที่ทำหน้าที่ตัดสินใจยกระดับจึงเป็นโปรแกรมธรรมดาที่สามารถถูกแทรกแซงได้ด้วยเทคนิคที่ใช้กับโปรแกรมทั่วไป ข้อที่สองคือผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบมีสิทธิ์เต็มอยู่แล้วในเชิงบัญชี สิ่งที่ UAC ทำคือเลือกว่าจะใช้สิทธิ์นั้นเมื่อใด ไม่ได้ทำให้สิทธิ์นั้นหายไป ข้อที่สามคือระบบอนุญาตให้โปรแกรมบางประเภทขอยกระดับได้เองโดยไม่ต้องแสดงกล่องยืนยัน ซึ่งเป็นคุณสมบัติที่จำเป็นสำหรับโปรแกรมของระบบ แต่ก็เป็นช่องทางที่ถูกนำไปใช้ในทางที่ผิด

ผลในทางปฏิบัติคือ ผู้ที่ได้สิทธิ์ในนามของผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบสามารถยกระดับได้โดยไม่ต้องใช้ช่องโหว่ของซอฟต์แวร์เลย เพราะเขาใช้สิทธิ์ที่มีอยู่แล้วผ่านช่องทางที่ระบบเปิดไว้ ต่างจากการยกระดับจากบัญชีผู้ใช้ธรรมดาไปเป็นผู้ดูแลระบบ ซึ่งเป็นการข้ามเส้นแบ่งสิทธิ์จริงและต้องอาศัยช่องโหว่หรือการตั้งค่าที่ผิดพลาด

ความเข้าใจนี้มีผลโดยตรงต่อการประเมินความเสี่ยง องค์กรที่คิดว่าการให้ผู้ใช้เป็นสมาชิกกลุ่มผู้ดูแลระบบบนเครื่องของตนเป็นเรื่องที่ UAC คุ้มครองอยู่แล้ว ย่อมประเมินความเสี่ยงต่ำกว่าความเป็นจริง เพราะเมื่อผู้ใช้ถูกหลอกให้รันโปรแกรม การยกระดับเป็นเพียงการกดยืนยันหนึ่งครั้ง หรือในบางกรณีไม่ต้องกดเลย

สิ่งที่ผู้ตรวจสอบต้องอ่านจากโทเคน

การอ่านโทเคนให้ประโยชน์สามประการในการทำงานจริง ประการแรกคือทำให้รู้ว่าตัวเองอยู่ระดับใดและมีสิทธิ์อะไรบ้าง ซึ่งกำหนดว่าขั้นตอนถัดไปทำได้หรือไม่ ประการที่สองคือทำให้รู้ว่าบัญชีที่ยึดมาได้มีสิทธิ์จริงตามที่คาดหรือไม่ เพราะบัญชีที่อยู่ในกลุ่มผู้ดูแลระบบอาจมีโทเคนที่ถูกกรอง ประการที่สามคือทำให้ตรวจพบสิทธิ์พิเศษที่ถูกมอบให้บัญชีอย่างไม่ตั้งใจ

ลำดับการอ่านที่ใช้ได้ผลในทางปฏิบัติมีสี่ขั้น ขั้นแรกอ่านระดับความสมบูรณ์จาก whoami /groups แล้วดูบรรทัดที่ขึ้นต้นด้วย Mandatory Label ขั้นที่สองอ่านรายการสิทธิ์พิเศษจาก whoami /priv แล้วเทียบกับรายการสิทธิ์ที่ควรมีสำหรับผู้ใช้ประเภทนั้น ขั้นที่สามตรวจว่ามีสิทธิ์ที่อนุญาตให้เขียนไฟล์โดยข้ามสิทธิ์ปกติหรือไม่ ขั้นที่สี่ตรวจว่าบัญชีเป็นสมาชิกกลุ่มใดบ้าง โดยเฉพาะกลุ่มที่ให้สิทธิ์ในระดับสูง

ข้อควรระวังที่สำคัญที่สุดคือการสรุปว่า "ได้สิทธิ์ผู้ดูแลระบบแล้ว" เพราะเห็นชื่อบัญชีอยู่ในกลุ่มผู้ดูแลระบบ การสรุปเช่นนั้นผิดได้ง่ายในระบบที่มีการกรองโทเคน หลักฐานที่ถูกต้องคือระดับความสมบูรณ์ของโทเคนในกระบวนการที่กำลังใช้งานอยู่ ไม่ใช่สมาชิกภาพของบัญชี

อีกข้อที่ควรระวังคือความแตกต่างระหว่างการเข้าสู่ระบบแบบมีหน้าจอกับแบบเครือข่าย การเข้าสู่ระบบแบบเครือข่ายไม่ได้สร้างเดสก์ท็อปและไม่ได้ผ่านกลไกยกระดับในลักษณะเดียวกัน ผู้ที่ได้เชลล์มาจากบริการระยะไกลจึงมักอยู่ในสถานะที่ต่างจากผู้ใช้ที่นั่งอยู่หน้าเครื่อง แม้จะเป็นบัญชีเดียวกันก็ตาม

3.6 PowerShell: หลักการและคำสั่งที่ใช้บ่อย

สิ่งที่ทำให้ PowerShell ต่างจากเชลล์อื่น

ผู้เรียนที่มาจากบทที่แล้วจะคุ้นเคยกับแนวคิดที่ว่าเชลล์ของลินุกซ์ส่งต่อข้อมูลระหว่างคำสั่งเป็นข้อความ ls | grep log ทำงานได้เพราะ ls เขียนชื่อไฟล์ออกมาเป็นข้อความ แล้ว grep อ่านข้อความนั้นและกรองบรรทัดที่ตรงกับคำค้น แนวทางนี้ยืดหยุ่นมากแต่มีจุดอ่อนคือทุกคำสั่งต้องตกลงรูปแบบข้อความร่วมกัน และการดึงข้อมูลหนึ่งฟิลด์ออกมาจากข้อความต้องอาศัยการตัดสตริงซึ่งพังง่ายเมื่อรูปแบบเปลี่ยน

PowerShell เลือกทางอื่น มันส่งต่อ ออบเจกต์ (Object) ระหว่างคำสั่ง ไม่ใช่ข้อความ ออบเจกต์คือโครงสร้างข้อมูลที่มีชื่อฟิลด์และชนิดข้อมูลกำกับชัดเจน คำสั่งหนึ่งส่งออบเจกต์ที่แทนบริการของระบบออกมา คำสั่งถัดไปจึงสามารถอ้างถึงฟิลด์ชื่อ Status หรือ StartType ได้โดยตรงโดยไม่ต้องตัดสตริงเลย

ผลต่างนี้มีนัยสำคัญสามข้อ ข้อแรกคือการกรองทำได้แม่นกว่า เพราะเปรียบเทียบข้อมูลตามชนิดของมัน เช่น เปรียบเทียบตัวเลขกับตัวเลข ไม่ใช่ข้อความกับข้อความ อีกข้อคือคำสั่งไม่ต้องกังวลเรื่องรูปแบบการแสดงผล เพราะการจัดตารางหรือแปลงเป็นรูปแบบต่างๆ เป็นหน้าที่ของคำสั่งที่แสดงผล ไม่ใช่ของคำสั่งที่ผลิตข้อมูล ข้อสุดท้ายคือผลลัพธ์นำไปใช้ต่อได้ง่าย ทั้งการส่งออกเป็นไฟล์ข้อมูล การแปลงเป็นรายงาน หรือการส่งให้โปรแกรมอื่น

ชื่อคำสั่งและรูปแบบการเรียก

คำสั่งใน PowerShell เรียกว่า cmdlet และมีธรรมเนียมการตั้งชื่อแบบ กริยา-นาม (Verb-Noun) เช่น Get-Service, Stop-Service, New-Item, Remove-Item การตั้งชื่อแบบนี้มีประโยชน์เพราะผู้ใช้สามารถเดาชื่อคำสั่งที่ตนต้องการได้จากสิ่งที่อยากทำ และสามารถค้นหาคำสั่งทั้งหมดที่ทำกริยาหนึ่งได้

Get-Command -Verb Get
Get-Command -Noun Service

คำสั่งแรกแสดงคำสั่งทั้งหมดที่ขึ้นต้นด้วยกริยา Get และคำสั่งที่สองแสดงคำสั่งทั้งหมดที่ทำงานกับบริการ คำสั่ง Get-Help ใช้ดูวิธีใช้โดยละเอียด และมีตัวเลือก -Examples ที่แสดงตัวอย่างซึ่งมักเพียงพอต่อการใช้งานจริง

คำสั่งส่วนใหญ่รับพารามิเตอร์ที่ระบุชื่อได้ เช่น -Name หรือ -ComputerName และ PowerShell อนุญาตให้ละชื่อพารามิเตอร์ได้หากตำแหน่งของค่าบอกอยู่แล้ว การเขียนแบบเต็มจึงอ่านง่ายกว่าและปลอดภัยกว่าเมื่อคำสั่งยาวขึ้น

การต่อท่อ

การต่อท่อ (Pipeline) ใน PowerShell ใช้เครื่องหมาย | เหมือนเชลล์อื่น แต่สิ่งที่ไหลผ่านท่อคือออบเจกต์ คำสั่งที่ใช้บ่อยในท่อมีสี่ตัวที่ควรจำ

ตาราง 3.22 คำสั่งที่ใช้บ่อยในการต่อท่อ
คำสั่งหน้าที่ตัวอย่างการใช้
Where-Objectกรองออบเจกต์ตามเงื่อนไขWhere-Object { $_.State -eq 'Running' }
Select-Objectเลือกฟิลด์หรือจำนวนรายการSelect-Object Name, Status

สัญลักษณ์ $_ ที่เห็นในเงื่อนไขหมายถึงออบเจกต์ปัจจุบันที่กำลังไหลผ่านท่อ เป็นสิ่งที่ต้องทำความคุ้นเคยเพราะปรากฏในเกือบทุกคำสั่งกรอง การอ่านว่า "กรองออบเจกต์ที่ฟิลด์ State มีค่าเท่ากับ Running" จะทำให้เข้าใจได้ทันที

ตัวอย่างที่แสดงพลังของการต่อท่อคือการหาบริการที่ทำงานอยู่และเริ่มอัตโนมัติ พร้อมแสดงเฉพาะชื่อและบัญชีที่ใช้รัน

Get-Service |
    Where-Object { $_.Status -eq 'Running' -and $_.StartType -eq 'Automatic' } |
    Select-Object Name, DisplayName, StartType

คำสั่ง Get-Process ทำงานในลักษณะเดียวกันกับกระบวนการ โดยคืนออบเจกต์ของทุกโปรแกรมที่กำลังทำงานพร้อมชื่อ หมายเลขโปรแกรม และหน่วยความจำที่ใช้อยู่ ตัวอย่างการหาสิบโปรแกรมที่ใช้หน่วยความจำมากที่สุด

Get-Process |
    Sort-Object WorkingSet64 -Descending |
    Select-Object -First 10 Name, Id, WorkingSet64

ข้อจำกัดที่ควรรู้คือบางฟิลด์ของกระบวนการ เช่น เส้นทางไฟล์ของโปรแกรม จะอ่านได้เฉพาะกระบวนการที่ผู้ใช้ปัจจุบันมีสิทธิ์เข้าถึง สำหรับกระบวนการของบัญชีอื่นหรือของระบบ ฟิลด์เหล่านี้อาจว่างเปล่า การใช้ Get-Process เพื่อหาเส้นทางไฟล์ของมัลแวร์ที่ทำงานด้วยสิทธิ์ของระบบจึงอาจไม่ให้ผล และต้องใช้เครื่องมืออื่นหรือสิทธิ์ที่สูงกว่า

ข้อควรระวังที่ผู้เริ่มต้นมักพลาดคือการนำคำสั่งจัดรูปแบบไปไว้กลางท่อ Format-Table และ Format-List เปลี่ยนออบเจกต์ให้กลายเป็นข้อความสำหรับแสดงผล ผลคือคำสั่งถัดไปในท่อจะไม่ได้รับออบเจกต์อีกต่อไปและมักให้ผลผิดพลาด คำสั่งจัดรูปแบบจึงควรอยู่ท้ายท่อเสมอ

ผู้ให้บริการข้อมูล

ความสามารถที่ทำให้ PowerShell ทรงพลังกว่าที่เห็นคือแนวคิด ผู้ให้บริการข้อมูล (Provider) ซึ่งทำให้แหล่งข้อมูลที่ต่างชนิดกันเข้าถึงได้ด้วยวิธีเดียวกัน ผู้ให้บริการที่สำคัญมีสี่ตัวคือระบบไฟล์ รีจิสทรี ใบรับรอง และตัวแปร

ผู้ให้บริการแต่ละตัวถูกมองเป็นไดรฟ์ ทำให้ใช้คำสั่งเดียวกันได้ทั้งหมด คำสั่ง Get-PSDrive แสดงไดรฟ์ที่มีทั้งหมด และจะเห็นว่า HKLM: และ HKCU: ปรากฏอยู่ในรายการนั้นด้วย

Get-ChildItem 'HKLM:\SYSTEM\CurrentControlSet\Services' |
    Select-Object -First 10

ประโยชน์ของแนวทางนี้คือผู้เรียนไม่ต้องเรียนรู้คำสั่งใหม่สำหรับรีจิสทรี คำสั่ง Get-ChildItem, Get-Item, Get-ItemProperty, New-Item และ Remove-Item ใช้ได้กับทั้งไฟล์และคีย์รีจิสทรีโดยเปลี่ยนเพียงเส้นทาง

การสอบถามข้อมูลระบบด้วย CIM

คำสั่งที่ใช้สอบถามข้อมูลลึกของระบบคือ Get-CimInstance ซึ่งทำงานกับ แบบจำลองข้อมูลกลาง (Common Information Model) หรือ CIM แบบจำลองนี้เป็นมาตรฐานที่อธิบายว่าองค์ประกอบของระบบ เช่น กระบวนการ บริการ ดิสก์ และการตั้งค่าเครือข่าย มีคุณสมบัติอะไรบ้าง

Get-CimInstance Win32_Process |
    Sort-Object WorkingSetSize -Descending |
    Select-Object -First 15 Name, ProcessId, WorkingSetSize, CommandLine

ชื่อคลาสที่ขึ้นต้นด้วย Win32_ คือคลาสมาตรฐานที่ใช้บ่อยที่สุด การค้นหาคลาสที่ต้องการทำได้ด้วยคำสั่ง Get-CimClass ซึ่งรับคำค้นได้

ความแตกต่างที่ควรรู้คือ CIM มีสองช่องทางในการสื่อสารกับระบบ วิธีแรกคือผ่านโปรโตคอลแบบเดิมที่ใช้ร่วมกับเครื่องอื่นในวงเดียวกัน และวิธีที่สองคือผ่านบริการบริหารจัดการระยะไกลที่ทำงานบน HTTP ซึ่งเปิดใช้งานได้ง่ายกว่าในสภาพที่เครือข่ายปิดพอร์ตแบบเดิม ในเครื่องเดียวกันทั้งสองวิธีให้ผลเหมือนกัน แต่เมื่อต้องสอบถามเครื่องอื่น ความแตกต่างนี้มีผลต่อการตั้งค่าและต่อการตรวจจับของเครื่องมือป้องกัน

ใน PowerShell รุ่นใหม่ คำสั่งที่ใช้แบบจำลองนี้แทนที่คำสั่งรุ่นเก่าที่ขึ้นต้นด้วย Get-WmiObject ซึ่งถูกถอดออกไปแล้ว คำสั่งรุ่นเก่ายังใช้ได้ในรุ่น 5.1 และเป็นคำสั่งที่ผู้เรียนจะพบในเอกสารเก่าจำนวนมาก การรู้ว่าทั้งสองคำสั่งทำงานเดียวกันแต่ใช้ชื่อต่างกันจึงช่วยให้อ่านเอกสารรุ่นเก่าได้โดยไม่สับสน

นโยบายการเรียกใช้สคริปต์

นโยบายการเรียกใช้ (Execution Policy) คือค่าที่กำหนดว่า PowerShell จะยอมให้รันไฟล์สคริปต์หรือไม่ ค่าที่พบบ่อยมีห้าระดับ

ค่าพฤติกรรม
Restrictedไม่ยอมให้รันไฟล์สคริปต์ใดๆ เป็นค่าเริ่มต้นของเครื่องทั่วไป

สิ่งที่ต้องเข้าใจให้ถูกต้องคือค่านี้ไม่ใช่กลไกความปลอดภัย เพราะมันถูกออกแบบมาเพื่อป้องกันการรันสคริปต์โดยไม่ตั้งใจ ไม่ได้ออกแบบมาเพื่อหยุดผู้ที่ตั้งใจจะรันสคริปต์ ผู้ใช้ที่มีสิทธิ์ในเครื่องสามารถระบุค่านี้ใหม่ได้ทุกครั้งที่เรียก PowerShell หรือส่งเนื้อหาสคริปต์เข้าไปทางช่องทางอื่นที่ไม่ผ่านการตรวจสอบไฟล์

ผู้ตรวจสอบจึงไม่ควรใช้การอ่านค่านี้เป็นหลักฐานว่าองค์กรปลอดภัยจากการรันสคริปต์ และไม่ควรสรุปว่าเครื่องที่ตั้งค่าไว้สูงกว่าปลอดภัยกว่าโดยอัตโนมัติ สิ่งที่มีความหมายกว่าคือบันทึกการทำงานของ PowerShell ซึ่งจะกล่าวถึงในหัวข้อถัดไป

การบันทึกและการตรวจจับ

PowerShell มีกลไกบันทึกสามชั้นที่ทำงานต่างกัน ชั้นแรกคือ การบันทึกบล็อกสคริปต์ (Script Block Logging) ซึ่งบันทึกเนื้อหาของโค้ดที่ถูกประมวลผลลงในบันทึกเหตุการณ์หมายเลข 4104 กลไกนี้สำคัญมากเพราะมันบันทึกโค้ดที่ถูกสร้างขึ้นในหน่วยความจำด้วย ไม่ใช่เพียงโค้ดที่อยู่ในไฟล์ ทำให้เห็นคำสั่งที่ถูกประกอบขึ้นในขณะทำงานและถูกเรียกใช้ทันที

ชั้นที่สองคือ การบันทึกโมดูล (Module Logging) ซึ่งบันทึกการเรียกใช้คำสั่งในโมดูลที่กำหนด ลงในบันทึกเหตุการณ์หมายเลข 4103 กลไกนี้ให้ข้อมูลระดับคำสั่ง แต่ไม่เห็นโค้ดที่ประกอบขึ้นมาเอง

ชั้นที่สามคือ การบันทึกบทสนทนา (Transcription) ซึ่งบันทึกทุกอย่างที่ปรากฏบนหน้าจอลงเป็นไฟล์ข้อความ กลไกนี้มีประโยชน์ในการตรวจสอบย้อนหลัง แต่ปิดไว้โดยค่าเริ่มต้นและผู้ใช้ที่รู้เรื่องสามารถปิดระหว่างใช้งานได้

กลไกอีกชั้นที่ทำงานนอกระบบบันทึกคือ ส่วนติดต่อตรวจสอบมัลแวร์ (Antimalware Scan Interface) ซึ่งเป็นช่องทางที่ให้เครื่องมือป้องกันเข้าตรวจโค้ดก่อนที่มันจะถูกประมวลผล กลไกนี้ทำงานในหน่วยความจำและไม่ทิ้งบันทึกของตัวเอง แต่ผลการตรวจจับจะไปปรากฏในบันทึกของเครื่องมือป้องกันนั้น

สำหรับผู้ตรวจสอบ ลำดับความสำคัญคือดูว่าองค์กรเปิดการบันทึกบล็อกสคริปต์หรือไม่ เพราะหากไม่เปิด โค้ดที่ถูกประกอบขึ้นในหน่วยความจำจะไม่เหลือร่องรอยใดเลยแม้จะถูกเรียกใช้บนเครื่องก็ตาม

ความแตกต่างระหว่างรุ่น

PowerShell มีสองสายที่ทำงานคู่กันอยู่ในปัจจุบัน สายแรกคือ Windows PowerShell ซึ่งมาพร้อมระบบตั้งแต่รุ่น 7 และหยุดอยู่ที่รุ่น 5.1 สายที่สองคือ PowerShell รุ่นใหม่ซึ่งติดตั้งแยกและพัฒนาต่อเนื่อง

ความแตกต่างที่ผู้เริ่มต้นชนบ่อยที่สุดไม่ใช่เรื่องความสามารถ แต่เป็นเรื่องชื่อคำสั่งที่ซ้ำกัน ในรุ่น 5.1 คำสั่ง curl และ wget ถูกกำหนดเป็นชื่อย่อของคำสั่ง Invoke-WebRequest เพื่อให้ผู้ใช้ที่คุ้นเคยกับเครื่องมือบนลินุกซ์ใช้งานได้ง่ายขึ้น ผลคือผู้ที่พิมพ์ curl ใน PowerShell 5.1 จะไม่ได้เรียกโปรแกรม curl จริง แต่เรียกคำสั่งของ PowerShell ซึ่งรับพารามิเตอร์ต่างกันโดยสิ้นเชิง ความสับสนนี้ทำให้คำสั่งที่เขียนไว้ใช้ได้บนเครื่องหนึ่งแต่ล้มเหลวบนอีกเครื่องหนึ่ง การตรวจสอบว่าชื่อที่พิมพ์เป็นคำสั่งจริงหรือชื่อย่อทำได้ด้วยคำสั่ง Get-Command

3.7 CMD และ wmic ในงานตรวจสอบ

เหตุใดจึงยังต้องรู้จัก CMD

คำถามที่ผู้เรียนมักถามทันทีคือ ถ้า PowerShell ทำได้ทุกอย่างและดีกว่า เหตุใดจึงต้องเสียเวลาเรียนเชลล์รุ่นเก่า คำตอบมีสามข้อ และทั้งสามข้อเป็นเหตุผลเชิงปฏิบัติไม่ใช่เหตุผลเชิงประวัติศาสตร์

เหตุผลข้อแรกคือ เครื่องมือเก่ายังมีอยู่จริงในองค์กร ระบบที่ติดตั้งมานานหลายปีมักมีสคริปต์เริ่มทำงานที่ผูกกับ CMD และมีนโยบายขององค์กรที่รันคำสั่งผ่าน CMD ผู้ตรวจสอบที่เข้าไปในเครื่องลักษณะนี้จะพบว่าคำสั่งที่คนในองค์กรใช้สื่อสารกันเป็นคำสั่งของ CMD ไม่ใช่ของ PowerShell การอ่านและเขียนคำสั่งเหล่านั้นได้จึงเป็นทักษะที่จำเป็น

เหตุผลข้อที่สองคือ CMD ทำงานได้ในสภาพที่ PowerShell ถูกจำกัด ในสภาพที่ระบบถูกจำกัดการเรียกใช้สคริปต์หรือมีนโยบายที่ตัดความสามารถของ PowerShell ออก การใช้คำสั่งของ CMD ซึ่งเป็นโปรแกรมเดี่ยวที่ทำงานได้ทันทีจึงเป็นทางเลือกที่หลงเหลืออยู่ ผู้บุกรุกใช้ข้อเท็จจริงนี้บ่อยครั้ง และผู้ตรวจสอบต้องเข้าใจว่าการจำกัด PowerShell เพียงอย่างเดียวไม่ได้ปิดช่องทางนี้

เหตุผลข้อที่สามคือ CMD เป็นทางผ่านไปยังเครื่องมืออื่น โปรแกรมจำนวนมากที่ไม่มีหน้าจอทำงานได้ดีที่สุดเมื่อถูกเรียกผ่าน CMD และการเรียกโปรแกรมหนึ่งผ่านอีกโปรแกรมหนึ่งเป็นพฤติกรรมปกติในสคริปต์ขององค์กร การเข้าใจว่าคำสั่งหนึ่งถูกเรียกผ่าน cmd.exe /c ทำงานอย่างไรจึงช่วยแยกความแตกต่างระหว่างพฤติกรรมปกติกับพฤติกรรมที่น่าสงสัย

ความแตกต่างเชิงสถาปัตยกรรมที่ควรรู้คือ CMD รับคำสั่งและคืนผลลัพธ์เป็นข้อความ ส่วน PowerShell คืนออบเจกต์ ผลคือคำสั่งของ CMD ที่ยาวและซับซ้อนต้องอาศัยการตัดต่อข้อความซึ่งเปราะบางต่อการเปลี่ยนรูปแบบ และผลลัพธ์ของ CMD มีแนวโน้มขึ้นกับภาษาของระบบมากกว่า ตัวอย่างที่ชัดเจนคือการค้นหาข้อความในผลลัพธ์ของ systeminfo ซึ่งจะได้ผลก็ต่อเมื่อรู้ว่าหัวข้อในเครื่องนั้นเขียนเป็นภาษาใด

คำสั่งของ CMD ที่ผู้ตรวจสอบใช้บ่อยมีไม่มาก และแต่ละตัวตอบคำถามหนึ่งข้อที่ชัดเจน

ข้อควรระวังในการใช้คำสั่งเหล่านี้คือผลลัพธ์บางส่วนขึ้นกับภาษาของระบบ การเขียนสคริปต์ที่ค้นหาคำว่า Running ในผลลัพธ์ของ sc query จะใช้ได้กับเครื่องที่ตั้งภาษาอังกฤษเท่านั้น วิธีที่ทนกว่าคือใช้ findstr กับรหัสตัวเลข หรือเปลี่ยนไปใช้ PowerShell ซึ่งให้ค่าที่เป็นออบเจกต์และไม่ขึ้นกับภาษา

wmic และสถานะการเลิกใช้

wmic คือเครื่องมือบรรทัดคำสั่งที่ใช้สอบถามแบบจำลองข้อมูลกลาง ซึ่งเป็นแบบจำลองเดียวกับที่ PowerShell ใช้ผ่าน Get-CimInstance เครื่องมือนี้มีประโยชน์เพราะเรียกได้ทันทีโดยไม่ต้องเขียนสคริปต์ และผลลัพธ์จัดเป็นตารางที่อ่านง่าย

wmic service get Name, State, StartMode, PathName
wmic process get Name, ProcessId, CommandLine
wmic product get Name, Version

ข้อจำกัดของ wmic มีสองข้อที่สำคัญ ข้อแรกคือผลลัพธ์เป็นข้อความ จึงกรองและคำนวณได้ยากกว่าออบเจกต์ ข้อที่สองคือคำสั่ง wmic product ซึ่งแสดงรายการโปรแกรมที่ติดตั้งผ่านตัวติดตั้งมาตรฐาน ทำงานช้าและให้ผลไม่ครบ เพราะไม่เห็นโปรแกรมที่ติดตั้งด้วยวิธีอื่น

สถานะในปัจจุบันคือเครื่องมือนี้ถูกประกาศเลิกใช้และถูกถอดออกจากระบบรุ่นใหม่แล้ว โดยในระบบรุ่นล่าสุดมันไม่มีมาให้ใช้เป็นค่าเริ่มต้น ผลในทางปฏิบัติคือสคริปต์เก่าที่เรียก wmic จะล้มเหลวบนเครื่องใหม่ และผู้ตรวจสอบต้องเตรียมคำสั่งทดแทนไว้ล่วงหน้า

การเรียกใช้ผ่าน cmd

การเรียกคำสั่งของ CMD จากภายใน PowerShell หรือจากโปรแกรมอื่นต้องผ่าน cmd.exe ด้วยตัวเลือกที่สั่งให้รับคำสั่งเป็นข้อความ เช่น

cmd.exe /c "whoami /all > C:\Temp\whoami.txt"

รูปแบบนี้พบบ่อยมากในสคริปต์ขององค์กรและในเครื่องมือบริหารจัดการ และมันเป็นสาเหตุของรูปแบบการเกิดโปรแกรมที่ผู้ตรวจสอบต้องรู้จัก คือโปรแกรมหนึ่งถูกเรียกโดย cmd.exe ซึ่งถูกเรียกโดยโปรแกรมอื่นอีกที รูปแบบซ้อนเช่นนี้ไม่ใช่ความผิดปกติโดยตัวเอง แต่เป็นรูปแบบที่ควรอธิบายให้ได้ว่ามีเหตุผลอะไร

ในทางกลับกัน ผู้บุกรุกใช้ cmd.exe เป็นตัวกลางเพื่อหลบเลี่ยงการตรวจสอบที่เฝ้าดูโปรแกรมโดยตรง หรือเพื่อให้คำสั่งที่ยาวถูกตีความเป็นข้อความเดียว ผู้ตรวจสอบจึงควรระวังคำสั่งที่มีลักษณะหลายชั้นเกินความจำเป็น หรือคำสั่งที่ใช้ cmd.exe เพียงเพื่อรันคำสั่งเดียวสั้นๆ ซึ่งทำได้โดยไม่ต้องมีตัวกลาง

3.8 การเขียนสคริปต์อัตโนมัติ

เหตุใดงานตรวจสอบจึงต้องเขียนสคริปต์

การตรวจสอบเครื่องหนึ่งเครื่องด้วยมือใช้เวลาหลายนาที แต่การตรวจสอบเครื่องหนึ่งร้อยเครื่องด้วยมือเป็นงานที่เป็นไปไม่ได้ในทางปฏิบัติ ทั้งเพราะเวลาที่ใช้และเพราะความไม่สม่ำเสมอของผลลัพธ์ ผู้ตรวจสอบคนเดียวกันที่ทำงานตอนเช้ากับตอนบ่ายอาจลืมตรวจรายการหนึ่งหรือตีความผลต่างกัน สคริปต์แก้ปัญหาทั้งสองข้อพร้อมกัน คือทำให้งานเร็วขึ้นและทำให้ผลลัพธ์มีรูปแบบเดียวกันทุกครั้ง

คุณค่าที่แท้จริงของสคริปต์ไม่ได้อยู่ที่ความเร็ว แต่อยู่ที่ ความสามารถทำซ้ำได้ (Reproducibility) ผลลัพธ์ที่ได้จากสคริปต์สามารถถูกตรวจทานโดยคนอื่นได้ เปรียบเทียบระหว่างเครื่องได้ และรันซ้ำในภายหลังเพื่อยืนยันว่าสภาพของระบบเปลี่ยนไปหรือไม่ คุณสมบัติข้อนี้เองที่ทำให้สคริปต์มีคุณค่าในฐานะหลักฐาน ไม่ใช่เพียงในฐานะเครื่องมืออำนวยความสะดวก

โครงของสคริปต์ที่ใช้งานได้จริง

สคริปต์ที่ใช้งานในงานจริงมีโครงสี่ส่วนที่ควรมีครบทุกครั้ง ส่วนแรกคือการประกาศพารามิเตอร์ ส่วนที่สองคือการตั้งค่าพฤติกรรมเมื่อเกิดข้อผิดพลาด ส่วนที่สามคือการทำงานหลัก และส่วนที่สี่คือการส่งออกผลลัพธ์

param(
    [string]$OutputPath = "C:\Temp\service-audit.csv"
)

$ErrorActionPreference = 'Stop'

try {
    $results = Get-CimInstance Win32_Service |
        Select-Object Name, State, StartMode, StartName, PathName

    $results | Export-Csv -Path $OutputPath -NoTypeInformation -Encoding UTF8
    Write-Output "บันทึกผลลัพธ์แล้วที่ $OutputPath จำนวน $($results.Count) รายการ"
}
catch {
    Write-Error "ตรวจสอบบริการไม่สำเร็จ: $($_.Exception.Message)"
    exit 1
}

ส่วน param() ทำให้สคริปต์รับค่าได้แทนการแก้โค้ดภายในทุกครั้งที่ต้องการเปลี่ยนเส้นทางไฟล์ การมีค่าเริ่มต้นทำให้สคริปต์ยังใช้งานได้แม้ไม่ระบุค่าใด การทำเช่นนี้มีผลต่อการนำสคริปต์ไปใช้ซ้ำในสภาพแวดล้อมอื่น

การจัดการข้อผิดพลาด

พฤติกรรมเริ่มต้นของ PowerShell เมื่อเกิดข้อผิดพลาดคือ เขียนข้อความแล้วทำงานต่อ ซึ่งเป็นพฤติกรรมที่อันตรายในสคริปต์ตรวจสอบ เพราะสคริปต์อาจรายงานว่าทำงานสำเร็จทั้งที่บางขั้นตอนล้มเหลว ผลลัพธ์ที่ได้จึงไม่ครบแต่ไม่มีใครรู้

ตัวแปร $ErrorActionPreference ควบคุมพฤติกรรมนี้ การตั้งเป็น 'Stop' ทำให้ข้อผิดพลาดกลายเป็นการหยุดทำงานทันที ซึ่งทำให้ความล้มเหลวปรากฏชัดแทนที่จะถูกกลืนหายไป คำสั่งแต่ละตัวยังรับพารามิเตอร์ -ErrorAction เพื่อกำหนดพฤติกรรมเฉพาะจุดได้ ซึ่งมีประโยชน์เมื่อบางคำสั่งล้มเหลวได้ตามปกติและไม่ควรหยุดทั้งสคริปต์

โครง try และ catch ใช้ดักข้อผิดพลาดที่เกิดขึ้นและจัดการอย่างชัดเจน ในบล็อก catch ตัวแปร $_ แทนข้อผิดพลาดที่เกิดขึ้น และการอ่านข้อความจาก $_.Exception.Message ให้ข้อความที่อธิบายสาเหตุ

สิ่งที่ต้องระวังคือมีสองระบบข้อผิดพลาดที่ทำงานคู่กันใน PowerShell ระบบแรกคือข้อผิดพลาดของ PowerShell เอง ซึ่ง try และ catch จับได้ ระบบที่สองคือ รหัสออกของโปรแกรมภายนอก ซึ่งไม่ถือเป็นข้อผิดพลาดของ PowerShell และไม่ถูกจับด้วย try และ catch การตรวจรหัสออกทำได้ด้วยตัวแปร $LASTEXITCODE ซึ่งเก็บค่าที่โปรแกรมภายนอกส่งกลับมา ค่า 0 หมายถึงสำเร็จ และค่าอื่นหมายถึงมีปัญหา

    Write-Warning "อ่านสิทธิ์ไม่สำเร็จ รหัส $LASTEXITCODE"
}

การส่งออกผลลัพธ์

ผลลัพธ์ของงานตรวจสอบต้องถูกเก็บในรูปแบบที่เครื่องอื่นอ่านได้ ไม่ใช่เพียงแสดงบนหน้าจอ รูปแบบที่ใช้บ่อยมีสองแบบ คือไฟล์ค่าคั่นด้วยจุลภาคซึ่งเปิดได้ในโปรแกรมตารางคำนวณ และไฟล์ข้อมูลแบบมีโครงสร้างซึ่งเหมาะกับการนำไปประมวลผลต่อ

คำสั่ง Export-Csv เขียนออบเจกต์ออกเป็นไฟล์ที่แต่ละบรรทัดคือหนึ่งรายการและแต่ละคอลัมน์คือหนึ่งฟิลด์ ตัวเลือก -NoTypeInformation ตัดบรรทัดหัวเรื่องที่ PowerShell เพิ่มโดยอัตโนมัติออก ซึ่งทำให้ไฟล์สะอาดขึ้นสำหรับเครื่องมืออื่น ส่วน -Encoding UTF8 จำเป็นเมื่อข้อมูลมีอักษรไทย เพราะการเข้ารหัสแบบเก่าจะทำให้ข้อความเพี้ยน

คำสั่ง ConvertTo-Json แปลงออบเจกต์เป็นข้อความแบบมีโครงสร้าง ซึ่งเหมาะเมื่อผลลัพธ์มีข้อมูลซ้อนกันหลายชั้น เช่นรายการงานตามกำหนดเวลาที่แต่ละงานมีรายการการทำงานย่อยอยู่ข้างใน ข้อควรระวังคือโครงสร้างที่ซ้อนลึกอาจถูกตัดทิ้งหากไม่ระบุ -Depth ให้เพียงพอ

คำสั่ง Start-Transcript บันทึกทุกอย่างที่ปรากฏบนหน้าจอลงไฟล์ เหมาะกับงานที่ต้องแสดงว่าได้ทำอะไรไปบ้างตามลำดับ แต่ไม่ควรใช้แทนการส่งออกข้อมูล เพราะข้อความบนหน้าจอถูกตัดคอลัมน์และจัดรูปแบบซึ่งทำให้อ่านกลับด้วยเครื่องมืออื่นได้ยาก

ความต่างที่สำคัญที่สุดคือข้อแรก ทั้งสองระบบใช้สัญลักษณ์ท่อเหมือนกันแต่ความหมายต่างกันโดยสิ้นเชิง ผลที่ตามมาคือเทคนิคที่ใช้ได้ผลในระบบหนึ่งอาจใช้ไม่ได้ในอีกระบบหนึ่ง การคาดเดาว่าคำสั่งจะทำงานเหมือนกันเพราะชื่อคล้ายกันเป็นสาเหตุที่ทำให้สคริปต์ล้มเหลวบ่อยที่สุดเมื่อย้ายข้ามระบบ

หลักความปลอดภัยในการเขียนสคริปต์

สคริปต์ที่ผู้ตรวจสอบเขียนมีผลต่อระบบเป้าหมายจริง จึงต้องยึดหลักสี่ข้อตลอดเวลา

หลักข้อแรกคือ อ่านก่อนเขียน สคริปต์ควรเริ่มจากการอ่านและรายงานผลก่อนเสมอ การแก้ไขควรเป็นขั้นตอนที่แยกออกมาและต้องสั่งอย่างชัดเจน การรวมสองอย่างไว้ในสคริปต์เดียวทำให้ไม่สามารถรันส่วนอ่านโดยไม่มีความเสี่ยงได้

หลักข้อที่สองคือ บันทึกค่าก่อนแก้ไข เมื่อจำเป็นต้องเปลี่ยนค่าใด ค่าเดิมต้องถูกบันทึกไว้ในไฟล์หรือในหน้าจอก่อน และต้องมีวิธีคืนค่าที่ชัดเจน หากไม่มีวิธีคืนค่า การเปลี่ยนแปลงนั้นไม่ควรทำ

หลักข้อที่สามคือ จำกัดผลกระทบ สคริปต์ควรระบุขอบเขตให้ชัดว่าจะแตะเฉพาะเครื่องที่ระบุหรือโฟลเดอร์ที่ระบุ การเขียนสคริปต์ที่ไล่ทำงานกับทุกเครื่องในโดเมนโดยไม่มีตัวกรองเป็นสิ่งที่เสี่ยงเกินกว่าจะใช้ในงานจริง

หลักข้อที่สี่คือ ตรวจสอบก่อนรายงาน ผลลัพธ์ที่สคริปต์สร้างต้องถูกตรวจด้วยสายตาอย่างน้อยหนึ่งครั้งก่อนนำไปสรุป สคริปต์ที่ดึงข้อมูลผิดฟิลด์หรือกรองผิดเงื่อนไขจะให้ผลที่ดูน่าเชื่อถือแต่ผิด และความผิดพลาดแบบนี้ตรวจพบได้ยากกว่าความผิดพลาดที่ทำให้สคริปต์ล้มเหลว

✓ สรุปท้ายบท

บทนี้พาผู้เรียนอ่านเครื่องวินโดวส์ในฐานะหลักฐาน โดยเริ่มจากคำถามว่าทำไมระบบนี้จึงเป็นเป้าหมายหลักขององค์กร คำตอบไม่ได้อยู่ที่ความง่ายหรือความยากของระบบ แต่อยู่ที่ตำแหน่งของมันในองค์กร เครื่องปลายทางส่วนใหญ่เป็นเครื่องวินโดวส์ และเครื่องเหล่านั้นเก็บข้อมูลที่มีค่าที่สุดขององค์กรไว้

จากนั้นบทนี้วางพื้นฐานสามชั้นที่ต่อเนื่องกัน ชั้นแรกคือสถาปัตยกรรม ซึ่งอธิบายว่าวินโดวส์แบ่งการทำงานเป็นสองโหมด มีกระบวนการหลักชุดหนึ่งที่ทำหน้าที่ตายตัว และใช้ระบบวัตถุกับแฮนเดิลเป็นกลไกกลางในการเข้าถึงทุกสิ่ง การรู้ลำดับการเริ่มระบบช่วยให้เข้าใจว่ากลไกใดทำงานก่อนที่ผู้ใช้จะเห็นหน้าจอ

ชั้นที่สองคือรีจิสทรี ซึ่งเป็นฐานข้อมูลกลางที่เก็บค่าปรับแต่งแทบทั้งหมดของระบบ บทนี้อธิบายโครงสร้างสามระดับของคีย์ รายการย่อย และค่า ระบุฮีฟแต่ละอันพร้อมไฟล์บนดิสก์ และแจกแจงจุด Autostart ที่ผู้บุกรุกใช้คงอยู่ในระบบมากกว่าที่อื่น จุดสำคัญที่ควรจำคือตำแหน่งที่ผู้ใช้ทั่วไปเขียนได้ไม่ใช่เรื่องเล็ก เพราะมันเปิดทางให้โปรแกรมที่ทำงานด้วยสิทธิ์สูงโหลดโค้ดของผู้ใช้

ชั้นที่สามคือบริการและงานตามกำหนดเวลา ซึ่งเป็นกลไกที่ทำงานโดยไม่ต้องมีผู้ใช้ และเป็นเหตุผลว่าทำไมการคงอยู่ในรูปแบบนี้จึงตรวจพบได้ยากกว่าการคงอยู่ในรูปแบบโปรแกรมที่ผู้ใช้ต้องเปิดเอง บทนี้เน้นว่าค่าที่ต้องอ่านทุกครั้งคือเส้นทางของโปรแกรม บัญชีที่ใช้รัน และนโยบายการเริ่มทำงาน

ส่วนที่อธิบายกลไกสิทธิ์คือหัวข้อ UAC โทเคน และระดับความสมบูรณ์ ซึ่งเป็นหัวข้อที่ผู้เริ่มต้นเข้าใจผิดมากที่สุด ประเด็นที่ต้องจำให้แม่นคือสิทธิ์ของบัญชีกับสิทธิ์ของกระบวนการเป็นสองเรื่องที่ต่างกัน ระบบตัดสินจากโทเคน ไม่ใช่จากชื่อบัญชี และระดับความสมบูรณ์คือเพดานที่กำหนดว่ากระบวนการหนึ่งเขียนทับอะไรได้บ้าง

ครึ่งหลังของบทเปลี่ยนจาก "ระบบทำอะไร" ไปเป็น "เราถามระบบได้อย่างไร" PowerShell ถูกอธิบายในฐานะเชลล์ที่ส่งต่อออบเจกต์ ไม่ใช่ข้อความ ซึ่งทำให้การกรองและการส่งออกข้อมูลแม่นยำกว่าวิธีแบบเดิม บทนี้เน้นคำสั่งไม่กี่ตัวที่ใช้บ่อยและอธิบายหลักการที่อยู่เบื้องหลัง มากกว่าการท่องจำรายการคำสั่งทั้งหมด

CMD และ wmic ถูกกล่าวถึงในฐานะเครื่องมือที่ยังมีอยู่จริงในองค์กรและยังใช้ได้ในสภาพที่ PowerShell ถูกจำกัด พร้อมกับชี้ว่าทั้งสองเครื่องมือกำลังถูกแทนที่ และผู้ตรวจสอบต้องเตรียมคำสั่งทดแทนไว้

ส่วนสุดท้ายคือการเขียนสคริปต์ ซึ่งบทนี้เน้นว่าคุณค่าของสคริปต์อยู่ที่ความสามารถทำซ้ำได้ ไม่ใช่ความเร็ว และเน้นหลักสี่ข้อที่ต้องยึดคืออ่านก่อนเขียน บันทึกค่าก่อนแก้ไข จำกัดผลกระทบ และตรวจสอบก่อนรายงาน

สิ่งที่ควรจำให้แม่นจากบทนี้ไม่ใช่รายละเอียดของทุกคีย์หรือทุกคำสั่ง แต่เป็นวิธีคิดสามข้อ ข้อแรกคือทุกอย่างที่ระบบทำถูกบันทึกไว้ที่ใดที่หนึ่งเสมอ ทั้งในรีจิสทรี ในบันทึกเหตุการณ์ และในไฟล์ระบบ ข้อที่สองคือสิทธิ์ที่แท้จริงของกระบวนการอ่านได้จากโทเคนของมัน ไม่ใช่จากชื่อบัญชี ข้อที่สามคือเครื่องมือที่ดีที่สุดในงานตรวจสอบคือเครื่องมือที่มีอยู่ในระบบแล้ว เพราะมันไม่ต้องติดตั้งเพิ่มและไม่ทำให้ระบบเปลี่ยนสภาพ

ข้อ 3เพราะเหตุใด HKLM\HARDWARE จึงไม่มีประโยชน์สำหรับการตรวจสอบย้อนหลัง และข้อจำกัดนี้บอกอะไรเกี่ยวกับการวางแผนเก็บหลักฐาน
ข้อ 4จงเปรียบเทียบจุด Autostart สองตำแหน่งที่มีระดับสิทธิ์ต่างกัน และอธิบายว่าความต่างนี้เปลี่ยนความรุนแรงของเหตุการณ์อย่างไร
ข้อ 5เหตุใดการพบว่าบัญชีหนึ่งเป็นสมาชิกกลุ่มผู้ดูแลระบบจึงยังไม่เพียงพอต่อการสรุปว่าผู้ใช้มีสิทธิ์สูงสุดในขณะนั้น
ข้อ 6จงอธิบายหลักการของนโยบายห้ามเขียนขึ้น และยกตัวอย่างทั้งกรณีที่มันป้องกันได้และกรณีที่มันป้องกันไม่ได้
ข้อ 7เพราะเหตุใดผู้ผลิตระบบจึงระบุว่า UAC ไม่ใช่ขอบเขตความปลอดภัย และข้อเท็จจริงนี้ควรเปลี่ยนวิธีประเมินความเสี่ยงขององค์กรอย่างไร
ข้อ 8จงอธิบายว่าการบันทึกบล็อกสคริปต์ให้ข้อมูลอะไรที่การบันทึกแบบอื่นให้ไม่ได้ และเหตุใดจึงสำคัญต่องานตรวจสอบ

Aa คำศัพท์สำคัญ

คำศัพท์คำอธิบาย
รีจิสทรี (Registry)ฐานข้อมูลแบบลำดับชั้นที่เก็บค่าปรับแต่งของระบบและโปรแกรม
ฮีฟ (Hive)ไฟล์ที่เก็บข้อมูลรีจิสทรีส่วนหนึ่ง ซึ่งถูกโหลดเข้าใช้เมื่อระบบเริ่มทำงาน
คีย์ (Key)องค์ประกอบของรีจิสทรีที่ทำหน้าที่เหมือนโฟลเดอร์
ค่า (Value)ข้อมูลจริงที่เก็บอยู่ในคีย์หนึ่ง พร้อมชื่อและชนิดข้อมูล
จุด Autostartตำแหน่งใดๆ ที่ทำให้โปรแกรมทำงานเองโดยไม่ต้องมีผู้ใช้สั่ง
ตัวจัดการบริการ (Service Control Manager)กระบวนการที่ดูแลการเริ่ม หยุด และสอบถามสถานะของบริการทั้งหมด
งานตามกำหนดเวลา (Scheduled Task)กลไกที่รันคำสั่งเมื่อถึงเงื่อนไขที่กำหนด เช่น เวลาหรือเหตุการณ์
โทเคนการเข้าถึง (Access Token)โครงสร้างข้อมูลที่ระบุตัวตนและสิทธิ์ของกระบวนการ
โทเคนแสดงตน (Impersonation Token)โทเคนชั่วคราวที่ผูกกับเธรดเพื่อทำงานในนามของผู้อื่น
ระดับความสมบูรณ์ (Integrity Level)ป้ายที่กำหนดเพดานการเขียนทับวัตถุของโทเคน
การแยกโทเคน (Token Splitting)การสร้างโทเคนสองชุดสำหรับผู้ใช้ที่เป็นสมาชิกกลุ่มผู้ดูแลระบบ
การควบคุมบัญชีผู้ใช้ (UAC)กลไกที่ให้ผู้ใช้ทำงานด้วยสิทธิ์ปานกลางและยกระดับเมื่อจำเป็น
ผู้ให้บริการข้อมูล (Provider)กลไกที่ทำให้แหล่งข้อมูลต่างชนิดเข้าถึงได้ด้วยคำสั่งชุดเดียวกัน
cmdletคำสั่งใน PowerShell ที่ตั้งชื่อตามรูปแบบกริยา-นาม
นโยบายการเรียกใช้ (Execution Policy)ค่าที่กำหนดว่า PowerShell จะยอมรันไฟล์สคริปต์หรือไม่
การบันทึกบล็อกสคริปต์ (Script Block Logging)กลไกที่บันทึกโค้ดที่ถูกประมวลผลลงในบันทึกเหตุการณ์
สตรีมข้อมูลทางเลือก (Alternate Data Stream)คุณสมบัติของ NTFS ที่เก็บข้อมูลหลายสตรีมในไฟล์เดียว
ตัวระบุความปลอดภัย (SID)ตัวเลขที่ระบบใช้ระบุบัญชีและกลุ่มแทนการใช้ชื่อ
RIDหมายเลขท้ายของ SID ที่ระบุบัญชีภายในเครื่องหรือโดเมน
การจี้การเชื่อมโยงคลาสออบเจกต์ (COM Hijacking)การใช้ลำดับความสำคัญของฮีฟของผู้ใช้เพื่อให้โปรแกรมโหลดไลบรารีของผู้บุกรุก
