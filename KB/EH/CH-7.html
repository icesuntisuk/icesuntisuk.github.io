บทที่ 6 ปิดท้ายด้วยคำถามว่าข้อมูลจากผู้ใช้ไหลไปสิ้นสุดที่ใด ในระบบสารสนเทศส่วนใหญ่ ปลายทางของข้อมูลคือฐานข้อมูล ระบบทะเบียน ระบบสั่งซื้อ ระบบสมาชิก และระบบเนื้อหา ล้วนเก็บข้อมูลไว้ในฐานข้อมูลแทบทั้งสิ้น และเพื่อให้ผู้ใช้ค้นหาและแก้ไขข้อมูลได้ ฐานข้อมูลจึงถูกเรียกใช้จากหน้าเว็บอยู่ตลอดเวลา

ช่องโหว่ของฐานข้อมูลจึงเป็นช่องโหว่ที่มีผลกระทบกว้างที่สุดในบรรดาช่องโหว่ของเว็บ เพราะข้อมูลที่ได้คือข้อมูลทั้งหมดที่บัญชีนั้นเข้าถึงได้ ไม่ใช่เพียงข้อมูลหนึ่งหน้าหรือหนึ่งไฟล์ ช่องโหว่นี้อาจเปิดเผยรายชื่อผู้ใช้ รหัสผ่านที่เข้ารหัสแล้ว ข้อมูลลูกค้า ข้อมูลทางการเงิน และข้อมูลที่กฎหมายกำหนดให้ต้องป้องกัน

ลำดับของบทเริ่มจากภาษาที่ฐานข้อมูลพูดกับแอปพลิเคชัน แล้วจึงแสดงวิธีทดสอบด้วยมือทีละขั้น การทดสอบด้วยมือสำคัญเพราะมันทำให้เห็นว่าแต่ละคำตอบบอกอะไร และเมื่อเข้าใจกลไกแล้ว การใช้เครื่องมืออัตโนมัติจึงเป็นการทำงานซ้ำให้เร็วขึ้น ไม่ใช่การกดปุ่มโดยไม่รู้ว่าเกิดอะไรขึ้น

ผู้บรรยายควรย้ำตลอดบทว่าการทดสอบต้องทำในระบบที่ได้รับอนุญาต คำสั่งที่ใช้ในการทดสอบมีผลต่อข้อมูลจริง คำสั่งที่ผิดพลาดเพียงตัวเดียวสามารถทำให้ข้อมูลเสียหายหรือทำให้ระบบหยุดให้บริการได้ และการดึงข้อมูลออกมาทั้งฐานเป็นสิ่งที่ต้องได้รับอนุญาตชัดเจนก่อนทุกครั้ง

7.1 กลไกการเกิด SQL Injection

ภาษาของฐานข้อมูล

ฐานข้อมูลเชิงสัมพันธ์เก็บข้อมูลในตาราง แต่ละตารางมีคอลัมน์และแถว แอปพลิเคชันเข้าถึงข้อมูลด้วยภาษาที่ชื่อว่า SQL ซึ่งเป็นภาษาแบบประกาศ คือผู้เขียนบอกว่าต้องการอะไร แล้วระบบจะหาวิธีทำให้เอง คำสั่งที่ใช้บ่อยมีสี่กลุ่ม ได้แก่ SELECT สำหรับอ่าน INSERT สำหรับเพิ่ม UPDATE สำหรับแก้ไข และ DELETE สำหรับลบ

คำสั่ง SELECT มีโครงสร้างที่ต้องจำให้ขึ้นใจ เพราะทุกเทคนิคในบทนี้สร้างมาจากส่วนประกอบของมัน

SELECT username, email FROM users WHERE id = 1 AND active = 1;

คำสั่งนี้ประกอบด้วยส่วนที่บอกว่าอ่านคอลัมน์ใด (username, email) จากตารางใด (users) ภายใต้เงื่อนไขใด (id = 1 AND active = 1) เงื่อนไขหลัง WHERE คือส่วนที่กำหนดว่าแถวใดจะถูกเลือก และเป็นส่วนที่ผู้โจมตีใช้เปลี่ยนแปลงตรรกะของคำสั่ง

อีกส่วนที่สำคัญคือเครื่องหมายคำพูด ข้อความใน SQL เขียนอยู่ในเครื่องหมายคำพูดเดี่ยว เช่น 'alice' ซึ่งหมายความว่าเมื่อใดก็ตามที่แอปพลิเคชันนำข้อความจากผู้ใช้ไปต่อในคำสั่งโดยไม่แยกให้ชัด ข้อความนั้นจะกลายเป็นส่วนหนึ่งของคำสั่งทันที

การต่อสายอักขระคือต้นเหตุ

แอปพลิเคชันจำนวนมากสร้างคำสั่ง SQL ด้วยการนำค่าจากผู้ใช้ไปต่อกับข้อความคงที่ ถ้าผู้ใช้กรอกสิ่งที่คาดหวัง คำสั่งที่ได้ก็ถูกต้อง แต่ถ้าผู้ใช้กรอกอักขระที่มีความหมายพิเศษในภาษา SQL โครงสร้างของคำสั่งจะเปลี่ยน

<?php
$id = $_GET['id'];
$sql = "SELECT name, price FROM products WHERE id = " . $id;
$result = mysqli_query($conn, $sql);
?>

โค้ดข้างต้นตั้งใจให้ผู้ใช้ส่งหมายเลขสินค้า แล้วระบบสร้างคำสั่งเพื่ออ่านข้อมูลสินค้านั้น ผู้ใช้ทั่วไปส่งค่า 15 แล้วได้คำสั่งที่ถูกต้อง แต่ผู้ใช้ที่ส่งค่า 15 OR 1=1 จะได้คำสั่งที่อ่านสินค้าทั้งตาราง

แถวที่สี่คือตัวอย่างการข้ามการยืนยันตัวตนที่รู้จักกันดี เมื่อผู้ใช้ส่งข้อความที่ปิดเครื่องหมายคำพูดเดิม แล้วเพิ่มเงื่อนไขที่เป็นจริงเสมอ เงื่อนไขรหัสผ่านที่ตามมาจะถูกตัดออกด้วยเครื่องหมายความคิดเห็น ผลลัพธ์คือระบบตรวจพบผู้ใช้หนึ่งคนและถือว่าการยืนยันตัวตนผ่าน

สิ่งที่ต้องเข้าใจคือช่องโหว่นี้ไม่ได้เกิดจากภาษา SQL แต่เกิดจาก การที่แอปพลิเคชันไม่แยกข้อมูลออกจากคำสั่ง ตัวภาษาไม่ได้ผิด และตัวฐานข้อมูลก็ไม่ได้ผิด ผู้พัฒนาต่างหากที่สร้างคำสั่งด้วยการต่อข้อความซึ่งเป็นวิธีที่ไม่มีทางแยกสองส่วนนั้นได้อย่างปลอดภัย

ทำไมการกรองอักขระจึงไม่ใช่คำตอบ

คำตอบแรกที่ผู้พัฒนามักคิดถึงคือการลบเครื่องหมายคำพูดหรือคำสงวนออกจากค่าที่รับมา วิธีนี้ให้ความรู้สึกว่าปลอดภัย แต่ในทางปฏิบัติมีปัญหาสองข้อ

ข้อแรกคือการกรองที่เข้มงวดเกินไปจะทำให้ผู้ใช้กรอกข้อมูลจริงไม่ได้ เช่น ชื่อที่มีเครื่องหมายคำพูดหรือข้อความที่มีคำว่า select ปรากฏอยู่ ข้อที่สองคือการกรองที่หละหลวมเกินไปจะถูกหลบได้ด้วยการเข้ารหัส การใช้ตัวพิมพ์สลับ หรือไวยากรณ์ทางเลือกของฐานข้อมูล

วิธีที่ถูกต้องคือการแยกคำสั่งออกจากข้อมูลตั้งแต่ต้น ด้วยการกำหนดคำสั่งไว้ล่วงหน้าแล้วส่งค่าเข้าไปเป็นพารามิเตอร์ต่างหาก ฐานข้อมูลจะรู้ว่าส่วนใดคือคำสั่งและส่วนใดคือค่า จึงไม่มีทางที่ค่าจะกลายเป็นคำสั่งได้ หลักการนี้จะกล่าวถึงในหัวข้อ 7.7

จุดรับข้อมูลที่ต้องตรวจ

ช่องโหว่นี้เกิดได้ทุกที่ที่ค่าจากผู้ใช้ไปถึงคำสั่ง SQL ซึ่งมากกว่าที่ผู้เริ่มต้นคาดคิด จุดที่พบบ่อยได้แก่

  • พารามิเตอร์ในที่อยู่ เช่น product.php?id=15
  • ตัวข้อมูลในคำขอแบบ POST เช่น ช่องค้นหา ช่องกรอกฟอร์ม
  • คุกกี้ที่แอปพลิเคชันนำไปใช้ในคำสั่ง เช่น ค่า sort หรือ lang
  • หัวข้อของคำขอที่แอปพลิเคชันบันทึกหรือนำไปใช้ เช่น User-Agent ในระบบสถิติ
  • ชื่อคอลัมน์หรือชื่อตารางที่แอปพลิเคชันรับมาจากผู้ใช้เพื่อใช้เรียงลำดับ

จุดสุดท้ายเป็นกรณีที่ผู้ทดสอบมักมองข้าม เพราะการเรียงลำดับและแบ่งหน้าในตารางมักไม่ยอมให้ส่งค่าเป็นพารามิเตอร์โดยตรง จึงต้องสร้างชื่อคอลัมน์จากค่าที่รับมา ซึ่งเปิดทางให้ผู้ใช้กำหนดคำสั่ง SQL ได้

สิ่งที่ช่องโหว่นี้ให้ได้

ผลลัพธ์ของช่องโหว่นี้ขึ้นกับสิทธิ์ของบัญชีฐานข้อมูลที่แอปพลิเคชันใช้ หากบัญชีนั้นมีสิทธิ์อ่านเพียงตารางเดียว ผู้โจมตีก็อ่านได้เพียงตารางนั้น แต่หากบัญชีเป็นบัญชีผู้ดูแลซึ่งผู้พัฒนากรอกไว้เพื่อความสะดวก ผู้โจมตีก็อ่านได้ทั้งฐานข้อมูล

ระดับของผลลัพธ์ที่ควรประเมินมีห้าระดับ ระดับแรกคือการอ่านข้อมูลในตารางที่แอปพลิเคชันใช้อยู่ ระดับที่สองคือการอ่านข้อมูลจากตารางอื่นในฐานข้อมูลเดียวกัน ซึ่งทำได้ผ่านตารางข้อมูลเมตา ระดับที่สามคือการเพิ่ม แก้ไข หรือลบข้อมูล ซึ่งขึ้นกับว่าไดรเวอร์ยอมรับหลายคำสั่งหรือไม่ ระดับที่สี่คือการอ่านหรือเขียนไฟล์บนเซิร์ฟเวอร์ ซึ่งขึ้นกับสิทธิ์ของบัญชีและค่าตั้งของฐานข้อมูล และระดับที่ห้าคือการสั่งให้ระบบปฏิบัติการทำงาน ซึ่งพบได้น้อยกว่าแต่มีผลกระทบสูงที่สุด

การประเมินว่าช่องโหว่หนึ่งอยู่ระดับใดต้องอาศัยการทดสอบที่ระมัดระวัง เพราะการทดสอบเพื่อไประดับที่สามขึ้นไปมีความเสี่ยงต่อระบบสูงกว่าการอ่านข้อมูลมาก

ขอบเขตและข้อควรระวังตั้งแต่ต้นบท

การทดสอบในบทนี้แตกต่างจากบทที่ 6 ตรงที่คำสั่งที่ส่งไปมีผลต่อข้อมูลโดยตรง คำสั่ง ' OR 1=1-- ในฟอร์มเข้าสู่ระบบไม่มีผลข้างเคียง แต่คำสั่ง '; DROP TABLE users-- มีผลข้างเคียงร้ายแรง และการทดสอบที่ขาดความระมัดระวังอาจทำให้ข้อมูลจริงเสียหายได้

ผู้ทดสอบจึงต้องยึดหลักสามข้อ ข้อแรกคือทดสอบเฉพาะระบบที่ได้รับอนุญาตเป็นลายลักษณ์อักษร ข้อที่สองคือเลือกใช้ค่าที่ไม่เปลี่ยนแปลงข้อมูลเป็นลำดับแรก และข้อที่สามคือบันทึกทุกคำขอที่ส่งไปเพื่อให้ตรวจสอบย้อนกลับได้

การทดสอบบนระบบที่ให้บริการจริงควรทำในช่วงเวลาที่ตกลงไว้และควรมีผู้ดูแลระบบรับรู้ เพราะคำสั่งที่มี SLEEP หรือคำสั่งที่ดึงข้อมูลจำนวนมากอาจทำให้ระบบช้าลงหรือหยุดตอบสนองชั่วคราว

7.2 การทดสอบด้วยมือขั้นพื้นฐาน

เตรียมคำขอให้พร้อมก่อนลงมือ

การทดสอบด้วยมือเริ่มจากการมีคำขอที่ทำซ้ำได้ คำขอที่ดีคือคำขอที่บันทึกไว้ใน Burp Suite หรือบันทึกเป็นไฟล์ข้อความ เพราะทุกขั้นตอนต่อไปจะเป็นการแก้ค่าเดิมแล้วส่งซ้ำ การพิมพ์คำขอใหม่ทุกครั้งจะทำให้เกิดความผิดพลาดที่หาไม่พบ

การเตรียมการมีสองส่วน ส่วนแรกคือเลือกจุดรับข้อมูลหนึ่งจุด แล้วส่งค่าปกติไปหนึ่งครั้ง บันทึกรหัสสถานะ ขนาดคำตอบ และเนื้อหาสำคัญไว้เป็นฐานอ้างอิง การมีฐานอ้างอิงทำให้แยกได้ว่าความเปลี่ยนแปลงที่เห็นเกิดจากค่าที่ใส่เข้าไป ไม่ใช่จากความแปรปรวนปกติของระบบ

ส่วนที่สองคือตรวจว่าคำตอบเปลี่ยนไปในทางที่บ่งชี้ว่าค่าถูกนำไปใช้ในคำสั่ง SQL หรือไม่ ตัวอย่างเช่น หากส่งค่าที่เป็นตัวเลขแล้วระบบตอบข้อมูลสินค้าหมายเลขนั้น แต่ส่งค่าที่เป็นข้อความแล้วระบบตอบข้อผิดพลาด แสดงว่าค่านั้นน่าจะถูกใช้ในบริบทที่คาดหวังตัวเลข

ขั้นที่หนึ่ง การตรวจหาความผิดปกติ

วิธีที่ตรงที่สุดคือการใส่อักขระที่มีความหมายพิเศษในภาษา SQL แล้วดูว่าคำตอบเปลี่ยนหรือไม่ อักขระที่ใช้บ่อยที่สุดคือเครื่องหมายคำพูดเดี่ยว เพราะมันปิดสายอักขระในคำสั่งและทำให้โครงสร้างคำสั่งเสีย

?id=15'

หากระบบตอบข้อความผิดพลาดของฐานข้อมูล แสดงว่าคำขอนี้ไปถึงฐานข้อมูลจริงและอักขระที่ใส่ไปมีผลต่อคำสั่ง ข้อความผิดพลาดที่พบบ่อยมีลักษณะดังนี้

You have an error in your SQL syntax; check the manual that corresponds to
your MySQL server version for the right syntax to use near ''15''' at line 1

ข้อความข้างต้นบอกฐานข้อมูลและตำแหน่งที่คำสั่งเสีย ซึ่งเป็นข้อมูลที่มีค่ามาก ทั้งยังยืนยันว่าช่องทางนี้เปิดอยู่

แต่การไม่เห็นข้อความผิดพลาดไม่ได้หมายความว่าไม่มีช่องโหว่ เพราะระบบจำนวนมากปิดการแสดงข้อผิดพลาดและตอบหน้าเดิมทุกกรณี ในกรณีเช่นนี้ต้องใช้วิธีที่อาศัยความแตกต่างเล็กๆ ของคำตอบแทน ซึ่งจะกล่าวถึงในหัวข้อ 7.3

ขั้นที่สอง การยืนยันด้วยเงื่อนไขจริงและเท็จ

เมื่อสงสัยว่าจุดนั้นมีช่องโหว่ วิธีที่เชื่อถือได้กว่าการดูข้อความผิดพลาดคือการส่งเงื่อนไขที่ตั้งใจให้เป็นจริงและเงื่อนไขที่ตั้งใจให้เป็นเท็จ แล้วเปรียบเทียบคำตอบ

?id=15 AND 1=1
?id=15 AND 1=2

คำขอแรกควรให้คำตอบเหมือนปกติ เพราะเงื่อนไข 1=1 เป็นจริง คำขอที่สองควรให้คำตอบที่ต่างออกไปหรือว่างเปล่า เพราะเงื่อนไข 1=2 เป็นเท็จ หากความแตกต่างนี้เกิดขึ้นสม่ำเสมอเมื่อส่งซ้ำ แสดงว่าค่าที่ใส่เข้าไปถูกตีความในฐานะส่วนหนึ่งของคำสั่ง SQL

การทดสอบแบบนี้มีข้อดีคือไม่ต้องพึ่งข้อความผิดพลาด และเห็นผลได้แม้ระบบจะตอบหน้าเดิมทุกกรณี แต่ต้องทำซ้ำอย่างน้อยสองสามครั้งเพื่อยืนยันว่าความแตกต่างเกิดจากเงื่อนไข ไม่ใช่จากความแปรปรวนของระบบ

ขั้นที่สาม การหาจำนวนคอลัมน์

เทคนิค UNION ต้องรู้จำนวนคอลัมน์ของคำสั่งเดิมก่อน เพราะคำสั่ง UNION กำหนดให้ทั้งสองฝั่งมีจำนวนคอลัมน์เท่ากัน วิธีที่ใช้บ่อยมีสองวิธี

วิธีแรกคือการใช้ ORDER BY ซึ่งเรียงผลลัพธ์ตามคอลัมน์ที่ระบุ หากหมายเลขคอลัมน์เกินจำนวนจริง ฐานข้อมูลจะตอบข้อผิดพลาด

?id=15 ORDER BY 1-- -
?id=15 ORDER BY 2-- -
?id=15 ORDER BY 3-- -
?id=15 ORDER BY 4-- -

ในตัวอย่างนี้ หากคำสั่งแรกถึงคำสั่งที่สามทำงานปกติ แต่คำสั่งที่สี่เกิดข้อผิดพลาด แสดงว่าคำสั่งเดิมมีสามคอลัมน์

วิธีที่สองคือการเติมค่า NULL ต่อท้ายด้วย UNION SELECT แล้วเพิ่มจำนวนไปเรื่อยๆ จนคำตอบกลับมาปกติ

?id=15 UNION SELECT NULL-- -
?id=15 UNION SELECT NULL,NULL-- -
?id=15 UNION SELECT NULL,NULL,NULL-- -

วิธีนี้ใช้ได้แม้ระบบจะไม่แสดงข้อความผิดพลาด เพราะจำนวนที่ถูกต้องจะทำให้คำตอบกลับมาเป็นปกติ ส่วนจำนวนที่ผิดจะทำให้คำตอบผิดปกติหรือว่างเปล่า

เครื่องหมายความคิดเห็นและไวยากรณ์ที่ต่างกัน

การตัดส่วนที่เหลือของคำสั่งเดิมออกเป็นขั้นตอนสำคัญ เพราะคำสั่งเดิมมักมีส่วนต่อท้ายที่ทำให้คำสั่งที่เราใส่เข้าไปเสียรูป เครื่องหมายที่ใช้ตัดแตกต่างกันตามฐานข้อมูล

ขั้นที่สี่ การหาคอลัมน์ที่แสดงผล

เมื่อรู้จำนวนคอลัมน์แล้ว ขั้นถัดไปคือดูว่าคอลัมน์ใดปรากฏบนหน้าเว็บ เพราะข้อมูลที่ดึงมาจะต้องถูกวางในคอลัมน์ที่แสดงผล วิธีที่ตรงที่สุดคือการใส่ค่าที่แตกต่างกันในแต่ละตำแหน่ง

?id=15 UNION SELECT 1,2,3-- -

หากหน้าเว็บแสดงตัวเลข 2 และ 3 ในตำแหน่งที่คาดไม่ถึง แสดงว่าคอลัมน์ที่สองและสามถูกนำไปแสดงผล ผู้ทดสอบจึงใช้สองตำแหน่งนี้ในการดึงข้อมูลจริง

ในทางปฏิบัติ ค่าที่ใส่ไม่จำเป็นต้องเป็นตัวเลข การใส่สายอักขระที่ไม่มีในระบบ เช่น 0x414243 หรือ 'ax' ช่วยให้เห็นตำแหน่งได้ชัดขึ้น เพราะตัวเลขอาจซ้ำกับข้อมูลที่มีอยู่แล้ว

ขั้นที่ห้า การอ่านข้อมูลเมตา

เมื่อรู้ตำแหน่งที่แสดงผลแล้ว ผู้ทดสอบสามารถดึงข้อมูลเกี่ยวกับฐานข้อมูลเองได้ ฐานข้อมูล MySQL และ MariaDB เก็บข้อมูลเมตาไว้ในฐานข้อมูลชื่อ information_schema ซึ่งมีตารางที่บอกชื่อฐานข้อมูล ชื่อตาราง และชื่อคอลัมน์ทั้งหมด

?id=15 UNION SELECT 1,table_name,3 FROM information_schema.tables
WHERE table_schema=database()-- -

คำสั่งข้างต้นดึงรายชื่อตารางในฐานข้อมูลปัจจุบัน การรู้รายชื่อตารางทำให้เห็นว่าข้อมูลสำคัญอยู่ที่ใด และการดึงรายชื่อคอลัมน์ของตารางนั้นจะบอกว่าควรอ่านคอลัมน์ใด

?id=15 UNION SELECT 1,column_name,3 FROM information_schema.columns
WHERE table_name='users'-- -

ขั้นตอนนี้มีค่ามากเพราะช่วยให้ผู้ทดสอบไม่ต้องเดาชื่อตารางหรือชื่อคอลัมน์ ซึ่งเป็นการเดาที่เสียเวลาและสร้างคำขอจำนวนมากบนระบบเป้าหมาย

ขั้นที่หก การดึงข้อมูลจริง

เมื่อรู้ชื่อตารางและชื่อคอลัมน์แล้ว การดึงข้อมูลเป็นการนำชื่อเหล่านั้นไปใส่ในคำสั่ง UNION

?id=15 UNION SELECT 1,username,password FROM users-- -

ผลลัพธ์คือรายชื่อผู้ใช้และรหัสผ่านที่เข้ารหัสแล้ว ซึ่งเป็นข้อมูลที่ต้องจัดการอย่างระมัดระวังที่สุดในงานทดสอบ เพราะมันเป็นข้อมูลของบุคคลจริงและอาจครอบคลุมด้วยกฎหมายคุ้มครองข้อมูลส่วนบุคคล

ในรายงานผลการทดสอบ ไม่จำเป็นต้องแสดงข้อมูลจริงทั้งหมด การแสดงเพียงสองสามระเบียนแรกพร้อมการปิดบางส่วนของข้อมูลก็เพียงพอต่อการพิสูจน์ว่าช่องโหว่มีอยู่จริง และลดความเสี่ยงจากการรั่วไหลของรายงานเอง

การบันทึกผลระหว่างทาง

ทุกขั้นตอนควรถูกบันทึกพร้อมคำขอเต็มและคำตอบย่อ เพราะการทดสอบ SQL Injection มีหลายขั้นที่ต้องย้อนกลับมาเมื่อผลไม่เป็นไปตามคาด หากไม่บันทึกไว้จะต้องเริ่มใหม่ตั้งแต่ต้น

บันทึกที่ดีควรมีหมายเลขกำกับแต่ละความพยายาม และระบุว่าความพยายามนั้นให้ผลอย่างไร เช่น "เพิ่มจำนวนคอลัมน์เป็น 4 แล้วได้ข้อผิดพลาด แสดงว่าคำสั่งเดิมมี 3 คอลัมน์" การเขียนเช่นนี้ทำให้ผู้อ่านรายงานเข้าใจเส้นทางการวิเคราะห์ ไม่ใช่เพียงเห็นผลลัพธ์สุดท้าย

ข้อควรระวังอีกข้อคือการบันทึกข้อมูลที่ได้จากการดึง ควรเก็บไว้ในที่ที่เข้าถึงได้จำกัด และลบเมื่อสิ้นสุดงานตามข้อตกลงกับผู้ว่าจ้าง การเก็บสำเนาข้อมูลลูกค้าไว้ในเครื่องส่วนตัวหลังจบงานเป็นความเสี่ยงที่ไม่จำเป็นและอาจผิดข้อตกลงการรักษาความลับ

7.3 ชนิดของ SQL Injection และสัญญาณที่สังเกตได้

การแบ่งชนิดตามช่องทางที่ใช้ส่งข้อมูลกลับ

เทคนิค SQL Injection ทั้งหมดมีเป้าหมายเดียวกัน คือทำให้ผู้ทดสอบเห็นข้อมูลที่ไม่มีสิทธิ์เห็น ความแตกต่างอยู่ที่ช่องทางที่ใช้ส่งข้อมูลกลับมา บางระบบส่งข้อความผิดพลาดกลับมาจนอ่านโครงสร้างได้ บางระบบแสดงผลลัพธ์บนหน้าเว็บ บางระบบไม่แสดงอะไรเลยจนต้องอนุมานทีละบิต

การรู้ว่าตัวเองกำลังอยู่ในสถานการณ์ใดจึงเป็นก้าวแรกของการเลือกเทคนิค และการเลือกผิดจะทำให้เสียเวลาไปกับคำขอจำนวนมากโดยไม่จำเป็น

ตาราง 7.4 ชนิดของ SQL Injection และเงื่อนไขที่ต้องมี
ชนิดหลักการเงื่อนไขที่ต้องมีจำนวนคำขอ
Error-basedใช้ข้อความผิดพลาดเป็นช่องทางส่งข้อมูลระบบแสดงข้อผิดพลาดของฐานข้อมูลน้อย
UNION-basedต่อผลลัพธ์ของคำสั่งใหม่เข้ากับคำสั่งเดิมรู้จำนวนคอลัมน์และมีคอลัมน์ที่แสดงผลน้อย
Boolean-basedถามคำถามใช่หรือไม่ แล้วดูความต่างของหน้าหน้าเว็บตอบต่างกันเมื่อเงื่อนไขจริงและเท็จมาก
Time-basedถามคำถามใช่หรือไม่ แล้วดูเวลาตอบสนองคำสั่งหน่วงเวลาทำงานได้มาก
Stacked queriesต่อคำสั่งที่สองด้วยเครื่องหมายอัฒภาคไดรเวอร์ฐานข้อมูลยอมรับหลายคำสั่งน้อย
Out-of-bandส่งข้อมูลออกทางเครือข่ายฐานข้อมูลส่งคำขอออกภายนอกได้น้อย

Error-based

เทคนิคนี้ใช้ข้อความผิดพลาดของฐานข้อมูลเป็นช่องทางส่งข้อมูล หลักการคือการสร้างคำสั่งที่ตั้งใจให้ผิดพลาด และให้ข้อความผิดพลาดนั้นมีข้อมูลที่ต้องการฝังอยู่ ตัวอย่างใน MySQL คือฟังก์ชันที่ใช้แปลงข้อมูลเป็นรูปแบบที่ผิด ซึ่งจะทำให้เกิดข้อความผิดพลาดที่มีค่าของข้อมูลปนออกมา

ข้อดีคือได้ข้อมูลจำนวนมากในคำขอเดี่ยว และอ่านผลได้ตรงไปตรงมา ข้อจำกัดคือใช้ได้เฉพาะระบบที่แสดงข้อผิดพลาด และมักถูกปิดในระบบที่ตั้งค่าเพื่อการใช้งานจริง

ข้อควรระวังคือข้อความผิดพลาดอาจถูกบันทึกไว้ในไฟล์บันทึกของระบบ ซึ่งหมายความว่าข้อมูลที่ดึงออกมาอาจไปปรากฏในที่ที่ผู้ดูแลระบบเห็น การทดสอบจึงไม่ควรใช้เทคนิคนี้กับข้อมูลที่มีความอ่อนไหว

UNION-based

เทคนิคนี้ต่อผลลัพธ์ของคำสั่งใหม่เข้ากับผลลัพธ์ของคำสั่งเดิม ทำให้ข้อมูลจากตารางอื่นปรากฏบนหน้าเดียวกับข้อมูลปกติ เป็นเทคนิคที่เร็วและอ่านง่ายที่สุดเมื่อทำได้

เงื่อนไขสามข้อที่ต้องครบคือ จำนวนคอลัมน์ของทั้งสองฝั่งต้องเท่ากัน ชนิดข้อมูลของแต่ละคอลัมน์ต้องเข้ากันได้ และอย่างน้อยหนึ่งคอลัมน์ต้องถูกนำไปแสดงบนหน้าเว็บ หากขาดข้อใดข้อหนึ่งจะไม่ได้ผลลัพธ์ หรือได้ผลลัพธ์ที่แสดงเฉพาะบางตำแหน่ง

การหาว่าคอลัมน์ใดแสดงผลได้เป็นขั้นตอนที่ต้องทำเสมอ เพราะการวางข้อมูลผิดตำแหน่งจะทำให้เห็นผลลัพธ์ว่างเปล่าทั้งที่คำสั่งทำงานถูก

Boolean-based Blind

เมื่อระบบไม่แสดงข้อผิดพลาดและไม่แสดงผลลัพธ์จากคำสั่งใหม่ ผู้ทดสอบยังสามารถถามคำถามที่ตอบได้เพียงใช่หรือไม่ โดยดูว่าหน้าเว็บเปลี่ยนไปหรือไม่ ตัวอย่างเช่น การถามว่าตัวอักษรตัวแรกของชื่อฐานข้อมูลคือ a หรือไม่

หากหน้าเว็บแสดงผลปกติ แสดงว่าคำตอบคือใช่ หากหน้าเว็บว่างหรือแสดงข้อความไม่พบข้อมูล แสดงว่าคำตอบคือไม่ใช่ การถามซ้ำกับตัวอักษรแต่ละตัวจะให้ข้อมูลที่ต้องการทีละตัว

การถามทีละตัวอักษรใช้คำขอมาก แต่จำนวนสามารถลดลงได้ด้วยการค้นหาแบบแบ่งครึ่ง คือถามว่าค่ามากกว่าหรือน้อยกว่าค่ากลาง แล้วแบ่งช่วงลงเรื่อยๆ วิธีนี้ลดจำนวนคำขอจากประมาณเก้าสิบหกครั้งต่อตัวอักษรเหลือประมาณเจ็ดครั้ง

Time-based Blind

เมื่อหน้าเว็บตอบเหมือนเดิมทุกกรณีจนแยกความต่างไม่ได้ ผู้ทดสอบยังใช้เวลาเป็นสัญญาณได้ ด้วยการสั่งให้ฐานข้อมูลหน่วงเวลาหากเงื่อนไขเป็นจริง

หากคำตอบใช้เวลามากกว่าปกติประมาณสามวินาที แสดงว่าคำตอบคือใช่ วิธีนี้ใช้ได้แม้ระบบจะตอบหน้าเดิมทุกกรณี แต่มีข้อเสียคือช้าและสร้างภาระต่อระบบมาก เพราะทุกคำขอต้องรอจนครบเวลาหน่วง

เวลาหน่วงที่เลือกควรสั้นที่สุดที่ยังแยกออกจากเวลาปกติได้ สามถึงห้าวินาทีมักเพียงพอ การใช้ค่าสูงเช่นสามสิบนาทีจะทำให้การทดสอบใช้เวลานานและอาจทำให้ระบบตรวจพบว่าเป็นการโจมตี

Stacked Queries

เทคนิคนี้ต่อคำสั่งที่สองเข้ากับคำสั่งเดิมด้วยเครื่องหมายอัฒภาค ทำให้สามารถรันคำสั่งอื่นได้ เช่น การเพิ่มผู้ใช้ใหม่หรือการลบตาราง ความสามารถนี้ขึ้นกับไดรเวอร์ที่ใช้ ไม่ใช่ขึ้นกับฐานข้อมูลเพียงอย่างเดียว

ไดรเวอร์ของ PHP หลายตัวไม่อนุญาตให้รันหลายคำสั่งในครั้งเดียว แต่บางตัวอนุญาต จึงต้องทดสอบว่าใช้งานได้หรือไม่ก่อนใช้เทคนิคนี้

ข้อควรระวังคือเทคนิคนี้เป็นเทคนิคที่เปลี่ยนแปลงข้อมูลได้ทันที การทดสอบว่าใช้งานได้ด้วยคำสั่งที่ไม่ทำอันตราย เช่น การเลือกค่าคงที่ เป็นวิธีที่ปลอดภัยกว่า และไม่ควรใช้คำสั่งที่แก้ไขหรือลบข้อมูลเด็ดขาด

Out-of-band

เทคนิคนี้ส่งข้อมูลออกทางเครือข่าย แทนที่จะส่งกลับมาทางหน้าเว็บ ตัวอย่างเช่น การสั่งให้ฐานข้อมูลแปลงข้อมูลเป็นชื่อโดเมนแล้วส่งคำขอ DNS ออกไปยังเซิร์ฟเวอร์ที่ผู้ทดสอบควบคุม

เทคนิคนี้ใช้เมื่อช่องทางอื่นถูกปิดหมด และต้องอาศัยสิทธิ์และสภาพเครือข่ายที่เอื้ออำนวย ผู้ทดสอบต้องมีเซิร์ฟเวอร์ที่รับคำขอได้และต้องได้รับอนุญาตให้ใช้โดเมนนั้นในงานทดสอบ

ข้อจำกัดคือข้อมูลที่ส่งออกได้มีขนาดเล็กและช้ากว่าช่องทางอื่น จึงเหมาะกับการยืนยันว่าช่องโหว่มีอยู่จริง มากกว่าการดึงข้อมูลจำนวนมาก

การเลือกเทคนิคจากคำตอบที่เห็น

ลำดับการเลือกที่ใช้ได้จริงคือ เริ่มจาก Error-based หากระบบแสดงข้อผิดพลาด ถ้าไม่ได้ผลให้ลอง UNION-based หากพอเดาจำนวนคอลัมน์ได้ ถ้ายังไม่ได้ผลให้เปลี่ยนเป็น Boolean-based และปิดท้ายด้วย Time-based เมื่อไม่เหลือสัญญาณอื่น

การเลือกเช่นนี้ช่วยให้ได้ผลเร็วที่สุดโดยใช้คำขอน้อยที่สุด ซึ่งดีทั้งต่อเวลาในการทดสอบและต่อภาระของระบบเป้าหมาย

สิ่งที่ต้องระวังคือการยึดติดกับเทคนิคเดียว ผู้ทดสอบที่ถนัด UNION-based อาจใช้เวลานานกับระบบที่แสดงผลเพียงบางคอลัมน์ ในขณะที่การเปลี่ยนไปใช้ Boolean-based จะให้ผลเร็วกว่า การรู้จักสังเกตว่าตัวเองติดอยู่ที่ใดจึงสำคัญ

ข้อผิดพลาดที่พบบ่อยในการเลือกเทคนิค

ข้อผิดพลาดข้อแรกคือการสรุปว่าไม่มีช่องโหว่เพราะไม่เห็นข้อความผิดพลาด ทั้งที่ระบบเพียงปิดการแสดงข้อผิดพลาด ข้อผิดพลาดข้อที่สองคือการใช้เทคนิค Time-based กับระบบที่ตอบสนองช้าไม่สม่ำเสมออยู่แล้ว ซึ่งทำให้แยกสัญญาณไม่ออก

ข้อผิดพลาดข้อที่สามคือการลืมว่าฐานข้อมูลอาจไม่ใช่ MySQL เทคนิคและไวยากรณ์ที่ใช้ได้กับ MySQL อาจใช้ไม่ได้กับ MSSQL หรือ Oracle การอ่านข้อมูลที่ได้จากคำตอบ เช่น ชื่อฟังก์ชันในข้อความผิดพลาด หรือหัวข้อ Server ของคำตอบ จะช่วยบอกชนิดของฐานข้อมูล

ข้อผิดพลาดข้อที่สี่คือการทดสอบบนระบบที่ใช้ตัวกรองคำขอ ซึ่งตัดแปลงคำขอจนผลไม่ตรงกับที่ควรเป็น ในกรณีเช่นนี้ต้องดูว่าคำขอที่ไปถึงเซิร์ฟเวอร์จริงหน้าตาเป็นอย่างไร ไม่ใช่ดูเพียงคำขอที่เราส่งออกไป

7.4 การอ่านข้อมูลเมตาและการดึงข้อมูล

ข้อมูลเมตาคือแผนที่ของฐานข้อมูล

ก่อนจะดึงข้อมูลจริง ผู้ทดสอบต้องรู้ก่อนว่ามีฐานข้อมูลใด มีตารางใด และแต่ละตารางมีคอลัมน์ใด ข้อมูลนี้เรียกว่าข้อมูลเมตา (Metadata) และฐานข้อมูลส่วนใหญ่เก็บไว้ในฐานข้อมูลระบบที่อ่านได้ด้วยสิทธิ์ทั่วไป

ใน MySQL และ MariaDB ฐานข้อมูลนี้ชื่อ information_schema และมีตารางที่สำคัญสี่ตาราง ตาราง schemata เก็บรายชื่อฐานข้อมูล ตาราง tables เก็บรายชื่อตาราง ตาราง columns เก็บรายชื่อคอลัมน์ และตาราง routines เก็บรายชื่อโพรซีเยอร์และฟังก์ชันที่ผู้พัฒนาเขียนไว้

การอ่านข้อมูลเมตาผ่าน information_schema ใช้ได้กับฐานข้อมูลหลายตัวเพราะเป็นมาตรฐานกลาง แต่ชื่อฐานข้อมูลและรูปแบบคำสั่งอาจต่างกันเล็กน้อย จึงควรเริ่มจาก information_schema เสมอ แล้วปรับตามชนิดของฐานข้อมูลเมื่อจำเป็น

ฟังก์ชันที่บอกข้อมูลเกี่ยวกับตัวเอง

นอกจากตารางเมตาแล้ว ฐานข้อมูลยังมีฟังก์ชันที่คืนค่าข้อมูลเกี่ยวกับสภาพแวดล้อมปัจจุบัน ซึ่งมีประโยชน์ทั้งในการระบุชนิดของฐานข้อมูลและการตรวจสอบสิทธิ์

ตาราง 7.7 ฟังก์ชันตรวจสอบสภาพแวดล้อมใน MySQL และ MariaDB
ฟังก์ชันผลลัพธ์ใช้เมื่อใด
database()ชื่อฐานข้อมูลปัจจุบันเริ่มต้นสำรวจ
user()ชื่อผู้ใช้และที่อยู่ที่เชื่อมต่อประเมินสิทธิ์
version()รุ่นของฐานข้อมูลเลือกไวยากรณ์ให้ถูก
@@version_commentข้อความประกอบรุ่นแยก MySQL กับ MariaDB
@@datadirไดเรกทอรีเก็บข้อมูลประเมินความเป็นไปได้ในการอ่านไฟล์
@@hostnameชื่อเครื่องระบุตำแหน่งของเซิร์ฟเวอร์
connection_id()หมายเลขการเชื่อมต่อใช้ตรวจว่าคำขอมาจากเรา

การเรียกฟังก์ชันเหล่านี้ทำได้ด้วยเทคนิค UNION หรือเทคนิคอื่นที่ใช้อยู่แล้ว เช่น

?id=15 UNION SELECT 1,database(),version()-- -

ผลลัพธ์บอกทั้งชื่อฐานข้อมูลและรุ่น ซึ่งช่วยเลือกไวยากรณ์สำหรับขั้นถัดไปได้ถูกต้อง และยังเป็นการยืนยันว่าคำสั่งที่ส่งไปทำงานจริง ไม่ใช่เพียงถูกกรองแล้วส่งกลับมาเป็นหน้าเดิม

การดึงรายชื่อตารางและคอลัมน์

เมื่อรู้ชื่อฐานข้อมูลแล้ว ขั้นถัดไปคือการดูรายชื่อตารางในฐานข้อมูลนั้น การกรองด้วย table_schema=database() ช่วยจำกัดผลให้เหลือเฉพาะฐานข้อมูลที่แอปพลิเคชันใช้อยู่ ซึ่งลดจำนวนข้อมูลที่ต้องอ่านและลดภาระต่อระบบ

?id=15 UNION SELECT 1,table_name,3 FROM information_schema.tables
WHERE table_schema=database()-- -

หากผลลัพธ์มีหลายแถวจนอ่านไม่สะดวก ให้ใช้ GROUP_CONCAT() รวมชื่อตารางไว้ในช่องเดียว หรือใช้ LIMIT จำกัดจำนวนแถว

?id=15 UNION SELECT 1,GROUP_CONCAT(table_name),3 FROM information_schema.tables
WHERE table_schema=database()-- -

เมื่อได้รายชื่อตารางแล้ว ให้เลือกระบุตารางที่น่าสนใจที่สุดหนึ่งตารางก่อน แล้วดึงรายชื่อคอลัมน์ของตารางนั้น การทำทีละตารางช่วยให้คำขอมีขนาดเล็กและอ่านผลได้ง่ายกว่าการดึงทั้งหมดพร้อมกัน

?id=15 UNION SELECT 1,GROUP_CONCAT(column_name),3 FROM information_schema.columns
WHERE table_name='users'-- -

ชื่อคอลัมน์ที่ได้มักบอกได้ทันทีว่าควรอ่านอะไร เช่น username, password, email, role, created_at การเห็นคอลัมน์ชื่อ role หรือ is_admin เป็นข้อมูลที่มีค่า เพราะบอกว่าระบบมีการแบ่งระดับสิทธิ์ และอาจนำไปสู่การยกระดับสิทธิ์ในแอปพลิเคชัน

การดึงข้อมูลจริงอย่างจำกัดขอบเขต

เมื่อรู้ชื่อตารางและคอลัมน์แล้ว การดึงข้อมูลเป็นการนำชื่อเหล่านั้นไปใส่ในคำสั่ง UNION ตามจำนวนคอลัมน์ที่รู้ไว้

?id=15 UNION SELECT 1,username,password FROM users LIMIT 0,3-- -

การใส่ LIMIT 0,3 จำกัดให้ได้เพียงสามแถวแรก ซึ่งเพียงพอต่อการยืนยันว่าอ่านข้อมูลได้ และลดปริมาณข้อมูลที่ไหลออกจากระบบเป้าหมาย การดึงทั้งตารางไม่ใช่สิ่งที่ควรทำในการทดสอบทั่วไป เพราะเพิ่มความเสี่ยงต่อข้อมูลส่วนบุคคลและทำให้ระบบรับภาระหนัก

หากต้องการรวมหลายค่าไว้ในช่องเดียว เช่น การเห็นชื่อผู้ใช้และรหัสผ่านคู่กัน ให้ใช้ฟังก์ชันเชื่อมข้อความ CONCAT() และคั่นด้วยอักขระที่ไม่มีในข้อมูล เช่นเครื่องหมายโคลอน

?id=15 UNION SELECT 1,CONCAT(username,0x3a,password),3 FROM users LIMIT 0,3-- -

ค่า 0x3a คือเครื่องหมายโคลอนในรูปเลขฐานสิบหก ซึ่งใช้ได้โดยไม่ต้องใส่เครื่องหมายคำพูด และหลบตัวกรองที่ตัดเครื่องหมายคำพูดออกได้ในบางกรณี

ชนิดของรหัสผ่านที่พบ

รหัสผ่านในฐานข้อมูลไม่ได้เก็บเป็นข้อความตรงๆ แต่เก็บเป็นค่าที่ผ่านฟังก์ชันทางเดียว ใน MySQL รุ่นเก่าและ MariaDB ค่าที่เห็นมักขึ้นต้นด้วยเครื่องหมายดอกจันตามด้วยเลขฐานสิบหกสี่สิบตัว ซึ่งเกิดจากการเข้ารหัสสองชั้นด้วย SHA-1

การเห็นรูปแบบนี้บอกได้สองอย่าง อย่างแรกคือระบบใช้วิธีเก็บรหัสผ่านแบบเก่าที่ออกแบบมาให้คำนวณเร็ว ซึ่งทำให้การเดารหัสผ่านแบบออฟไลน์ทำได้เร็วตามไปด้วย อย่างที่สองคือค่าที่ได้ไม่สามารถย้อนกลับเป็นรหัสผ่านได้โดยตรง ต้องอาศัยการเดาแล้วเทียบ ซึ่งเป็นเนื้อหาของบทที่ 8

ใน MySQL รุ่นใหม่ วิธีเก็บรหัสผ่านเปลี่ยนไปใช้กลไกที่แข็งแรงขึ้น และค่าที่เก็บมีรูปแบบต่างออกไป ไม่ใช่เลขฐานสิบหกสี่สิบตัวอีกต่อไป การเห็นรูปแบบที่แตกต่างจึงเป็นข้อมูลที่บอกรุ่นและวิธีตั้งค่าของระบบ

การอ่านข้อมูลจากตารางอื่น

เมื่ออ่านตารางหลักได้แล้ว ผู้ทดสอบอาจพบว่ามีตารางที่เกี่ยวข้องซึ่งให้ข้อมูลเพิ่ม เช่น ตาราง orders ที่ผูกกับตาราง users ผ่านหมายเลขผู้ใช้ การอ่านตารางเหล่านี้ต้องใช้คำสั่งที่ซับซ้อนขึ้น แต่หลักการยังเหมือนเดิม

ข้อควรระวังคือการอ่านตารางที่มีข้อมูลปริมาณมาก เช่น ตารางบันทึกเหตุการณ์หรือตารางธุรกรรม คำสั่งที่ไม่มี LIMIT อาจทำให้ฐานข้อมูลใช้เวลานานและทำให้เว็บแอปพลิเคชันหยุดตอบสนองชั่วคราว ในระบบที่ให้บริการจริง ควรหลีกเลี่ยงการอ่านตารางขนาดใหญ่ หรือใช้ LIMIT ที่น้อยมาก

ข้อจำกัดที่อาจพบ

การอ่านข้อมูลเมตาอาจถูกจำกัดด้วยสิทธิ์ของบัญชีฐานข้อมูล บัญชีที่ถูกจำกัดสิทธิ์อาจอ่าน information_schema ได้เพียงบางส่วน หรืออ่านไม่ได้เลย ในกรณีเช่นนี้ต้องอาศัยการเดาชื่อตารางจากสิ่งที่เห็นในแอปพลิเคชัน เช่น ชื่อเส้นทาง ชื่อฟิลด์ในฟอร์ม และข้อความผิดพลาดที่หลุดออกมา

ข้อจำกัดอีกอย่างคือการแปลงชนิดข้อมูล ในคำสั่ง UNION บางตำแหน่งอาจต้องการชนิดข้อมูลเฉพาะ เช่น ตัวเลขหรือวันที่ การใส่สายอักขระในตำแหน่งที่เป็นตัวเลขจะทำให้คำสั่งล้มเหลว วิธีแก้คือใช้ฟังก์ชันแปลงชนิด เช่น CAST() หรือเลือกวางข้อมูลในตำแหน่งที่ยอมรับสายอักขระ

ข้อจำกัดที่สามคือการเข้ารหัสอักขระ หากฐานข้อมูลเก็บข้อมูลเป็นภาษาอื่น การดึงข้อมูลออกมาอาจได้อักขระที่อ่านไม่ออก การแปลงด้วยฟังก์ชันที่กำหนดชุดอักขระชัดเจนช่วยให้อ่านได้ถูกต้อง

การจัดการข้อมูลที่ได้

ข้อมูลที่ดึงออกมาควรถูกจัดการในลักษณะเดียวกับหลักฐาน คือบันทึกว่าดึงมาจากที่ใด เมื่อใด และด้วยคำขอใด แล้วเก็บไว้ในที่ที่เข้าถึงได้จำกัด

การเผยแพร่ข้อมูลจริงในรายงานเป็นสิ่งที่ควรหลีกเลี่ยง การแสดงเพียงบางส่วนที่ปิดบังไว้ก็พิสูจน์ได้ว่าเข้าถึงข้อมูลได้จริง เช่นการแสดงชื่อผู้ใช้สามรายแรกและรหัสผ่านที่ตัดเหลือสี่ตัวแรก

หากผู้ว่าจ้างต้องการหลักฐานที่ครบถ้วน ให้ส่งมอบผ่านช่องทางที่ตกลงกันไว้และลบสำเนาทั้งหมดเมื่อสิ้นสุดงาน การเก็บสำเนาไว้นานเกินความจำเป็นเป็นความเสี่ยงที่ไม่มีประโยชน์ต่อใคร

7.5 การใช้ sqlmap อย่างมีความรับผิดชอบ

เครื่องมือนี้ทำอะไร

sqlmap เป็นเครื่องมือที่ทำงานอัตโนมัติในทุกขั้นตอนที่อธิบายมาแล้วในหัวข้อ 7.2 ถึง 7.4 มันตรวจหาจุดที่คำสั่ง SQL ถูกต่ออย่างไม่ปลอดภัย เลือกเทคนิคที่ใช้ได้กับระบบนั้น แล้วดึงข้อมูลตามที่ผู้ใช้สั่ง

คุณค่าที่แท้จริงของมันคือการทำงานซ้ำที่ต้องใช้คำขอจำนวนมาก เช่น การเดาตัวอักษรทีละตัวในระบบที่ไม่แสดงผลลัพธ์ ซึ่งทำด้วยมือได้แต่ใช้เวลานานมาก sqlmap ยังจำลองรูปแบบคำขอที่แตกต่างกันหลายร้อยแบบ ซึ่งช่วยให้พบจุดที่ผู้ทดสอบด้วยมืออาจมองข้าม

แต่คุณค่านี้มาพร้อมความเสี่ยง เพราะเครื่องมือไม่ได้รู้จักขอบเขตของงาน ไม่ได้รู้ว่าตารางใดมีข้อมูลอ่อนไหว และไม่รู้ว่าคำขอที่ส่งไปจะทำให้ระบบช้าลงหรือไม่ ผู้ใช้ต้องเป็นผู้กำหนดข้อจำกัดเองทั้งหมด

เตรียมคำขอก่อนเรียกเครื่องมือ

วิธีที่แนะนำคือให้ Burp Suite จับคำขอที่ต้องการทดสอบ แล้วบันทึกเป็นไฟล์ข้อความ การทำงานกับไฟล์คำขอมีข้อดีกว่าการพิมพ์ที่อยู่ตรงๆ สามข้อ ข้อแรกคือคำขอมีหัวข้อและคุกกี้ครบตามที่ระบบต้องการ ข้อที่สองคือการทดสอบซ้ำทำได้ง่าย ข้อที่สามคือคำขอที่ใช้ทดสอบเป็นคำขอเดียวกับที่บันทึกไว้ในหลักฐาน

POST /login.php HTTP/1.1
Host: shop.example.local
Content-Type: application/x-www-form-urlencoded
Cookie: PHPSESSID=8f14e45fceea167a5a36dedd4bea2543

username=alice&password=secret

เมื่อบันทึกเป็นไฟล์แล้ว จึงเรียกเครื่องมือโดยระบุไฟล์และพารามิเตอร์ที่ต้องการทดสอบ

sqlmap -r login.txt -p username --batch

ตัวเลือก -p จำกัดการทดสอบไว้ที่พารามิเตอร์เดียว ซึ่งสำคัญมากเพราะการปล่อยให้เครื่องมือทดสอบทุกพารามิเตอร์พร้อมกันจะสร้างคำขอจำนวนมหาศาลและทำให้ไม่รู้ว่าจุดใดคือจุดที่มีช่องโหว่

--tamperแปลงคำขอเพื่อหลบตัวกรองใช้เมื่อถูกบล็อกเท่านั้น
--output-dirกำหนดที่เก็บผลควรอยู่ในที่ที่เข้าถึงจำกัด

ตัวเลือก --dump ควรใช้พร้อม -D, -T และ -C เพื่อจำกัดเฉพาะฐานข้อมูล ตาราง และคอลัมน์ที่ต้องการ การใช้ --dump โดยไม่ระบุจะทำให้เครื่องมือดึงทุกตารางในฐานข้อมูล ซึ่งเป็นปริมาณข้อมูลที่มากเกินความจำเป็นและเสี่ยงต่อข้อมูลส่วนบุคคล

ระดับความเสี่ยงและระดับความพยายาม

sqlmap มีตัวปรับสองตัวที่ผู้ใช้ใหม่มักไม่เข้าใจความหมาย ตัวแรกคือ --level ซึ่งควบคุมจำนวนและความหลากหลายของคำขอที่เครื่องมือลอง ตัวที่สองคือ --risk ซึ่งควบคุมความรุนแรงของคำสั่งที่ยอมให้ใช้

ตาราง 7.9 ความหมายของระดับความเสี่ยงและระดับความพยายาม
ค่าระดับผลที่เกิดขึ้น
--level=1ต่ำสุด (ปริยาย)ทดสอบพารามิเตอร์หลักไม่กี่รูปแบบ
--level=2ต่ำเพิ่มการทดสอบหัวข้อและคุกกี้
--level=3กลางเพิ่มการทดสอบค่าที่ซับซ้อนขึ้น
--level=5สูงสุดทดสอบเกือบทุกจุดที่เป็นไปได้ ใช้เวลามาก
--risk=1ต่ำสุด (ปริยาย)ใช้คำสั่งอ่านเท่านั้น
--risk=2กลางเพิ่มคำสั่งที่อาจหนักต่อฐานข้อมูล
--risk=3สูงรวมคำสั่งที่อาจแก้ไขข้อมูล

ระดับ --risk=3 ไม่ควรใช้ในระบบที่ให้บริการจริง เพราะคำสั่งที่เครื่องมือเลือกอาจเป็นคำสั่งที่เขียนทับข้อมูล แม้เจตนาจะเป็นการทดสอบก็ตาม การใช้ระดับนี้ควรทำในระบบฝึกหรือระบบที่แยกออกจากข้อมูลจริงเท่านั้น

ตัวอย่างลำดับการใช้งาน

ลำดับที่ปลอดภัยคือเริ่มจากการยืนยันว่ามีช่องโหว่ก่อน แล้วจึงค่อยขยายขอบเขตทีละขั้น

sqlmap -r login.txt -p username --batch --dbms=mysql
sqlmap -r login.txt -p username --batch --dbs
sqlmap -r login.txt -p username --batch -D shop --tables
sqlmap -r login.txt -p username --batch -D shop -T users --columns
sqlmap -r login.txt -p username --batch -D shop -T users -C username,password --dump

แต่ละคำสั่งให้ข้อมูลสำหรับคำสั่งถัดไป และแต่ละคำสั่งมีขอบเขตชัดเจนว่าดึงอะไร การทำเช่นนี้ทำให้เห็นว่าข้อมูลใดออกจากระบบในขั้นใด ซึ่งจำเป็นต่อการรายงานผลและการลบข้อมูลในภายหลัง

เครื่องมือจะเก็บสถานะของแต่ละเป้าหมายไว้ในไดเรกทอรีใต้บ้านของผู้ใช้ หากต้องการเริ่มการทดสอบใหม่ทั้งหมดโดยไม่ใช้ข้อมูลเดิม ให้ใช้ --flush-session แต่ต้องเข้าใจว่าการทำเช่นนี้จะทำให้เครื่องมือทดสอบซ้ำตั้งแต่ต้น ซึ่งเพิ่มจำนวนคำขอต่อระบบเป้าหมาย

ตรวจสอบสิ่งที่เครื่องมือส่งออกไป

ข้อควรปฏิบัติที่สำคัญที่สุดคือการดูคำขอที่เครื่องมือส่งจริง ผู้ทดสอบสามารถกำหนดให้เครื่องมือส่งคำขอผ่านพร็อกซีที่ตัวเองควบคุม เพื่อบันทึกทุกอย่างที่ออกไป

sqlmap -r login.txt -p username --batch --proxy=http://127.0.0.1:8080

การดูคำขอที่ส่งจริงช่วยตอบคำถามสามข้อ ข้อแรกคือเครื่องมือกำลังทดสอบจุดที่เราต้องการจริงหรือไม่ ข้อที่สองคือมีคำขอที่เสี่ยงต่อข้อมูลหรือไม่ ข้อที่สามคือระบบตอบอย่างไรต่อคำขอเหล่านั้น

ผู้ทดสอบจำนวนมากใช้เครื่องมือโดยไม่ดูคำขอเลย แล้วพบภายหลังว่ามีคำขอที่ทำให้ข้อมูลเปลี่ยนไป หรือมีคำขอจำนวนมากที่ทำให้ระบบช้าลง การตรวจสอบระหว่างทางจึงเป็นกิจนิสัยที่ต้องทำ ไม่ใช่เรื่องทางเลือก

ข้อจำกัดและความเสี่ยงต่อฐานข้อมูลจริง

sqlmap ไม่ได้ออกแบบมาสำหรับระบบที่ห้ามหยุดให้บริการ มันส่งคำขอจำนวนมากในเวลาสั้น และบางคำขออาจใช้ทรัพยากรของฐานข้อมูลสูง เช่น การเรียงลำดับตารางขนาดใหญ่หรือการคำนวณฟังก์ชันซ้ำๆ

ผลที่อาจเกิดได้แก่ ระบบตอบสนองช้าลง ฐานข้อมูลใช้หน่วยประมวลผลเต็ม ระบบตรวจพบและบล็อกหมายเลขผู้ทดสอบ หรือในกรณีร้ายแรง ฐานข้อมูลหยุดทำงานเพราะหน่วยความจำไม่พอ

ความเสี่ยงอีกข้อคือคำสั่งที่เครื่องมือเลือกอาจแก้ไขข้อมูลโดยไม่ตั้งใจ โดยเฉพาะเมื่อใช้ --risk=3 หรือเมื่อเครื่องมือเลือกเทคนิคที่ต้องเขียนไฟล์ ความเสี่ยงนี้แก้ได้ด้วยการกำหนด --technique ให้ใช้เฉพาะเทคนิคอ่าน เช่น ระบุเฉพาะเทคนิค UNION และ Boolean

เมื่อใดควรใช้และเมื่อใดควรทำด้วยมือ

sqlmap เหมาะกับงานที่ต้องทดสอบซ้ำจำนวนมาก เช่น การยืนยันช่องโหว่ในหลายพารามิเตอร์ หรือการดึงข้อมูลที่ต้องใช้คำขอหลายพันครั้งในระบบที่ไม่แสดงผลลัพธ์

การทำด้วยมือเหมาะกับงานที่ต้องเข้าใจกลไก เช่น การทดสอบครั้งแรกในระบบใหม่ การตรวจสอบว่าระบบตอบสนองต่อคำสั่งอย่างไร และการทดสอบที่ต้องการคำขอเพียงไม่กี่ครั้งเพื่อยืนยันผล

ในทางปฏิบัติ การทำงานที่ดีคือใช้มือเพื่อเข้าใจและยืนยัน แล้วใช้เครื่องมือเพื่อทำงานซ้ำให้เร็วขึ้น ไม่ใช่ใช้เครื่องมือแทนความเข้าใจตั้งแต่ต้น เพราะเมื่อเครื่องมือให้ผลที่ไม่ชัดเจน ผู้ที่เข้าใจกลไกเท่านั้นที่จะรู้ว่าควรถอยกลับไปทางใด

การรายงานผลจากเครื่องมือ

ผลที่ได้จากเครื่องมือต้องถูกตรวจสอบก่อนนำไปเขียนในรายงาน อย่างน้อยที่สุดควรยืนยันด้วยคำขอที่ทำด้วยมือหนึ่งครั้งว่าเทคนิคที่เครื่องมือรายงานนั้นใช้งานได้จริง

รายงานควรระบุเครื่องมือและคำสั่งที่ใช้ ระบุคำขอที่ทดสอบ ระบุข้อมูลที่ดึงออกมาโดยไม่เปิดเผยเนื้อหาทั้งหมด และระบุเวลาที่ใช้ เพื่อให้ผู้ว่าจ้างประเมินภาระที่ระบบได้รับได้

หากเครื่องมือรายงานว่าพบช่องโหว่แต่ไม่สามารถดึงข้อมูลได้ ให้บันทึกตามความเป็นจริงว่า "ตรวจพบพฤติกรรมที่บ่งชี้ว่ามีช่องโหว่ แต่ยังไม่สามารถยืนยันผลกระทบได้" การเขียนว่า "ไม่พบช่องโหว่" ในกรณีนี้เป็นการรายงานที่คลาดเคลื่อน

7.6 ผลกระทบและการต่อยอด

จากช่องโหว่หนึ่งจุดสู่ความเสียหายทั้งระบบ

ช่องโหว่ SQL Injection มักถูกมองว่าเป็นเรื่องของการอ่านข้อมูล แต่ผลกระทบที่แท้จริงกว้างกว่านั้นมาก เพราะคำสั่ง SQL มีอำนาจเหนือข้อมูลทั้งหมดที่บัญชีฐานข้อมูลเข้าถึง และในบางระบบยังมีอำนาจเหนือระบบไฟล์และกระบวนการของระบบปฏิบัติการด้วย

การประเมินผลกระทบจึงต้องทำเป็นชั้น เริ่มจากสิ่งที่พิสูจน์ได้แล้วในระบบจริง แล้วจึงประเมินชั้นถัดไปว่ามีเงื่อนไขใดบ้างที่ทำให้เป็นไปได้ ชั้นที่ประเมินจากสมมติฐานโดยไม่ตรวจสอบจะทำให้รายงานกล่าวเกินจริงหรือกล่าวต่ำกว่าความจริง ซึ่งทั้งสองแบบทำให้ผู้ว่าจ้างตัดสินใจผิด

ตาราง 7.10 ระดับผลกระทบของ SQL Injection
ระดับความสามารถเงื่อนไขที่ต้องมีผลกระทบต่อองค์กร
1อ่านข้อมูลในตารางที่แอปพลิเคชันใช้มีช่องโหว่และสิทธิ์อ่านข้อมูลรั่วเฉพาะส่วน
2อ่านข้อมูลทุกตารางในฐานข้อมูลสิทธิ์อ่านข้อมูลเมตาข้อมูลทั้งระบบรั่ว
3เพิ่ม แก้ไข หรือลบข้อมูลไดรเวอร์ยอมรับหลายคำสั่งข้อมูลเสียหายและเชื่อถือไม่ได้
4อ่านหรือเขียนไฟล์บนเซิร์ฟเวอร์บัญชีมีสิทธิ์ไฟล์และค่าตั้งเปิดอาจยึดเซิร์ฟเวอร์ได้
5สั่งให้ระบบปฏิบัติการทำงานมีช่องทางส่วนขยายหรือฟีเจอร์พิเศษยึดเครื่องได้ทั้งหมด

การข้ามการยืนยันตัวตน

ผลกระทบที่เห็นได้ทันทีที่สุดคือการเข้าสู่ระบบโดยไม่รู้รหัสผ่าน เมื่อฟอร์มเข้าสู่ระบบสร้างคำสั่ง SQL ด้วยการต่อสายอักขระ การส่งค่าที่ทำให้เงื่อนไขรหัสผ่านเป็นจริงเสมอจะทำให้ระบบคืนข้อมูลผู้ใช้หนึ่งรายและถือว่าการยืนยันตัวตนสำเร็จ

username: admin' --
password: อะไรก็ได้

เครื่องหมาย -- ตัดส่วนที่เหลือของคำสั่งออก จึงเหลือเพียงเงื่อนไขชื่อผู้ใช้ ผลลัพธ์คือระบบตรวจพบผู้ใช้ admin และเข้าสู่ระบบในฐานะผู้ดูแล

ผลกระทบไม่ได้หยุดที่การเข้าได้ แต่ขยายไปถึงสิ่งที่บัญชีนั้นทำได้ หากเป็นบัญชีผู้ดูแล ระบบก็เปิดทางให้แก้ไขข้อมูล เพิ่มผู้ใช้ หรือเปลี่ยนค่าตั้ง ซึ่งเป็นการยกระดับจาก "อ่านข้อมูล" เป็น "ควบคุมระบบ"

ในบางระบบ การข้ามการยืนยันตัวตนยังนำไปสู่การเข้าถึงข้อมูลของผู้อื่น เพราะระบบระบุตัวผู้ใช้จากค่าที่ส่งมาแทนที่จะอ่านจากเซสชัน ซึ่งเป็นช่องโหว่อีกชนิดที่มักอยู่ร่วมกัน

การขโมยข้อมูล

การขโมยข้อมูลคือผลกระทบที่พบบ่อยที่สุดและสร้างความเสียหายระยะยาวที่สุด เพราะข้อมูลที่รั่วออกไปแล้วไม่สามารถเรียกคืนได้ ข้อมูลที่มักเป็นเป้าหมายได้แก่ รายชื่อและรหัสผ่านผู้ใช้ ข้อมูลติดต่อ ข้อมูลคำสั่งซื้อ ข้อมูลทางการเงิน และข้อมูลสุขภาพ

รหัสผ่านที่ได้มาแม้จะเข้ารหัสแล้วยังมีค่า เพราะมันนำไปสู่การเดารหัสผ่านแบบออฟไลน์ ซึ่งเป็นการคำนวณบนเครื่องของผู้โจมตีที่ไม่ถูกจำกัดจำนวนครั้ง ในระบบที่ผู้ใช้ใช้รหัสผ่านซ้ำ การถอดได้หนึ่งบัญชีอาจนำไปสู่การเข้าถึงบัญชีอื่นในองค์กรเดียวกัน

ขนาดของข้อมูลที่รั่วมีผลต่อระดับความรุนแรงทางกฎหมาย ระบบที่รั่วข้อมูลลูกค้าหนึ่งแสนรายต้องแจ้งเหตุและดำเนินการตามกฎหมายคุ้มครองข้อมูลส่วนบุคคล ซึ่งมีค่าใช้จ่ายและผลกระทบต่อชื่อเสียงมากกว่าตัวช่องโหว่เองหลายเท่า

การแก้ไขและทำลายข้อมูล

ช่องโหว่ที่ใช้คำสั่งแบบหลายชั้นอนุญาตให้ผู้โจมตีแก้ไขหรือลบข้อมูลได้ ซึ่งเป็นผลกระทบที่ร้ายแรงกว่าการอ่านมาก เพราะข้อมูลที่ถูกลบหรือแก้ไขอาจกู้คืนไม่ได้ และอาจทำให้ระบบทำงานผิดพลาดต่อเนื่อง

การโจมตีที่พบบ่อยในกลุ่มนี้ได้แก่การเปลี่ยนระดับสิทธิ์ของบัญชีตัวเอง การเปลี่ยนราคาสินค้า การลบหลักฐานการทำธุรกรรม และการใส่ข้อมูลเท็จเพื่อทำให้รายงานผิดเพี้ยน

ในงานทดสอบ การพิสูจน์ว่าสามารถแก้ไขข้อมูลได้ไม่จำเป็นต้องแก้ไขข้อมูลจริง การใช้คำสั่งที่แสดงว่าจะแก้ไขอะไรหากดำเนินการต่อ ก็เพียงพอต่อการยืนยันความเสี่ยง และปลอดภัยกว่ามาก

การอ่านไฟล์จากเซิร์ฟเวอร์

ฐานข้อมูล MySQL และ MariaDB มีฟังก์ชัน LOAD_FILE() ที่อ่านไฟล์จากเซิร์ฟเวอร์ที่ฐานข้อมูลทำงานอยู่ การใช้ฟังก์ชันนี้ต้องมีสิทธิ์ FILE และต้องผ่านข้อจำกัดที่ชื่อ secure_file_priv

?id=15 UNION SELECT 1,LOAD_FILE('/etc/passwd'),3-- -

ค่าตั้ง secure_file_priv กำหนดว่าอ่านหรือเขียนไฟล์ได้เฉพาะในไดเรกทอรีใด ค่าที่เป็นสายอักขระว่างหมายถึงไม่จำกัดไดเรกทอรี ค่าที่ระบุเส้นทางหมายถึงจำกัดเฉพาะในเส้นทางนั้น และค่า NULL หมายถึงปิดการอ่านและเขียนไฟล์ทั้งหมด

การเห็นค่าที่ได้จาก @@secure_file_priv จึงเป็นข้อมูลที่บอกว่าควรลงทุนกับเทคนิคนี้ต่อหรือไม่ หากค่าตั้งปิดไว้ การพยายามอ่านไฟล์จะไม่เกิดประโยชน์และสร้างคำขอที่ไม่จำเป็น

ไฟล์ที่มีค่าที่สุดในการอ่านคือไฟล์ค่าตั้งของแอปพลิเคชัน ซึ่งมักมีข้อมูลรับรองของฐานข้อมูลและคีย์ต่างๆ การอ่านไฟล์เหล่านี้อาจนำไปสู่การเชื่อมต่อฐานข้อมูลโดยตรง ซึ่งให้สิทธิ์มากกว่าการใช้ช่องโหว่ผ่านเว็บ

การเขียนไฟล์ขึ้นเซิร์ฟเวอร์

เมื่อมีสิทธิ์เขียนไฟล์ ผู้ทดสอบอาจสร้างไฟล์สคริปต์ในไดเรกทอรีที่เว็บเข้าถึงได้ ซึ่งนำไปสู่การสั่งให้ระบบทำงาน คำสั่งที่ใช้คือ INTO OUTFILE ซึ่งเขียนผลลัพธ์ของคำสั่งลงไฟล์

?id=15 UNION SELECT 1,'<?php echo "PROOF"; ?>',3
INTO OUTFILE '/var/www/html/proof.php'-- -

เงื่อนไขที่ต้องครบมีหลายข้อ ต้องมีสิทธิ์ FILE ต้องผ่านค่าตั้ง secure_file_priv ต้องมีสิทธิ์เขียนในไดเรกทอรีเป้าหมาย และไฟล์ปลายทางต้องยังไม่มีอยู่ เพราะคำสั่งนี้ไม่เขียนทับไฟล์เดิม เงื่อนไขที่มากขนาดนี้ทำให้เทคนิคนี้ใช้ได้น้อยลงในระบบที่ตั้งค่าตามมาตรฐาน

การต่อยอดสู่ระดับระบบปฏิบัติการ

การสั่งให้ระบบปฏิบัติการทำงานผ่านฐานข้อมูลมีหลายช่องทาง แต่ละช่องทางใช้ได้เฉพาะบางฐานข้อมูลและต้องมีเงื่อนไขพิเศษ

ใน Microsoft SQL Server ช่องทางที่รู้จักกันดีคือโพรซีเยอร์ที่สั่งคำสั่งของระบบ ซึ่งปิดไว้โดยปริยายและต้องเปิดด้วยสิทธิ์ผู้ดูแล ใน PostgreSQL มีคำสั่งที่ให้เขียนผลลัพธ์ของคำสั่งลงไฟล์หรือส่งไปยังโปรแกรม ซึ่งถูกจำกัดสิทธิ์อย่างเข้มงวด ใน MySQL การสั่งคำสั่งมักต้องติดตั้งส่วนขยายเพิ่ม ซึ่งไม่ใช่สิ่งที่เกิดขึ้นได้จากการฉีดคำสั่งเพียงอย่างเดียว

การทดสอบช่องทางเหล่านี้มีความเสี่ยงสูงมาก เพราะคำสั่งที่รันจะทำงานด้วยสิทธิ์ของบัญชีฐานข้อมูล ซึ่งในบางระบบเป็นบัญชีที่มีสิทธิ์สูง ในงานทดสอบทั่วไปจึงไม่ควรดำเนินการต่อในชั้นนี้ เว้นแต่ขอบเขตกำหนดไว้ชัดเจนและมีผู้ดูแลระบบร่วมสังเกตการณ์

ผลกระทบต่อธุรกิจ

ผลกระทบทางเทคนิคเป็นเพียงส่วนหนึ่งของเรื่อง ผลกระทบต่อธุรกิจมักหนักกว่าและใช้เวลานานกว่า

ด้านกฎหมาย ระบบที่รั่วข้อมูลส่วนบุคคลต้องแจ้งเหตุต่อหน่วยงานกำกับดูแลและต่อเจ้าของข้อมูลภายในเวลาที่กฎหมายกำหนด การไม่แจ้งมีโทษปรับ และการแจ้งล่าช้ามีผลต่อความเชื่อมั่นของลูกค้า

ด้านการดำเนินงาน ระบบที่ถูกแก้ไขข้อมูลต้องใช้เวลาในการตรวจสอบและกู้คืน ซึ่งอาจหมายถึงการหยุดให้บริการชั่วคราว และในบางกรณีต้องกู้คืนจากข้อมูลสำรอง ซึ่งทำให้ข้อมูลที่เกิดขึ้นหลังการสำรองหายไป

ด้านชื่อเสียง ข่าวการรั่วไหลของข้อมูลแพร่กระจายได้เร็วกว่าการแก้ไข และผลกระทบต่อยอดขายอาจคงอยู่เป็นปี การประเมินผลกระทบจึงต้องรวมเรื่องเหล่านี้ไว้ในรายงาน ไม่ใช่เพียงรายการข้อมูลที่อ่านได้

การเขียนรายงานผลกระทบ

รายงานที่ดีควรแยกให้ชัดระหว่างสิ่งที่พิสูจน์แล้วกับสิ่งที่ประเมินจากเงื่อนไข ตัวอย่างการเขียนที่เหมาะสมคือ "สามารถอ่านข้อมูลตารางผู้ใช้ได้ 1,200 ระเบียน และพบว่าบัญชีฐานข้อมูลมีสิทธิ์ FILE ซึ่งหากค่าตั้ง secure_file_priv ไม่จำกัดไดเรกทอรี อาจนำไปสู่การเขียนไฟล์และยึดเซิร์ฟเวอร์ได้"

การเขียนเช่นนี้บอกผู้อ่านว่าอะไรคือข้อเท็จจริงและอะไรคือความเสี่ยงที่ยังต้องตรวจสอบ ทำให้ผู้ว่าจ้างจัดลำดับการแก้ไขได้ถูกต้อง และไม่กล่าวโทษระบบเกินจริง

ในทางกลับกัน การเขียนว่า "ระบบถูกยึดทั้งหมด" โดยยังไม่ได้ทดสอบการเขียนไฟล์ เป็นการกล่าวเกินจริงที่ทำให้รายงานขาดความน่าเชื่อถือ และอาจทำให้ผู้ว่าจ้างไม่เชื่อถือผลอื่นในรายงานเดียวกัน

7.7 การป้องกันและการตรวจสอบ

หลักการเดียวที่แก้ต้นเหตุ

ช่องโหว่นี้แก้ที่ปลายเหตุได้ไม่จบ เพราะการกรองอักขระมีช่องให้หลบเสมอ วิธีที่แก้ต้นเหตุคือการแยกคำสั่งออกจากข้อมูลอย่างเด็ดขาด ฐานข้อมูลจะได้รับคำสั่งที่กำหนดไว้ล่วงหน้าและได้รับค่าแยกต่างหาก จึงไม่มีทางที่ค่าจะกลายเป็นส่วนหนึ่งของคำสั่งได้

วิธีนี้มีชื่อเรียกหลายแบบตามภาษาและเครื่องมือ เช่น คำสั่งเตรียมไว้ (Prepared Statement) พารามิเตอร์ผูกค่า (Bound Parameter) หรือคำสั่งที่กำหนดพารามิเตอร์ (Parameterized Query) แต่หลักการเดียวกันทั้งหมด

<?php
$stmt = $conn->prepare("SELECT name, price FROM products WHERE id = ?");
$stmt->bind_param("i", $_GET['id']);
$stmt->execute();
?>

ในตัวอย่างนี้เครื่องหมายคำถามคือตำแหน่งที่ค่าจะถูกใส่ และชนิดของค่าถูกกำหนดว่าเป็นจำนวนเต็ม ถ้าผู้ใช้ส่งข้อความที่ดูเหมือนคำสั่ง ฐานข้อมูลจะมองเป็นค่าที่ไม่ใช่จำนวนเต็มและปฏิเสธ ไม่ใช่ตีความเป็นคำสั่ง

การป้องกันหลายชั้น

แม้การแยกคำสั่งออกจากข้อมูลจะเป็นมาตรการหลัก แต่การป้องกันที่ดีมีหลายชั้น เพราะระบบจริงมีโค้ดเก่าและจุดที่ควบคุมไม่ได้ทั้งหมด

ตาราง 7.11 มาตรการป้องกันและสิ่งที่มาตรการนั้นแก้
มาตรการแก้อะไรข้อจำกัด
คำสั่งเตรียมไว้พร้อมพารามิเตอร์ต้นเหตุของการฉีดต้องใช้กับทุกจุดที่รับข้อมูล
การตรวจชนิดข้อมูลที่ฝั่งเซิร์ฟเวอร์ค่าที่ผิดรูปแบบไม่ทดแทนการแยกคำสั่ง
การจำกัดสิทธิ์ของบัญชีฐานข้อมูลความเสียหายเมื่อถูกโจมตีลดผลกระทบ ไม่ได้ปิดช่องโหว่
การปิดการแสดงข้อผิดพลาดลดข้อมูลที่รั่วไม่ได้ป้องกันการฉีด
การแยกข้อมูลเมตาออกจากผู้ใช้การฉีดในชื่อคอลัมน์ต้องใช้รายการที่อนุญาต
ไฟร์วอลล์สำหรับเว็บแอปพลิเคชันคำขอที่รูปแบบชัดเจนหลบได้และไม่ใช่การแก้โค้ด
การบันทึกและแจ้งเตือนตรวจจับการทดสอบไม่ได้ป้องกันด้วยตัวเอง

การจำกัดสิทธิ์คือมาตรการที่ให้ผลตอบแทนสูงเมื่อเทียบกับความพยายาม ระบบที่บัญชีฐานข้อมูลมีสิทธิ์อ่านอย่างเดียวในตารางที่จำเป็น จะจำกัดความเสียหายได้มากแม้จะมีช่องโหว่หลงเหลืออยู่ การให้บัญชีเว็บมีสิทธิ์ผู้ดูแลฐานข้อมูลเป็นเรื่องที่พบได้บ่อยแต่เป็นความเสี่ยงที่ไม่จำเป็นเลย

การปิดการแสดงข้อผิดพลาดมีประโยชน์เพราะลดข้อมูลที่ผู้โจมตีได้ฟรี แต่ไม่ควรถูกใช้แทนการแก้โค้ด เพราะผู้โจมตีที่ใช้เทคนิคแบบตาบอดยังได้ข้อมูลแม้ไม่เห็นข้อผิดพลาด

การจัดการชื่อคอลัมน์และคำสั่งที่เปลี่ยนรูปได้

มีกรณีที่การแยกคำสั่งออกจากข้อมูลทำได้ไม่ตรงไปตรงมา เช่น การเรียงลำดับตามคอลัมน์ที่ผู้ใช้เลือก หรือการเลือกตารางตามหมวดหมู่ ในกรณีเหล่านี้ไม่สามารถใช้พารามิเตอร์แทนชื่อคอลัมน์ได้โดยตรง เพราะฐานข้อมูลต้องการชื่อที่แน่นอนในคำสั่ง

วิธีที่ปลอดภัยคือใช้รายการที่อนุญาต ผู้พัฒนากำหนดรายการชื่อคอลัมน์ที่ยอมรับไว้ล่วงหน้า แล้วตรวจว่าค่าที่รับมาตรงกับรายการใดรายการหนึ่ง หากไม่ตรงก็ใช้ค่าเริ่มต้นแทน วิธีนี้ทำให้ผู้ใช้เลือกได้เฉพาะสิ่งที่ผู้พัฒนาอนุญาต ไม่ใช่ข้อความอิสระ

วิธีที่ผิดคือการนำค่าที่รับมาเติมในคำสั่งโดยตรง แม้จะผ่านการกรองเครื่องหมายคำพูดแล้วก็ตาม เพราะชื่อคอลัมน์ไม่ต้องใช้เครื่องหมายคำพูดและสามารถใส่นิพจน์ SQL ได้

การตรวจจับระหว่างให้บริการ

การตรวจจับการทดสอบ SQL Injection อาศัยรูปแบบของคำขอที่ผิดปกติ ซึ่งแตกต่างจากคำขอปกติของผู้ใช้อย่างชัดเจนในหลายกรณี

ตาราง 7.12 สัญญาณที่ใช้ตรวจพบการทดสอบ SQL Injection
สัญญาณตัวอย่างความหมาย
เครื่องหมายคำพูดในพารามิเตอร์ตัวเลขid=15'ความพยายามปิดสายอักขระ
คำสงวนในค่าที่ส่งUNION, SELECT, ORDER BYความพยายามสร้างคำสั่งใหม่
เครื่องหมายความคิดเห็น--, #, /*ความพยายามตัดส่วนที่เหลือของคำสั่ง
เงื่อนไขที่เป็นจริงเสมอOR 1=1, 'a'='a'ความพยายามข้ามเงื่อนไข
ฟังก์ชันหน่วงเวลาSLEEP, pg_sleep, WAITFORความพยายามทดสอบแบบอาศัยเวลา
ชื่อตารางระบบinformation_schemaความพยายามอ่านข้อมูลเมตา
คำขอซ้ำจำนวนมากในเวลาสั้นรูปแบบเดิมหลายพันครั้งการทำงานของเครื่องมืออัตโนมัติ

การแจ้งเตือนเพียงอย่างเดียวไม่พอ ต้องมีกระบวนการตรวจสอบว่าการแจ้งเตือนนั้นคือการทดสอบที่ได้รับอนุญาตหรือการโจมตีจริง เพราะในช่วงที่มีการทดสอบตามแผน ระบบจะมีการแจ้งเตือนจำนวนมากซึ่งอาจกลบเหตุการณ์จริง

การตรวจสอบโค้ด

วิธีที่เชื่อถือได้ที่สุดในการหาช่องโหว่นี้คือการอ่านโค้ด โดยมองหาจุดที่คำสั่ง SQL ถูกสร้างด้วยการต่อสายอักขระ แล้วตรวจว่ามีจุดใดที่ใช้พารามิเตอร์แทน

การค้นหาทำได้ด้วยการมองหาคำสำคัญ เช่น SELECT, INSERT, UPDATE, DELETE, WHERE แล้วดูว่าคำสั่งนั้นประกอบขึ้นอย่างไร หากเห็นเครื่องหมายบวกหรือการเชื่อมสายอักขระในคำสั่ง SQL นั่นคือจุดที่ต้องตรวจ

เครื่องมือช่วยอ่านโค้ดอัตโนมัติมีประโยชน์ในการหาจุดที่ต้องดู แต่ไม่สามารถยืนยันได้ว่าจุดนั้นปลอดภัยจริง เพราะบริบทของโค้ดเป็นสิ่งที่ต้องอ่านด้วยมนุษย์

การทดสอบว่าแก้ไขแล้วจริง

หลังการแก้ไข ควรทดสอบซ้ำด้วยคำขอเดิมที่เคยได้ผล หากระบบตอบเหมือนค่าปกติและไม่เกิดความแตกต่างระหว่างเงื่อนไขจริงกับเท็จ แสดงว่าการแก้ไขได้ผล

การทดสอบควรครอบคลุมทั้งจุดที่เคยพบและจุดอื่นที่ใช้โค้ดรูปแบบเดียวกัน เพราะการแก้ไขมักทำเฉพาะจุดที่ถูกรายงาน ทำให้จุดอื่นที่ใช้วิธีเดียวกันยังคงมีช่องโหว่อยู่

การทดสอบซ้ำควรทำโดยผู้ที่ไม่ได้แก้ไขโค้ด หรืออย่างน้อยควรมีขั้นตอนที่เขียนไว้ล่วงหน้า เพื่อลดโอกาสที่ผู้แก้ไขจะทดสอบเฉพาะกรณีที่ตัวเองคิดไว้แล้ว

ข้อผิดพลาดในการป้องกันที่พบบ่อย

ข้อผิดพลาดข้อแรกคือการใช้คำสั่งเตรียมไว้แต่ยังต่อสายอักขระในส่วนอื่นของคำสั่ง เช่น การต่อชื่อตารางหรือชื่อคอลัมน์ ซึ่งยังเปิดช่องให้ฉีดได้ ข้อผิดพลาดข้อที่สองคือการเชื่อว่าการกรองอักขระเพียงพอ ซึ่งไม่จริงในทุกบริบท

ข้อผิดพลาดข้อที่สามคือการเก็บข้อมูลรับรองของฐานข้อมูลไว้ในไฟล์ที่เว็บอ่านได้ ซึ่งทำให้ช่องโหว่อื่นกลายเป็นช่องโหว่ที่รุนแรงขึ้น ข้อผิดพลาดข้อที่สี่คือการให้บัญชีเว็บมีสิทธิ์มากเกินจำเป็น ซึ่งทำให้ผลกระทบของช่องโหว่ขยายออกไปโดยไม่จำเป็น

7.8 การประกอบรอบทดสอบ

จากหัวข้อแยกส่วนสู่รอบทดสอบเดียว

หัวข้อ 7.1 ถึง 7.7 อธิบายแต่ละส่วนของงานแยกจากกัน แต่การทดสอบจริงต้องทำต่อเนื่องกัน และลำดับที่เลือกมีผลต่อทั้งคุณภาพของผลลัพธ์และภาระที่ระบบเป้าหมายได้รับ ลำดับที่ดีคือการยืนยันให้แน่ใจว่าจุดนั้นมีช่องโหว่จริงก่อน แล้วจึงค่อยขยายการทดสอบออกไปทีละชั้น

หลักการที่ใช้คือ ยืนยันด้วยคำขอให้น้อยที่สุด แล้วจึงเพิ่มความลึกเมื่อมีหลักฐานรองรับ การทดสอบที่เริ่มด้วยเครื่องมืออัตโนมัติทันทีจะทำให้ไม่รู้ว่าผลที่ได้มาจากจุดใด และเมื่อระบบล่มจะไม่รู้ว่าคำขอใดเป็นสาเหตุ

ตาราง 7.13 ลำดับการทดสอบ SQL Injection หนึ่งรอบ
ขั้นสิ่งที่ทำผลลัพธ์ที่ต้องได้ระดับความเสี่ยง
1บันทึกคำขอเป้าหมายและส่งค่าปกติคำตอบฐานอ้างอิงพร้อมรหัสสถานะและขนาดไม่มี
2ใส่อักขระพิเศษและสังเกตคำตอบหลักฐานว่าค่าไปถึงคำสั่ง SQLต่ำ
3ทดสอบเงื่อนไขจริงและเท็จความแตกต่างที่เกิดซ้ำได้ต่ำ
4นับจำนวนคอลัมน์และหาตำแหน่งที่แสดงผลจำนวนคอลัมน์และตำแหน่งที่ใช้ได้ต่ำ
5อ่านข้อมูลเมตาของฐานข้อมูลชื่อฐานข้อมูล ตาราง และคอลัมน์ต่ำ
6ดึงข้อมูลจำนวนจำกัดเพื่อยืนยันหลักฐานเพียงพอต่อการรายงานกลาง
7ประเมินชั้นผลกระทบถัดไปโดยไม่ลงมือข้อสรุปที่มีเงื่อนไขชัดเจนไม่มี
8ลบข้อมูลที่สร้างขึ้นและเขียนรายงานระบบกลับสู่สภาพเดิมและเอกสารครบถ้วนไม่มี

ขั้นที่หนึ่งและสองให้ข้อมูลมากที่สุดเมื่อเทียบกับความเสี่ยงที่ต่ำมาก เพราะเป็นการสังเกตคำตอบโดยไม่เปลี่ยนแปลงข้อมูล ขั้นที่หกเป็นขั้นที่ต้องขออนุญาตชัดเจนที่สุด เพราะเป็นการนำข้อมูลจริงออกจากระบบ

ขั้นที่เจ็ดคือขั้นที่ผู้ทดสอบมือใหม่มักข้าม ทั้งที่เป็นขั้นที่ต้องใช้ความรู้มากที่สุด การประเมินว่าหากมีสิทธิ์มากขึ้นจะเกิดอะไรขึ้น ต้องอาศัยการอ่านค่าตั้ง การดูสิทธิ์ของบัญชี และการเข้าใจเงื่อนไขของฐานข้อมูล ซึ่งเป็นการวิเคราะห์ที่ไม่สร้างความเสี่ยงเพิ่ม

ตัวอย่างการเดินเรื่องหนึ่งรอบในห้องฝึก

สมมติระบบฝึกมีหน้า product.php?id=15 ที่แสดงรายละเอียดสินค้า ลำดับที่เป็นธรรมชาติคือการส่งค่า 15 ตามปกติและบันทึกคำตอบไว้เป็นฐานอ้างอิง จากนั้นส่งค่า 15' และดูว่าคำตอบเปลี่ยนเป็นข้อความผิดพลาดของฐานข้อมูลหรือไม่

เมื่อเห็นข้อความผิดพลาดที่บอกตำแหน่งใกล้ '15''' แสดงว่าค่าถูกนำไปต่อในคำสั่งจริง ขั้นถัดไปคือการทดสอบ 15 AND 1=1 กับ 15 AND 1=2 เพื่อยืนยันด้วยความแตกต่างของคำตอบ ซึ่งเป็นหลักฐานที่หนักแน่นกว่าข้อความผิดพลาดเพียงอย่างเดียว

เมื่อยืนยันได้แล้ว จึงนับจำนวนคอลัมน์ด้วย ORDER BY ทีละค่า จนกระทั่งเกิดข้อผิดพลาด แล้วจึงหาตำแหน่งที่แสดงผลด้วย UNION SELECT ที่มีค่าต่างกันในแต่ละช่อง

ขั้นต่อมาคือการอ่านชื่อฐานข้อมูลด้วย database() แล้วอ่านรายชื่อตารางในฐานข้อมูลนั้น เมื่อเห็นตาราง users จึงอ่านรายชื่อคอลัมน์และดึงข้อมูลเพียงสามแถวแรกเพื่อยืนยัน

แต่ละขั้นให้ข้อมูลสำหรับขั้นถัดไป และแต่ละขั้นมีหลักฐานที่ชัดเจนว่าควรไปต่อหรือควรหยุด การเดินเรื่องแบบนี้ทำให้ผลลัพธ์ตรวจสอบย้อนกลับได้ และทำให้ผู้ทดสอบคนอื่นทำซ้ำได้ในระบบทดสอบเดียวกัน

เกณฑ์การหยุด

การทดสอบไม่มีจุดสิ้นสุดตามธรรมชาติ เพราะยังมีคำถามที่ถามได้อีกเสมอ คำถามจึงไม่ใช่ว่าลองครบหรือยัง แต่คือข้อมูลที่ได้เพียงพอต่อการตอบคำถามของผู้ว่าจ้างหรือยัง

เกณฑ์ที่ใช้ได้จริงมีสามข้อ ข้อแรกคือช่องโหว่ที่พบได้รับการยืนยันด้วยคำขอที่ทำซ้ำได้ ข้อที่สองคือผลกระทบได้รับการประเมินครบทุกชั้นที่มีเงื่อนไขเป็นไปได้ ข้อที่สามคือความเสี่ยงของความพยายามเพิ่มเติมมีมากกว่าคุณค่าที่จะได้

เมื่อครบสามข้อนี้ การทดสอบเพิ่มเติมควรถูกบันทึกเป็นข้อเสนอสำหรับรอบถัดไป ไม่ใช่ทำต่อในรอบนี้ ตัวอย่างเช่น หากยังไม่ได้ทดสอบการเขียนไฟล์เพราะต้องขออนุญาตเพิ่ม ควรเขียนไว้ในรายงานว่าเป็นสิ่งที่ยังไม่ได้ตรวจและต้องใช้เงื่อนไขใด

การบันทึกที่ทำให้งานตรวจสอบย้อนกลับได้

บันทึกที่ดีต้องตอบคำถามได้ว่าทำอะไร เมื่อใด กับอะไร และได้ผลอย่างไร โดยไม่ต้องพึ่งความจำของผู้ทดสอบ ตารางถัดไปสรุปฟิลด์ที่ควรมีในบันทึก

การแยกช่อง "การตีความ" ออกจากช่อง "คำตอบย่อ" เป็นรายละเอียดที่มีผลมาก เพราะมันบังคับให้เขียนสิ่งที่เห็นก่อนแล้วจึงเขียนสิ่งที่คิด ซึ่งเป็นวิธีเดียวที่จะตรวจพบว่าข้อสรุปบางข้อไม่ได้มีหลักฐานรองรับ

การประสานกับผู้ดูแลระบบ

การทดสอบที่กระทบฐานข้อมูลควรมีผู้ดูแลระบบรับรู้ตลอดช่วงเวลา เพราะหากระบบตอบสนองช้าลงหรือหยุดทำงาน ผู้ดูแลจะรู้ว่าสาเหตุมาจากการทดสอบ ไม่ใช่จากการโจมตีจริง และสามารถตัดสินใจหยุดการทดสอบได้ทันที

ควรตกลงล่วงหน้าว่าจะทำอะไรได้บ้าง โดยเฉพาะการทดสอบที่อาจแก้ไขข้อมูล การทดสอบที่ใช้ฟังก์ชันหน่วงเวลา และการทดสอบที่ดึงข้อมูลจำนวนมาก ข้อตกลงเหล่านี้ควรอยู่ในเอกสารขอบเขตงาน ไม่ใช่เพียงคำพูดในที่ประชุม

หากพบว่าระบบมีปัญหาหรือเริ่มตอบสนองผิดปกติ ควรหยุดและแจ้งผู้ดูแลทันที การฝืนทดสอบต่อเพื่อให้ได้ผลครบตามแผนเป็นเหตุผลที่ยอมรับไม่ได้ เพราะความเสียหายต่อระบบที่ให้บริการจริงมีน้ำหนักมากกว่าความสมบูรณ์ของรายงาน

สิ่งที่ต้องทำเมื่อจบรอบ

เมื่อจบรอบทดสอบ ต้องตรวจว่ามีสิ่งที่สร้างขึ้นค้างอยู่ในระบบหรือไม่ เช่น ไฟล์ที่เขียนผ่าน INTO OUTFILE ผู้ใช้ที่เพิ่มผ่านคำสั่งแบบหลายชั้น หรือข้อมูลที่แก้ไขระหว่างการทดสอบ สิ่งเหล่านี้ต้องถูกลบหรือคืนค่าให้กลับสู่สภาพเดิม

ต้องตรวจด้วยว่าข้อมูลที่ดึงออกมาถูกเก็บไว้ที่ใด และลบสำเนาที่ไม่จำเป็นตามข้อตกลง การเก็บข้อมูลลูกค้าไว้ในเครื่องส่วนตัวหลังจบงานเป็นความเสี่ยงที่ไม่ก่อให้เกิดประโยชน์ และอาจผิดข้อตกลงการรักษาความลับ

สุดท้ายคือการทบทวนว่าคำขอที่ส่งไปทั้งหมดถูกบันทึกครบหรือไม่ หากพบว่ามีบางช่วงที่ไม่ได้บันทึก ควรกลับไปเติมจากบันทึกของพร็อกซีหรือไฟล์ของเครื่องมือก่อนเขียนรายงาน เพราะรายงานที่อ้างถึงคำขอซึ่งตรวจสอบย้อนกลับไม่ได้จะลดความน่าเชื่อถือของทั้งฉบับ

✓ สรุป

บทนี้อธิบายช่องโหว่ที่เกิดจากการที่แอปพลิเคชันนำข้อมูลจากผู้ใช้ไปต่อเป็นส่วนหนึ่งของคำสั่งฐานข้อมูล จุดตั้งต้นคือการต่อสายอักขระซึ่งดูเหมือนเรื่องเล็ก แต่ปลายทางคือการอ่านข้อมูลทั้งฐาน การแก้ไขข้อมูล และในบางระบบคือการยึดเซิร์ฟเวอร์

แนวคิดที่สำคัญที่สุดของบทคือ ข้อมูลกับคำสั่งต้องแยกจากกันโดยโครงสร้าง ไม่ใช่โดยการตรวจอักขระ ข้อนี้ฟังดูเรียบง่าย แต่ช่องโหว่ในบทนี้ทั้งหมดล้วนเกิดจากการฝ่าฝืนข้อนี้ การกรองอักขระแก้ได้เฉพาะกรณีที่ผู้พัฒนาคิดไว้ ส่วนการแยกคำสั่งออกจากข้อมูลแก้ได้ทุกกรณีเพราะฐานข้อมูลรู้เองว่าส่วนใดคือคำสั่ง

การทดสอบด้วยมือเป็นพื้นฐานที่ขาดไม่ได้ เพราะมันทำให้เห็นว่าคำตอบแต่ละแบบบอกอะไร การนับคอลัมน์ด้วย ORDER BY การหาตำแหน่งที่แสดงผลด้วย UNION SELECT และการอ่านข้อมูลเมตาจาก information_schema เป็นขั้นตอนที่ต้องเข้าใจก่อนใช้เครื่องมือ เมื่อเข้าใจแล้วจึงเห็นว่าผลที่เครื่องมือรายงานหมายถึงอะไร และรู้ว่าควรตรวจสอบจุดใดด้วยมือ

การเลือกเทคนิคขึ้นกับช่องทางที่ระบบเปิดให้ ระบบที่แสดงข้อผิดพลาดตอบได้เร็วด้วย Error-based ระบบที่แสดงผลลัพธ์ตอบได้เร็วด้วย UNION-based ระบบที่ปิดทุกช่องทางเหลือเพียงการอนุมานทีละบิต ซึ่งช้าแต่ยังได้ข้อมูล การรู้ว่าตัวเองอยู่สถานการณ์ใดจึงประหยัดทั้งเวลาและคำขอ

ผลกระทบของช่องโหว่นี้ประเมินเป็นชั้น ตั้งแต่การอ่านตารางที่แอปพลิเคชันใช้ ไปจนถึงการอ่านไฟล์และการสั่งให้ระบบปฏิบัติการทำงาน แต่ละชั้นมีเงื่อนไขของตัวเอง และการประเมินโดยไม่ตรวจสอบเงื่อนไขจะทำให้รายงานคลาดเคลื่อนทั้งทางบวกและทางลบ

การป้องกันที่ได้ผลคือการใช้คำสั่งเตรียมไว้พร้อมพารามิเตอร์ในทุกจุดที่รับข้อมูล เสริมด้วยการจำกัดสิทธิ์ของบัญชีฐานข้อมูล การปิดการแสดงข้อผิดพลาด และการเฝ้าตรวจคำขอที่ผิดรูปแบบ มาตรการเหล่านี้ไม่ได้แทนกัน แต่ทำงานร่วมกันเพื่อลดทั้งโอกาสเกิดและความเสียหายเมื่อเกิด

ท้ายที่สุด เนื้อหาทั้งบทอยู่ภายใต้เงื่อนไขเดียวที่ห้ามละเลย คือการทดสอบต้องทำในระบบที่ได้รับอนุญาต คำสั่งในบทนี้มีผลต่อข้อมูลจริง คำสั่งที่ผิดพลาดเพียงตัวเดียวสามารถทำให้ข้อมูลเสียหายหรือทำให้ระบบหยุดให้บริการได้ การบันทึกอย่างละเอียด การจำกัดขอบเขต และการลบสิ่งที่สร้างขึ้นจึงเป็นส่วนหนึ่งของงาน ไม่ใช่ภาระเพิ่มเติม

ข้อ 1จงอธิบายว่าการต่อสายอักขระทำให้ตรรกะของคำสั่ง SQL เปลี่ยนไปได้อย่างไร และเพราะเหตุใดการกรองเครื่องหมายคำพูดจึงไม่ใช่การแก้ที่ต้นเหตุ
ข้อ 2เหตุใดการทดสอบด้วยเงื่อนไขจริงและเท็จจึงให้หลักฐานที่หนักแน่นกว่าการดูข้อความผิดพลาดเพียงอย่างเดียว และควรทำซ้ำอย่างน้อยกี่ครั้งเพราะเหตุใด
ข้อ 3จงอธิบายขั้นตอนการหาจำนวนคอลัมน์ด้วย ORDER BY และอธิบายว่าเพราะเหตุใดวิธีนี้จึงใช้ไม่ได้กับระบบที่ไม่แสดงข้อผิดพลาด พร้อมเสนอวิธีทดแทน
ข้อ 4เพราะเหตุใด MySQL จึงต้องมีช่องว่างหลังเครื่องหมาย -- และการเขียนเป็น -- - ช่วยแก้ปัญหานี้อย่างไร
ข้อ 5จงเปรียบเทียบเทคนิค Boolean-based กับ Time-based ในด้านจำนวนคำขอ ความน่าเชื่อถือ และภาระต่อระบบเป้าหมาย
ข้อ 6จงอธิบายว่าตาราง information_schema.columns ให้ข้อมูลอะไร และเพราะเหตุใดการอ่านตารางนี้จึงลดจำนวนคำขอที่ต้องส่งไปยังระบบเป้าหมาย
ข้อ 7เพราะเหตุใดการใช้ --risk=3 ในระบบที่ให้บริการจริงจึงไม่ควรทำ และมีตัวเลือกใดของ sqlmap ที่ช่วยจำกัดความเสี่ยงนี้
ข้อ 8หากพบว่าบัญชีฐานข้อมูลของเว็บมีสิทธิ์ FILE และค่าตั้ง secure_file_priv ไม่ได้จำกัดไดเรกทอรี ผู้ทดสอบควรประเมินผลกระทบอย่างไร และควรบันทึกในรายงานว่าอะไรคือข้อเท็จจริงและอะไรคือความเสี่ยงที่ยังไม่ได้ตรวจ

Aa คำศัพท์สำคัญ

คำศัพท์คำอธิบาย
การฉีดคำสั่งฐานข้อมูล (SQL Injection)ช่องโหว่ที่เกิดจากการนำข้อมูลจากผู้ใช้ไปต่อเป็นส่วนหนึ่งของคำสั่ง SQL
ภาษาสอบถามเชิงโครงสร้าง (SQL)ภาษาที่ใช้สร้าง อ่าน แก้ไข และลบข้อมูลในฐานข้อมูลเชิงสัมพันธ์
การต่อสายอักขระ (String Concatenation)การนำข้อความหลายส่วนมาต่อกัน ซึ่งเป็นต้นเหตุของการฉีดคำสั่ง
คำสั่งเตรียมไว้ (Prepared Statement)คำสั่งที่กำหนดโครงสร้างไว้ล่วงหน้าและรับค่าแยกต่างหาก
พารามิเตอร์ผูกค่า (Bound Parameter)ค่าที่ถูกส่งเข้าไปในตำแหน่งที่กำหนดไว้โดยไม่กลายเป็นส่วนของคำสั่ง
เงื่อนไข (Clause)ส่วนของคำสั่ง SQL ที่กำหนดว่าจะเลือก แก้ไข หรือลบแถวใด
คำสงวน (Reserved Word)คำที่มีความหมายเฉพาะในภาษา SQL เช่น SELECT, WHERE, UNION
เครื่องหมายความคิดเห็น (Comment)ไวยากรณ์ที่ทำให้ฐานข้อมูลข้ามส่วนที่เหลือของบรรทัดหรือบล็อก
การข้ามการยืนยันตัวตน (Authentication Bypass)การเข้าสู่ระบบโดยไม่ผ่านการตรวจรหัสผ่านตามปกติ
ข้อผิดพลาดจากฐานข้อมูล (Database Error)ข้อความที่ฐานข้อมูลส่งกลับเมื่อคำสั่งไม่ถูกต้อง และมักบอกโครงสร้างของคำสั่ง
การฉีดแบบอาศัยข้อผิดพลาด (Error-based)เทคนิคที่ใช้ข้อความผิดพลาดเป็นช่องทางส่งข้อมูลกลับ
การฉีดแบบยูเนียน (UNION-based)เทคนิคที่ต่อผลลัพธ์ของคำสั่งใหม่เข้ากับผลลัพธ์ของคำสั่งเดิม
การฉีดแบบตาบอด (Blind)เทคนิคที่อนุมานข้อมูลจากความแตกต่างของคำตอบโดยไม่เห็นข้อมูลโดยตรง
การฉีดแบบอาศัยเวลา (Time-based)เทคนิคที่ใช้ระยะเวลาตอบสนองเป็นสัญญาณของคำตอบ
คำสั่งหลายชั้น (Stacked Queries)การต่อคำสั่ง SQL มากกว่าหนึ่งคำสั่งในครั้งเดียวด้วยเครื่องหมายอัฒภาค
ข้อมูลเมตา (Metadata)ข้อมูลที่อธิบายโครงสร้างของฐานข้อมูล เช่น ชื่อฐานข้อมูล ตาราง และคอลัมน์
โครงสร้างข้อมูลกลาง (information_schema)ฐานข้อมูลระบบที่เก็บข้อมูลเมตาของฐานข้อมูลใน MySQL และ MariaDB
จำนวนคอลัมน์ (Column Count)จำนวนช่องผลลัพธ์ของคำสั่ง ซึ่งต้องเท่ากันทั้งสองฝั่งของ UNION
การรวมค่า (GROUP_CONCAT)ฟังก์ชันที่รวมหลายค่าไว้ในสายอักขระเดียว
การเชื่อมข้อความ (CONCAT)ฟังก์ชันที่ต่อค่าหลายค่าเข้าด้วยกัน
เลขฐานสิบหก (Hexadecimal)การเขียนตัวเลขและไบต์ในฐานสิบหก ใช้แทนอักขระเพื่อหลบตัวกรอง
ฟังก์ชันหน่วงเวลา (Sleep Function)ฟังก์ชันที่ทำให้ฐานข้อมูลรอตามเวลาที่กำหนด
การดึงข้อมูล (Dump)การอ่านข้อมูลออกมาจากฐานข้อมูลเป็นจำนวนมาก
ค่าตั้งจำกัดไดเรกทอรีไฟล์ (secure_file_priv)ค่าตั้งของ MySQL ที่จำกัดไดเรกทอรีที่อ่านหรือเขียนไฟล์ได้
การอ่านไฟล์ (LOAD_FILE)ฟังก์ชันของ MySQL ที่อ่านเนื้อหาไฟล์บนเซิร์ฟเวอร์
การเขียนไฟล์ผลลัพธ์ (INTO OUTFILE)คำสั่งของ MySQL ที่เขียนผลลัพธ์ของคำสั่งลงไฟล์
รหัสผ่านแบบแฮช (Password Hash)ค่าที่ได้จากการผ่านรหัสผ่านเข้าฟังก์ชันทางเดียว ใช้เทียบแทนการเก็บรหัสผ่านจริง
ไฟร์วอลล์เว็บแอปพลิเคชัน (WAF)อุปกรณ์หรือซอฟต์แวร์ที่ตรวจและกรองคำขอเว็บตามรูปแบบที่กำหนด
รายการที่อนุญาต (Allowlist)แนวทางตรวจที่ยอมรับเฉพาะค่าที่ระบุไว้ล่วงหน้า

เมื่ออ่านข้อมูลจากฐานข้อมูลได้แล้ว คำถามถัดไปคือข้อมูลที่ได้นั้นมีค่าแค่ไหน ในบรรดาข้อมูลทั้งหมดที่ช่องโหว่นี้เปิดเผย รหัสผ่านที่เข้ารหัสแล้วคือข้อมูลที่นำไปใช้ต่อได้ทันที เพราะมันเป็นกุญแจที่ระบบเก็บไว้แทนรหัสผ่านจริง

บทนี้อธิบายว่าช่องโหว่เกิดเมื่อข้อมูลกับคำสั่งถูกหลอมเป็นเนื้อเดียวกัน และจบลงที่การอ่านข้อมูลซึ่งรวมถึงรหัสผ่านที่เข้ารหัสแล้ว บทถัดไปจะเริ่มจากจุดนั้นและอธิบายว่าค่าที่เห็นนั้นถูกสร้างขึ้นอย่างไร ที่มาของความแตกต่างระหว่างรูปแบบ และทำไมบางรูปแบบจึงถูกเดาได้เร็วกว่าอย่างมาก

บทถัดไปจะแนะนำเครื่องมือสองตัวที่ใช้กันทั่วไปในงานนี้ คือ John the Ripper และ Hashcat ซึ่งทำงานบนเครื่องของผู้ทดสอบโดยไม่ต้องส่งคำขอไปยังระบบเป้าหมายเลย ความแตกต่างนี้สำคัญเพราะมันเปลี่ยนขอบเขตของความเสี่ยง จากเดิมที่ระบบเป้าหมายรับภาระทั้งหมด มาเป็นความรับผิดชอบของผู้ทดสอบที่จะจัดการข้อมูลที่ได้มาอย่างระมัดระวัง

สิ่งที่บทนี้สร้างไว้จะถูกใช้ซ้ำในบทถัดไปในสองลักษณะ อย่างแรกคือข้อมูลตั้งต้นที่ได้จากการดึงฐานข้อมูล ซึ่งเป็นวัตถุดิบของการทดสอบแบบออฟไลน์ อย่างที่สองคือวินัยในการจำกัดขอบเขต การบันทึกผล และการลบข้อมูลเมื่อจบงาน ซึ่งยังคงใช้เหมือนเดิมแม้จะไม่ได้แตะระบบเป้าหมายอีกเลย

บทสรุปของสองบทนี้คือระบบไม่ได้ล้มเหลวเพราะมีจุดอ่อนเพียงจุดเดียว แต่ล้มเหลวเพราะจุดอ่อนหนึ่งจุดเปิดทางไปสู่จุดถัดไป การเห็นความเชื่อมโยงระหว่างช่องโหว่ที่อ่านข้อมูลได้กับรหัสผ่านที่นำไปเดาต่อได้ คือการมองระบบในฐานะห่วงโซ่ ไม่ใช่รายการช่องโหว่แยกส่วน
