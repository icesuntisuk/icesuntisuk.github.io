บทที่ 10 การตรวจสอบระบบปฏิบัติการและโครงสร้างพื้นฐานเครือข่าย (Operating System and Network Infrastructure Audit)

ในการตรวจสอบความมั่นคงปลอดภัยไซเบอร์ภาคปฏิบัติ คณะผู้ตรวจสอบมักเปรียบเทียบระบบสารสนเทศระดับองค์กรว่าเปรียบเสมือน "ป้อมปราการดิจิทัล" โดยมี โครงสร้างพื้นฐานเครือข่าย (Network Infrastructure) ทำหน้าที่เป็นคูเมือง กำแพง และประตูด่านหน้า คอยกลั่นกรองและควบคุมการสัญจรของข้อมูล ในขณะที่ ระบบปฏิบัติการ (Operating System: OS) ทำหน้าที่เป็นปราสาทชั้นในที่ควบคุมทรัพยากร บัญชีผู้ใช้งาน สิทธิ์การเข้าถึง และการประมวลผลของฐานข้อมูลและแอปพลิเคชันหลัก

หากกำแพงเครือข่ายเปิดกว้างอย่างหละหลวม หรือประตูระบบปฏิบัติการใช้ลูกบิดที่ไม่ได้มาตรฐาน ต่อให้แอปพลิเคชันระดับบนจะพัฒนาขึ้นมาอย่างประณีตเพียงใด ผู้โจมตีก็สามารถลักลอบเจาะทะลวงเข้ามาควบคุมระบบทั้งหมดได้ในเวลาเพียงไม่กี่นาที

อย่างไรก็ตาม หน้าที่ของ ผู้ตรวจสอบด้านความมั่นคงปลอดภัย (Security Auditor) แตกต่างอย่างมีนัยสำคัญจาก ผู้ทดสอบเจาะระบบ (Penetration Tester) หรือ วิศวกรผู้ดูแลระบบ (System Administrator):

  • ผู้ดูแลระบบมองการตั้งค่าเพื่อเน้นให้ระบบทำงานได้ราบรื่น (Functionality & Availability)
  • ผู้ทดสอบเจาะระบบมุ่งหาช่องทางใดก็ได้เพื่อยึดครองสิทธิ์ (Exploit & Compromise)
  • ผู้ตรวจสอบมุ่งประเมิน "ประสิทธิผลของการควบคุม (Control Effectiveness)" โดยแยกแยะปัญหาทางเทคนิค (Configuration Issue) ออกจาก "ข้อค้นพบการตรวจสอบ (Audit Finding)" ที่มีเกณฑ์อ้างอิงและผลกระทบต่อภารกิจองค์กรรองรับอย่างชัดเจน

ในบทนี้ นักศึกษาจะได้ลงลึกสู่ภาคสนามทางเทคนิคของทั้งสองโลก: การตรวจสอบระบบปฏิบัติการ Windows และ Linux ตั้งแต่ระดับบัญชี การพิสูจน์ตัวตน การ Hardening การปะแพตช์ และการเก็บ Log ควบคู่ไปกับการตรวจสอบเครือข่าย ทั้งผังเครือข่าย การแบ่งโซน กฎไฟร์วอลล์ การเข้าถึงทางไกล (VPN) และเครือข่ายไร้สาย พร้อมทั้งฝึกบันทึกผลลงในกระดาษทำการ (Audit Working Paper) อย่างมืออาชีพ

ผลลัพธ์การเรียนรู้ของบท (Course Learning Outcomes)

เมื่อสิ้นสุดการเรียนรู้ในบทนี้ นักศึกษาสามารถ:

  1. ระบุและตรวจสอบประเด็นความมั่นคงปลอดภัยสำคัญของระบบปฏิบัติการ Windows และ Linux ได้ (CLO1, CLO3): วิเคราะห์และประเมินความเสี่ยงของการบริหารจัดการบัญชี (Account Management), การพิสูจน์ตัวตน (Authentication), การกำหนดสิทธิ์ (Authorization), การเสริมความมั่นคงปลอดภัย (Hardening), การบริหารแพตช์ (Patch Management) และการบันทึก Log ตามมาตรฐาน CIS Benchmarks ได้
  2. วิเคราะห์สถาปัตยกรรมและมาตรการควบคุมเครือข่ายจากเอกสารและค่ากำหนดจริงได้ (CLO3, CLO4): ตรวจทานผังเครือข่าย (Network Diagrams), ประเมินประสิทธิผลของการแบ่งโซน (Network Segmentation), ตรวจสอบกฎไฟร์วอลล์ (Firewall Rules Audit), การเข้าถึงระยะไกล (VPN), และความปลอดภัยเครือข่ายไร้สายได้
  3. แยกแยะความแตกต่างระหว่าง "Configuration Issue" กับ "Audit Finding" ได้อย่างมีหลักการ (CLO1, CLO3): อธิบายเงื่อนไข 4 ประการของข้อค้นพบการตรวจ (Condition, Criteria, Cause, Effect) และสามารถเปลี่ยนปัญหาการตั้งค่าหลุดให้กลายเป็นข้อค้นพบที่มีเกณฑ์อ้างอิงและน้ำหนักทางวิชาชีพได้
  4. จัดทำกระดาษทำการตรวจสอบด้านโครงสร้างพื้นฐาน (Infrastructure Working Paper) ฉบับสมบูรณ์ได้ (CLO3, CLO4): วิเคราะห์หลักฐานจำลอง 5 ชุด บันทึกขั้นตอนการทดสอบ (Test Procedures) บันทึกผลเชิงประจักษ์ และระบุข้อสังเกตเบื้องต้นได้อย่างถูกต้องตามมาตรฐานสากล

1.1 การบริหารจัดการบัญชีผู้ใช้งาน (Account Management)

ผู้ตรวจสอบต้องสุ่มตรวจและตรวจสอบสถานะของบัญชีผู้ใช้ในระบบปฏิบัติการ โดยจำแนกออกเป็น 6 ประเภทบัญชี:

  1. Active Accounts (บัญชีที่เปิดใช้งานปกติ): ต้องมีรายชื่อผู้ครอบครองที่เป็นปัจจุบันและผูกกับพนักงานที่มีสถานะทำงานจริงในองค์กร
  2. Dormant / Inactive Accounts (บัญชีที่ไม่ได้ใช้งานเป็นเวลานาน): บัญชีที่ไม่มีการล็อกอินเกิน 30, 60 หรือ 90 วัน (ตามนโยบาย) ต้องถูกระงับสิทธิ์ (Disable) โดยอัตโนมัติ เพื่อป้องกันการถูกสวมรอย
  3. Default Accounts (บัญชีเริ่มต้นของระบบ): บัญชีที่ติดมากับระบบปฏิบัติการ เช่น Guest, Administrator (Windows), หรือ root (Linux) ต้องถูกเปลี่ยนชื่อ (Rename) ปิดการใช้งาน (Disable) หรือห้ามล็อกอินผ่านรีโมตคอนโซลโดยตรง
  4. Shared / Generic Accounts (บัญชีที่ใช้ร่วมกัน): บัญชีส่วนกลางที่ไม่มีเจ้าของระบุชัดเจน เช่น admin, operator, temp ถือเป็นข้อบกพร่องร้ายแรงทางวิชาชีพ เนื่องจากขัดต่อหลักการความรับผิดชอบเฉพาะบุคคล (Individual Accountability)
  5. Service Accounts (บัญชีบริการสำหรับแอปพลิเคชัน): บัญชีที่สร้างขึ้นเพื่อให้ระบบรัน Service (เช่น svc_oracle, svc_backup) ต้อง:
  • ห้ามมีสิทธิ์ล็อกอินแบบ Interactive Shell หรือ Remote Desktop
  • ต้องกำหนดสิทธิ์เฉพาะเจาะจงเท่าที่จำเป็นต่อการรันโปรเซสเท่านั้น
  • มีการตั้งค่ารหัสผ่านที่ซับซ้อนสูงและไม่มีวันหมดอายุ หรือใช้ Managed Service Accounts (gMSA บน Windows)
  1. Privileged Accounts (บัญชีสิทธิ์ระดับสูง): บัญชีที่มีสิทธิ์ระดับ Local Administrators บน Windows หรือสมาชิกกลุ่ม wheel / sudo บน Linux ต้องมีจำนวนน้อยที่สุดเท่าที่จำเป็น และต้องล็อกอินผ่าน Jump Host หรือ PAM เสมอ

1.2 การพิสูจน์ตัวตน (Authentication Controls)

การพิสูจน์ตัวตนเป็นกลไกยืนยันว่าผู้ที่ขอเข้าใช้งานคือตัวจริง จุดตรวจสอบสำคัญประกอบด้วย:

  • Password Policy (นโยบายรหัสผ่าน): ตรวจสอบการตั้งค่า Group Policy Object (GPO) บน Windows หรือไฟล์ /etc/security/pwquality.conf บน Linux:
  • ความยาวขั้นต่ำ (Minimum Password Length): ไม่น้อยกว่า 12–14 ตัวอักษรสำหรับผู้ใช้ทั่วไป และไม่น้อยกว่า 16 ตัวอักษรสำหรับแอดมิน
  • ความซับซ้อน (Complexity): ต้องประกอบด้วยตัวพิมพ์ใหญ่ พิมพ์เล็ก ตัวเลข และอักขระพิเศษ
  • อายุประวัติรหัสผ่าน (Password History): ห้ามใช้รหัสผ่านซ้ำเดิมอย่างน้อย 5–10 รุ่นก่อนหน้า
  • Multi-Factor Authentication (MFA): บังคับใช้ MFA สำหรับการเข้าถึงระบบปฏิบัติการผ่านรีโมต (Remote Desktop / SSH) และการเข้าถึงจากเครือข่ายภายนอก
  • Account Lockout Threshold (การล็อกบัญชีเมื่อใส่รหัสผิด): ต้องตั้งค่าล็อกบัญชีชั่วคราวเมื่อใส่รหัสผ่านผิดเกิน 3–5 ครั้ง เพื่อป้องกันการโจมตีแบบ Brute Force หรือ Password Spraying
  • Session Timeout (การตัดเซสชันเมื่อไม่มีการใช้งาน): ต้องตั้งค่าให้ล็อกหน้าจอ (Screen Lock) อัตโนมัติเมื่อไม่มีการเคลื่อนไหวภายใน 10–15 นาที และตัดเซสชันการเชื่อมต่อรีโมตเมื่อไม่มีการใช้งาน (Idle Timeout)
  • Authentication Logging: ตรวจสอบว่าระบบเปิดบันทึกทั้งการล็อกอินสำเร็จและไม่สำเร็จ (Success & Failure Audit) เช่น Event ID 4624 (Successful Logon) และ 4625 (Failed Logon) บน Windows

1.4 การเสริมความมั่นคงปลอดภัยระบบ (System Hardening)

การ Hardening คือการปิดกั้นประตูและช่องทางที่ไม่จำเป็น เพื่อลดพื้นที่การถูกโจมตี (Attack Surface Reduction) ตามมาตรฐาน CIS Benchmarks:

  1. Unnecessary Services & Ports: ปิดบริการที่ไม่จำเป็น เช่น Telnet, FTP, TFTP, Print Spooler (บนเซิร์ฟเวอร์ที่ไม่ใช่ Print Server), Simple TCP/IP Services
  2. Default Configurations: ลบแอปพลิเคชันตัวอย่าง (Sample Apps), รหัสผ่านเริ่มต้น, ปิดฟังก์ชัน Directory Browsing
  3. Secure Protocols: ปิดการใช้งานโปรโตคอลเก่าที่ไม่ปลอดภัย เช่น SMBv1, SSLv3, TLS 1.0, TLS 1.1 และบังคับใช้เฉพาะ SSHv2, TLS 1.2, TLS 1.3
  4. Host-based Firewall: ตรวจสอบว่า Windows Defender Firewall หรือ Linux iptables/ufw/firewalld มีสถานะ Active / Enabled และไม่อนุญาตให้เปิดรับพอร์ตแบบเปิดกว้าง (Inbound Any)
  5. Anti-malware & Endpoint Protection (EDR): เครื่องแม่ข่ายต้องติดตั้งระบบป้องกันไวรัสและภัยคุกคาม มีการอัปเดต Signature สม่ำเสมอ และมีการตั้งค่า Real-time Protection เปิดใช้งานอยู่เสมอ

2.3 การตรวจสอบกฎไฟร์วอลล์ (Firewall Audit: 8 จุดตรวจสำคัญ)

INTERACTIVE WIDGET 10.2
Network Segmentation & Firewall Rule Evaluator (8 จุดตรวจสำคัญ)

ทดสอบส่งแพ็กเก็ตทราฟฟิกจำลองเข้าสู่ระบบเครือข่าย เพื่อประเมินว่ากฎไฟร์วอลล์และสถาปัตยกรรมการแบ่งโซนมีความปลอดภัย หรือมีช่องโหว่ร้ายแรงตาม 8 จุดตรวจสำคัญ:

จำลองการส่งข้อมูล (Traffic Simulation):

ไฟร์วอลล์คือหัวใจของการคัดกรองข้อมูล ผู้ตรวจสอบต้องนำตารางกฎไฟร์วอลล์ (Rulebase Export) มาตรวจสอบอย่างละเอียดตาม 8 จุดตรวจสำคัญ:

  1. Rule Owner & Business Justification: ทุกกฎที่เปิดรับส่งข้อมูล ต้องมีระบุชื่อเจ้าของคำขอ (Requester) และเหตุผลทางธุรกิจที่จำเป็น
  2. Approval Process: ต้องมีบันทึกการอนุมัติคำขอเปลี่ยนแปลง (Change Request Ticket) ผ่านการอนุมัติจากผู้มีอำนาจ
  3. Specific Source & Destination: กฎที่ดีต้องระบุ IP ต้นทางและปลายทางอย่างเจาะจง ห้ามใช้ Source: Any หรือ Destination: Any ในโซนที่มีความเสี่ยงสูง
  4. Specific Service & Port: ต้องระบุพอร์ตและโปรโตคอลที่จำเป็นอย่างเจาะจง เช่น TCP 443 ห้ามใช้ Service: Any
  5. Rule Expiry Date: กฎที่เปิดเพื่อการทดสอบชั่วคราวหรือเปิดให้คู่ค้าภายนอกทำงาน ต้องกำหนดวันหมดอายุของกฎ (Expiry Date) ไว้อย่างชัดเจน
  6. The "Any-to-Any" Danger: การตรวจพบกฎ Source: Any -> Dest: Any -> Service: Any -> Action: Permit บนไฟร์วอลล์ ถือเป็นข้อค้นพบวิกฤต (Critical Finding) เว้นแต่จะเป็นกฎบล็อกปลายทาง (Clean-up Rule / Implicit Deny)
  7. Obsolete & Redundant Rules: กฎที่เชื่อมโยงไปยัง IP ปลายทางที่ปลดระวางแล้ว หรือกฎที่ไม่มี Traffic วิ่งผ่านเลยในรอบ 6–12 เดือน (Zero Hit Count) ต้องถูกทบทวนและลบออก
  8. Logging Enabled: ทุกกฎอนุญาตและกฎปฏิเสธ ต้องมีการเปิดการบันทึก Log (Log at Session End) และส่งไปยังศูนย์รวม Log (SIEM)

2.4 การเข้าถึงจากระยะไกล (Remote Access Security)

การทำงานแบบ Work from Home และการจ้างผู้พัฒนาภายนอก ทำให้การเข้าถึงระยะไกลกลายเป็นเป้าหมายหลักของผู้โจมตี:

  • VPN Architecture & Encryption: ต้องใช้เทคโนโลยี VPN ที่ได้มาตรฐานความปลอดภัย (IPsec หรือ SSL-VPN) ที่ใช้การเข้ารหัสแข็งแกร่ง (AES-256) และปิดการใช้งานโหมดเก่าที่ไม่ปลอดภัย (เช่น PPTP หรือ L2TP ที่ไม่เข้ารหัส)
  • Mandatory Multi-Factor Authentication (MFA): บัญชีผู้ใช้งาน VPN ทุกบัญชี ต้องถูกบังคับใช้ MFA เสมอ การอนุญาตให้ใช้เฉพาะ Username/Password เข้า VPN ถือเป็นข้อบกพร่องระดับสำคัญ (Major Non-conformity)
  • Administrative Access via Jump Host: ผู้ดูแลระบบที่ล็อกอินจากระยะไกล ห้ามเข้าถึงเซิร์ฟเวอร์ปลายทางโดยตรง ต้องเชื่อมต่อผ่าน Jump Host / Bastion Host ที่มีการบันทึกภาพหน้าจอและคำสั่ง (Session Recording)
  • Third-Party / Vendor Connections: บัญชี VPN สำหรับผู้ให้บริการภายนอก (Outsourced Vendors) ต้องถูกตั้งค่าเป็น Disabled โดยค่าเริ่มต้น และเปิดใช้งานเฉพาะเมื่อมีการแจ้งขอเข้าปฏิบัติงานเป็นลายลักษณ์อักษร พร้อมทั้งกำหนดเวลาปิดอัตโนมัติ

2.5 การบริหารจัดการอุปกรณ์เครือข่าย (Network Device Management)

สวิตช์ เราเตอร์ และไฟร์วอลล์ ต้องได้รับการดูแลรักษาความปลอดภัยอย่างเข้มงวด:

  • Secure Management Protocols: ต้องปิดการใช้งาน Telnet, HTTP, และ SNMPv1/v2c (ซึ่งส่ง Community String แบบ Plaintext) และบังคับใช้เฉพาะ SSHv2, HTTPS, และ SNMPv3 (ที่มีการพิสูจน์ตัวตนและเข้ารหัส)
  • Configuration Backup & Testing: ต้องมีการสำรองไฟล์การตั้งค่า (Running Configuration) ของอุปกรณ์เครือข่ายทุกตัวเป็นประจำ และจัดเก็บในที่ปลอดภัยพร้อมเข้ารหัส ตลอดจนมีการทดสอบกู้คืน
  • Centralized Authentication: ต้องไม่อาศัย Local Account บนอุปกรณ์เครือข่ายเป็นหลัก แต่ต้องเชื่อมต่อกับระบบควบคุมตัวตนกลาง เช่น TACACS+ หรือ RADIUS เพื่อให้ทราบตัวตนของผู้ที่ล็อกอินเข้าพิมพ์คำสั่งบนสวิตช์ได้อย่างแม่นยำ
  • Firmware Updates: ตรวจสอบประวัติการอัปเกรด Firmware ของอุปกรณ์เครือข่าย เพื่อป้องกันช่องโหว่ประเภท Remote Code Execution (RCE)
  • NTP Synchronization: อุปกรณ์เครือข่ายทุกชิ้นต้องตั้งค่าให้ซิงก์เวลากับเครื่องแม่ข่ายเวลามาตรฐาน (NTP Server) เดียวกัน เพื่อให้ Timestamp ของ Log สามารถนำมาสอบทานยันกันได้อย่างถูกต้อง

2.6 ความมั่นคงปลอดภัยของเครือข่ายไร้สาย (Wireless Security)

สัญญาณ Wi-Fi กระจายทะลุกำแพงอาคาร ทำให้ผู้โจมตีสามารถดักรับข้อมูลได้จากระยะไกล:

  • Enterprise Authentication: เครือข่ายไร้สายสำหรับบุคลากรภายในองค์กร ต้องใช้มาตรฐาน WPA3-Enterprise หรือ WPA2-Enterprise (802.1X EAP-TLS / PEAP) ที่ผูกกับบัญชีผู้ใช้รายบุคคล ห้ามใช้รหัสผ่านชุดเดียวกันทั้งองค์กร (Pre-Shared Key: WPA2-Personal) บนเครือข่ายระดับองค์กร
  • Guest Wi-Fi Isolation: เครือข่าย Wi-Fi สำหรับผู้มาติดต่อ (Guest) ต้องแยก VLAN ออกจากเครือข่ายภายในอย่างเด็ดขาด มีระบบลงทะเบียนตัวตน (Captive Portal) ตาม พ.ร.บ.คอมพิวเตอร์ฯ และจำกัดให้ใช้งานได้เฉพาะการออกสู่ Internet เท่านั้น (ห้ามคุยข้ามเครื่องใน Subnet เดียวกัน - Client Isolation)
  • Rogue AP Monitoring: ต้องมีมาตรการเฝ้าระวังจุดเชื่อมต่อสัญญาณแปลกปลอม (Rogue Access Points) หรืออุปกรณ์พกพาที่พนักงานแอบนำมาเสียบเพื่อปล่อย Wi-Fi เอง

01 // CONDITION
สภาพที่ตรวจพบ (Condition)
ข้อเท็จจริงเชิงประจักษ์ที่ค้นพบในระหว่างการตรวจ พร้อมหลักฐานสนับสนุนที่ยืนยันได้ (What is)

02 // CRITERIA
เกณฑ์อ้างอิง (Criteria)
มาตรฐาน กฎหมาย นโยบาย หรือข้อตกลงสัญญาที่ใช้วัดความถูกต้อง (What should be)

03 // CAUSE
สาเหตุที่เกิด (Cause)
รากเหง้าของปัญหา (Root Cause) ว่าทำไมจึงเกิดสภาพความไม่สอดคล้องนี้ขึ้น (Why did it happen)
ตัวอย่าง: ขาดกระบวนการทบทวนกฎไฟร์วอลล์ประจำปี และไม่มีกระบวนการควบคุมการเข้าถึงชั่วคราว
04 // EFFECT
ผลกระทบ (Effect)
ความเสี่ยง ความเสียหายต่อการดำเนินงาน การเงิน หรือผลกระทบทางกฎหมายหากไม่แก้ไข (What is the impact)
ตัวอย่าง: เสี่ยงต่อการถูกโจมตีด้วย Ransomware เจาะยึดเครื่องแม่ข่าย และข้อมูลนักศึกษารั่วไหล

IMPORTANT
กฎเหล็กของผู้ตรวจสอบ: หากตรวจพบการตั้งค่าที่ไม่ดี (Condition) แต่ ไม่มี Criteria ใดๆ ในองค์กรระบุห้ามไว้เลย ผู้ตรวจสอบ ห้ามเขียนเป็น Non-conformity (NCR) แต่ให้บันทึกเป็น ข้อสังเกตหรือโอกาสในการปรับปรุง (Observation / Opportunity for Improvement: OFI) พร้อมเสนอแนะให้องค์กรกำหนดนโยบายในเรื่องนั้น

  1. Focusing only on Vulnerability Scanners: พึ่งพาแต่รายงานสรุปจากเครื่องมือสแกน (เช่น Nessus) โดยไม่ได้เปิดดูคอนฟิกจริงหรือตรวจสอบนโยบายขององค์กร
  2. Accepting Outdated Network Diagrams: เชื่อถือผังเครือข่ายในกระดาษโดยไม่ได้สุ่มทดสอบเส้นทาง Routing หรือ Ping จริง
  3. Ignoring Service Accounts: ตรวจเฉพาะบัญชีพนักงานที่เป็นบุคคล แต่ละเลยบัญชี Service Accounts ซึ่งมักถูกตั้งรหัสผ่านง่ายและมีสิทธิ์ระดับ Local System
  4. Writing Findings without Root Cause: เขียนรายงานเพียงว่า "พบพอร์ตเปิดอยู่" โดยไม่ได้สืบหาสาเหตุว่าทำไมจึงเปิด (เช่น ขาดกระบวนการ Firewall Change Management) ทำให้องค์กรไม่สามารถแก้ปัญหาที่ต้นตอได้

ส่วนที่ 7: แบบฝึกหัดและการบ้านประจำบทที่ 10

เพื่อเป็นส่วนหนึ่งของการจัดทำแฟ้มสะสมงาน Cybersecurity Audit Portfolio (ชิ้นงานที่ 10) ให้นักศึกษานำ ชุดหลักฐานจำลอง 5 ชุด (EV-10-01 ถึง EV-10-05) จากกรณีศึกษามหาวิทยาลัยดิจิทัลสมมติในบทนี้ ไปวิเคราะห์และจัดทำเอกสาร:

  1. Audit Working Paper ด้านระบบปฏิบัติการและเครือข่าย:
  • จัดทำกระดาษทำการบันทึกขั้นตอนการทดสอบ ผลลัพธ์เชิงประจักษ์ และข้อสรุปผลการตรวจอย่างละเอียด
  1. การจัดทำรายการข้อสังเกตและข้อค้นพบเบื้องต้นอย่างน้อย 5 ประเด็น:
  • เลือก 5 ประเด็นความเสี่ยงสำคัญจากหลักฐานจำลอง (เช่น EOL OS, Insecure RDP, Any-to-Any, Vendor VPN without MFA, Segmentation Failure)
  • เขียนอธิบายให้ครบถ้วนตามโครงสร้าง 4 องค์ประกอบ:
  • สภาพที่ตรวจพบ (Condition)
  • เกณฑ์อ้างอิง (Criteria: อ้างอิง ISO 27001 / ประกาศ กกม. / นโยบาย)
  • สาเหตุที่เกิด (Cause)
  • ผลกระทบที่อาจเกิดขึ้น (Effect)
  • หมายเหตุ: ต้องเชื่อมโยงกับเกณฑ์ตรวจให้ชัดเจน ห้ามระบุเป็นข้อบกพร่องลอยๆ โดยไม่มี Criteria รองรับ

ส่วนที่ 8: คำถามทบทวนท้ายบท (Review Questions & Detailed Answers)

  1. คำถาม: จงอธิบายความแตกต่างระหว่าง Service Account และ User Account ทั่วไป พร้อมระบุแนวทางการควบคุมความปลอดภัยของ Service Account
  • แนวคำตอบ: User Account เป็นบัญชีของบุคคลสำหรับล็อกอินใช้งานคอมพิวเตอร์ ส่วน Service Account เป็นบัญชีที่สร้างขึ้นเพื่อให้แอปพลิเคชันหรือเซอร์วิสของระบบรันเบื้องหลัง การควบคุม Service Account ต้อง: (1) ห้ามมีสิทธิ์ Interactive Shell หรือ RDP (2) กำหนดสิทธิ์เท่าที่จำเป็น (Least Privilege) (3) ใช้รหัสผ่านที่ซับซ้อนสูงและไม่มีการแชร์ให้บุคคลทั่วไป หรือใช้เทคโนโลยี Group Managed Service Accounts (gMSA)
  1. คำถาม: เพราะเหตุใดระบบปฏิบัติการที่สิ้นสุดระยะเวลาการสนับสนุน (End-of-Life: EOL) จึงถือเป็นความเสี่ยงระดับวิกฤตในการตรวจสอบ?
  • แนวคำตอบ: เพราะผู้ผลิต (Vendor) จะยุติการพัฒนาและแจกจ่ายแพตช์ความมั่นคงปลอดภัยสำหรับระบบนั้นโดยสิ้นเชิง ทำให้เมื่อมีช่องโหว่ใหม่ (Zero-Day Vulnerability) ถูกค้นพบ ระบบจะไม่ได้รับการป้องกันอีกต่อไป ผู้โจมตีสามารถใช้ Exploit โจมตีระบบได้สำเร็จอย่างง่ายดาย
  1. คำถาม: หากองค์กรมีความจำเป็นต้องใช้งานเซิร์ฟเวอร์รุ่นเก่าที่ไม่สามารถปะแพตช์ได้ ผู้ตรวจสอบควรแนะนำให้ใช้มาตรการใด?
  • แนวคำตอบ: แนะนำให้ใช้ มาตรการชดเชย (Compensating Controls) ได้แก่: (1) ย้ายเซิร์ฟเวอร์ไปอยู่ใน Isolated VLAN ที่แยกขาดจากเครือข่ายอื่น (2) กำหนดกฎไฟร์วอลล์บล็อกการเข้าถึงจากภายนอกอย่างเด็ดขาด (3) ใช้งาน Virtual Patching บน Web Application Firewall (WAF) หรือ IPS (4) จัดทำเอกสารขออนุมัติยกเว้น (Exception Form) ที่ผู้บริหารลงนามรับทราบความเสี่ยง
  1. คำถาม: จงอธิบายความเสี่ยงของการมีกฎแบบ "Any-to-Any" บนไฟร์วอลล์
  • แนวคำตอบ: กฎ Any-to-Any ที่อนุญาตให้ทราฟฟิกใดๆ วิ่งผ่านได้โดยไม่จำกัด IP และพอร์ต จะทำลายคุณสมบัติการแบ่งโซนเครือข่าย (Segmentation) ทำให้ไฟร์วอลล์ไม่สามารถทำหน้าที่คัดกรองข้อมูลได้ หากเครือข่ายจุดใดจุดหนึ่งถูกเจาะ ผู้โจมตีจะสามารถแพร่กระจายการโจมตี (Lateral Movement) ไปยังทุกระบบทั่วทั้งองค์กรได้อย่างอิสระ
  1. คำถาม: เหตุใดการเปิดพอร์ต RDP (TCP 3389) ตรงสู่เครือข่ายอินเทอร์เน็ตจึงเป็นข้อห้ามร้ายแรงในเชิงความมั่นคงปลอดภัย?
  • แนวคำตอบ: เพราะ RDP เป็นเป้าหมายหลักในการโจมตีแบบ Brute Force, Credential Stuffing และมักมีช่องโหว่ระดับ Remote Code Execution (เช่น BlueKeep) ซึ่งเป็นช่องทางหลักที่กลุ่มแรนซัมแวร์ (Ransomware) ใช้ในการเจาะทะลวงระบบเพื่อฝังมัลแวร์เรียกค่าไถ่
  1. คำถาม: ในการตรวจสอบระบบไร้สาย (Wi-Fi) เหตุใดองค์กรจึงไม่ควรใช้ WPA2-Personal (Pre-Shared Key)?
  • แนวคำตอบ: เพราะ WPA2-Personal ใช้รหัสผ่านชุดเดียวกันร่วมกันทั้งองค์กร ทำให้: (1) ไม่สามารถระบุตัวตนผู้ใช้งานรายบุคคลได้ (ขาด Individual Accountability) (2) หากพนักงานลาออกหรือทำรหัสหลุด ทุกคนต้องเปลี่ยนรหัสใหม่ทั้งหมด ซึ่งในทางปฏิบัติทำได้ยาก องค์กรจึงควรใช้ WPA2/WPA3-Enterprise ที่ยืนยันตัวตนแยกตามบัญชีผู้ใช้
  1. คำถาม: จงอธิบายความแตกต่างระหว่าง "Configuration Issue" กับ "Audit Finding"
  • แนวคำตอบ: Configuration Issue คือข้อบกพร่องทางเทคนิคในการตั้งค่าระบบที่ไม่ตรงตาม Best Practice ในมุมมองของแอดมิน ส่วน Audit Finding คือข้อสรุปเชิงประเมินของผู้ตรวจสอบที่ชี้ชัดว่าสภาพความเป็นจริง (Condition) ขัดแย้งกับเกณฑ์มาตรฐานหรือนโยบาย (Criteria) ที่องค์กรต้องปฏิบัติตาม โดยมีหลักฐานเชิงประจักษ์และระบุผลกระทบต่อความเสี่ยงองค์กรชัดเจน
  1. คำถาม: จงระบุ 4 องค์ประกอบสำคัญของ Audit Finding พร้อมยกตัวอย่างสั้นๆ
  • แนวคำตอบ: (1) Condition: พบกฎไฟร์วอลล์เปิดพอร์ต RDP สู่เน็ต (2) Criteria: นโยบายไอทีข้อ 6.1 ห้ามเปิด RDP สู่ภายนอก (3) Cause: ขาดการทบทวนกฎประจำปี (4) Effect: เสี่ยงต่อการถูกแรนซัมแวร์โจมตี
  1. คำถาม: ในการตรวจสอบบัญชีสิทธิ์สูงบน Linux ผู้ตรวจสอบควรตรวจสอบไฟล์ใดเป็นพิเศษ และมองหาจุดเสี่ยงใด?
  • แนวคำตอบ: ควรตรวจสอบไฟล์ /etc/sudoers และ /etc/sudoers.d/ โดยมองหาการกำหนดสิทธิ์แบบกว้างเกินไป โดยเฉพาะการใช้คำสั่ง NOPASSWD: ALL ซึ่งทำให้ผู้ใช้สามารถยกระดับเป็น root ได้โดยไม่ต้องใส่รหัสผ่าน ตลอดจนตรวจสอบไฟล์ /etc/passwd เพื่อดูว่ามีบัญชีอื่นนอกจาก root ที่มี UID เป็น 0 หรือไม่
  1. คำถาม: เหตุใดการตรวจสอบการเข้าถึงผ่าน VPN ของบริษัทภายนอก (Vendor) จึงต้องมีการตั้งค่าให้บัญชี Disabled เป็นค่าเริ่มต้น?
  • แนวคำตอบ: เพื่อป้องกันไม่ให้บุคคลภายนอกสามารถล็อกอินเข้าสู่เครือข่ายภายในขององค์กรได้ตลอดเวลาโดยที่องค์กรไม่รู้ตัว บัญชีควรถูกเปิดใช้งานเฉพาะเมื่อมีคำขอปฏิบัติงานที่มีกำหนดเวลาชัดเจน และปิดทันทีเมื่องานเสร็จสิ้น เพื่อจำกัดพื้นที่การโจมตี (Attack Surface)

สรุปบทที่ 10

การตรวจสอบระบบปฏิบัติการและโครงสร้างพื้นฐานเครือข่ายเป็นการตรวจสอบในชั้นเทคนิคที่มีความสำคัญยิ่งยวดต่อความอยู่รอดขององค์กรในยุคไซเบอร์

การตรวจสอบระบบปฏิบัติการ (OS Audit) มุ่งเน้นการควบคุมบัญชีผู้ใช้ตามหลัก Least Privilege การบังคับใช้นโยบายรหัสผ่านและ MFA การทำ System Hardening ตามมาตรฐาน CIS Benchmarks การปิดกั้นเซอร์วิสที่ไม่จำเป็น การบริหารจัดการแพตช์สำหรับช่องโหว่วิกฤต และการเปิดใช้นโยบายบันทึก Log อย่างเพียงพอ

การตรวจสอบโครงสร้างพื้นฐานเครือข่าย (Network Audit) มุ่งเน้นความถูกต้องของผังเครือข่าย การแบ่งแยกโซนความปลอดภัย (Network Segmentation) เพื่อป้องกันการแพร่กระจายของภัยคุกคาม การตรวจสอบกฎไฟร์วอลล์เพื่อกำจัดกฎ Any-to-Any และกฎตกค้าง การควบคุมการเข้าถึงระยะไกล (VPN) ด้วย MFA และการบริหารจัดการอุปกรณ์เครือข่ายด้วยโปรโตคอลที่เข้ารหัส

ที่สำคัญที่สุด ผู้ตรวจสอบต้องมีวุฒิภาวะทางวิชาชีพในการ แยกแยะระหว่าง Configuration Issue ออกจาก Audit Finding โดยนำเสนอข้อค้นพบที่มีโครงสร้างครบทั้ง 4 ด้าน (Condition, Criteria, Cause, Effect) เพื่อให้ข้อเสนอแนะสามารถนำไปสู่การปรับปรุงความมั่นคงปลอดภัยได้อย่างตรงจุดและสร้างคุณค่าต่อองค์กรอย่างแท้จริง
